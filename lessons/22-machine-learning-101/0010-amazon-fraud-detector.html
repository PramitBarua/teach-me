Amazon Fraud Detector

Lesson 10 of 11 · ~5 min

Source: Adrian Cantrill SAA-C03 · Amazon Fraud Detector availability change · Choose a model type

Service lifecycle: closed to new customers
As of November 7, 2025, AWS stopped accepting new customers for Amazon Fraud Detector. Existing customers can keep using it as normal, but anyone evaluating a fraud-detection solution today is pointed toward alternatives such as Amazon SageMaker, the open-source AutoGluon library, or AWS WAF Fraud Control (for account-creation-fraud scenarios specifically). The exam may still test the underlying architecture and model-type concepts covered below even though the product itself is closed to new adopters.

Amazon Fraud Detector is a fully managed fraud-detection service. It looks at historical trends and related data to identify potential fraud around online activity — typically things like new account creation, payments, or guest checkouts.

Architecture: Import, Choose a Model, Score

Like the other managed ML services in this module, the pattern is: upload historical data, choose a model type, and let the service score incoming events. Fraud Detector offers three model types, each suited to a different situation:

Online Fraud Insights
For when little or no history exists on the entity being evaluated — a brand-new account signup, for example. Little historical data means the model instead looks at general risk-signal trends surrounding the event.
Transaction Fraud Insights
For when a transaction history does exist for the customer — commonly used for credit-card validation, using patterns like stores used, purchase amounts, countries, and time of day to build a profile of normal behavior.
Account Takeover Insights
Detects signals of account compromise — for example, a phishing- or credential-stuffing-style login from an unusual location or an unusual referral source.
Exam heuristic: match the model to the data you have
The exam-level distinction between the three model types comes down to what history exists for the entity being evaluated: no history on a new user → Online Fraud Insights; an established transaction history → Transaction Fraud Insights; suspected account compromise signals like unusual login location → Account Takeover Insights.

Rules and Positioning

Once events are scored, you build rules — decision logic that reacts to those scores according to your business's risk tolerance. Like Forecast, this is a backend service: it's integrated into applications and environments rather than used interactively from the console.

Retrieval Practice

1. A brand-new user is signing up for an account, so there is no prior activity history to draw on. Which Fraud Detector model type is designed for this situation?

2. A payments team wants to validate incoming credit-card transactions against a customer's established purchase history — stores used, typical amounts, and countries. Which model type fits?

3. A security team notices a login attempt for an existing account from an unfamiliar country and an unusual referral source. Which model type is designed to flag this kind of signal?
