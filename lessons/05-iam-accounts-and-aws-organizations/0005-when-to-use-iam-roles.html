When to Use IAM Roles

Lesson 05 of 11 · ~8 min

Source: Adrian Cantrill SAA-C03 · AWS: Common role scenarios

The five scenarios

ScenarioWhy a role?
AWS Services
e.g. Lambda, EC2, ECS		 Services can't hold long-term credentials. Assign a role so the service gets temporary credentials automatically.
Emergency / break-glass An operator normally has limited access but needs elevated access for an incident. Assume a role temporarily instead of granting permanent elevation.
Existing corporate identity (federation) Your company already uses Active Directory or another IdP. Map AD groups to roles so staff log in with their corporate password — no separate IAM user needed, and the 5 000-user limit is bypassed.
External identity providers
Google, Facebook, etc.		 Web/mobile users can't have IAM users. Use Web Identity Federation: the external provider authenticates them, then they assume a role to call AWS APIs.
Cross-account access Account A's user needs to do work in Account B. Account B creates a role that trusts Account A. The user assumes it — no need for a separate IAM user in Account B.
Exam tip
Any scenario involving an AWS service doing work on your behalf (Lambda reads S3, EC2 calls DynamoDB, etc.) always means a role — never an access key embedded in code.

Retrieval Practice

1. A Lambda function needs to write objects to S3. Which is the correct approach?

2. A company has 10 000 employees already in Active Directory. Which identity approach avoids creating 10 000 IAM users?

3. Team A (Account 111) needs to manage EC2 instances in Account 222. No new IAM users should be created in Account 222. What is the correct solution?
