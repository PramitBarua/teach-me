      Scenario 1

      A finance analyst has two customer managed policies attached to her IAM user: one allows s3:GetObject on the "reports" bucket, the other allows dynamodb:Query on the "ledger" table. She has no other policies, and neither policy contains a Deny statement. Which of these can she actually do?

      • A. Only s3:GetObject, since attaching a second managed policy silently replaces the first one's grants
      • B. Both actions — s3:GetObject and dynamodb:Query — since IAM evaluates the union of every attached policy with no explicit deny
      • C. Neither action, since two separate managed policies without a bound inline policy always default-deny
      • D. Only dynamodb:Query, since the most recently attached policy is the one IAM evaluates last

      Topic: IAM identity policies

      Correct answer: B

      • A. Wrong — attaching a second managed policy adds to an identity's permissions, it never silently replaces an earlier one; there's no "last policy wins" replacement behavior in IAM.
      • B. Correct — with no explicit Deny anywhere, IAM combines every attached policy's Allow statements into a union. She gets both grants simultaneously, from two independent policies.
      • C. Wrong — there's no rule requiring an inline policy to "activate" managed policies; managed policies are fully effective on their own once attached, with nothing extra needed.
      • D. Wrong — attachment order and recency don't determine which policy IAM evaluates; every attached policy is evaluated together, not in a most-recent-wins sequence.

      Scenario 2

      A newly created IAM user has no managed policy, no inline policy, and no group membership. The user tries to call ec2:DescribeInstances from the CLI using their new access key. Security policy requires that no identity ever gets standing access it wasn't explicitly granted. What happens, and does it satisfy the policy?

      • A. The call fails with AccessDenied, satisfying the policy — everything is denied by default until an explicit Allow is attached
      • B. The call succeeds, because DescribeInstances is a read-only action AWS permits without any attached policy
      • C. The call succeeds, because the user inherits a default "NewUserReadOnly" policy AWS attaches automatically
      • D. The call fails, but only because the new access key needs time to propagate before it can authenticate at all

      Topic: IAM identity policies

      Correct answer: A

      • A. Correct — with zero statements matching this request, evaluation falls through to implicit deny. Everything in AWS is denied unless something explicitly allows it, which is exactly what the policy requires.
      • B. Wrong — no action is free by default, read-only or not; even a harmless Describe call requires an explicit Allow statement somewhere or it's denied.
      • C. Wrong — AWS does not attach any default policy to new users; a brand-new user genuinely starts with zero permissions until someone attaches one.
      • D. Wrong — this invents a propagation delay that isn't the actual cause here; the user has no policy granting the action at all, so the call would fail the same way regardless of key age.

      Scenario 3

      A contractor's IAM user has a customer managed policy called "BaselineReadOnly" attached, shared by 40 other users, granting broad read access. For this one contractor only, security wants to block reading a single sensitive Secrets Manager secret, without changing what any of the other 40 users can do. What's the best way to add this restriction?

      • A. Edit the BaselineReadOnly policy directly to add a Deny statement for that secret
      • B. Detach BaselineReadOnly from the contractor and recreate an identical copy just for them, then add the Deny
      • C. Attach an inline policy to the contractor's user with an explicit Deny on that specific secret
      • D. Create a permissions boundary on the contractor's user that simply omits Secrets Manager actions

      Topic: IAM identity policies

      Correct answer: C

      • A. Wrong — this works mechanically, but BaselineReadOnly is shared by 40 other users; editing it directly would deny that secret to all of them too, violating the "without changing anyone else" requirement.
      • B. Wrong — cloning an entire policy just to add one exception is unnecessary duplication that's hard to maintain long-term, when the same one-off restriction can be layered on cleanly.
      • C. Correct — an inline policy scoped to exactly this one user is the textbook exceptional, one-off case inline policies exist for. It layers an explicit Deny on top of the shared managed policy without touching the other 40 users.
      • D. Wrong — a permissions boundary caps the maximum envelope of what a user's policies can grant; omitting Secrets Manager broadly isn't the same as a targeted deny on one specific secret, and it's a coarser, easy-to-misconfigure tool for this job.

      Scenario 4

      An identity policy statement has Effect: Allow, Action: "s3:GetObject", Resource: "arn:aws:s3:::project-x/*". The user tries to call s3:ListBucket on the same bucket "project-x" instead. What happens?

      • A. Allowed, because the Resource ARN's wildcard covers the entire bucket, including listing it
      • B. Allowed, because ListBucket is a common read action closely related enough to GetObject to be covered
      • C. Denied, but only because the Resource ARN is missing the bucket-level ARN and covers just the objects inside it
      • D. Denied, because the Action field only lists s3:GetObject — a statement must match on both Action and Resource

      Topic: IAM identity policies

      Correct answer: D

      • A. Wrong — a Resource wildcard only controls which resources a statement's actions apply to; it can't substitute for an action the statement never lists in the first place.
      • B. Wrong — IAM never infers "closely related" actions; every action needs its own explicit match. GetObject and ListBucket are two entirely separate permissions.
      • C. Wrong — it's true that ListBucket technically needs the bucket-level ARN as its resource, but that's not why this specific statement fails: the Action field doesn't even list ListBucket, so the resource detail is moot here.
      • D. Correct — a statement only applies when both its Action and Resource match the request. This statement's Action is only s3:GetObject, so a ListBucket call falls through to implicit deny regardless of the resource wildcard.

      Scenario 5

      An engineer has five different customer managed policies attached to their role, granting broad EC2 permissions. One of the five, added months ago for a now-decommissioned project, contains a single explicit Deny on ec2:TerminateInstance that nobody remembers. The engineer's team assumes they have full EC2 access and tries to terminate an unused instance. What happens?

      • A. The termination succeeds, since 4 of the 5 policies allow it and majority-allow governs evaluation
      • B. The termination succeeds, since an explicit Deny in an old, unused-project policy is ignored by IAM as stale
      • C. The termination fails; the lone explicit Deny among the five policies overrides every Allow, no matter how many grant it
      • D. The termination fails, but only because the role needs a fresh explicit Allow added in a sixth policy to override the deny

      Topic: IAM identity policies

      Correct answer: C

      • A. Wrong — IAM evaluation isn't a vote; there's no "majority of policies allow it" rule. A single matching Deny is enough to block the action outright.
      • B. Wrong — IAM has no concept of a policy going "stale" because its project is decommissioned; the Deny statement remains fully active until someone actually detaches or edits the policy.
      • C. Correct — explicit Deny always wins over explicit Allow, regardless of how many other attached policies grant the action. The forgotten policy's single Deny statement blocks the termination outright.
      • D. Wrong — this describes the actual failure but for the wrong reason; no amount of additional Allow statements can override an existing explicit Deny, so a sixth policy wouldn't fix anything unless the Deny itself is removed.

      Scenario 6

      A developer writes a policy granting s3:ListBucket and s3:GetObject on a bucket called "invoices", using a single Resource entry: "arn:aws:s3:::invoices/*". Testing shows GetObject works but ListBucket always fails. What's the fix?

      • A. Add a second Resource entry, "arn:aws:s3:::invoices" with no trailing /*, since ListBucket operates on the bucket itself
      • B. Change the wildcard from /* to /** so it also implicitly matches the bucket-level ARN
      • C. Move ListBucket into a separate resource-based bucket policy instead of the identity policy
      • D. Replace the ARN's region field with a wildcard so ListBucket is authorized across every region

      Topic: IAM users and ARNs

      Correct answer: A

      • A. Correct — ListBucket is a bucket-level operation and needs the bucket's own ARN, arn:aws:s3:::invoices, as its resource. The object-key wildcard invoices/* only covers actions on objects, like GetObject.
      • B. Wrong — /** is not valid ARN wildcard syntax and doesn't implicitly reach up to match the bucket-level ARN; a single * is the only wildcard IAM recognizes here.
      • C. Wrong — this would work mechanically since a bucket policy could grant ListBucket, but it's unnecessary extra infrastructure for a same-account fix that a one-line Resource addition already solves.
      • D. Wrong — S3 bucket ARNs don't include a region segment at all, since bucket names are globally unique; there's no region field here to wildcard, and it has nothing to do with ListBucket failing.

      Scenario 7

      A security engineer writes a policy meant to allow ec2:StopInstances on all instances in every region of the account, using Resource: "arn:aws:ec2:us-east-1:123456789012:instance/*". After deployment, instances in eu-west-1 can't be stopped by this policy. What's wrong?

      • A. The account-id segment must also be a wildcard, since EC2 ARNs don't actually include account IDs
      • B. The region segment is hardcoded to us-east-1; it must be a wildcard ("*") to cover every region
      • C. EC2 instance ARNs don't support wildcards anywhere in the resource-id segment
      • D. The policy needs a separate, near-identical Allow statement duplicated once for every region instead of one wildcard

      Topic: IAM users and ARNs

      Correct answer: B

      • A. Wrong — this states the opposite of reality: unlike S3, EC2 ARNs do include an account-id segment, and it's correctly populated here; that's not the problem.
      • B. Correct — the ARN pins the region to us-east-1, so the statement only matches instances there. Swapping it for arn:aws:ec2:*:123456789012:instance/* makes it match instances in every region.
      • C. Wrong — EC2 instance ARNs do support a wildcard in the resource-id segment (that's exactly what instance/* is doing here); the resource-id isn't the part that's scoped too narrowly.
      • D. Wrong — this would technically work, listing one statement per region, but it's needless duplication and ongoing maintenance burden compared to a single wildcarded region segment achieving the same coverage.

      Scenario 8

      A B2B SaaS company provisions one IAM user per customer company for API access, and has reached 4,800 IAM users as it approaches the 5,000 limit. Growth projections show 3,000 more customers signing up next year. What should they do before hitting the ceiling?

      • A. Request a limit increase from AWS support, since 5,000 IAM users per account is a soft, adjustable limit
      • B. Delete IAM users for inactive customers to free up headroom, then keep provisioning new users the same way
      • C. Switch new customers to IAM roles assumed via STS (or federation), since the 5,000-user cap can't be raised
      • D. Split customers across several new AWS accounts, provisioning up to 5,000 IAM users in each one

      Topic: IAM users and ARNs

      Correct answer: C

      • A. Wrong — 5,000 IAM users per account is a hard limit; no support request raises it, so this path dead-ends regardless of how it's framed.
      • B. Wrong — this buys a bit of temporary headroom, but it doesn't fix the design and risks disrupting customers later mistaken for "inactive," while next year's 3,000 new signups blow past the ceiling again anyway.
      • C. Correct — since the user cap is fixed, the scalable pattern is IAM roles assumed via STS (or external federation) for new customers, avoiding the creation of any new long-term IAM users at all.
      • D. Wrong — multi-account strategies are a real and valid AWS pattern for other reasons, but here they just relocate the same per-customer-user model into more accounts instead of removing the actual scaling constraint.

      Scenario 9

      An operations engineer has one IAM user, "svc-deploy", used both by a human logging into the console with a password and by a CI/CD pipeline calling the API with that same user's access key. An audit can't distinguish which caller performed a given destructive action, since both authenticate as the identical principal. What's the best fix to restore accountability?

      • A. Rotate the shared access key more frequently, so at least the pipeline's calls are time-boxed and traceable
      • B. Add a CloudTrail alarm that triggers whenever "svc-deploy" performs a destructive API action
      • C. Enable MFA on the "svc-deploy" user, so both the human and the pipeline must provide a second factor
      • D. Create separate IAM identities — a distinct user or role for the human and another for the pipeline

      Topic: IAM users and ARNs

      Correct answer: D

      • A. Wrong — rotating a shared key more often is a real hygiene practice, but it still leaves one principal used by two different callers; CloudTrail events would still show "svc-deploy" for both, solving nothing about attribution.
      • B. Wrong — an alarm on destructive actions is a useful monitoring layer, but every triggered alert would still just say "svc-deploy" did it — it adds noise, not the missing distinction between human and pipeline.
      • C. Wrong — MFA challenges a login attempt, but programmatic API calls using access keys don't authenticate with MFA the way console sessions do, and it wouldn't tag which caller made a given API call either way.
      • D. Correct — giving the human and the pipeline separate identities (a user for one, a role for the other) means every CloudTrail event now records a distinct principal, restoring exactly the accountability the audit needs.

      Scenario 10

      A junior engineer is confused why the ARN for an S3 bucket, arn:aws:s3:::finance-data, has two empty segments, while the ARN for an IAM user, arn:aws:iam::123456789012:user/bob, has only the region segment empty. What's the correct explanation?

      • A. This is a documentation inconsistency; both ARN types should always populate every segment
      • B. Empty segments always mean "wildcard, matches anything," identical in meaning to using *
      • C. Only global services like IAM omit segments; regional services like S3 always populate both region and account-id
      • D. S3 bucket names are globally unique, so region and account-id aren't needed; IAM is account-scoped and needs the account-id but has no regional concept

      Topic: IAM users and ARNs

      Correct answer: D

      • A. Wrong — this isn't an error; different resource types legitimately require different segments depending on what's needed to uniquely identify them.
      • B. Wrong — this is the exact trap to avoid: an omitted segment means "not required for this resource type," which is a different concept from a wildcard * meaning "match every value."
      • C. Wrong — this gets the pattern backwards; S3 is a regional-ish service that still omits both segments because bucket names are globally unique, while global services like IAM populate the account-id but never region.
      • D. Correct — S3 bucket names are unique across all of AWS, so no region or account-id is needed to pinpoint one. IAM resources live inside one account with no regional scope, so the account-id is required but the region segment stays empty.

      Scenario 11

      A user's own inline policy explicitly denies all iam:* actions. The user also belongs to the "Admins" group, which grants full AdministratorAccess. The user tries to call iam:CreateUser. What happens?

      • A. Allowed, because the group-level AdministratorAccess policy takes priority over the user's own inline policy
      • B. Denied, because policies are merged across the user and all their groups, and the explicit Deny wins
      • C. Allowed, because inline policies on a user are evaluated separately from, and after, group policies
      • D. Denied, but only until the user is removed from the Admins group, at which point it would be allowed

      Topic: IAM groups

      Correct answer: B

      • A. Wrong — there's no such priority rule; group-attached policies and the user's own policies are combined as equals, not ranked by source.
      • B. Correct — IAM merges the user's own policies with every group's policies into one evaluation. The inline policy's explicit Deny on iam:* overrides the group's AdministratorAccess Allow, so the call is blocked.
      • C. Wrong — there is no separate or delayed evaluation pass for inline versus group policies; all attached policies, from any source, are evaluated together in a single pass.
      • D. Wrong — the Deny lives on the user's own inline policy, not on group membership, so removing the user from Admins wouldn't change this outcome at all — the deny persists either way.

      Scenario 12

      A new AWS account administrator wants every current and future IAM user to automatically get a baseline "AllUsersReadOnly" policy the moment they're created, without manually attaching anything. She looks for a default "AllUsers" group to attach the policy to. What should she do?

      • A. Use the built-in "AllUsers" group that AWS creates automatically in every new account
      • B. Create her own group, attach the policy to it, and manually add every user — new users must be added explicitly, since AWS has no automatic mechanism for this
      • C. Use a permissions boundary set at the account level, which automatically applies to every IAM identity
      • D. Attach the policy directly to the account's root user, since permissions cascade down from root to all IAM users

      Topic: IAM groups

      Correct answer: B

      • A. Wrong — AWS never creates a default "AllUsers" group; every group in an account is one an administrator has to create and manage themselves.
      • B. Correct — there's no built-in all-users mechanism, so the closest available design is a self-managed group with the policy attached, and adding each new user to it — with no automation from AWS for the "future users" part.
      • C. Wrong — permissions boundaries aren't account-wide defaults; they must be attached to each identity individually and only cap what that identity's policies can grant, they don't broadcast a baseline allow to everyone automatically.
      • D. Wrong — the root user's permissions don't cascade to IAM users at all; each IAM user's access is governed purely by its own attached policies, independent of root.

      Scenario 13

      A user was previously a member of the "Billing" group, which grants billing:* actions. An admin removes the user from the Billing group but forgets to check anything else. The user still successfully calls billing:ViewBillingAccount. What's the most likely explanation?

      • A. Group membership changes can take up to 24 hours to fully propagate through IAM
      • B. Groups retain a cached copy of their permissions on former members for a grace period
      • C. The Billing group's policy was accidentally duplicated as an account-wide default for all users
      • D. The user has their own separate policy, or belongs to another group, that independently grants billing access

      Topic: IAM groups

      Correct answer: D

      • A. Wrong — this sounds like a plausible eventual-consistency story, but IAM permission changes, including group membership removal, take effect essentially immediately, not after a day-long delay.
      • B. Wrong — a group has no rights of its own to "retain" or cache; the moment membership ends, the member no longer inherits anything from that group's policies.
      • C. Wrong — this describes a specific misconfiguration the scenario gives no evidence for; it's a fabricated mechanism, not something IAM does on its own.
      • D. Correct — since a group itself grants nothing and removal from it takes effect immediately, continued access almost always means the user's own policy, or membership in a different group, is independently granting the same permission.

      Scenario 14

      A platform team wants a "Contractors" group nested inside a broader "AllExternal" group, so contractors automatically inherit AllExternal's policies plus their own Contractors-specific ones, mirroring how they organized OUs in AWS Organizations. When they try to add the Contractors group as a member of AllExternal, the console won't allow it. Why, and what should they do instead?

      • A. IAM groups cannot contain other groups; instead, attach both groups' policies directly to each contractor user, or also attach AllExternal's policies to the Contractors group
      • B. Nesting requires enabling a "hierarchical groups" account setting first, which is off by default
      • C. Only 300 groups can exist per account, and adding a nested group would exceed that limit
      • D. Nesting is supported, but only for groups federated through IAM Identity Center, not native IAM groups

      Topic: IAM groups

      Correct answer: A

      • A. Correct — unlike Organizations OUs, IAM groups have no nesting at all; only users can be group members. To get the same combined effect, attach both sets of policies to the Contractors group (or to each user) directly.
      • B. Wrong — there's no such account setting; nesting isn't a togglable feature that's simply disabled by default, it's a structural restriction of IAM groups that can't be turned on.
      • C. Wrong — 300 is the (soft) limit on total groups per account, a real number, but it's unrelated to why nesting itself is rejected — the team is nowhere near that ceiling here.
      • D. Wrong — this confuses IAM groups with IAM Identity Center permission sets and account assignments; native IAM groups don't support nesting through any AWS feature, Identity Center included.

      Scenario 15

      A power user already belongs to 10 IAM groups — the maximum — and needs a policy from an 11th group to do new work. The team's first instinct is to file an AWS Support limit-increase request, the same way they'd handle the 300-groups-per-account cap. Will that work here, and what should they actually do?

      • A. No — 10 groups per user is a hard limit that cannot be raised; instead consolidate two groups' policies into one, or attach a policy directly to the user
      • B. Yes — like the 300-group account limit, the 10-groups-per-user limit is also just a soft default
      • C. No — the user must be moved to a different AWS account, which comes with a fresh 10-group allowance
      • D. Yes, but only after first reducing the account's total group count below 300 to make room

      Topic: IAM groups

      Correct answer: A

      • A. Correct — unlike the 300-groups-per-account soft limit, the 10-groups-per-user cap is hard and cannot be increased by any support request. The practical fix is consolidating policies across fewer groups, or attaching the needed policy straight to the user.
      • B. Wrong — this conflates the two different limits; the per-account cap is adjustable, but the per-user cap explicitly is not, no matter how the request is framed.
      • C. Wrong — this would technically sidestep the number, since a fresh account starts its own count, but relocating an entire user to a new AWS account is a wildly disproportionate response to a group-count ceiling that a simple policy consolidation already solves.
      • D. Wrong — the account-wide group total has nothing to do with how many groups one specific user can join; reducing it wouldn't raise this user's individual 10-group ceiling at all.

      Scenario 16

      A role's trust policy lists the EC2 service (ec2.amazonaws.com) as its only trusted principal, and its permission policy grants s3:GetObject on a specific bucket. An EC2 instance is launched with this role attached, and code on the instance successfully reads from the bucket. A teammate then tries to directly call sts:AssumeRole on this same role from their own IAM user. What happens, and why?

      • A. It fails, since the trust policy only names the EC2 service as a trusted principal — the teammate's IAM user isn't listed and can't assume it
      • B. It succeeds, since the permission policy (not the trust policy) is what actually controls who may assume a role
      • C. It succeeds, since any authenticated IAM principal in the account can assume any role that has a valid permission policy
      • D. It fails, since IAM roles can only ever be assumed by AWS services, never by an IAM user

      Topic: IAM roles (technical mechanics)

      Correct answer: A

      • A. Correct — the trust policy is what governs who may call AssumeRole, and it names only ec2.amazonaws.com. The teammate's IAM user isn't a listed trusted principal, so the assumption is denied regardless of the permission policy's contents.
      • B. Wrong — this swaps the two policies' jobs. The permission policy only defines what the role can do once assumed; it plays no part in deciding who is allowed to assume it in the first place.
      • C. Wrong — assuming a role is never account-wide by default; only principals explicitly named in that specific role's trust policy can assume it, no matter what else the account contains.
      • D. Wrong — roles can absolutely be assumed by IAM users, other roles, or external identities — it all depends on what the trust policy lists; the limitation here is what's named, not a blanket "services only" rule.

      Scenario 17

      A batch job assumes a role via STS with a 1-hour session duration and starts a data export expected to take 3 hours. Two hours in, API calls start failing with credential errors. What's happening, and what should the job be designed to do?

      • A. The role's trust policy expired and must be manually re-attached by an administrator before the job continues
      • B. The temporary credentials expired after 1 hour; the job must detect this and call AssumeRole again for a fresh set
      • C. IAM automatically extends session duration up to 12 hours the first time credentials are about to expire
      • D. The permission policy silently revoked access after detecting the job ran longer than a typical operation

      Topic: IAM roles (technical mechanics)

      Correct answer: B

      • A. Wrong — trust policies don't have an expiry of their own; what expires is the temporary session credentials issued when the role was assumed, not the trust policy document itself.
      • B. Correct — the credentials returned by AssumeRole are only valid for the requested session duration, here 1 hour. Once that elapses, calls fail until the job re-assumes the role for a new set of temporary credentials — long-running jobs must build in this refresh logic themselves.
      • C. Wrong — sessions can be configured with a longer max duration up front, but IAM doesn't silently auto-extend an already-running 1-hour session; the requester has to explicitly re-assume the role.
      • D. Wrong — permission policies don't monitor runtime duration or revoke access mid-flight based on how long a job has been running; that isn't how policy evaluation works.

      Scenario 18

      A security review flags a role whose trust policy trusts arn:aws:iam::333333333333:root, intending to allow only one specific automation role in that account to assume it. Currently, any IAM principal in account 333333333333 with sts:AssumeRole permission on this ARN can assume it. What change makes the trust policy match the intended scope?

      • A. Nothing needs to change — :root already restricts trust to a single default role in that account
      • B. Replace the root ARN with the specific automation role's ARN, e.g. arn:aws:iam::333333333333:role/automation-role
      • C. Add a Condition block requiring MFA, which narrows :root down to exactly one principal automatically
      • D. Remove the trust policy entirely and rely on the automation role's own permission policy to restrict assumption

      Topic: IAM roles (technical mechanics)

      Correct answer: B

      • A. Wrong — :root in a trust policy means the entire account is trusted, not a single default role; that's precisely the over-broad behavior the review is flagging.
      • B. Correct — naming the exact role ARN instead of the account root scopes trust down to that one specific principal, matching the intended restriction precisely.
      • C. Wrong — an MFA condition adds a real security requirement, but it narrows the authentication method, not which principal is trusted; every principal in the account is still eligible, just now needing MFA too.
      • D. Wrong — removing the trust policy doesn't restrict assumption, it would break assumption for everyone (a role with no trusted principals can't be assumed at all); and the permission policy governs what the role can do, not who may assume it.

      Scenario 19

      A team wants an S3 bucket policy's Principal field to reference an identity, so that whichever identity is assumed gets bucket access, and they want to reuse the same reference for multiple rotating team members without listing individuals. They're deciding between referencing an IAM Role's ARN or an IAM Group's ARN as the Principal. Which works, and why?

      • A. Either works identically, since both roles and groups can be resource-policy principals
      • B. Only the group ARN works — bucket policies are designed to grant access to a batch of users, which is what a group represents
      • C. Only the role ARN works — roles are valid resource-policy principals, while groups can never be referenced as a principal anywhere
      • D. Neither works — resource-based policies can only reference IAM users or the account root, never roles or groups

      Topic: IAM roles (technical mechanics)

      Correct answer: C

      • A. Wrong — the two aren't interchangeable here; only one of them is actually a valid resource-policy principal type.
      • B. Wrong — this is the classic exam trap: a group is a natural-sounding fit for "many rotating members," but IAM groups are never valid principals in any resource-based policy, no matter how well the intuition fits.
      • C. Correct — IAM roles are a valid principal type in resource-based policies like S3 bucket policies. Groups are categorically excluded from the Principal field everywhere, so a role achieves the "shared, reusable identity" goal that a group cannot.
      • D. Wrong — resource-based policies accept more than just users and the account root as principals; roles and specific AWS services are valid principal types too.

      Scenario 20

      A federated user assumes a role and, in the same AssumeRole call, passes an inline session policy that further restricts the resulting session to read-only S3 actions, even though the role's own permission policy allows full S3 read/write. What access does the resulting temporary session actually have?

      • A. Full read/write, since a role's permission policy always takes precedence over any session policy passed at assume-time
      • B. Full read/write, since session policies are purely advisory metadata and aren't enforced by AWS
      • C. Read-only, but only because the session policy overwrites and replaces the role's permission policy for that session
      • D. Read-only, since the session policy and the role's permission policy are intersected, and the session policy is the more restrictive of the two

      Topic: IAM roles (technical mechanics)

      Correct answer: D

      • A. Wrong — this gets the relationship backwards; a session policy passed at assume-time doesn't defer to the role's permission policy, it further restricts what that session can do.
      • B. Wrong — session policies are fully enforced, not advisory; AWS actively evaluates them alongside the role's own permission policy for every request in that session.
      • C. Wrong — the final read-only outcome is right, but the mechanism is described wrong: the session policy doesn't replace or overwrite the role's permission policy, it narrows it.
      • D. Correct — the effective permissions of an assumed-role session are the intersection of the role's permission policy and any session policy passed at assume-time. Since the session policy caps it at read-only, that's the binding restriction even though the role itself allows write.

      Scenario 21

      A containerized batch-processing job running on ECS needs to read encrypted objects from S3 and write results to DynamoDB. The security team requires that no long-term secrets ever exist inside the container image or its environment variables. Which approach satisfies this?

      • B. Correct — code and configuration changes are management (control-plane) events, logged by default. Invocations are data-plane operations, which require data events to be explicitly enabled on the trail for that function.

      • D. Wrong — a CloudWatch Logs subscription forwards log events to another destination; it has no mechanism to inject new events into CloudTrail, so it can't be used to record invocations as CloudTrail API calls.

      Scenario 47

      A company's audit policy mandates exactly one CloudTrail trail per account, to avoid fragmented, hard-to-correlate logs. Their single trail lives in eu-west-1 with "include global service events" turned off. During an investigation, the team can't find any record of an IAM policy change made last week, even though the trail is otherwise logging normally. What is the correct fix?

      • A. Create a second, dedicated trail in us-east-1 solely to capture IAM and other global service events
      • B. Move the existing trail's home region to us-east-1, since a single-Region trail only receives global service events there
      • C. Convert the trail to a multi-Region trail with "include global service events" enabled, so global-service activity is captured regardless of home Region
      • D. Enable CloudTrail Insights on the trail, since Insights is required before global service activity can be logged

      Topic: CloudTrail

      Correct answer: C

      • A. Wrong — this would likely surface the missing IAM events, but it creates a second trail, directly violating the audit policy's one-trail-per-account mandate.
      • B. Technically works — a single-Region trail only receives global service events when its home Region is us-east-1, so relocating it there would fix the gap — but it's an unnecessary constraint: it ties the account's entire trail to one specific Region for no operational reason, when a multi-Region trail solves the same problem without that dependency.
      • C. Correct — IAM is a global service. A single-Region trail only receives global service events if it lives in us-east-1; a multi-Region trail, by contrast, captures them regardless of its home Region as long as "include global service events" is on. Converting the existing trail keeps the one-trail-per-account policy intact while fixing the gap for good, independent of Region.
      • D. Wrong — Insights analyzes anomalies in events the trail is already logging; it has no role in gating whether global service events are captured in the first place.

      Scenario 48

      A finance team's AWS bill spiked because hundreds of unexpected EC2 instances were launched over a short window overnight. They want CloudTrail to automatically flag unusual spikes in API call volume like this going forward, without manually scanning event history every day. What should they configure?

      • A. A CloudWatch Logs metric filter on the CloudTrail S3 delivery bucket matching "RunInstances", alerting on a manually chosen count threshold
      • B. An AWS Config rule that counts running EC2 instances every 24 hours and flags accounts above a static threshold
      • C. A CloudTrail trail with data events enabled for EC2, since RunInstances is a data-plane operation needing extra logging
      • D. CloudTrail Insights on the trail, to establish a baseline of normal management event activity and automatically surface unusual deviations

      Topic: CloudTrail

      Correct answer: D

      • A. Wrong — this requires the logs to already be in CloudWatch Logs format and someone to guess a fixed threshold up front; it's a bolted-together workaround, not automatic baseline-based anomaly detection.
      • B. Wrong — this technically could catch the spike, but checking only once every 24 hours against a fixed, manually-picked threshold isn't automatic anomaly detection, and Config tracks resource inventory, not API call volume patterns.
      • C. Wrong — RunInstances is a management (control-plane) event, already captured by default; enabling data events for EC2 doesn't address this gap and adds unrelated cost.
      • D. Correct — CloudTrail Insights automatically establishes a baseline of normal management event activity (like typical RunInstances volume) and flags deviations from it, exactly the automatic anomaly detection the finance team wants.

      Scenario 49

      After a suspected compromise, a security team needs to prove — potentially in court — that the CloudTrail log files stored in S3 have not been altered or deleted since they were delivered. Which feature provides this proof?

      • A. Enable log file integrity validation on the trail, which produces periodic digest files containing hashes that can cryptographically prove the logs haven't been altered
      • B. Enable CloudTrail Insights on the trail, since Insights independently re-verifies every past log file's checksum
      • C. Turn on S3 versioning on the destination bucket, so any modified log file is only ever a still-recoverable prior version
      • D. Enable S3 Object Lock in governance mode on the destination bucket, since it prevents the log objects from ever being deleted

      Topic: CloudTrail

      Correct answer: A

      • A. Correct — log file integrity validation generates signed digest files with hashes of the delivered log files, giving a cryptographic way to prove afterward that a specific log file was not modified or deleted — exactly the evidentiary proof needed here.
      • B. Wrong — Insights analyzes API call volume patterns for anomalies; it has no function related to verifying whether log files have been tampered with.
      • C. Wrong — versioning is a real, useful complementary control that preserves prior copies of overwritten objects, but it doesn't itself produce a cryptographic proof of non-tampering the way signed integrity digests do.
      • D. Wrong — governance mode blocks deletion for most principals, but users with the special bypass permission can still override it, so it doesn't provide the guaranteed, irrefutable proof of non-tampering that court-ready evidence requires.

      Scenario 50

      A company using AWS Organizations with 40 member accounts wants every account's CloudTrail activity — including all new accounts created in the future — automatically logged to a single centralized S3 bucket in a security account, without configuring a trail in each member account individually. What should they set up?

      • A. Manually create a CloudTrail trail in each of the 40 accounts, each configured to deliver to the same central S3 bucket via a bucket policy
      • B. Create an organization trail once in the management account, which automatically applies to all existing and future member accounts
      • C. Deploy a CloudFormation StackSet that creates an identical trail resource in every account in the organization
      • D. Create a CloudTrail trail in the management account with cross-account data events enabled for each member account's S3 buckets

      Topic: CloudTrail

      Correct answer: B

      • A. Wrong — this can centralize delivery, but it requires manual setup in every one of the 40 accounts today and doesn't automatically extend to accounts created in the future, contradicting the stated goal.
      • B. Correct — an organization trail is created once, in the management account, and automatically applies to every existing member account as well as any account created afterward, with logs delivered centrally.
      • C. Wrong — a StackSet can deploy a trail to every account and even auto-deploy to new ones if configured, but it's a bespoke solution the team must build and maintain themselves rather than the purpose-built, natively-integrated organization trail feature.
      • D. Wrong — cross-account data events for S3 buckets is not how organization-wide API activity logging works, and it wouldn't capture non-S3 management or data events happening in the other accounts at all.

      Scenario 51

      A company wants to guarantee that member accounts under a specific OU can never disable CloudTrail logging, even for a moment, rather than merely being told about it after the fact. Which type of guardrail should be applied?

      • A. A detective guardrail, implemented as a Config rule, which flags the account as non-compliant if CloudTrail is disabled
      • B. A mandatory guardrail combined with a CloudWatch alarm that automatically re-enables CloudTrail moments after it is disabled
      • C. A preventive guardrail, implemented as an SCP, which blocks the disabling action outright before it can happen
      • D. An IAM permissions boundary applied to every role in the OU's accounts, denying the CloudTrail disable action

      Topic: AWS Control Tower

      Correct answer: C

      • A. Wrong — a detective guardrail only reports non-compliance after the fact; it doesn't stop the disable action from succeeding in the first place, which violates the "never, even for a moment" requirement.
      • B. Wrong — this sounds like fast protection, but there's still a window where logging was actually off before anything re-enables it, and this "auto re-enable" mechanism isn't how Control Tower guardrails are implemented at all.
      • C. Correct — a preventive guardrail is enforced as an SCP, which blocks the prohibited action outright at the permissions layer, so CloudTrail can never actually be disabled in the first place.
      • D. Wrong — permissions boundaries are per-principal IAM constructs an administrator would have to apply and maintain manually on every role; they aren't a Control Tower guardrail mechanism and wouldn't automatically cover future accounts in the OU.

      Scenario 52

      A member account's S3 bucket has public access accidentally enabled, which trips a Control Tower detective guardrail. A week later, the bucket is still publicly accessible and the setting hasn't changed. The team assumed the guardrail would have fixed it automatically. What actually describes detective guardrail behavior?

      • A. Detective guardrails only run once, when an account first joins the landing zone, so a bucket changed afterward is never rechecked
      • B. Detective guardrails should have blocked the setting change entirely, so the fact it succeeded means the guardrail was misconfigured
      • C. Detective guardrails do remediate automatically, but only after an account has been non-compliant for a minimum of 30 days
      • D. Detective guardrails only report non-compliance in the Control Tower dashboard; they don't automatically remediate the underlying resource

      Topic: AWS Control Tower

      Correct answer: D

      • A. Wrong — detective guardrails, built on Config rules, continuously evaluate resource state over time; they aren't limited to a single check at account creation.
      • B. Wrong — blocking an action outright is the job of a preventive guardrail (SCP-based), not a detective one; the fact that a detective guardrail caught this after the change succeeded is expected behavior, not a misconfiguration.
      • C. Wrong — this invents a 30-day auto-remediation threshold that doesn't exist; detective guardrails don't automatically remediate resources at all, regardless of how long they've been non-compliant.
      • D. Correct — detective guardrails identify and report non-compliant resources in the Control Tower dashboard so the team can act on them; they don't take remediation action on the resource themselves.

      Scenario 53

      A platform team currently creates new AWS accounts by hand through the Organizations console, then manually attaches SCPs, sets up a CloudTrail trail, and configures baseline IAM roles in each one — a process prone to inconsistency and human error. Which capability should replace this manual process?

      • A. Account Factory, a self-service capability that provisions new accounts already wired up with the landing zone's guardrails, logging, and baseline configuration
      • B. Preventive guardrails attached directly to the Organizations root, applied retroactively to catch any missed baseline steps
      • C. A CloudFormation StackSet with automatic deployment enabled, targeting the Organizations root so new accounts inherit the stack
      • D. Migrating all workloads into a single shared account instead, removing the need to provision new accounts at all

      Topic: AWS Control Tower

      Correct answer: A

      • A. Correct — Account Factory is the purpose-built, self-service mechanism that vends new accounts pre-configured with the landing zone's guardrails, logging, and IAM baselines, eliminating the manual per-account setup.
      • B. Wrong — guardrails restrict what actions are possible within an existing account; they don't create accounts or perform the baseline setup steps the team is doing by hand.
      • C. Wrong — a StackSet with automatic deployment can genuinely auto-deploy resources to new accounts, but it's a bespoke solution the team has to design and maintain themselves, rather than the pre-integrated, purpose-built Account Factory.
      • D. Wrong — collapsing into a single shared account abandons the multi-account isolation model and the standard security practice it supports, rather than actually automating the account provisioning process.

      Scenario 54

      A company has already been running AWS Organizations for two years, with an established OU structure and several SCPs. They now want to adopt Control Tower for its guardrails and Account Factory, without dismantling their existing setup. What should they expect?

      • A. They must first delete their existing AWS Organizations setup, since Control Tower requires building its own organization from scratch
      • B. Control Tower can be enabled on top of the existing Organizations setup, since it uses Organizations as its underlying plumbing and layers governance on top
      • C. Control Tower cannot be layered onto a pre-existing Organizations setup at all; it only works on brand-new organizations created at Control Tower setup time
      • D. Control Tower will run as a completely separate, parallel governance system alongside the existing Organizations account, with no shared underlying structure

      Topic: AWS Control Tower

      Correct answer: B

      • A. Wrong — this would destroy the company's two years of existing OU structure and SCPs, directly violating the requirement to keep the setup intact; it's also not actually necessary.
      • B. Correct — Control Tower is built on top of AWS Organizations, using it as the underlying plumbing. It can be enabled on an existing Organizations setup and add its governance layer without requiring the org to be rebuilt.
      • C. Wrong — this is factually incorrect; Control Tower does support being enabled on a pre-existing Organizations setup, subject to some prerequisites, rather than only working on brand-new organizations.
      • D. Wrong — this misrepresents the relationship between the two services; Control Tower doesn't run as a separate parallel system, it directly uses and governs the existing Organizations structure underneath.

      Scenario 55

      A newly formed company wants every future AWS account they create to start from the same pre-configured baseline — the same OU placement, logging setup, and security tooling — rather than assembling that baseline by hand each time. Which concept describes this baseline environment itself, as opposed to the tool that provisions new accounts against it?

      • A. Account Factory, since it is the component that literally contains the OU hierarchy and baseline settings, with guardrails treated as a downstream feature of it
      • B. A detective guardrail set applied at the Organizations root, since guardrails are what define the baseline security posture for the whole company
      • C. The landing zone, the multi-account environment with pre-configured OUs, accounts, and baselines that Control Tower sets up and every future account is provisioned against
      • D. A single CloudFormation template stored in the management account that every new account references directly at creation time

      Topic: AWS Control Tower

      Correct answer: C

      • A. Wrong — Account Factory is the provisioning mechanism that vends new accounts into the baseline environment; it's easy to confuse with that environment, but the two are distinct concepts, and guardrails aren't a "downstream feature" of it.
      • B. Wrong — guardrails are ongoing policy enforcement (preventive or detective) applied within the environment; they don't themselves constitute the OU/account/baseline environment being described.
      • C. Correct — the landing zone is the pre-configured multi-account environment itself — the OU hierarchy, accounts, and baselines — that Control Tower establishes and that every future account is provisioned against.
      • D. Wrong — relying on a single template every account manually references reintroduces the hand-assembled toil the company wants to avoid, rather than using Control Tower's own automated landing zone and Account Factory mechanism.
