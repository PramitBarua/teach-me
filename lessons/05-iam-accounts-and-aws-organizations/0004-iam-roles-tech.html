IAM Roles – The Tech

Lesson 04 of 11 · ~10 min

Roles vs Users: the key difference

An IAM Role is not tied to one specific person or application. It represents a level of access that can be assumed temporarily by any trusted identity.

IAM UserIAM Role
Who uses itOne named entityAny trusted principal
CredentialsLong-term (password / access key)Short-term (temporary security credentials)
Good forKnown, countable principalsServices, unknown count, federation
When to choose a role over a user
If you cannot name exactly one thing using the identity, or there could be more than 5 000 principals, prefer an IAM Role.

Two Policies on Every Role

Trust Policy
Answers: Who is allowed to assume this role? It lists trusted principals — IAM users, other roles, AWS services, external identity providers (Google, Facebook), or other AWS accounts.
Permission Policy
Answers: What can the role do once assumed? Standard IAM policy statements with Allow/Deny.

Assuming a Role: the flow

  1. A principal (inside or outside the account) calls STS AssumeRole.
  2. AWS checks the role's Trust Policy — is this principal listed?
  3. If yes, AWS issues temporary credentials (Access Key ID + Secret + Session Token) with a configurable expiry.
  4. The principal uses those credentials to call AWS APIs. The Permission Policy governs what it can do.
  5. Credentials expire. To continue, the principal must re-assume the role.
Exam tip
A role can be referenced as a principal in resource-based policies (e.g. S3 bucket policies). An IAM Group cannot.
