Simple Storage Service (S3)

S3 Bucket Keys

Lesson 07 of 16 · ~6 min

Source: Adrian Cantrill SAA-C03 · S3 Bucket Keys Docs

The Problem: KMS at Scale

When using SSE-KMS, every single object upload triggers a separate API call to KMS to generate a new Data Encryption Key. KMS is a managed service with rate limits on API calls and a cost per request. Uploading millions of objects means millions of KMS calls — slow, expensive, and potentially throttled.

The Solution: S3 Bucket Keys

When a bucket key is enabled, KMS generates a single time-limited bucket key and hands it to the S3 bucket. The bucket then uses that key locally to generate individual DEKs for each object — without calling KMS for every upload.

Without Bucket KeyWith Bucket Key
KMS API calls1 per object upload1 per time-limited bucket key period
CostHigher (per-object KMS cost)Lower (bulk DEK generation in S3)
ScalabilityRate-limited by KMSS3 handles DEK generation locally

Replication Behaviour

  • If you replicate a plaintext object to a destination bucket that has default encryption or a bucket key, S3 encrypts the object using the destination bucket's configuration. This can change the ETag between source and destination.
  • If the bucket key is enabled on the source bucket, the encryption settings are preserved during same-account or cross-account replication.
Exam tip
Bucket keys reduce KMS API calls and cost — they are purely an optimisation layer for SSE-KMS. The encryption itself is unchanged; only the DEK generation is offloaded to S3.
