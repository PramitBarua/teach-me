Network Storage & Data Lifecycle

EFS Architecture

Lesson 01 of 02 · ~8 min

Source: Adrian Cantrill SAA-C03 · Amazon EFS User Guide

Every EC2 instance you've used so far stores its data on EBS — storage tied to one instance, in one Availability Zone. That's fine until you need many instances to share the same files, or you need an instance to be disposable without losing its data. EFS (Elastic File System) solves this: a network file system that multiple Linux instances can mount and use at the same time.

File Storage, Not Block Storage

EFS is AWS's managed implementation of NFS version 4 (Network File System), a common shared-storage standard. Where EBS is block storage — a raw volume attached to a single instance — EFS is file storage: Linux mounts it into its directory tree (e.g. /nfs/media) and it behaves like a local folder, except the underlying data lives outside any one instance and can be attached to many instances simultaneously.

Think of a WordPress-style app storing user-uploaded media on local disk: lose the instance, lose the media. Move that media onto an EFS file system instead, and the instance becomes closer to stateless — it can be replaced without losing anything, and every instance in a fleet sees the same files.

Architecture: File Systems and Mount Targets

EFS is a private, VPC-scoped service by default. The base entity is the file system, which uses POSIX permissions — the standard permission model every Linux distribution understands.

Instances don't connect to the file system directly. They connect through mount targets — elastic network interfaces placed in specific subnets, each taking an IP address from that subnet's range. An instance mounts the file system via the mount target's IP.

Exam tip
For high availability, place a mount target in every Availability Zone the VPC uses — exactly the same HA pattern as NAT Gateways. One mount target per AZ means an AZ failure doesn't cut off access to the file system for instances in the other AZs.

Because EFS is VPC-scoped, access from outside the VPC — an on-premises data center, for example — requires hybrid networking: VPC peering, a VPN connection, or AWS Direct Connect. Any Linux server reachable through one of those paths can mount the same file system as instances inside the VPC.

Performance Modes

ModeBest for
General Purpose (default)Latency-sensitive workloads — web servers, CMS, home directories, general file serving
Max I/OHighly parallel workloads needing higher aggregate throughput/operations-per-second, at the cost of increased latency — big data, media processing, scientific analysis

Throughput Modes

ModeHow it behaves
Bursting (default)Throughput scales with file system size, with a burst pool — same trade-off as EBS gp2
ProvisionedThroughput is set independently of how much data is stored — same trade-off as EBS io1

Storage Classes

EFS mirrors S3's cost/access trade-off with two storage classes: Standard (default, for frequently accessed files) and Infrequent Access (IA) (lower cost, for files that aren't touched often). Just like S3, lifecycle policies can automatically move files between classes based on access patterns.

Scope
EFS is officially supported for Linux instances only. If a scenario mentions Windows instances needing shared file storage, EFS is the wrong answer — that points toward FSx instead.
