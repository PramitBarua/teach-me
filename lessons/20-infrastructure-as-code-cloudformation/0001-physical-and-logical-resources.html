Infrastructure as Code (CloudFormation)

Physical and Logical Resources

Lesson 01 of 17 · ~8 min

Source: Adrian Cantrill SAA-C03 · CloudFormation template sections · CloudFormation template Resources syntax · Generate templates from existing resources with IaC generator

CloudFormation is AWS's native infrastructure-as-code product. Everything it does starts from a template — a document written in YAML or JSON — and everything it manages comes down to two related but distinct ideas: logical resources and physical resources. Get comfortable with the difference between the two, and the rest of CloudFormation's behavior falls into place.

Logical Resources: The What, Not the How

A logical resource is defined inside a template and represents what you want — an EC2 instance, an S3 bucket, a VPC — without you having to script how it gets built. You give it a logical name (unique within the template), a Type such as AWS::EC2::Instance, and a set of properties CloudFormation uses to configure the eventual real-world resource.

Resources:
  MyInstance:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: ami-0abcdef1234567890
      InstanceType: t3.micro
      KeyName: my-ssh-key

Here, MyInstance is the logical name; everything below it describes intent, not mechanics. A template can contain one logical resource or hundreds, and the same template can be reused to create one stack, ten stacks, or the same stack repeated across many accounts and Regions. A template written this way — with no hard-coded, environment-specific values — is called a portable template, and portability is one of CloudFormation's central design goals.

Stacks Turn Logical into Physical

A stack is what you get when you hand a template to CloudFormation and ask it to act. For every logical resource in the template, the stack creates a matching physical resource — an actual EC2 instance with a real instance ID, an actual S3 bucket that exists in your account. The logical resource is the blueprint; the physical resource is the built thing.

Keeping the two in sync
A stack's entire job is to keep logical and physical resources synchronized. Update the template and update the stack, and CloudFormation diffs the logical resources, then adds, modifies, or deletes the matching physical resources to match. Delete the stack, and its logical resources disappear, taking their physical counterparts with them.

Once a logical resource reaches a create complete state — meaning its physical resource now exists — other logical resources in the same template can reference it. A subnet's logical resource might reference the physical ID of a VPC's logical resource, for example, so that the subnet is created inside the correct VPC. This referencing is what lets templates describe genuinely interconnected infrastructure rather than a pile of unrelated resources.

Why This Distinction Matters

Because CloudFormation deals in logical resources within a template but produces and manages physical resources through a stack, you get a clean separation: you author intent once, and CloudFormation repeatedly and reliably turns that intent into real infrastructure — one deployment, a hundred deployments, or a change-managed, peer-reviewed template stored in a source repository before it's ever applied.

Stale vs. current: templates can now also come from resources
The transcript (and this lesson) describes a one-way flow: template → stack → physical resources. Since the course was recorded, AWS shipped the IaC generator, which runs the process in reverse — it scans resources already sitting in your account that CloudFormation didn't create, and generates a matching template you can then import into a new or existing stack. It's a genuinely useful tool for bringing manually-created resources under CloudFormation management, but it doesn't change anything about how the physical/logical relationship works once a stack owns the resource — the core model in this lesson still holds.
