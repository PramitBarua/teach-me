cfn-hup

Lesson 15 of 17 · ~7 min

Source: Adrian Cantrill SAA-C03 · cfn-hup reference · CloudFormation helper scripts reference

The previous lesson covered cfn-init: a helper script that applies desired-state configuration from a logical resource's metadata. There's a catch worth sitting with — cfn-init only runs once, during initial bootstrap. If you later edit the template's metadata and run an update-stack operation, that change is not automatically reapplied to already-running instances.

Updating a stack does not rebootstrap anything by default
Neither user data nor cfn-init re-executes just because you changed the template and updated the stack. Whatever bootstrapped the instance at launch is, by default, a one-time event.

What cfn-hup Adds

cfn-hup is a separate helper tool — a daemon you install and configure yourself, typically during the same bootstrap process as everything else. Once running, it watches a specific logical resource's metadata for changes. When it detects one, it runs a configurable action — most commonly, rerunning cfn-init so the new configuration actually gets applied.

Put together: update the template's metadata, run update-stack, and cfn-hup (already running on the instance) notices the change, reruns cfn-init, and the instance's configuration catches up — no replacement, no manual SSH session, no re-launch.

Configuration Files

cfn-hup relies on two config files that you place on the instance during bootstrap:

  • cfn-hup.conf — which stack to watch and the credentials to use
  • hooks.conf — the actions to run when a watched path changes
[cfn-auto-reloader-hook]
triggers=post.update
path=Resources.WebServerInstance.Metadata.AWS::CloudFormation::Init
action=/opt/aws/bin/cfn-init -v --stack ${AWS::StackId} \
  --resource WebServerInstance --configsets wordpress_install \
  --region ${AWS::Region}

By default, cfn-hup polls for metadata changes every 10 minutes — worth knowing if a change doesn't seem to land instantly after a stack update.

cfn-init vs. cfn-hup, in one line
cfn-init applies desired-state configuration once, at launch. cfn-hup is what makes that configuration stay in sync across future stack updates, by re-triggering cfn-init whenever the watched metadata changes.
