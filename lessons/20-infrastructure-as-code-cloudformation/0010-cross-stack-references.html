Cross-Stack References

Lesson 10 of 17 · ~8 min

Source: Adrian Cantrill SAA-C03 · Refer to resource outputs in another stack · Fn::ImportValue reference

The previous lesson's nested stacks solve reuse of a template — but every reuse creates a brand-new, separate physical resource. Sometimes that's the wrong outcome. Imagine a well-secured, shared VPC that many short-lived application stacks need to plug into — you don't want ten copies of that VPC, you want all ten stacks using the same one. That's the job of cross-stack references.

Export an Output

Stacks are isolated by design — one stack's Ref can't reach into another. To bridge that gap, a stack can export one of its outputs, publishing it to a list of exports maintained per Region, per account. The export name has to be unique within that list.

Outputs:
  SharedVpcId:
    Value: !Ref SharedVPC
    Export:
      Name: SharedVpcId

Import with Fn::ImportValue

Any other stack in the same Region, same account can then pull that value in using Fn::ImportValue — it replaces Ref exactly where you'd normally reference a local resource, only this time the value comes from the account-wide exports list rather than the local template.

Resources:
  WebServer:
    Type: AWS::EC2::Instance
    Properties:
      SubnetId: !ImportValue SharedSubnetId
Region and account scope only
Exports and Fn::ImportValue only work within one Region of one account — there is no cross-Region or cross-account version of this mechanism. AWS's current documentation also confirms a practical guardrail worth remembering for the exam: you can't delete a stack while another stack still imports one of its exported outputs — the importing stack must stop referencing it first.
Flagged in the course diagrams as exam-critical
This is the same decision point introduced in the nested stacks lesson, viewed from the other side. Cross-stack references let you reuse an actual resource — the same physical VPC, the same subnets — across stacks with genuinely independent, service-oriented lifecycles. Contrast that with nested stacks, which reuse a template and always produce a fresh physical copy. Choose cross-stack references when the shared component has a long lifecycle while its consumers churn independently and shorter-lived — for example, a shared VPC that many short-lived CI/CD test-and-teardown application stacks plug into. Choose nested stacks only when everything is lifecycle-linked as one solution. Getting this backwards in a real deployment — or on the exam — produces a design that doesn't hold up.

When to Reach for Cross-Stack References

  • Service-oriented architectures, where one stack provides a service (like networking) consumed by several others.
  • A churn of short-lived stacks that all need to consume from one long-lived shared resource, such as a shared VPC.
  • Anywhere you need to reuse the actual resource a stack created, not just the template that created it.

Remember: a template is not a stack. A template can be used to create many stacks (nested stacks), or a single stack's actual resources can be shared with many consumers (cross-stack references). Confusing the two is the most common mistake in this part of the exam.
