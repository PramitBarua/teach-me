Stack Sets

Lesson 11 of 17 · ~9 min

Source: Adrian Cantrill SAA-C03 · StackSets concepts · Choose the concurrency mode for StackSets

StackSets let CloudFormation create, update, or delete the same infrastructure across many Regions and, potentially, many AWS accounts — all from one place, instead of you manually switching accounts and Regions and applying the template yourself each time.

Core Concepts

Admin account
The account where the stack set itself is created and managed. Nothing structurally special about it — the label just distinguishes it from the accounts being deployed into.
Stack set
A container, applied in the admin account, that references many stack instances.
Stack instance
A reference to one actual stack in one Region of one target account. Stack instances persist even if the underlying stack fails to create — they exist to record what happened.
Target account
An ordinary AWS account that a stack set is configured to deploy into.

Every stack a stack set creates is a completely normal CloudFormation stack, built from a completely normal template — there's nothing special about the template itself. What StackSets adds is the orchestration: given a set of target accounts and Regions, it uses either self-managed roles (you create the IAM roles and trust relationships yourself) or service-managed permissions (roles are provisioned automatically via AWS Organizations) to assume into each target account, create a stack instance, and create the stack.

Concurrency and Failure Tolerance

Two settings control how a stack set operation rolls out across accounts:

  • Concurrent accounts — how many target accounts CloudFormation deploys into at the same time. Higher concurrency generally means a faster overall rollout.
  • Failure tolerance — how many individual account/Region deployments are allowed to fail before the whole stack set operation is considered failed.
Stale-vs-current: concurrency now has a mode switch
The classic behavior above (concurrency and failure tolerance interacting to throttle a rollout) is still accurate, but AWS has since added a ConcurrencyMode setting with two options. STRICT_FAILURE_TOLERANCE is the original behavior — concurrency is dynamically lowered as failures occur, so deployment speed drops the more failures you see. SOFT_FAILURE_TOLERANCE, added in November 2023, decouples concurrency from the failure count entirely — the operation keeps running at your configured concurrency level regardless of failures, prioritizing deployment speed over the older throttling safety behavior. For the exam, know that failure tolerance and concurrent accounts still exist as concepts, but current StackSets can be told explicitly whether to slow down on failures or push through at full speed.

Retaining Stacks on Removal

Removing a stack instance from a stack set deletes the underlying stack by default. If you want to keep the actual infrastructure in place — just detaching it from the stack set's management — you can set RetainStacks so the stack itself survives in its account and Region even after the instance is removed.

Common Use Cases

  • Enabling AWS Config, or deploying Config rules (MFA enforcement, Elastic IP checks, EBS encryption checks), across a large fleet of accounts.
  • Rolling out cross-account IAM roles at scale, instead of creating the same role manually in every account.
