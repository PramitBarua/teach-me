Template and Pseudo Parameters

Lesson 02 of 17 · ~7 min

Source: Adrian Cantrill SAA-C03 · CloudFormation template Parameters syntax · Get AWS values using pseudo parameters

Lesson 01 established that a template's logical resources describe what to build. But not everything a template needs can be baked in as a static value — some information should come from whoever (or whatever) is creating the stack, and some should come from AWS itself. That's the job of template parameters and pseudo parameters.

Template Parameters: Input from a Human or a Process

A template parameter is declared in a template's Parameters section, alongside Resources. When someone creates or updates a stack — via the console, CLI, or API — they supply a value for each parameter, or accept a default if one exists. Logical resources elsewhere in the template can then reference that parameter's value, letting a single template adapt to different situations: different instance sizes, different environments, different AMIs.

Parameters:
  InstanceType:
    Type: String
    Default: t3.micro
    AllowedValues: [t3.micro, t3.small, t3.medium]
    Description: Size of the web server instance

Each parameter can carry several kinds of configuration:

Default
The value used automatically if nothing else is supplied.
AllowedValues
A restricted list of valid inputs — useful for constraining instance types or environment names.
Restrictions
Minimum/maximum length or an allowed pattern, for validating free-text input.
NoEcho
Hides the input as it's typed — the standard choice for passwords.
Type
Simple types like String, Number, or List, plus AWS-specific types that can populate a live list of VPCs or subnets straight from the console.

Pseudo Parameters: Input from AWS Itself

Pseudo parameters look and behave like template parameters — you reference them the same way — but nobody supplies their value. AWS injects them automatically, and they exist even if you never declare them in the Parameters section.

  • AWS::Region — the Region the stack is being created in
  • AWS::StackName — the name of the stack
  • AWS::StackId — the stack's unique ID
  • AWS::AccountId — the account the stack belongs to

Because AWS::Region always resolves to wherever the stack is actually being deployed, a template that references it never needs a hard-coded Region — the same template stays portable across every Region it's applied in.

Template vs. pseudo parameters aren't mutually exclusive
A template routinely uses both kinds side by side — a template parameter for the environment name, a pseudo parameter for the account ID used inside an IAM policy ARN. The distinction is only about who supplies the value: a human or process for template parameters, AWS itself for pseudo parameters.
Best practice: minimize required input
Every parameter that demands explicit input from a human is one more thing that can be entered wrong. Favor sensible defaults, and favor pseudo parameters over template parameters wherever AWS can supply the value itself — it's one less decision left to whoever runs the stack.
