Wait Conditions, CreationPolicy, and cfn-signal

Lesson 08 of 17 · ~10 min

Source: Adrian Cantrill SAA-C03 · CreationPolicy attribute · Create wait conditions in a template

By default, CloudFormation's idea of "done" is naive. Take an EC2 instance bootstrapped with WordPress via user data: CloudFormation asks EC2 to create the instance, and the moment EC2 reports the instance provisioned, CloudFormation marks the logical resource create complete — regardless of whether the bootstrapping inside that instance ever actually finished, let alone succeeded. The instance can be sitting there mid-install, or permanently broken, and the stack will still report success.

CreationPolicy, wait conditions, and the cfn-signal helper script exist to close that gap — letting a resource genuinely signal back to CloudFormation whether it's actually ready.

How Signaling Works

The mechanism is the same either way: you configure CloudFormation to hold a resource until it receives a set number of success signals, within a configured timeout. The cfn-signal utility — part of the cfn-bootstrap package — runs on the instance (or wherever the bootstrapping happens) and sends that signal back to CloudFormation once its work is done.

  • A success signal, once the required count is reached, moves the resource — and the stack — to create complete.
  • A failure signal fails the resource, and the stack, immediately.
  • No signal at all before the timeout expires is treated as an implicit failure — same outcome as an explicit failure signal.

The maximum timeout you can configure is 12 hours (43200 seconds), expressed in ISO 8601 duration format as PT#H#M#S.

CreationPolicy: the Recommended Default

For EC2 instances and Auto Scaling groups specifically, AWS recommends CreationPolicy — it's an attribute attached directly to the resource being signaled, rather than a separate resource of its own.

AutoScalingGroup:
  Type: AWS::AutoScaling::AutoScalingGroup
  Properties: { ... }
  CreationPolicy:
    ResourceSignal:
      Count: 3
      Timeout: PT15M

Here, the Auto Scaling group launches three instances, but won't move to create complete until it has received three success signals within 15 minutes. Each instance's user data runs its bootstrapping — say, installing an app — then finishes with a call to cfn-signal, which sends that instance's one signal. Get all three within the timeout and the group completes; miss the count, get a failure signal, or run out the clock, and the stack fails instead.

Wait Conditions: the General-Purpose Alternative

A wait condition works on the same principle, but as its own standalone logical resource rather than an attribute bolted onto an existing one. That makes it useful when the thing you're waiting on isn't a single EC2 instance or Auto Scaling group — say, an external IT system completing some process outside the stack entirely.

A wait condition needs a companion wait condition handle — a resource whose only job is to generate a pre-signed URL that anything can send a signal to, without needing AWS credentials of its own:

MyWaitHandle:
  Type: AWS::CloudFormation::WaitConditionHandle

MyWaitCondition:
  Type: AWS::CloudFormation::WaitCondition
  DependsOn: MyEC2Instance
  Properties:
    Handle: !Ref MyWaitHandle
    Timeout: "3600"
    Count: 1

Whatever is doing the signaling — an EC2 instance, an external server — sends a small JSON document to that pre-signed URL: a Status (SUCCESS or FAILURE), a UniqueId, a Reason, and a Data field that can carry back arbitrary information about the event. That Data value isn't just discarded once the wait condition completes — you can pull it into the rest of the template with !GetAtt MyWaitCondition.Data, letting the signal carry real information (a license key, a status detail) into the stack, not just a bare yes/no.

CreationPolicy vs. wait condition, at a glance
Use CreationPolicy for EC2 instances and Auto Scaling groups — it's simpler, and it's what AWS recommends for those cases. Reach for a wait condition when you need to gate progress on something that isn't tied to one specific resource, or when you need the richer data-passing that a wait condition's Data field provides.
Stale vs. current: CreationPolicy now covers a fourth resource type
The transcript describes CreationPolicy as applying to EC2 instances and Auto Scaling groups, with wait conditions as the fallback for everything else. AWS's current documentation confirms both of those still hold — but a CreationPolicy can now also be attached directly to a wait condition resource itself (as an alternative to signaling it manually), and to AWS::AppStream::Fleet, letting an AppStream fleet's start-up be gated by a signal the same way. The core mental model in this lesson — CreationPolicy for the common resource-level case, wait conditions for everything more general — is unchanged.
