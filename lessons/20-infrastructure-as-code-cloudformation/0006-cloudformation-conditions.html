CloudFormation Conditions

Lesson 06 of 17 · ~8 min

Source: Adrian Cantrill SAA-C03 · CloudFormation template Conditions syntax

Conditions let a single template react differently depending on input — deploying more (or less, or different) infrastructure based on a parameter value. They're a simple feature, but they're what turns a fixed template into a genuinely reusable one.

Conditions Are Evaluated First

Like Outputs, the Conditions section is optional. Every condition you declare inside it resolves to true or false, and — critically — CloudFormation evaluates the entire Conditions section before it starts processing logical resources. Whatever a condition resolves to is already settled by the time CloudFormation decides which physical resources to actually create.

Conditions are built from a small set of intrinsic functions: Fn::And, Fn::Equals, Fn::If, Fn::Not, and Fn::Or. A condition can evaluate a parameter value, a pseudo parameter, a mapping value, or another condition — but it can't reference a resource's logical ID or attributes, since resources haven't been created yet at the point conditions are evaluated.

Attaching a Condition to a Resource

Any logical resource can carry a Condition key referencing one of these true/false results:

Parameters:
  EnvType:
    Type: String
    AllowedValues: [dev, prod]

Conditions:
  IsProd: !Equals [!Ref EnvType, prod]

Resources:
  WordPress2:
    Type: AWS::EC2::Instance
    Condition: IsProd
    Properties: { ... }

If IsProd evaluates to true, WordPress2 gets created. If it evaluates to false, CloudFormation skips it entirely — no physical resource is created for that logical resource, no error, nothing. A resource with no Condition key is created regardless, unconditionally, every time.

Picture Bob, a developer, applying this template with EnvType set to either dev or prod. If he sets prod, IsProd resolves true, and — alongside the base WordPress instance that always gets created — a second instance WordPress2 and its Elastic IPs also get created. Set dev, and only the base, unconditional resources appear.

Nesting Conditions

Conditions can reference other conditions, letting you build compound logic: an IsProd condition, a separate CreateS3Bucket condition, and then a third condition — say CreateBucketPolicy — that's only true when both of the others are true, using Fn::And. This lets a bucket policy resource depend on "we're creating a bucket and this is production," entirely through condition composition, with no extra logic in the resource itself.

Two common exam patterns
Conditions built from a numeric or enum-style parameter (say, an AZ count of 1, 2, or 3, each with its own condition controlling a duplicated block of resources) and conditions built from an environment-type parameter (controlling instance size or resource count between dev and prod) are both extremely common in real templates — and both are worth being able to read at a glance.
Conditions can't see resources
Because the entire Conditions section resolves before any resource is processed, a condition can only be built from parameters, pseudo parameters, mappings, and other conditions — never from a resource's logical ID or a Fn::GetAtt lookup. If you need resource-derived logic, that has to live inside the resource itself (for example, via Fn::If in a property value), not inside the Conditions section.
