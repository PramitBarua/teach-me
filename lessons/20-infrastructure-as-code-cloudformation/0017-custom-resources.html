Infrastructure as Code (CloudFormation)

Custom Resources

Lesson 17 of 17 · ~9 min

Source: Adrian Cantrill SAA-C03 · Custom provisioning logic with custom resources · Lambda-backed custom resources

CloudFormation's logical-to-physical resource model is straightforward: define what you want, CloudFormation creates, updates, or deletes the matching physical resource. But CloudFormation doesn't support everything AWS offers, and it never will support some things natively. Custom resources are the escape hatch — a logical resource type that lets CloudFormation do whatever you tell it to, including talking to systems outside AWS entirely.

The Architecture: ServiceToken and Event Data

A custom resource is backed by one of two things, specified as its ServiceToken: a Lambda function ARN, or an SNS topic ARN. Whenever the custom resource is created, updated, or deleted, CloudFormation sends an event to that endpoint containing the operation type and any resource properties you configured.

Whatever is backing the custom resource — say, a Lambda function — does whatever work you've programmed it to do, then reports back success or failure to a response URL supplied in that same event data. On success, the custom resource is marked created, and any data the function returned becomes available elsewhere in the template.

Worked Example: A Bucket That Cleans Up After Itself

Consider a template that creates an empty S3 bucket, plus a Lambda-backed custom resource. On create, CloudFormation invokes the Lambda function, passing it the bucket's name. The function downloads some objects into that bucket, then reports success — the stack reaches CREATE_COMPLETE, and now there's a bucket full of objects.

Later, someone manually uploads a few more files directly into the bucket — outside CloudFormation entirely. Now you delete the stack. Without a custom resource, CloudFormation would try to delete the bucket directly, fail, because S3 refuses to delete a non-empty bucket, and the whole stack deletion would stall.

But because the custom resource was created using the bucket, CloudFormation knows there's a dependency between them. On delete, it works in reverse dependency order: the custom resource is deleted first. CloudFormation sends a delete event — same event-data shape, now flagged as a delete, still carrying the bucket name — to the Lambda function, which empties the bucket (including the manually added files) and signals success via the response URL. Only once the custom resource is gone does CloudFormation move on to deleting the now-empty bucket, which succeeds.

The pattern to recognize
Any scenario where CloudFormation "can't do X natively" — populate a bucket, clean up before deletion, call an external system, fetch a value from something outside AWS — is a custom resource question. The mechanism is always the same: ServiceToken → Lambda or SNS → response URL back to CloudFormation.
A newer, complementary mechanism: CloudFormation Hooks
Custom resources extend what CloudFormation can do — reactively, as part of provisioning. Since 2022, CloudFormation Hooks solve a different problem: proactively validating or blocking a create, update, or delete operation before it happens, typically for governance — for example, rejecting a stack update that would create a non-compliant resource. If a question is about extending functionality (populate a bucket, call an external API), think custom resources. If it's about pre-provisioning compliance checks that can stop an operation before anything is touched, that's Hooks.
