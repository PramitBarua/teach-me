Stack Roles

Lesson 13 of 17 · ~7 min

Source: Adrian Cantrill SAA-C03 · CloudFormation service role

Creating a stack means CloudFormation creates physical AWS resources, and every one of those operations needs permission. By default, CloudFormation uses the permissions of whoever is creating the stack — so to run a template that creates a VPC, an EC2 instance, and an RDS database, the identity applying that template needs permission both to manage stacks and to create a VPC, an EC2 instance, and an RDS database directly.

That's often more access than an organization wants to hand out. Stack roles (CloudFormation service roles) solve this: CloudFormation assumes an IAM role to perform the actual resource operations, so the identity driving the stack never needs those resource permissions itself.

Role Separation in Practice

Picture two identities: Gabby, an account administrator, and Phil, a help-desk engineer who should only be able to manage infrastructure through CloudFormation, never directly.

  1. Gabby creates an IAM role with the permissions needed to create the resources in a given template. Phil can't edit this role, and has no permission to assume it directly.
  2. Phil is given only two things: permission to create/update/delete stacks, and iam:PassRole permission to pass Gabby's role into CloudFormation.
  3. When Phil creates a stack from Gabby's template, he selects that role in the console (or specifies it via the API/CLI). The role becomes attached to the stack.
  4. CloudFormation assumes the role to perform every resource operation for that stack — not Phil's own permissions.

Phil ends up able to deploy exactly the infrastructure Gabby has authorized, through CloudFormation, without ever holding the underlying resource permissions himself.

The exam scenario to recognize
Whenever a question describes an identity that needs to create or manage AWS resources only through CloudFormation, and not be able to touch those resources any other way, a service role attached to the stack is the answer. The identity only ever needs stack permissions plus iam:PassRole — never the resource-level permissions themselves.
Once attached, it's permanent
Per the current CloudFormation documentation, once a service role is associated with a stack, CloudFormation always uses that role for every subsequent operation on the stack — it cannot later be removed from the stack.

Retrieval Practice

Answer from memory. Explanations appear after each answer.

1. A help-desk engineer must be able to deploy a predefined CloudFormation template but should never have direct permission to create the resources it defines. What's the minimum set of permissions to give that engineer?

2. When a stack has a service role attached, which permissions does CloudFormation actually use to create the resources defined in the template?

3. An admin wants to detach a service role from an existing stack and go back to using the caller's own permissions instead. What does current CloudFormation documentation say about this?
