CloudFormation Init (cfn-init)

Lesson 14 of 17 · ~8 min

Source: Adrian Cantrill SAA-C03 · AWS::CloudFormation::Init · cfn-init reference

You already know one way to bootstrap an EC2 instance: user data, a script that EC2 (not CloudFormation) hands to the operating system on first boot. CloudFormation Init is a native CloudFormation alternative — configuration directives live directly in the template, attached to the same logical resource they configure.

Procedural vs. Desired State

The distinction that matters for the exam: user data is procedural. It's a list of commands executed in order — you tell the instance how to reach a state, step by step. CloudFormation Init is a desired-state system. You declare what you want to be true — a package installed, a service running — and the tool figures out how to get there.

Desired state brings two practical benefits. It's cross-platform, working consistently across Linux distributions (and in places, Windows). And it's idempotent: if Apache is already installed and your config says Apache should be installed, running it again does nothing. If a service is already defined and already started, nothing changes. You don't need to hand-write the "is this already done?" logic yourself — the system checks for you.

How It's Wired Together

The directives live under Metadata → AWS::CloudFormation::Init on an EC2 (or Auto Scaling) logical resource. A helper script called cfn-init, pre-installed on Amazon Linux and available for other platforms, is what actually reads that metadata and applies it. You invoke cfn-init yourself, from user data — so user data doesn't disappear, it just shrinks down to a couple of lines:

#!/bin/bash
/opt/aws/bin/cfn-init -v --stack ${AWS::StackId} \
  --resource WebServerInstance --configsets wordpress_install \
  --region ${AWS::Region}
/opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackId} \
  --resource WebServerInstance --region ${AWS::Region}

CloudFormation substitutes ${AWS::StackId} and ${AWS::Region} with real values before the instance ever sees this script. Those values are what let cfn-init call back to the CloudFormation service and fetch its own configuration — it knows exactly which stack and which logical resource it belongs to. cfn-signal afterwards tells CloudFormation whether bootstrapping succeeded, so the stack knows when the instance is genuinely ready.

Config Keys and Config Sets

Inside AWS::CloudFormation::Init, directives are grouped into config keys — named containers, each of which can hold the same seven sections, always processed in this order: packages, groups, users, sources, files, commands, services.

  • packages — software to install
  • groups / users — local OS group and user management
  • sources — archives to download and extract
  • files — files to create on disk
  • commands — arbitrary commands to run
  • services — services to enable and keep running

A single config key is often enough. But you can define several — say, install_cfn, install_wordpress, configure_wordpress — and bundle them into a config set, which names which config keys to use and in what order:

Metadata:
  AWS::CloudFormation::Init:
    configSets:
      wordpress_install:
        - install_cfn
        - install_wordpress
    install_cfn:
      files: { ... }
    install_wordpress:
      packages:
        yum: { wordpress: [] }

The --configsets wordpress_install flag on the cfn-init call above is what picks this bundle. A single template can define multiple config sets — one for a fresh install, another for an upgrade path — and cfn-init is simply told which one to run.

Exam framing
If a question emphasizes idempotency, desired state, or configuration defined in the template's metadata rather than as a shell script, that's cfn-init, not plain user data.
