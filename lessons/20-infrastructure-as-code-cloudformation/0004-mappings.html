Mappings

Lesson 04 of 17 · ~6 min

Source: Adrian Cantrill SAA-C03 · CloudFormation template Mappings syntax · Fn::FindInMap

A CloudFormation template is, at its top level, just a set of sections — Resources, Parameters, and now a third one: Mappings. Like parameters, mappings exist to help a template adapt to its surroundings instead of being static — but where a parameter takes input from a human or from AWS, a mapping is a lookup table baked directly into the template itself.

The Mappings Section: Keys to Values

A mapping maps a key to a value — or, more commonly, a top-level key to a second-level key to a value, giving you a two-level lookup. The classic example is looking up the right AMI ID for a given Region and a given architecture.

Mappings:
  RegionMap:
    us-east-1:
      HVM64: ami-0abcdef1234567890
    eu-west-1:
      HVM64: ami-0123456789abcdef0

Fn::FindInMap: Reading a Mapping

Fn::FindInMap is the function that performs the lookup. It always needs the mapping's name and a top-level key; supply a second-level key as well, and it drills one level deeper.

ImageId: !FindInMap [RegionMap, !Ref 'AWS::Region', HVM64]

Notice the top-level key here is !Ref 'AWS::Region' — a pseudo parameter, not a literal string. That's what turns a static lookup table into something genuinely portable: the same template automatically picks the right AMI for whichever Region it's deployed into, with no parameter for the deployer to fill in and no risk of picking the wrong AMI for the Region.

One or two levels — your choice
If you only ever need a single key mapped to a single value, a one-level mapping works fine. Two-level mappings are for exactly the kind of "by Region, then by architecture" (or "by Region, then by environment") lookups that come up constantly in portable templates.
Stale vs. current: two things worth knowing now
First, Fn::FindInMap gained a genuine enhancement since this course was recorded: under the AWS::LanguageExtensions transform, it now supports a default value parameter, returned when the requested keys aren't found in the mapping — the plain lookup behavior in this lesson still works exactly as described, this is purely additive. Second, and more practically: for the AMI-lookup use case specifically, current AWS guidance now steers away from maintaining a hand-built RegionMap at all. Instead, it recommends a dynamic reference to a public SSM parameter (for example, the latest Amazon Linux 2 AMI) so the template always resolves to the current AMI without anyone having to update the mapping by hand. Mappings remain a valid and commonly tested CloudFormation feature — this is a note about the specific AMI-table example, not a correction to how Fn::FindInMap itself works.
