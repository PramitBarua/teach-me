Nested Stacks

Lesson 09 of 17 · ~8 min

Source: Adrian Cantrill SAA-C03 · Working with nested stacks · AWS::CloudFormation::Stack reference

A single CloudFormation stack is isolated — every resource inside it is created, updated, and eventually deleted together, as one unit sharing a single lifecycle. That's fine for simple projects, but two limits push complex, professional-grade deployments toward using multiple stacks instead: a hard cap of 500 resources per stack, and the fact that a stack's resources can't be referenced from any other stack — Ref only works within the stack that defines the resource.

There are two architectural patterns for splitting work across multiple stacks: nested stacks (this lesson) and cross-stack references (next lesson). Choosing correctly between them is one of the more testable distinctions in the CloudFormation part of the exam.

Root Stacks and Parent Stacks

A root stack is the one stack in a nested architecture that a human or an automation process creates directly — through the console, the CLI, or a pipeline. Every other stack in the structure gets created indirectly, by another stack. Any stack that creates further nested stacks beneath it is called a parent stack — so a root stack is usually also a parent stack, and in deep architectures, a nested stack can itself be a parent to further nested stacks below it.

A Stack as a Logical Resource

Inside a template, you're used to logical resources like an S3 bucket or a VPC. CloudFormation also lets a stack itself be a logical resource, using the type AWS::CloudFormation::Stack. It points at a TemplateURL — the location of the child template — and supplies whatever Parameters that child template requires (every parameter needs a value unless the child template defines a default).

Resources:
  VPCStack:
    Type: AWS::CloudFormation::Stack
    Properties:
      TemplateURL: https://someurl.com/template.yaml
      Parameters:
        Param1: value-one
        Param2: value-two
        Param3: value-three

Once VPCStack finishes creating, its outputs become readable from the parent using !GetAtt VPCStack.Outputs.OutputName. That's the only way a parent can reach into a nested stack — you can read its declared outputs, but you can never reference an individual logical resource buried inside it directly.

Chaining Nested Stacks Together

A parent stack can hold several nested-stack resources, and later ones can depend on earlier ones — either because CloudFormation infers the dependency (one nested stack's parameters reference another's outputs) or because you set DependsOn explicitly. A typical chain: a VPCStack creates networking, an ADStack depends on it for a VPC ID to run Active Directory in, and an AppStack depends on ADStack for authentication. Outputs flow upward and sideways: the root stack collects each nested stack's outputs and feeds them in as parameters to the next.

Flagged in the course diagrams as exam-critical
The single decision point between nested stacks and cross-stack references comes down to one question: are you reusing a template, or reusing an actual resource? Nested stacks let you reuse a template — upload a VPC template once, and every nested stack that points at it gets its own separate, physical VPC. Nothing is shared; the code is reused, the resource is not. That's why nested stacks are the right choice only when everything in the structure is lifecycle-linked — created together, updated together, and deleted together as one solution. If you ever need multiple consumers sharing the same physical resource, or parts of the architecture need independent lifecycles, nested stacks are the wrong tool — that's what cross-stack references solve, covered next.

When to Reach for Nested Stacks

  • To get past the 500-resources-per-stack limit — five nested stacks give you room for 2,500 resources.
  • To modularize templates you plan to reuse structurally, such as a standard VPC template deployed across many projects.
  • To simplify large deployments — applying one root stack lets CloudFormation orchestrate every nested stack beneath it automatically.
