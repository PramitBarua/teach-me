Infrastructure as Code (CloudFormation)

DependsOn

Lesson 07 of 17 · ~7 min

Source: Adrian Cantrill SAA-C03 · DependsOn attribute

When CloudFormation creates, updates, or deletes the resources in a stack, it tries to be efficient — doing as much as possible in parallel. To do that safely, it also tries to work out a dependency order automatically. DependsOn is how you step in and state that order explicitly, for the cases where CloudFormation's automatic guess isn't enough.

Implicit Dependencies (the 99% case)

Most of the time, you never need DependsOn at all. If one logical resource's properties reference another — via !Ref, !GetAtt, or !Sub — CloudFormation infers an implicit dependency: it can't resolve that reference until the referenced resource is in a create-complete state, so it creates the referenced resource first automatically. An EC2 instance whose user data references an Aurora cluster's endpoint, for example, waits for that cluster without you writing anything special.

When Implicit Isn't Enough: the Gateway Attachment Problem

Consider a VPC and an Internet Gateway declared side by side in a template. Neither references the other — you can create an Internet Gateway with no VPC, and a VPC with no Internet Gateway — so CloudFormation sees no dependency between them at all.

Now add a VPCGatewayAttachment, which references both the VPC and the gateway. CloudFormation correctly infers that the attachment depends on both. But here's the catch: some other resources — most notably an Elastic IP associated with an instance in that VPC — actually require the gateway to be attached before they can be created, yet nothing in the EIP's own properties references the attachment resource. There's no !Ref to latch onto, so CloudFormation has no way to infer that dependency on its own.

Without an explicit dependency, whether the stack succeeds comes down to the random order CloudFormation happens to pick: create the EIP before the attachment exists, and you get an error. Delete the attachment before the EIP, and you get an error there too.

Resources:
  GatewayToInternet:
    Type: AWS::EC2::VPCGatewayAttachment
    Properties:
      VpcId: !Ref VPC
      InternetGatewayId: !Ref InternetGateway

  MyEIP:
    Type: AWS::EC2::EIP
    DependsOn: GatewayToInternet
    Properties:
      Domain: vpc

With DependsOn: GatewayToInternet added, CloudFormation will only create MyEIP once GatewayToInternet reaches create-complete — and on deletion, it reverses that order, removing MyEIP before the attachment. DependsOn takes either a single resource name, as above, or a list of names when a resource needs several explicit dependencies at once.

Exam-favorite scenario
"Elastic IP creation randomly fails, or stack deletion randomly fails" is one of the most recognizable DependsOn patterns on the exam. Whenever a resource requires an attached Internet Gateway (or other gateway) but has nothing in its own properties that references the attachment, that's the signal to add an explicit DependsOn.
It isn't only about gateways
AWS's own reference broadens this same pattern beyond Elastic IPs: any of an Auto Scaling group, an EC2 instance, a load balancer, an RDS instance, or a VPC route that includes the Internet Gateway can hit the identical problem when it has a public IP address in a VPC whose gateway attachment isn't otherwise referenced. The underlying cause, and the fix, are exactly the same in every case.

Retrieval Practice

Answer from memory. Explanations appear after each answer.

2. An Elastic IP resource's properties don't reference a VPCGatewayAttachment resource anywhere, yet the EIP needs that attachment to exist first. What's the correct fix?

3. A resource has DependsOn set to a list of two other resources rather than a single name. What does this configure?
