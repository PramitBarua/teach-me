IPSec VPN Fundamentals

Lesson 02 of 16 · ~9 min

Source: Adrian Cantrill SAA-C03 · Configure tunnel options for AWS Site-to-Site VPN

IPSec is a group of protocols that work together to build secure, encrypted tunnels across an otherwise insecure network — most commonly, the public internet. It connects two peers (routers) so that traffic between two networks — say, an on-premises data center and a VPC — is authenticated and encrypted in transit. Onlookers on the internet in between see only ciphertext: they can't read it, and they can't tamper with it undetected.

Interesting Traffic

IPSec tunnels aren't permanently up. They're built on demand around the concept of interesting traffic — traffic matching a defined set of rules (network prefixes, or more specific traffic types). When interesting traffic appears, a tunnel is established to carry it. When interesting traffic stops, the tunnel is eventually torn down, ready to be rebuilt the next time it's needed.

A Quick Refresher: Symmetric vs. Asymmetric Encryption

Symmetric encryption is fast and cheap to run, but both sides need the same key — and securely distributing that shared key is the hard problem. Asymmetric encryption is slower, but solves that problem: a public key encrypts data that only the matching private key can decrypt, so the public key can be shared freely while the private key never leaves its owner. Most secure internet protocols follow the same pattern: use asymmetric encryption briefly to safely exchange a symmetric key, then switch to fast symmetric encryption for the actual bulk of the traffic. IPSec follows exactly this pattern, split across two phases.

IKE Phase 1: Slow, Heavy, Establishes Trust

IKE (Internet Key Exchange — versions 1 and 2 exist, with v2 newer and more capable) governs how keys get exchanged. Phase 1 is the expensive part:

  1. The two peers authenticate to each other, using a pre-shared key or certificates — this step proves identity, it does not yet involve encryption keys.
  2. Each side runs Diffie-Hellman key exchange (DH): each generates a private key and a derived public key, the public keys are exchanged, and each side independently combines its own private key with the other's public key to compute the same shared DH key — without that key ever having crossed the network.
  3. The DH key is used to derive a phase 1 symmetric key, which secures an IKE Security Association (SA) — the phase 1 tunnel.

IKE Phase 2: Fast, Built on Phase 1

Phase 2 runs inside the phase 1 tunnel and is comparatively lightweight, because the heavy asymmetric work is already done:

  1. Using the phase 1 symmetric key to protect the negotiation, each peer advertises which cipher suites it supports; the peers agree on a shared method.
  2. A new, dedicated symmetric IPSec key is derived (built on the DH key material and the phase 2 negotiation) — this key is what actually encrypts and decrypts interesting traffic.
  3. The result is a pair of IPSec Security Associations — one per direction — which together form the phase 2 (IPSec) tunnel, running on top of the phase 1 tunnel.
Why split into two phases at all?
Because phase 1 is slow and phase 2 is fast, splitting them is a deliberate efficiency win: the phase 2 (IPSec) tunnel can be torn down when interesting traffic stops and rebuilt quickly on top of the same, still-standing phase 1 tunnel — without repeating the expensive authentication and Diffie-Hellman work. Only if the phase 1 tunnel itself goes down does that heavy setup need to happen again.

Policy-Based vs. Route-Based VPNs

Both VPN styles use the same phase 1 / phase 2 mechanics underneath — they differ in how they classify interesting traffic and how many security associations that produces.

TypeMatches onSA pairs
Route-basedNetwork prefix (e.g. send 192.168.0.0/24 over this tunnel)One SA pair per prefix — simpler to configure
Policy-basedRules matching specific traffic typesOne SA pair per matched rule — more flexible, more configuration

With a policy-based VPN, different traffic types to the same network (say, infrastructure management traffic, CCTV feeds, and financial data) can each get their own SA pair with independently tuned security settings. A route-based VPN keeps it simple: one prefix, one SA pair, all traffic to that prefix treated identically.

Two facts worth memorizing cold
1. Phase 1 authenticates and derives shared key material via Diffie-Hellman; phase 2, built on top of phase 1, negotiates the cipher and derives the key actually used to encrypt data. 2. Route-based VPNs match by prefix (one SA pair per prefix, simple); policy-based VPNs match by rule (one SA pair per rule, flexible but more complex). AWS Site-to-Site VPN, covered next, is route-based.
