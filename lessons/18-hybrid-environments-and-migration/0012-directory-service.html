AWS Directory Service

Lesson 12 of 16 · ~9 min

Source: Adrian Cantrill SAA-C03 · What Is AWS Directory Service? · AWS Managed Microsoft AD

A directory stores identity and asset information — users, groups, computer objects, server objects, file shares — arranged in a hierarchical, tree-like structure usually called a domain. Multiple domains grouped together form a forest. Directories let corporate IT centrally manage identity: join laptops, desktops, and servers to a single directory, and the same username and password works everywhere. Microsoft Active Directory (Active Directory Domain Services, ADDS) is the dominant standard; Samba is a well-known open-source alternative that provides only partial compatibility with it.

AWS Directory Service is AWS's managed directory offering — roughly the same relationship to Active Directory that RDS has to databases: AWS runs it, patches it, and makes it highly available across multiple subnets and Availability Zones, removing the admin overhead of running your own domain controllers. It's a private, VPC-based service. Some AWS services can optionally use a directory (Windows EC2 instances can join one for login and centralized management); others require one outright — Amazon WorkSpaces is the standard example, since a virtual desktop has to authenticate its users against a registered directory.

Directory Service offers three modes, and picking between them is really an exam-style decision problem.

Simple AD — the default

Simple AD is the cheapest, simplest mode: an open-source directory powered by Samba 4, aiming for broad Active Directory compatibility without being a real AD implementation. It comes in two sizes — Small (up to ~500 users) and Large (up to ~5,000 users) — and supports user accounts, group memberships, group policies, EC2 domain join, and Kerberos-based SSO. It integrates with a modest set of AWS applications: WorkSpaces, WorkDocs, WorkMail, and Management Console sign-in.

Simple AD is designed to run in isolation — it has no on-premises integration and cannot form trust relationships with another domain.

Two facts that have moved since this course was recorded — worth knowing right now
Simple AD's compatibility list is narrower than the transcript describes. Current AWS docs explicitly state Simple AD does not support Amazon RDS for SQL Server or Oracle, Amazon FSx, Amazon Chime, IAM Identity Center, MFA, or schema extensions — several of which older material (including this course) lists as working. Treat WorkSpaces, WorkDocs, WorkMail, and console sign-in as the safe, current answer set.

Simple AD itself is being closed to new customers on July 30, 2026. Existing Simple AD directories keep full functionality indefinitely, but after that date nobody can create a new one — AWS steers new customers toward AWS Managed Microsoft AD or AD Connector instead. The exam's "always default to Simple AD" framing is still the right theoretical answer today, but treat this as a service in its sunset window, not a long-term default to recommend in practice.

AWS Managed Microsoft AD

This mode is an actual implementation of Microsoft Active Directory — not an emulation, not Samba-based. It's used when an application genuinely requires real AD features such as schema extensions, or when it needs software like Microsoft SharePoint or SQL Server that expects a full AD deployment underneath it.

Beyond running as a self-contained directory in AWS, it can also establish a two-way trust relationship with an existing on-premises Active Directory, over a VPN or Direct Connect link. Because the AWS-side directory is fully functional on its own, if that private connection drops, AWS services relying on the directory keep working — only cross-directory trust operations are affected.

A version number worth updating
The transcript describes AWS Managed Microsoft AD as running Windows Server 2012 R2 — true when the course was recorded. Current AWS documentation confirms it now runs on Windows Server 2019 (AWS auto-upgraded existing directories starting in 2023). The architectural facts — real AD, schema extensions, two-way trust — are unchanged; only the underlying Windows Server version has moved on.

AD Connector

AD Connector is pure proxy — it stores zero directory data in AWS. You point it at an existing on-premises Active Directory over a VPN or Direct Connect link, and it forwards authentication requests from AWS services back to that on-premises directory. AWS services that require "a directory" see the connector and treat it as one, without knowing or caring that requests are actually being proxied elsewhere.

Because nothing is stored in AWS, AD Connector requires the on-premises directory and the private connection to it to be working at all times — if either fails, the connector fails along with it, and every AWS service depending on it stops authenticating.

Exam heuristic — decision order
Default to Simple AD for isolated directory needs with no on-premises integration. Move to Managed Microsoft AD only when an application needs a real AD schema, or when a trust relationship with on-premises AD is required. Use AD Connector only when directory data must never be stored in AWS at all — you already have an on-premises directory and simply want AWS services to use it.

Answer from memory. Explanations appear after each answer.

1. A startup needs Amazon WorkSpaces for 200 employees, has no existing on-premises directory, and needs nothing beyond basic user and group management. Which Directory Service mode fits, and why?

2. A company is deploying SharePoint on EC2, which requires genuine Active Directory schema extensions, and also wants a trust relationship with their existing on-premises AD over Direct Connect. Which mode is required?

3. A company already runs a mature on-premises Active Directory and wants a handful of AWS services to authenticate against it, but company policy forbids storing any directory data — even a replica — inside AWS. Which mode satisfies this, and what's the trade-off?
