AWS Site-to-Site VPN

Lesson 03 of 16 · ~9 min

Source: Adrian Cantrill SAA-C03 · Tunnel options for your AWS Site-to-Site VPN connection · Accelerated AWS Site-to-Site VPN connections

AWS Site-to-Site VPN is a logical, IPSec-encrypted connection between a VPC and an on-premises (or other external) network. It's the fastest way to establish a hybrid network link into AWS — usually provisionable in under an hour, in sharp contrast to a physical Direct Connect, which can take weeks or months. It typically transits the public internet (the exception — a VPN layered over Direct Connect for extra encryption — is covered in a later lesson).

Core Components

ComponentWhat it is
VPCThe AWS-side private network being connected
Virtual private gateway (VGW)A logical gateway object attached to one VPC; a valid route table target
Customer gateway (CGW)Both the logical AWS configuration and the physical on-premises router it represents
VPN connectionThe configuration linking one VGW to one CGW

From Partial to Full High Availability

This progression is the single most important thing to internalize about Site-to-Site VPN architecture.

Step 1 — attach a VGW. A VGW looks like a simple logical object, but behind the scenes it's already highly available: it has physical endpoints in multiple Availability Zones, each with its own public IPv4 address.

Step 2 — create a VPN connection to one CGW. This links the VGW to a single on-premises customer gateway, and AWS creates two VPN tunnels — one from each VGW endpoint to that same customer router. As long as at least one tunnel is up, the two networks stay connected.

One CGW is still a single point of failure
Even though the AWS side now spans two Availability Zones, every tunnel terminates at the same single on-premises router. If that router or its site fails, the whole connection fails — regardless of how resilient the AWS side is. This is partial high availability: HA on the AWS side, a single point of failure on the customer side.

Step 3 — add a second CGW. Add a second on-premises router, ideally with its own internet connection and ideally in a separate building, and create a second VPN connection from the same VGW to this new CGW. This provisions another pair of tunnels to another two AWS endpoints. Now either customer router, or either Availability Zone, can fail — and the connection survives. That's full high availability: resilience on both sides.

Static vs. Dynamic VPNs

TypeHow routes are learnedTradeoffs
StaticManually configured on both sidesSimple, works with almost any router; no advanced failover or load balancing
DynamicBGP exchanges routes between VGW and CGWRequires BGP-capable customer hardware; supports multi-link failover and load balancing

With a dynamic VPN, you can also enable route propagation on a VPC route table: any network the VGW learns via BGP while a VPN is active gets automatically added as a route, rather than requiring manual route table entries.

The throughput cap — a frequently tested number
A single VPN connection (its pair of tunnels combined) is capped at 1.25 Gbps, and that same 1.25 Gbps figure is also the aggregate cap across all connections on one virtual private gateway. If a scenario needs more throughput than that, plain Site-to-Site VPN is the wrong answer. AWS now also offers two ways past this ceiling: Accelerated Site-to-Site VPN, which routes tunnel traffic over the AWS global network via Global Accelerator for better and more consistent performance (works with Transit Gateway attachments), and Large Bandwidth Tunnels, which raise the per-tunnel cap to 5 Gbps for VPN connections attached to a Transit Gateway or Cloud WAN (not available on a plain VGW attachment, and not combinable with Accelerated VPN).

Other Considerations

  • Latency — traffic transits the public internet, with variable hop count and latency. If an application is latency-sensitive, Direct Connect is the better fit.
  • Cost — an hourly connection charge, plus data transfer out charges; traffic also consumes your on-premises internet bandwidth (and any data cap it carries).
  • Speed to provision — often hours, since it's entirely software-defined and IPSec is supported on almost any router (dynamic VPNs additionally need BGP support, which is less universal).
  • Pairing with Direct Connect — a VPN can stand up connectivity quickly while a much slower-to-provision Direct Connect request is in progress, and it also works well as a backup path for an existing Direct Connect connection.

Retrieval Practice

1. A company has one VGW attached to its VPC and one VPN connection to a single on-premises customer gateway. The AWS side spans two Availability Zones. What's the actual availability posture of this design?

2. An application needs guaranteed throughput of 3 Gbps between on-premises and a VPC, and the team wants to keep using a standard Site-to-Site VPN attached directly to a virtual private gateway. Is the default 1.25 Gbps cap a blocker here?

3. A company wants multiple VPN links between the same two sites to automatically share traffic and fail over based on link state, with routes learned dynamically rather than typed in by hand. Which VPN configuration supports this?
