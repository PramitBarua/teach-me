Transit Gateway

Lesson 07 of 16 · ~8 min

Source: Adrian Cantrill SAA-C03 · What is AWS Transit Gateway?

Transit Gateway (TGW) is a network transit hub — a highly available, scalable regional virtual router that connects VPCs to each other and to on-premises networks via Site-to-Site VPN and Direct Connect. It's designed to remove the complexity that plagues large hybrid network architectures.

The Problem It Solves

Consider a company with four VPCs (A, B, C, D) and a corporate office, all needing full, highly available connectivity to each other, using only tools covered so far:

  • VPC-to-VPC: peering isn't transitive, so a full mesh between 4 VPCs needs 6 peering connections.
  • Office-to-VPCs, partial HA: each of the 4 VPCs needs two VPN tunnels to a single customer gateway — 8 tunnels — but that single customer gateway is itself a single point of failure.
  • Office-to-VPCs, full HA: add a second customer gateway (ideally a separate premises and internet connection), doubling to 16 tunnels total.
Full mesh complexity explodes as you scale
This design already needs 6 peering connections plus 16 VPN tunnels for just four VPCs and one office — and every additional VPC or premises makes the required connection count grow faster still. It's a huge amount of overhead to plan, implement, and maintain, and it becomes unmanageable well before you reach a "real" enterprise network size.

How Transit Gateway Changes This

TGW replaces point-to-point sprawl with a single hub. You connect things to it using attachments:

  • VPC attachments — like interface endpoints, these require a subnet in each Availability Zone you want the TGW to use inside that VPC.
  • Site-to-Site VPN attachments — the TGW becomes the AWS-side termination point, so each customer gateway connects back to just the one TGW instead of to every VPC individually.
  • Direct Connect gateway attachments — lets physical, private connectivity reach the same hub too.

With attachments to VPCs A, B, C, D and to both customer gateways, the same level of high availability is preserved (still four AZ-diverse tunnels at the AWS side), but the number of connections to plan and manage drops dramatically — and every VPC can now reach every other VPC and the on-premises office through one device.

Exam tip: transitive routing is the key differentiator
A Transit Gateway supports transitive routing — traffic can flow between any two attachments as long as appropriate routes exist — which is exactly what VPC peering cannot do. If a scenario needs many networks to all reach each other without an exploding full-mesh connection count, that points to Transit Gateway, not more peering or more point-to-point VPNs.

Further Capabilities

  • TGW peering — transit gateways can peer with other transit gateways across Regions and accounts, riding the AWS global network for predictable cross-Region latency instead of the public internet.
  • Sharing via AWS RAM — Resource Access Manager lets a single transit gateway be shared across multiple AWS accounts.
  • Route tables — a TGW starts with a default route table governing traffic between attachments, but you can create multiple route tables to build more complex, segmented routing topologies (for example, isolating certain VPCs from others even though they share the same hub).
Three high-yield facts to memorize
1. Transit Gateway supports transitive routing (VPC peering does not). 2. It can peer cross-Region and cross-account. 3. It's shareable via AWS RAM. These three facts, together with the attachment types (VPC, VPN, Direct Connect gateway), cover the large majority of exam angles on this topic.

Retrieval Practice

Answer from memory. Explanations appear after each answer.

1. A company has 6 VPCs that all need to communicate with each other and with an on-premises office, and the number of VPCs is expected to keep growing. Using only VPC peering and point-to-point VPNs is becoming unmanageable. What should they adopt?

2. VPC A and VPC C are both attached to the same Transit Gateway, but neither is directly peered nor attached to each other in any other way. Can an instance in VPC A reach an instance in VPC C?

3. A global company has Transit Gateways in two different Regions, owned by two different AWS accounts, and wants traffic between them to stay off the public internet with predictable latency. What should they configure?
