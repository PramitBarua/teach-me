Storage Gateway: File Gateway

Lesson 10 of 16 · ~8 min

Source: Adrian Cantrill SAA-C03 · What Is Amazon S3 File Gateway? · Limits and Quotas for Amazon S3 File Gateway

File Gateway bridges on-premises file storage and S3: it presents one or more file shares over NFS (Linux) or SMB (Windows, with optional Active Directory authentication), and each share maps to a single S3 bucket — a pairing AWS calls a bucket share.

Exam tip — flagged in the course diagram
The single most important fact about File Gateway, and the one most likely to be tested against the other Storage Gateway modes: S3 is the primary, authoritative copy of the data — not the local on-premises cache. Anything written on-premises is copied up to S3 automatically; the local disk only ever holds a read/write cache for LAN-like performance. This is the opposite of Volume Gateway in Stored mode, where the on-premises volume is authoritative and S3 only holds an asynchronous backup. If a question hinges on "which copy is the real one," that's the distinction to reach for.

How files map to objects

Because S3 is authoritative, writing a file to a share creates (or updates) an object in the linked bucket, and any object placed directly into the bucket becomes visible on the share. The mapping is direct: a file named winky.jpg at the share root becomes an object named winky.jpg; a file at omgwow/ruffle.png becomes an object named omgwow/ruffle.png. Nested folder paths are folded into the object key — the same mechanism S3 itself uses to emulate a folder hierarchy on top of what is really a flat namespace.

Sizing facts
A single gateway supports up to 50 file shares (raised from an original limit of 10 — worth knowing the current ceiling if a scenario pushes on share count). Because S3 holds the authoritative copy, the local appliance only needs enough disk for its read/write cache, not for the full data set.

Multi-site architecture — and its caveats

File Gateway isn't limited to one site talking to one bucket. Multiple gateways at different premises can point at the same bucket, each presenting it as a local share. This unlocks a genuine multi-site architecture, but with two behaviors worth knowing cold:

  • Writes propagate to S3 automatically — a new or changed file appears as an S3 object immediately. But that update does not automatically appear on other gateways' shares. Each gateway only refreshes its view of the bucket on its next listing — to avoid unnecessary, continuous S3 API calls. AWS's "notify when uploaded" feature can push a CloudWatch Events notification when new objects land, so other sites can be told to refresh, but this has to be deliberately designed in — it isn't automatic.
  • No object locking. If two sites write to the same file at close to the same time, there's no coordination or conflict detection — one write can silently overwrite the other, causing data loss. Mitigate this by keeping only one share writable and the rest read-only, or by implementing your own access control over who can write and when.

DR and lifecycle, for free

Because the data genuinely lives in S3, standard S3 features work underneath a file share with no special integration work:

  • Cross-Region Replication — replicate the bucket to a second Region for multi-Region DR, without changing how the on-premises side operates.
  • S3 Lifecycle policies — a share is created with a default storage class (typically S3 Standard), but a lifecycle policy can transition objects to S3 Standard-IA after some number of days, then on to S3 Glacier later — all automatic, all transparent to whoever is accessing the share on-premises.

Because objects also live in an ordinary S3 bucket, anything that can use S3 as a source can reach the same data indirectly — S3 Event Notifications with Lambda, Athena queries, and so on.

Exam heuristic
See the keyword file, together with NFS or SMB, in a Storage Gateway question — default to File Gateway. Compare against the pattern from the previous two lessons: volumes → Volume Gateway, tapes → Tape Gateway, files/NFS/SMB → File Gateway.
