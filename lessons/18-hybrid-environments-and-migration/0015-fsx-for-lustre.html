Hybrid Environments and Migration

FSx for Lustre

Lesson 15 of 16 · ~8 min

Source: Adrian Cantrill SAA-C03 · Deployment and Storage Class Options for FSx for Lustre File Systems

FSx for Lustre is a managed implementation of the Lustre file system — built for Linux, using POSIX-style permissions, and designed for high-performance computing: machine learning, big data processing, and financial modeling. It scales to hundreds of GB/s of throughput with sub-millisecond latency.

Exam heuristic: which FSx?
Windows / SMB keywords → FSx for Windows File Server. Lustre / HPC / machine learning / SageMaker / POSIX / big-data-processing keywords → FSx for Lustre. This distinction, not Lustre's internals, is the testable core of the topic.

Deployment Types: Scratch vs. Persistent

The classic exam-tested framing is a choice between two deployment types:

Deployment typePerformanceResilienceBest for
ScratchMaximum raw performanceNo replication. A hardware failure loses the data on the affected server — other data on the file system is unaffected.Short-term / temporary workloads where raw speed matters more than durability.
PersistentHigh, but tuned for durability over peak speedReplicated within a single AZ (not multi-AZ) and self-healing — AWS automatically replaces failed hardware.Longer-term workloads that need resilience against hardware failure, but not a full AZ outage.
Persistent's high availability stops at the AZ boundary
Persistent's replication happens within one Availability Zone only. It protects you from hardware failure, but not from the loss of that entire AZ. Lustre is fundamentally a single-AZ file system in both deployment types — that's part of how it delivers such extreme performance.

Both deployment types support backing up file system data to S3, either manually or automatically, with a configurable retention window of 0–35 days (0 disables automatic backups, matching the pattern used elsewhere in AWS).

Stale-vs-current: AWS has added more generations since this framing
Current AWS documentation describes a richer picture than plain "Scratch vs. Persistent": there are now Scratch 1 / Scratch 2 and Persistent 1 / Persistent 2 generations, plus three storage classes (SSD, HDD, and Intelligent-Tiering). Notably, Persistent 2 file systems using the Intelligent-Tiering storage class now replicate data across multiple Availability Zones — a real exception to the "Persistent is single-AZ only" rule above for that specific configuration. The Scratch-vs-Persistent, single-AZ mental model above is still the right level of depth for SAA-C03, but don't be surprised if newer AWS material frames it with more nuance.

Architecture: MDTs, OSTs, and the S3 Repository

A Lustre file system splits stored data into two kinds of targets:

  • Metadata Target (MDT) — stores file names, timestamps, and permissions. There is exactly one per file system.
  • Object Storage Targets (OSTs) — store the actual file data, striped across multiple ~1.17 TiB units. Splitting data across many OSTs is how Lustre achieves its performance.

The file system is deployed into a client-managed VPC, reachable through a single Availability Zone / single ENI — the same private-networking access pattern as EFS and FSx for Windows (including reachability over VPN and Direct Connect, bandwidth permitting).

Optionally, you can associate the file system with an S3 repository (an S3 bucket) at creation time.

S3 repository objects are lazy-loaded, not synced
When a repository is attached, S3 objects appear in the Lustre namespace immediately — but they are not actually present in the file system until a client first accesses them. That first access triggers a lazy load from S3 into Lustre. There is no automatic two-way sync: changes made inside the Lustre file system are pushed back to the S3 repository only when you explicitly run hsm_archive. Think of Lustre and the S3 bucket as two genuinely separate stores that you can bridge on demand, not a live mirror.

Performance Model: Baseline + Burst Credits

Throughput is expressed per TiB of provisioned storage, with a baseline level and the ability to burst above it using a credit system — you earn credits while running below baseline and spend them while bursting above it, conceptually similar to EBS burst credits, just at much higher scale and with a more parallel architecture. Persistent deployments offer multiple baseline throughput tiers per TiB, giving you a cost/performance dial to turn.
