Storage Gateway: Tape Gateway (VTL)

Lesson 09 of 16 · ~7 min

Source: Adrian Cantrill SAA-C03 · What Is Tape Gateway? · AWS Storage Gateway Quotas

Tape Gateway, also called VTL mode (Virtual Tape Library), is the Storage Gateway mode built for one specific job: letting an organization keep its existing tape-based backup software and infrastructure, while replacing the physical tape hardware underneath it with AWS storage.

Physical tape backup, briefly

To appreciate what Tape Gateway replaces, it helps to know the physical vocabulary first. Enterprise tape backup uses several distinct pieces of equipment:

ComponentWhat it is
Tape driveReads from or writes to a single inserted tape — sequential access only, not random access like disk
Tape loader / robotA mechanical arm that inserts, removes, and swaps tapes between the drive and storage slots
Tape libraryA rack-mounted unit containing one or more drives, one or more loaders, and slots for tapes not currently in a drive
Tape shelfAny storage location that isn't the library — typically an off-site, third-party facility for disaster resilience

A common tape format is LTO (Linear Tape Open); the transcript's LTO9 generation stores 24 TB of data uncompressed per tape, up to roughly 60 TB compressed. The on-premises backup server talks to the tape library over iSCSI, which exposes the tape drives and a media changer (another name for the loader/robot) as devices. Running this yourself means capex for the hardware and software, plus ongoing opex for licensing, maintenance, and staff — and moving tapes to off-site shelf storage for resilience costs both money and time.

How Tape Gateway replaces it

Tape Gateway keeps the business premises and the backup server, but swaps the physical tape library for the Storage Gateway appliance. Critically, the appliance presents itself over iSCSI exactly like a physical tape library — a media changer plus tape drives — so the backup software cannot tell the difference. This is deliberate: little to no change is required to existing backup software beyond pointing it at the gateway.

Behind that iSCSI interface, the gateway keeps an upload buffer and local cache (much like Volume Gateway in cached mode) so backups happen at LAN speed locally, while data uploads to AWS in the background. On the AWS side, the Storage Gateway endpoint presents two capabilities:

  • Virtual Tape Library (VTL) — an AWS-hosted tape library, backed by S3, holding "active" virtual tapes.
  • Virtual Tape Shelf (VTS) — backed by S3 Glacier Flexible Retrieval or S3 Glacier Deep Archive, for virtual tapes that have been exported out of the library.

Exporting a tape in the backup software is the virtual equivalent of physically ejecting it and driving it to off-site storage: the gateway archives it from the VTL into the VTS, moving the underlying data from S3 into Glacier or Glacier Deep Archive. Glacier suits data you may still need to retrieve occasionally; Glacier Deep Archive suits long-term retention you expect to rarely or never touch (for example, for legal reasons). Either way, retrieving an archived tape moves it back from the VTS into the VTL, where the gateway can serve it again.

Capacity numbers worth memorizing
A virtual tape can be sized from 100 GiB up to 15 TiB. A single gateway supports up to 1,500 virtual tapes in its VTL, totaling up to 1 PiB of active library capacity. Once a tape is archived into the VTS, though, it no longer counts against that 1,500-tape / 1 PiB limit — archive capacity is effectively unlimited.
A number that's drifted since the course was recorded
Adrian's lesson ties the (then-current) 5 TiB maximum virtual tape size to S3's 5 TB maximum object size, calling it "not a coincidence" — both limits matched because tapes are literally stored as S3 objects. AWS has since raised the maximum virtual tape size to 15 TiB, while S3's single-object maximum has stayed at 5 TB. The underlying mechanism (a virtual tape backed by one S3 object) still holds, but the two numbers no longer match — don't expect a modern exam to test "tape size equals S3 object size" as a hard equivalence.

Why use it

Tape Gateway supports a few distinct architectural goals: keep an existing backup system running but swap expensive physical tape infrastructure for economical AWS storage; extend limited on-premises tape capacity into AWS alongside existing hardware; or support a migration, where historical tape backups move onto the gateway so the physical tape hardware can be decommissioned entirely, with the gateway itself (and a backup server) able to run from within AWS for any future restores.

Exam heuristic
Whenever a scenario mentions tape, a tape library, tape backup software, or tape-based restore, the answer is Tape Gateway / VTL mode — essentially without exception at the associate level.
