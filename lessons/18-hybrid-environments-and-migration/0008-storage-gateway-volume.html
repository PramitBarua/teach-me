Storage Gateway: Volume Gateway (Stored & Cached)

Lesson 08 of 16 · ~8 min

Source: Adrian Cantrill SAA-C03 · How Volume Gateway Works · AWS Storage Gateway Quotas

Storage Gateway acts as a bridge between on-premises storage and AWS, usually running as a virtual machine on-premises (a hardware appliance is also available). Locally it presents storage over iSCSI, NFS, or SMB; on the AWS side it integrates with EBS, S3, and Glacier. It's used for migrations, data center capacity extension, storage tiering, DR, and replacing legacy tape backup.

Exam tip — flagged in the course diagram: iSCSI is the Volume Gateway keyword
Both modes of Volume Gateway present raw block storage over iSCSI — exactly like traditional SAN/NAS hardware, so on-premises servers can build a file system on top just as they always have. If an exam question mentions iSCSI or raw block devices in a Storage Gateway context, think Volume Gateway first.

Stored Mode: On-Premises Is Primary

In stored mode, the gateway presents volumes over iSCSI, and all data lives on local on-premises storage as the primary, authoritative copy. Writes also land in a local upload buffer, from which the gateway asynchronously copies data to AWS — over the internet or a public VIF — landing in S3 as EBS snapshots. This happens continuously in the background with no manual intervention.

Exam tip — flagged in the course diagram: stored mode is backup and DR, not capacity relief
Because every byte still lives on local storage, stored mode is excellent for full-disk backup and disaster recovery — the resulting EBS snapshots can restore a volume or seed a brand-new EBS volume, giving strong RPO/RTO. What it does not do is extend on-premises capacity: since the primary copy of every volume still consumes local storage, running low on local disk space is a problem stored mode cannot fix.

Cached Mode: AWS Is Primary

In cached mode the relationship inverts. S3 becomes the primary, authoritative store for all volume data — specifically an AWS-managed area of S3 that isn't visible as a normal bucket through the S3 console or API. Only the frequently accessed working set is kept locally, in cache storage and the upload buffer, for low-latency access.

Exam tip — flagged in the course diagram: cached mode enables data center extension
Because only the working set is stored locally, a gateway with a modest amount of local cache can address hundreds of terabytes to a petabyte of AWS-backed data while consuming only a fraction of that locally. This is what enables a data center extension architecture — a business at capacity can keep serving its data at local-area-network speeds for hot data, while the bulk of it actually lives in AWS.

The exam heuristic that ties it together
If a Storage Gateway question uses the keyword "volume," default to Volume Gateway. From there, language about backup or disaster recovery points to stored mode; language about capacity relief or data center extension points to cached mode. Both modes create EBS snapshots and both use iSCSI — the difference is purely which side (on-premises or S3) holds the authoritative primary copy.
