AWS Config

Lesson 06 of 9 · ~7 min

Source: Adrian Cantrill SAA-C03 · What Is AWS Config? · Evaluating Resources with AWS Config Rules

AWS Config is frequently misunderstood, and the exam exploits exactly that misunderstanding. Its core job is simple: record configuration change history for resources in an account. It is not a permissions product, and it is not a protection product.

What Config Actually Records

Once enabled, Config monitors every resource's configuration. Every time a resource changes, a configuration item is created, capturing the pre-change state, the post-change state, the resource's relationships to other resources, and who made the change. If you added a rule to a security group attached to an EC2 instance, Config would capture the before and after state of the rule, the fact that it changed, who changed it, and the attachment to that instance.

All of this is stored in a standard format inside an S3 bucket known as the config bucket, accessible either directly or through the Config API. Config is a regional service, but it supports cross-region and cross-account aggregation so a security team can review compliance across an entire organization from one place.

Config never prevents anything
This is the single most exam-tested fact about the service: AWS Config is a detective control, not a preventive one. It can define what "compliant" looks like and can identify when a resource drifts from that standard, but it can never stop the non-compliant change from happening in the first place. If an exam question asks "does Config prevent X," the answer is always no — it only detects and reports X after the fact.

Config Rules: From Recording to Evaluating

The recorder and config bucket are the standard, always-on part of the product. Config Rules are the optional layer that adds real power. A rule can be AWS-managed (predefined) or custom, with custom rules evaluated by a Lambda function that you write. Each rule evaluates matching resources and marks them compliant or non-compliant against the standard the rule defines — for example, a list of allowed security group ports. Adding a disallowed port doesn't get blocked, but Config Rules will flag the resulting resource as non-compliant.

Closing the Loop: From Passive Recording to Active Response

Config alone only records and evaluates. Turning that into action needs other services layered on top:

MechanismPurpose
SNSNotifies people or systems about a stream of changes or compliance state changes
EventBridgeReacts to a compliance state change and invokes a target for remediation
Lambda (via EventBridge)Flexible, code-driven remediation — well suited to account-level fixes
SSM Automation documentsRemediation targeted at a specific instance's configuration
Detective now, remediation later
Think of the full pipeline as: resource changes → config item recorded → Config Rule evaluates compliance → SNS notifies and/or EventBridge triggers Lambda or SSM Automation to fix it. The remediation is real, but it's always event-driven and after the fact — never a block at the moment of change. That's what keeps Config in the "detective" category even once remediation is wired up.
