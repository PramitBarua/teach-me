Security, Deployment and Operations

CloudHSM

Lesson 05 of 9 · ~8 min

Source: Adrian Cantrill SAA-C03 · AWS CloudHSM cluster architecture · AWS CloudHSM FAQs

CloudHSM does the same broad job as KMS — creating, managing, and securing cryptographic key material — but the two products differ in ways that matter a lot for the exam. This lesson is fundamentally about one thing: given a scenario, can you tell which of the two you need? A handful of keywords settle it almost every time.

KMS, Briefly, as the Point of Comparison

KMS is AWS's native key management service. It integrates tightly with other AWS services for encryption, all access is controlled with ordinary IAM permissions, and all operations go through standard AWS APIs. Behind the scenes, KMS is backed by hardware security modules (HSMs) — but it's a shared, multi-tenant service. Your slice is isolated, but AWS manages the underlying hardware and software, and other accounts share the same fleet.

CloudHSM: True Single-Tenant Hardware

CloudHSM gives you a dedicated, single-tenant HSM appliance hosted in AWS. AWS provisions the hardware and handles maintenance, but the tamper-resistant partition that actually stores and uses your keys is something AWS has zero access to. If you lose your own access to a CloudHSM, that's it — there is no AWS-side rescue. You can reprovision new hardware, but the key material itself is unrecoverable.

FIPS 140: the standard has moved on since this course was recorded
The classic exam-prep framing is "FIPS 140-2 Level 3 → CloudHSM; KMS is overall Level 2, with only some internal parts at Level 3." That distinction still holds structurally, but the underlying standard itself has shifted from FIPS 140-2 to FIPS 140-3. AWS's current documentation states that CloudHSM's newest hardware generation (the hsm2m.medium instance type) is validated to FIPS 140-3 Level 3, and that KMS's HSMs are now also validated under FIPS 140-3 Security Level 3 — while the KMS product as a whole remains FIPS 140-2 Level 2 overall (that "overall" framing is about the certification boundary, not the underlying hardware). If an exam question was written against the older course material, expect FIPS 140-2 wording; if it reflects current AWS docs, expect FIPS 140-3. Either way, the decision logic is unchanged: Level 3 for the whole appliance → CloudHSM.

The Access-Method Distinction

This is the second pillar of the decision, and it's just as important as the compliance level:

NeedProduct
AWS-native integration via IAM and standard AWS APIsKMS
Industry-standard cryptographic APIs — PKCS#11, Java Cryptography Extensions (JCE), Microsoft CryptoNG (CNG)CloudHSM

KMS isn't accessible through these industry-standard APIs by design, and CloudHSM isn't accessed through ordinary AWS API calls by design. If you see any of PKCS#11, JCE, or CNG named in a scenario, that's CloudHSM.

The three facts to over-learn
Build a hard association between these keyword triggers and CloudHSM: FIPS 140 Level 3 for the whole appliance, industry-standard crypto APIs (PKCS#11 / JCE / CNG), and true single-tenant hardware with zero AWS access to key storage. If a question instead emphasizes AWS-native integration and IAM permissions, that points to KMS.

Architecture: An AWS-Managed VPC Injected Into Yours

CloudHSM appliances don't run inside a VPC you control. They live in an AWS-managed CloudHSM VPC you never see. To reach them, AWS injects one elastic network interface (ENI) per HSM node into your own VPC — one ENI per Availability Zone used. A single HSM is not itself highly available, so achieving HA means deploying multiple HSMs as a cluster, at least one per AZ; once clustered, the nodes automatically replicate keys, policies, and configuration among themselves.

Any EC2 instance that needs to talk to the cluster must have the CloudHSM client installed — a background process that lets the instance reach the HSM cluster over its injected ENIs and then use PKCS#11, JCE, or CNG against it.

Where CloudHSM Specifically Wins

  • Client-side encryption before S3 upload — CloudHSM has no native S3 SSE integration, so this means encrypting objects locally before they ever reach S3, not integrating with S3's own encryption.
  • SSL/TLS offload from web servers — dedicated crypto hardware handles the cryptographic load more cheaply and efficiently than general-purpose EC2 instances doing it themselves.
  • Oracle Transparent Data Encryption (TDE) — Oracle databases can use CloudHSM via industry-standard APIs to manage the keys behind TDE.
  • Private keys for a self-run certificate authority — CloudHSM can hold and protect a CA's private key material.
Custom keystore: blending both worlds
KMS supports a custom keystore feature that lets KMS use a CloudHSM cluster as its backing key store. This gives you CloudHSM's dedicated, single-tenant hardware together with KMS's native AWS integration — but for exam purposes, keep using the keyword triggers above to decide between plain KMS and plain CloudHSM first.
