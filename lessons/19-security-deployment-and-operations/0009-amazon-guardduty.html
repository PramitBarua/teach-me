Amazon GuardDuty

Lesson 09 of 9 · ~8 min

Source: Adrian Cantrill SAA-C03 · What is Amazon GuardDuty? · Feature names for protection plans in GuardDuty

GuardDuty is a continuous, account-wide threat-detection service. Once enabled, it never stops running: it uses machine learning, anomaly detection, and threat-intelligence feeds against ingested account activity to surface findings — unexpected or unauthorized activity. Critically, you don't hand-define what "normal" looks like; GuardDuty learns your account's behavior patterns itself. You can still influence it — allow-listing known-good IPs, for instance — but the baseline is learned, not configured.

Multi-Account Architecture

Like Macie and Inspector, GuardDuty uses an administrator/member account model with a single pane of management: enable GuardDuty in one account to make it the administrator, then invite other accounts to become members, all managed centrally.

Data Sources: The Transcript's List Is Now Only the Starting Point

The original course narration lists four data sources feeding GuardDuty: DNS logs (via Route 53), VPC Flow Logs, CloudTrail management events, and CloudTrail S3 data events. These are still accurate — they remain part of what AWS now calls GuardDuty's foundational data sources (alongside EKS audit logs, ingested automatically the moment GuardDuty is enabled).

GuardDuty has grown well beyond the transcript's four sources
Current AWS documentation confirms GuardDuty now offers a set of optional, separately-enabled protection plans layered on top of the foundational sources — each covering a specific workload type: S3 Protection (S3 data events), EKS Protection (audit logs and runtime activity), ECS Runtime Monitoring and EC2 Runtime Monitoring, Malware Protection (covering EC2/EBS volumes, S3 object uploads, and AWS Backup data), RDS Protection (Aurora and RDS login activity), and Lambda Protection (network activity logs). AWS's current docs also show a newer AI Protection plan covering CloudTrail data events from Bedrock, Bedrock AgentCore, and SageMaker AI. If a question names any of these newer workload types — EKS, RDS, Lambda, malware on EBS, or AI services — GuardDuty is still very likely the right answer, even though the original course material predates all of them.

Architecture: Findings to Response

Ingested data sources plus threat-intelligence feeds are analyzed together to generate findings. Findings route to EventBridge, which can drive:

  • SNS notifications to a team or an external security management system
  • Lambda-driven automatic remediation — for example, adding an explicit deny rule to a network ACL in response to a suspected intrusion
Exam heuristic: three "AWS finds problems for you" services, one job each
These three services get confused with each other because they all surface security findings automatically — but each has a distinct lane:
ServiceWhat it actually does
GuardDutyContinuous, ML/threat-intel-driven anomaly detection across the whole account — not a scan you trigger, not a data-classification tool
MacieDiscovers and classifies sensitive data specifically inside S3
InspectorVulnerability and CVE scanning of compute — EC2, ECR images, Lambda functions

If a scenario is about unusual account behavior, credential misuse, or an unexpected network connection — with no mention of scanning packages or classifying stored data — that's GuardDuty.
