Amazon Macie

Lesson 07 of 9 · ~8 min

Source: Adrian Cantrill SAA-C03 · What is Amazon Macie? · Quick reference: managed data identifiers by type

S3 is one of the most widely used AWS services precisely because it's so easy to host huge quantities of data at scale — and that popularity, combined with how easy it is to misconfigure a bucket into being public, has made accidental S3 data exposure a persistent risk. Amazon Macie is the purpose-built answer: a data security and privacy service for discovering, classifying, and monitoring sensitive data in S3.

Discovery Jobs and Data Identifiers

You point Macie at specific buckets by creating a discovery job — scheduled, running on whatever cadence you choose. Each job assesses bucket contents against data identifiers:

TypeHow it works
Managed data identifiersAWS-built, using pattern matching plus machine learning; cover PII, PHI, financial data, and credentials across many countries and regions
Custom data identifiersYour own regular expressions, refined with optional keywords that must appear within a definable maximum match distance, and optional ignore words that suppress an otherwise-matching result

A custom identifier might match a company's employee-ID pattern — letters, a dash, then eight digits — refined so it only counts as a match near the keyword "Employee ID" and doesn't fire on an unrelated coincidental match.

Two Categories of Findings

Running a job produces findings, and Macie splits them cleanly into two categories:

Policy findings vs. sensitive data findings
Policy findings fire when a bucket's security posture gets worse after Macie was enabled — block-public-access turned off, bucket encryption disabled, a bucket made public, or a bucket shared outside the organization. Sensitive data findings fire when Macie actually matches sensitive content inside objects — exposed credentials, financial data, personal or health data, or multiple types matched in one object. One category is about configuration drift; the other is about what's actually sitting in the objects.

Multi-Account Architecture

Macie supports a multi-account model: one administrator account manages Macie across member accounts, set up either through AWS Organizations or by explicitly inviting individual accounts. Once linked, buckets across every member account can be evaluated the same way from the administrator account.

From Finding to Response

Findings can be reviewed interactively in the console or in Security Hub, or routed to EventBridge for event-driven automation — for example, a Lambda function that automatically re-enables block-public-access the moment a policy finding reports it was disabled.

Exam heuristic
Any question about discovering, classifying, or automatically reacting to sensitive data specifically inside S3 points to Macie. If the scenario is about vulnerability scanning of compute, that's Inspector; if it's about broad account-wide threat detection, that's GuardDuty — Macie's lane is S3 data content and bucket posture, specifically.

Retrieval Practice

Answer from memory. Explanations appear after each answer.

1. After Macie is enabled on a bucket, someone disables the bucket's default encryption setting. Which type of finding does this generate?

2. A company needs Macie to detect its proprietary employee ID format, a pattern not covered by any built-in category like PII or financial data. What should they configure?

3. A security team manages Macie for 12 AWS accounts from one central account, without using AWS Organizations. How is this multi-account setup achieved?
