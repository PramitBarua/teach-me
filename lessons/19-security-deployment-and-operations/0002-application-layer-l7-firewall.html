Application Layer (L7) Firewalls

Lesson 02 of 9 · ~8 min

Source: Adrian Cantrill SAA-C03 · AWS Network Firewall: stateless and stateful rules engines

This lesson is deliberately generic and vendor-agnostic — it's about what an application-layer (layer 7) firewall is, conceptually, regardless of vendor. AWS's own concrete L7 firewall product, WAF, gets its own lesson next; nothing WAF-specific belongs here.

Why this lesson leans so heavily on the diagrams
The source material flags almost every single point below as exam-critical — not one or two highlights, but essentially the whole topic. So rather than treating a couple of callouts as a supplement to ordinary prose, this lesson is structured directly around those flagged points. If it reads like a tight, quotable checklist, that's intentional.

Where We Start: Layer 3/4 Firewalls

Picture a firewall protecting Catagram — a wildly popular app for sharing pictures of cats — sitting between a laptop and the server. At layer 3 and 4, the firewall only sees packets and segments: IP addresses and ports. It sees two separate flows — a request from laptop to server, and a response from server to laptop — and because the firewall operates only at layers 3 and 4, the request and response are different and unrelated to it. Each needs its own rule; the firewall has no notion that they're two halves of the same conversation.

Adding Layer 5: Session Awareness

Enhance that firewall with layer 5 (session) capability, and the picture changes: now the request and response can be considered as part of one session. That's a small-sounding change with real payoff — it reduces admin overhead (one rule instead of two) and allows for more "contextual" security, since response traffic can now be treated differently precisely because it's understood as a reply to a request already in flight, rather than an unrelated new flow.

Critically, in both cases — layer 3/4 only, or layer 3/4/5 — the firewall understands nothing above the layer it operates at. Everything above that is opaque: to a layer 5 firewall, HTTP payload is just undifferentiated data. A cat picture, a dog picture, and malware all look identical. That blindness to application content is exactly the gap layer 7 firewalls close.

Layer 7: Application-Aware Inspection

A layer 7 firewall keeps the same packet flow, but adds real understanding of the application protocol itself — HTTP, in the running example. Because it understands the protocol's structure — headers, hosts, data — it can identify normal or abnormal requests, which means it can defend against protocol-specific attacks and weaknesses that lower-layer firewalls simply cannot see.

That protocol awareness lets it act on content in ways no lower-layer firewall can: data at L7 can be inspected and blocked, replaced, or tagged — for example flagging or removing adult content, spam, or off-topic material. Back in Catagram terms: cat pictures are welcome, dog pictures might be borderline ("okish"), sheep might count as spam, and outright malware gets blocked outright. The firewall can even swap disallowed content for something acceptable rather than just dropping it. Taken further, this same visibility is what lets a firewall identify, block, and adjust specific applications — recognizing and acting on something like Facebook traffic specifically, not just "HTTP traffic" in general.

The Mechanic That Makes It Possible: HTTPS Termination

None of this application-content inspection works on an encrypted stream — so for an HTTPS connection, the firewall has to sit inside the encryption, not just alongside it. Encryption (HTTPS) is terminated (decrypted) on the L7 firewall: from the client's point of view, it appears to be talking directly to the server, but the original HTTPS tunnel actually ends at the firewall. The firewall then opens a new encrypted L7 connection between itself and the backend server. Both endpoints experience this as fully transparent — but in the middle, for the moment the traffic sits at the firewall, it's plain, unencrypted HTTP that the firewall can freely inspect, filter, or modify before it's re-encrypted and sent on.

Exam tip — the capability build-up, and what makes it possible
Think of this as a progressive build: L3/4 (packets, ports, no session concept) → add L5 (session awareness, request/response linked) → add L7 (application-protocol awareness). The mechanic that makes L7 inspection of encrypted traffic possible at all is decrypt-inspect-re-encrypt: HTTPS terminates at the firewall, gets inspected as plain HTTP, and a fresh encrypted connection carries it onward to the backend.
Exam tip — L7 firewalls add, they never subtract
A layer 7 firewall keeps all of the layer 3, 4, and 5 features it started with — it's a strict superset, not a replacement. On top of that base, it can additionally react to layer 7 elements: DNS names in use, the rate of connections, specific content, headers — whatever the particular L7 protocol it understands exposes. Some L7 firewalls only understand HTTP; others add protocols like SMTP (email). The limit is purely what the firewall's software supports, not the underlying architecture.
