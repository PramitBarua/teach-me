Private Distribution and Behaviors: Signed URLs vs. Signed Cookies

Lesson 08 of 10 · ~8 min

Source: Adrian Cantrill SAA-C03 · Serve Private Content with Signed URLs and Signed Cookies · Decide to Use Signed URLs or Signed Cookies

Previous lessons secured the origin-fetch side (preventing bypass of CloudFront). This lesson secures the viewer side: making sure only authorized customers can retrieve specific content through CloudFront at all.

Public vs. Private Behaviors

A distribution's default behavior starts public — any viewer can request anything it covers. Adding a signer to a behavior flips it to private: from then on, only requests carrying a valid signed URL or signed cookie are served; everything else is denied. Since this is a per-behavior setting, one distribution routinely mixes public behaviors (general app traffic) with private ones (premium/sensitive content).

Trusted Signers (Legacy) vs. Trusted Key Groups (Current)

Trusted signer (legacy)Trusted key group (current, preferred)
Managed byAWS account root user, via a CloudFront keyFlexible IAM-adjacent management, via the CloudFront API

RecommendationLegacy — avoid for new workUse this for all new deployments

Signed URLs vs. Signed Cookies

Exam tip: the one-line distinguisher
A signed URL grants access to exactly one object. A signed cookie can grant access to a group of objects (e.g. every file under a path, or every file of a type) without needing a unique URL per file. If a scenario needs one-off access to a single file, that's a signed URL; if it needs ongoing access to many files at once, that's a signed cookie.
Use signed URLs when…Use signed cookies when…
Only one object needs to be protectedMany objects need protecting under one grant
The client doesn't support cookiesYou want to preserve your application's existing URL format (cookies don't alter the URL the way signed URLs do)

Putting It Together: A Worked Architecture

A mobile app has a public behavior (general app operations, via API Gateway + Lambda) and a private behavior (sensitive media, via an S3 origin). The user authenticates (e.g. via a third-party identity provider), a Lambda "signer" function validates their access rights, and — because the distribution's private behavior has trusted key groups configured — that function generates a signed cookie granting access to their permitted images. The app then includes that cookie on every subsequent request; CloudFront validates it before allowing the origin fetch.

Private behaviors don't replace origin security
A private behavior only controls the viewer side. The origin (e.g. that S3 bucket) still needs OAI/OAC (Lesson 07) so it can't be reached directly, bypassing CloudFront's signed-cookie check entirely. Both layers are required for genuinely secure private content.
