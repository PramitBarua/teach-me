CloudFront and SSL/TLS

Lesson 05 of 10 · ~9 min

Source: Adrian Cantrill SAA-C03 · Requirements for Using SSL/TLS Certificates with CloudFront

Every CloudFront distribution gets a default *.cloudfront.net domain, and HTTPS works on it immediately using a shared default certificate covering *.cloudfront.net. The moment you want your own custom domain, things get more involved — and that's what this lesson works through.

Two Separate Connections, Two Sets of Certificate Rules

Every CloudFront request actually involves two connections: the viewer protocol (customer ↔ edge location) and the origin protocol (edge location ↔ origin). Both sides have the same hard requirement:

No self-signed certificates, ever
Both the viewer-side and origin-side certificates must be publicly trusted — self-signed certificates are not supported anywhere in a CloudFront architecture. Each certificate must also match the DNS name actually being used on that side of the connection.
Origin typeCertificate requirement
S3 originNone needed — S3 manages this natively, and you can't change it
Application Load BalancerPublicly trusted cert, generated externally or via ACM
Custom origin (EC2, on-prem)Publicly trusted cert, applied manually — not ACM-manageable, since ACM doesn't support these

Adding a Custom Domain

To use an alternate domain name, you need a certificate matching that name attached to the distribution — whether or not you even use HTTPS, since it's also how CloudFront verifies you actually control the domain. That certificate must come from ACM in us-east-1 (previous lesson) or be imported there.

On a behavior, you choose how HTTP vs. HTTPS is handled: allow both, redirect HTTP → HTTPS, or HTTPS-only (rejecting HTTP entirely).

SNI vs. Dedicated IP: Why CloudFront Charges Extra for Old Browsers

This is a genuinely old problem worth understanding, because the "why" is what the exam tests. TLS encryption happens at a lower layer than HTTP — before the browser ever sends the hostname it's requesting. Historically, that meant a server presenting a certificate had no way to know which site's certificate to present when multiple HTTPS sites shared one IP — so every HTTPS site needed its own dedicated IP.

The 2003 fix was SNI (Server Name Indication): an extension letting the client state which hostname it wants during the TLS handshake, so the server can return the matching certificate. This is what lets one IP serve many independent HTTPS sites.

Exam tip: the cost trade-off
Serving HTTPS via a custom certificate using SNI is free and is the standard, default approach. Only if you must support pre-2003, non-SNI-capable browsers/clients do you need CloudFront to allocate a dedicated IP per edge location for your distribution — historically priced around $600/month per distribution (verify current CloudFront pricing for the exact figure; this has been a stable, well-known number for years but always confirm before quoting it to a client). If a question doesn't mention legacy/pre-2003 clients, SNI is almost certainly the intended answer.
