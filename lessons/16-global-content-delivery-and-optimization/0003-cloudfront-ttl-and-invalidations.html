CloudFront TTL and Invalidations

Lesson 03 of 10 · ~9 min

Source: Adrian Cantrill SAA-C03 · Manage How Long Content Stays in the Cache · Invalidate Files to Remove Content

Here's the core problem this lesson solves: you update an image in your origin, but a customer near an edge location that's already cached the old version keeps getting served the old one — because CloudFront trusts a cached object as valid until it expires, and never checks the origin in the meantime.

Validity: What "Expired" Actually Triggers

When a cached object's TTL (time to live) elapses, it isn't discarded — it becomes stale. The next request for it makes the edge location check with the origin, which replies one of two ways:

  • 304 Not Modified — origin's version matches what's cached; the existing cached copy is served, and it's marked current again (no data transfer).
  • 200 OK — origin has a newer version; that new version is transferred and replaces the cached copy.

Setting TTL

TTL is a behavior-level setting (see previous lesson) with three values:

ValueRole
Default TTL24 hours out of the box — applies to any object with no per-object TTL specified
Minimum TTL / Maximum TTLDon't set behavior by themselves — they clamp whatever per-object TTL a header specifies

Per-object TTLs are set via headers your origin returns: Cache-Control: max-age, Cache-Control: s-maxage (both in seconds, functionally equivalent for this purpose), or Expires (a specific date/time). For custom origins, your app/web server sets these; for S3, they're set as object metadata via console, CLI, or API.

Exam tip: min/max TTL are clamps, not defaults
A per-object TTL below the behavior's minimum gets raised to the minimum. One above the maximum gets lowered to the maximum. Min/max TTL never take effect on their own — they only ever constrain a per-object value.

Invalidations: The Emergency Fix

An invalidation, performed at the distribution level, immediately expires matching objects across every edge location the distribution uses — regardless of remaining TTL. Patterns range from a single exact path, to a wildcard within one folder, to /* (everything, everywhere).

Invalidations cost the same no matter how much they match
A wildcard invalidation matching thousands of objects costs exactly the same as invalidating one object — but it isn't free at any volume beyond the free monthly allowance, and it isn't instantaneous. Treat invalidation as a tool for correcting mistakes, not a routine part of your deployment process.

The Better Pattern: Versioned Filenames

If you find yourself invalidating regularly, that's a signal to switch strategies: give updated content a new filename (e.g. whiskers_v2.jpg replacing whiskers_v1.jpg) and update your application to reference the new name. No invalidation needed — the "old" and "new" versions are simply different, independently-cached objects.

Exam tip: this is a frequent scenario answer
Versioned filenames beat invalidation on every axis the exam cares about: no cost (no invalidation calls), correct even for browser-cached copies (a new name is never affected by a client's local cache of the old one), and clean logging (you always know exactly which version served a given request). If a scenario asks for the most cost-effective way to roll out frequent content updates, versioned filenames is very often the intended answer.
Don't confuse this with S3 object versioning
Versioned filenames means genuinely different object names, each cached independently forever. S3 object versioning is a different feature entirely — multiple versions stored under the same key — and CloudFront, by default, always serves the latest S3 object version regardless of what's cached, which does not solve the stale-cache problem the same way.
