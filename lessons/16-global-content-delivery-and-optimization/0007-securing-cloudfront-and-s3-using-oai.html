Securing the Origin: OAI/OAC and Custom Origin Locking

Lesson 07 of 10 · ~8 min

Source: Adrian Cantrill SAA-C03 · Restrict Access to an Amazon S3 Origin · Add Custom Headers to Origin Requests

This lesson secures the origin-fetch side of the delivery path: making sure customers can only reach your content through CloudFront, never by bypassing it and hitting the origin directly.

Stale vs. current: OAC has superseded OAI
This lesson's source material teaches Origin Access Identity (OAI) as the primary mechanism, correctly noting a newer alternative existed. Since then, AWS has made that alternative — Origin Access Control (OAC) — the clearly recommended approach: it supports all buckets including opt-in Regions, S3 server-side encryption with KMS (SSE-KMS), and dynamic requests (PUT/POST/DELETE), none of which OAI supports. OAI is now the legacy option. The architecture and exam-relevant reasoning below apply to both — only the specific feature name differs — but for anything you build today, reach for OAC.

S3 Origins: Origin Access Identity / Control

An OAI (or its modern equivalent, an OAC) is a special identity — not an IAM user or role, but sharing some characteristics of both — that you associate with a CloudFront distribution. Once associated, requests from that distribution's edge locations to the S3 origin are that identity, which can then be referenced in the bucket policy.

The standard pattern:

  1. Create the OAI/OAC and associate it with the distribution.
  2. Add an explicit allow for that identity in the bucket policy.
  3. Add nothing else — the bucket's implicit deny now blocks every other access path, including direct public requests to the bucket.
Exam tip: one identity per distribution is the manageable default
OAIs/OACs can technically be shared across multiple distributions and buckets, but the transcript's own practical advice holds: use one per distribution for long-term manageability of permissions.

Custom Origins: No OAI/OAC — Two Other Options

OAI/OAC only works for genuine S3 origins. For custom origins (EC2, on-prem, anything else), lock things down using either or both of:

MethodHow it works
Custom headersCloudFront injects a secret header value on every origin request; the origin is configured to reject any request missing it. Since the whole path can run over HTTPS, this header can't be observed or faked in transit.
IP allow-listingAWS publishes CloudFront's edge location IP ranges; configure a traditional firewall in front of the custom origin to allow only those ranges.
Exam tip: match the mechanism to the origin type
S3 origin → OAI/OAC. Custom origin → custom headers and/or IP allow-listing. If a question describes securing a custom (non-S3) origin and offers OAI/OAC as an answer choice, it's a distractor — that mechanism doesn't apply outside S3 origins.
