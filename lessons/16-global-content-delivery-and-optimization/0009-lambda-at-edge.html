Lambda@Edge (and CloudFront Functions)

Lesson 09 of 10 · ~8 min

Source: Adrian Cantrill SAA-C03 · Customize at the Edge with Lambda@Edge · Differences Between CloudFront Functions and Lambda@Edge

Lambda@Edge runs lightweight Lambda functions directly at CloudFront edge locations, letting you programmatically adjust traffic between viewer and origin — without touching the origin application itself.

Four Hook Points

Every CloudFront interaction breaks into four legs, and a Lambda@Edge function can attach to any of them:

HookRunsTypical limits
Viewer requestAfter the edge location receives the viewer's request128 MB memory, 5-second timeout
Origin requestBefore CloudFront forwards the request to the originStandard Lambda limits, 30-second timeout
Origin responseAfter CloudFront receives the origin's replyStandard Lambda limits, 30-second timeout
Viewer responseBefore CloudFront returns the response to the viewer128 MB memory, 5-second timeout
Edge-specific limitations vs. normal Lambda
Only Node.js and Python runtimes are supported, there's no VPC access (functions run in the AWS public zone), and Lambda layers aren't supported. The exact numeric limits matter less than recognizing this is a deliberately constrained execution environment — don't expect full Lambda feature parity.

What It's Actually Used For

  • A/B testing — a viewer request function rewrites the requested URL to serve one of several image/content variants, based on a percentage split or other logic, with no redirect and no URL change visible to the user.
  • Gradual origin migration — an origin request function incrementally shifts a weighted percentage of traffic from an old S3 origin to a new one, adjustable over time without touching the distribution config.
  • Device-based customization — serving different object quality/resolution based on the requesting device's capabilities (e.g. high-DPI screens getting higher-DPI assets).
  • Country-based customization — an origin request function adjusting what's returned based on the viewer's country.
Exam tip: architecture over syntax
You won't be asked to write Lambda@Edge code for this exam — you need to recognize the architecture (which of the four hooks fits a given scenario) and the category of use case it solves (A/B testing, migration, personalization by device/location).
Not covered in the original course material: CloudFront Functions
Since this lesson was recorded, AWS introduced a second, lighter-weight edge compute option: CloudFront Functions. It's worth knowing both exist and when each applies:
CloudFront FunctionsLambda@Edge
LanguageJavaScript onlyNode.js or Python
Hook pointsViewer request / viewer response onlyAll four hooks
StartupSub-millisecond, extremely high scaleHeavier cold-start profile
Best forCache-key normalization, header manipulation, simple redirects/rewrites, lightweight auth token checksAnything needing origin-side hooks, filesystem access, or the request body
Rule of thumb for the exam: simple, viewer-side-only logic → CloudFront Functions is now the better-fit answer; anything needing an origin-side hook or heavier logic → Lambda@Edge. You cannot combine both on the same viewer request/response event, but any other combination of the two is fine.
