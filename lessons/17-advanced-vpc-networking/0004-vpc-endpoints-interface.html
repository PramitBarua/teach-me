VPC Endpoints: Interface Endpoints

Lesson 04 of 05 · ~9 min

Source: Adrian Cantrill SAA-C03 · Configure an Interface Endpoint · Connect Your VPC to Services Using AWS PrivateLink

Interface endpoints solve the same problem gateway endpoints do — private access to a public AWS service — for essentially everything else. The mechanism, though, is architecturally unrelated to gateway endpoints, and the differences are exactly what the exam tests.

Not highly available by default — this is the opposite of gateway endpoints
An interface endpoint is a genuine elastic network interface, placed in one specific subnet — meaning one specific AZ. Lose that AZ, lose that endpoint's availability. To be resilient across multiple AZs, you need one interface endpoint per AZ you use. Compare this directly against the previous lesson: gateway endpoints are automatically multi-AZ; interface endpoints are not, ever, without you deliberately building it that way.

What Interface Endpoints Are Built On: AWS PrivateLink

PrivateLink is the underlying technology — it's what lets an AWS service (or a supported third-party service) be injected directly into your VPC as network interfaces inside your own subnets. Interface endpoints are essentially "PrivateLink for AWS services," but the same PrivateLink mechanism is also how third-party vendors can offer their own products for private, in-VPC consumption — valuable in regulated environments needing private access to external SaaS-style services with no additional networking infrastructure.

S3 is now also available via interface endpoint
Historically S3 and DynamoDB were gateway-endpoint-only, and everything else used interface endpoints. That's since changed: S3 can now be accessed via either gateway or interface endpoints. DynamoDB remains gateway-endpoint-only. Where a choice exists, a gateway endpoint is generally simpler (free, automatically HA) — interface endpoints add value mainly where you specifically need security-group-level control or cross-VPC/PrivateLink-style access patterns.

DNS: How Traffic Actually Finds the Endpoint

Every interface endpoint gets DNS names: a regional name (works across every AZ, resolves to whichever interface makes sense) and a zonal name per AZ (resolves to that specific interface). Either can be used directly by applications updated to reference them — no other configuration required.

Exam tip: Private DNS removes the need to modify applications
Enabling Private DNS (on by default today) creates a Route 53 private hosted zone associated with the VPC that overrides the service's normal public DNS name to resolve to the interface endpoint's private IP instead. The practical effect: applications that were never touched, still using the default public service DNS name (e.g. sns.us-east-1.amazonaws.com), automatically route through the interface endpoint — no code changes, no redeployment.

Without Private DNS, only applications explicitly reconfigured to use the endpoint-specific DNS name benefit — anything still resolving the default public name goes out via the internet gateway as normal (and fails entirely from a fully private subnet with no internet path).
