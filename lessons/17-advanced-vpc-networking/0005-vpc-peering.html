VPC Peering

Lesson 05 of 05 · ~7 min

Source: Adrian Cantrill SAA-C03 · What Is VPC Peering?

VPC peering creates a private, encrypted network link between two VPCs — same account or different accounts, same Region or cross-Region (with some cross-Region limitations).

Two facts to memorize cold
1. One peering connection links exactly two VPCs — never more. 2. Peering is not transitive. If A is peered with B, and B is peered with C, there is no connectivity between A and C. You cannot route through an intermediary VPC. Full mesh connectivity between N VPCs requires a separate peering connection for every pair — 3 VPCs need 3 peers, 4 VPCs need 6, and it grows fast.

Required Configuration

Creating the peering connection itself only creates a logical gateway object in both VPCs — it doesn't establish connectivity by itself. Three things must all be in place:

  1. The peering connection (and acceptance by the peer VPC's owner).
  2. Route table entries in the relevant subnets of both VPCs, pointing the peer's CIDR range at the peering connection object.
  3. Security groups / NACLs on both sides actually permitting the traffic.
Overlapping CIDRs break peering entirely
Two VPCs with overlapping IP address ranges cannot be peered — full stop. This is exactly why planning non-overlapping CIDRs across all your VPCs from the start matters, even for VPCs with no immediate peering plans.

Useful Extras

  • DNS resolution across the peer — an optional setting that lets public DNS hostnames of instances in the peered VPC resolve to their private IP addresses, so the same names work whether or not the target is in a peered VPC.
  • Security group referencing — for same-Region peers only, you can reference the peer's security group ID directly in your own rules (the same nesting trick used within a single VPC). Cross-Region peers must instead reference specific IP ranges.
Exam tip: peering vs. Transit Gateway
Peering's non-transitive limitation is precisely the problem Transit Gateway solves (a separate, more feature-rich hub-and-spoke product covered elsewhere). If a scenario needs many VPCs to all communicate through a single hub without an exploding number of point-to-point connections, that's pointing toward Transit Gateway, not more peering connections.

Traffic across a peering connection is always encrypted; cross-Region peered traffic transits AWS's own global backbone network rather than the public internet — the same security and performance profile Global Accelerator relies on (previous module).

Retrieval Practice

Answer from memory. Explanations appear after each answer.

1. VPC A is peered with VPC B, and VPC B is peered with VPC C. Can an instance in VPC A directly communicate with an instance in VPC C using only these two peering connections?

2. Two VPCs both use the CIDR range 10.0.0.0/16. A team wants to create a VPC peering connection between them. What happens?

3. A company has 5 VPCs in the same Region and wants every VPC to be able to communicate directly with every other VPC, using only VPC peering. How many peering connections are needed, and is there a better alternative?
