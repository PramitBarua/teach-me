VPC Flow Logs

Lesson 01 of 05 · ~7 min

Source: Adrian Cantrill SAA-C03 · Logging IP Traffic Using VPC Flow Logs

VPC Flow Logs record details of traffic flowing through your VPC. The single most important fact to internalize first:

Metadata only, never packet contents
Flow logs capture packet metadata — source/destination IP, source/destination port, protocol, packet size, accept/reject — never the actual contents of a packet. If a scenario needs to inspect payload data, flow logs are the wrong tool; you'd need something like a packet sniffer running on an instance instead.

Three Levels of Attachment

Flow logs attach as virtual monitors at one of three levels, each capturing everything from that point downward:

LevelCaptures
VPCEvery network interface in every subnet in the VPC
SubnetEvery network interface in that specific subnet
Network interface (ENI)Just that one interface

You can also filter by traffic type: accepted only, rejected only, or all.

Exam tip: flow logs are not real time
There's a genuine delay between traffic occurring and it appearing in flow log data — flow logs are not a real-time telemetry source. If a question needs real-time visibility into traffic flow, flow logs are the wrong answer regardless of how they're configured.

Destinations

Flow log data can be delivered to S3 or CloudWatch Logs (Amazon Data Firehose is also now supported as a third destination). S3 suits direct file access and integration with your own or third-party tooling; CloudWatch Logs suits programmatic access, streaming to other destinations, and console-based review. Logs landing in S3 can be queried with Athena — a schema-on-read SQL engine billed only for the data actually scanned, useful when a data team needs formal, ad hoc querying over flow log history.

Reading a Flow Log Record

Each record is a row with fields including source/destination IP, source/destination port, protocol number (ICMP = 1, TCP = 6, UDP = 17), and the accept/reject action.

Exam tip: reading accept/reject pairs tells you which firewall acted
Security groups are stateful — an allowed request's response is automatically allowed, so you'll typically see just one log line per conversation. NACLs are stateless — request and response are evaluated independently, so a NACL blocking only the return leg produces two lines: an accept (request) and a reject (response). Seeing an accept immediately followed by a reject for what looks like the same flow is the signature of a NACL interfering with an otherwise-permitted security group conversation.

What's Never Logged

Flow logs exclude: traffic to the instance metadata service, DHCP traffic, Amazon time server traffic, and (Windows-only) traffic to the Amazon license server. These are excluded unconditionally — no configuration option brings them back.
