      Scenario 1

      Animals For Life runs a public hosted zone for animalsforlife.org and needs DNS resolution to keep working even if an entire AWS Region suffers a total outage. A teammate proposes running the zone's name servers in one Region with Multi-AZ redundancy, plus a replicated standby copy in a second Region for failover. Does Route 53 need this kind of custom multi-Region design to survive a regional outage?

      • A. No — Route 53's name servers are already globally distributed and each holds the same dataset, so no Region-level failover design is required
      • B. Yes — without the proposed Multi-AZ-plus-standby-Region design, one Region's outage would take the whole hosted zone offline
      • C. No, but only because Route 53 automatically fails the zone over to a warm-standby Region within seconds of an outage
      • D. No, but only because CloudFront edge locations cache the zone's DNS responses so the origin Region's health is irrelevant

      Topic: Public Hosted Zones

      Correct answer: A

      • A. Correct — Route 53's name servers are distributed globally and all serve the same dataset, so the service keeps functioning even during a full Regional outage, with no extra design needed.
      • B. Wrong — this misunderstands Route 53's architecture; a single Region's outage doesn't take a hosted zone offline in the first place, so the proposed design solves a problem that doesn't exist.
      • C. Wrong — Route 53 doesn't fail hosted zones over to a standby Region; its resilience comes from name servers already being global by design, not a DR failover process.
      • D. Wrong — CloudFront caches content at the edge, but it isn't what makes a Route 53 hosted zone itself resilient to a Regional outage.

      Scenario 2

      A resolver with an empty cache looks up app.animalsforlife.org for the very first time. Which sequence of servers does it walk through before finally reaching the four Route 53 name servers that hold the answer?

      • A. The four Route 53 name servers directly, skipping the root and TLD servers, since browsers cache their addresses
      • B. The DNS root servers, then the .org TLD servers, then the four Route 53 name servers for the zone
      • C. The .org TLD servers first, then the DNS root servers, then the four Route 53 name servers
      • D. The DNS root servers, then straight to the origin web server, bypassing Route 53 entirely

      Topic: Public Hosted Zones

      Correct answer: B

      • A. Wrong — no fresh resolver already knows the four Route 53 name servers; it must walk the tree starting from the root to discover them.
      • B. Correct — this is "walking the tree": root servers point to the .org TLD servers, which point to the four Route 53 name servers for the zone, and only then does Route 53 answer.
      • C. Wrong — this reverses the delegation order; the root servers must be consulted before the TLD servers, not after.
      • D. Wrong — the chain doesn't skip Route 53 and go straight to an origin server; the TLD servers delegate specifically to the zone's name servers.

      Scenario 3

      An EC2 instance sits in a private subnet with no NAT gateway or internet gateway route, inside a VPC that has DNS resolution enabled. It needs to resolve a record in the company's public hosted zone for animalsforlife.org, hosted in Route 53. Given it has no route to the public internet, how does it resolve the record?

      • A. By querying one of the four Route 53 name servers directly over the public internet
      • B. By converting the zone to a private hosted zone and associating it with the VPC
      • C. By querying the Route 53 resolver that lives at the VPC's base +2 address
      • D. By using a Direct Connect DNS forwarding rule to reach the four name servers

      Topic: Public Hosted Zones

      Correct answer: C

      • A. Wrong — this instance has no route to the public internet, so it can't reach the four name servers directly; and it doesn't need to when DNS resolution is enabled.
      • B. Wrong — converting a public zone to private would remove public reachability entirely; the instance can already reach the public zone via the VPC resolver without any conversion.
      • C. Correct — with DNS resolution enabled, instances inside the VPC query public hosted zones through the Route 53 resolver at the VPC's base +2 address, with no internet route required.
      • D. Wrong — no such Direct Connect DNS forwarding step exists for this; the built-in VPC resolver handles this natively without any extra configuration.

      Scenario 4

      catagram.io is registered with a third-party registrar (Hover), but the team wants Route 53 to host its DNS going forward, with zero downtime during the cutover. What is the correct order of steps?

      • A. Update the NS records at Hover first, then create the matching Route 53 hosted zone afterward
      • B. Re-register the domain a second time directly through Route 53 domain registration
      • C. Create a private hosted zone and associate it with the production VPC, skipping any change at Hover
      • D. Create a public hosted zone in Route 53 to get its four name servers, then update the NS records at Hover

      Topic: Public Hosted Zones

      Correct answer: D

      • A. Wrong — pointing NS records at a hosted zone that doesn't exist yet breaks resolution during the gap; the zone must be created first.
      • B. Wrong — the domain is already registered elsewhere; only the DNS hosting needs to move, not the registration itself.
      • C. Wrong — a private hosted zone is only reachable from associated VPCs, not the public internet, so it can't serve the domain to public visitors.
      • D. Correct — first create the public hosted zone in Route 53 to obtain its four allocated name servers, then update the NS records at Hover to point to them.

      Scenario 5

      A startup is estimating Route 53 costs before launch. Their public hosted zone will exist for months before the site is announced, so it will receive almost no queries at first, but it must exist from day one. Which cost components should they budget for?

      • A. Only the per-query charge applies; simply having the hosted zone exist costs nothing at all
      • B. A monthly fee is charged per hosted zone, plus a small additional charge per DNS query it serves
      • C. Only a one-time setup fee applies when the hosted zone is created, with no recurring charges after
      • D. A monthly fee is charged per hosted zone, but VPC-resolver queries are billed at a separate premium rate

      Topic: Public Hosted Zones

      Correct answer: B

      • A. Wrong — a monthly fee applies to the hosted zone's existence regardless of query volume; it isn't free just because queries are rare.
      • B. Correct — there's a monthly fee per hosted zone, plus a small per-query charge, and both apply from the moment the zone is created.
      • C. Wrong — the monthly fee is recurring, not a one-time setup charge; this resembles a domain registration fee model, not hosted zone billing.
      • D. Wrong — there's no separate premium rate for queries answered via the VPC resolver; this invents a billing distinction that doesn't exist.

      Scenario 6

      An EC2 instance sits inside VPC-A, which is associated with a private hosted zone for internal.animalsforlife.org. A separate on-premises application, connected to VPC-A over a Site-to-Site VPN, also points its resolver at the VPC's base +2 address to try resolving records in that same zone. Which statement correctly describes what each client can resolve?

      • A. Only the EC2 instance can resolve it; the on-premises app isn't running inside the associated VPC
      • B. Both clients can resolve it, since VPC-A's association covers anything network-reachable to its resolver
      • C. Neither can resolve it unless the private hosted zone is also converted into a public hosted zone
      • D. Only the on-premises app can resolve it, since VPN traffic is treated as originating inside the VPC

      Topic: Private Hosted Zones

      Correct answer: A

      • A. Correct — two conditions must both be true: the querying service must be running inside a VPC, and that VPC must be associated with the zone. The on-premises app fails the first condition even though VPC-A meets the second.
      • B. Wrong — mere network reachability to the resolver address isn't the same as running inside the associated VPC; the on-premises app doesn't meet both required conditions.
      • C. Wrong — converting to a public zone would defeat the purpose of keeping internal records private, and isn't required for the EC2 instance, which already resolves the zone fine.
      • D. Wrong — Site-to-Site VPN traffic isn't treated as originating inside the VPC for private-hosted-zone resolution purposes; the on-premises app still fails the "running inside the VPC" condition.

      Scenario 7

      A retailer wants employees on the corporate VPC who resolve shop.animalsforlife.org to reach an internal staging environment, while customers on the public internet resolving that very same name reach the live public storefront. Security insists staging must never be reachable from outside the VPC. What design satisfies this?

      • A. One public hosted zone with two records for the name, selected via latency-based routing
      • B. A single hosted zone using weighted routing, sending 0% of public traffic to the staging record
      • C. A private zone for the name associated with the VPC, plus a separate public zone for the same name
      • D. A public zone with the staging record restricted by a resolver query-source-IP rule

      Topic: Private Hosted Zones

      Correct answer: C

      • A. Wrong — latency-based routing picks the lowest-latency value, not "inside VPC vs. public internet," and a public zone can't hide the staging record from outside anyway.
      • B. Wrong — weighted routing distributes by percentage, not by requester origin; 0% still doesn't guarantee external invisibility within a single public zone.
      • C. Correct — this is split-view DNS: a private hosted zone associated with the corporate VPC answers for staging, and a separate public hosted zone for the same domain name serves only the storefront record.
      • D. Wrong — public hosted zones don't support restricting a record's visibility by querying source IP this way; that isn't how the split-view pattern works.

      Scenario 8

      Following an acquisition, a private hosted zone lives in Account A, but the workload VPC lives in Account B — a separate account, not yet joined into any AWS Organization. The team wants to associate the zone with that VPC using only the Route 53 console. Will this work?

      • A. Yes — the console fully supports selecting a VPC that belongs to a different AWS account
      • B. Yes, but only after the two accounts are joined into the same AWS Organization first
      • C. No — cross-account association isn't possible under any method whatsoever
      • D. No — cross-account association requires the CLI or API, not the console

      Topic: Private Hosted Zones

      Correct answer: D

      • A. Wrong — the console only supports associating VPCs within the same account; cross-account VPCs aren't selectable there.
      • B. Wrong — Organization membership doesn't change the requirement; cross-account association still needs the CLI or API regardless of Organization structure.
      • C. Wrong — cross-account association is possible, just not through the console; the CLI or API supports it directly.
      • D. Correct — same-account association can use the console, CLI, or API, but associating a zone with a VPC in a different account requires the CLI or API.

      Scenario 9

      Security wants a record like payroll-db.internal.animalsforlife.org that must never be resolvable by anyone outside specifically approved VPCs — not even other VPCs in the same AWS account. Which approach satisfies this, and what happens to a same-account VPC that's deliberately left unassociated?

      • A. A private zone with only the approved VPCs associated; an unassociated VPC gets no access at all
      • B. A public zone with the record hidden via a resource policy restricting which VPCs may query it
      • C. A private zone associated with the account's default VPC only, since all VPCs inherit that automatically
      • D. A private zone that relies on the account's IAM policies alone to block unapproved VPCs

      Topic: Private Hosted Zones

      Correct answer: A

      • A. Correct — associate only the approved VPCs with the private hosted zone; a VPC left unassociated has no access at all, in exactly the same position as a random internet user.
      • B. Wrong — public hosted zones don't support restricting which VPCs may query a given record; anything in a public zone is visible to any public resolver.
      • C. Wrong — VPC associations aren't automatically inherited by other VPCs in the account; each VPC must be explicitly associated with the zone.
      • D. Wrong — IAM policies control management-plane API access, not DNS resolution access, which is governed by explicit VPC association.

      Scenario 10

      A junior engineer asks whether a private hosted zone uses different DNS record types or a different resolver address than a public hosted zone, beyond simply who is allowed to reach it.

      • A. Yes — private zones support only A records, while public zones support MX, TXT, and more
      • B. No — private zones use the same record types and the same base +2 resolver mechanics as public zones
      • C. Yes — private zones require a dedicated resolver endpoint address distinct from the base +2 address
      • D. Yes — private zones use a completely separate global name-server fleet from public zones

      Topic: Private Hosted Zones

      Correct answer: B

      • A. Wrong — a private hosted zone works exactly like a public one, supporting the same range of record types, not a restricted subset.
      • B. Correct — private hosted zones use the same record types and resolver mechanics as public ones; the only difference is reachability, limited solely to associated VPCs.
      • C. Wrong — this confuses private hosted zones with a separate real feature (Route 53 Resolver endpoints); private zones themselves still use the VPC's base +2 address.
      • D. Wrong — private hosted zones don't get their own separate global name-server fleet; the distinction is about reachability, not infrastructure.

      Scenario 11

      Animals For Life needs the naked domain animalsforlife.org (no www) to point at an Application Load Balancer, which only publishes a DNS name, not a static IP. An engineer tries creating a CNAME record directly on animalsforlife.org and it's rejected. Why?

      • A. Because Route 53 hosted zones don't support CNAME records at any level, apex or otherwise
      • B. Because the ALB doesn't expose any DNS name that a CNAME could ever target
      • C. Because the DNS standard itself forbids a CNAME record at the zone apex, on any provider
      • D. Because CNAME records incur an extra creation fee specifically when placed at the apex

      Topic: CNAME vs. Route 53 Alias

      Correct answer: C

      • A. Wrong — Route 53 fully supports CNAME records at non-apex names like www.animalsforlife.org; the restriction is specific to the apex.
      • B. Wrong — the ALB does hand back a DNS name; that's precisely why a CNAME or alias record is being attempted here in the first place.
      • C. Correct — this isn't an AWS restriction; the DNS standard itself forbids a CNAME at the zone apex, on any DNS provider, which is exactly why alias records exist.
      • D. Wrong — the real cost distinction is about per-query billing (CNAME queries to AWS resources are billed, alias queries are free), not a record-creation fee tied to apex placement.

      Scenario 12

      A cost-conscious team is choosing between a CNAME and an alias record for www.animalsforlife.org, which will point at a CloudFront distribution and receive millions of queries a month. Both types are technically legal here since it isn't the zone apex. Which minimizes ongoing Route 53 query costs, and why?

      • A. CNAME — alias only avoids charges for queries made from inside a VPC, not from the internet
      • B. Neither — Route 53 charges the same per-query rate for CNAME and alias records regardless
      • C. Alias — Route 53 caches alias responses free of charge only after the first million monthly queries
      • D. Alias — Route 53 doesn't charge for alias queries to AWS resources, while CNAME queries are billed

      Topic: CNAME vs. Route 53 Alias

      Correct answer: D

      • A. Wrong — this invents a VPC-vs-internet billing split that doesn't exist; alias queries to AWS resources are free regardless of where the query originates.
      • B. Wrong — this contradicts the actual pricing model, where alias queries to AWS resources are free and CNAME queries are billed.
      • C. Wrong — there's no million-query free tier or caching threshold like this; alias queries to AWS resources are simply free from the first query.
      • D. Correct — Route 53 doesn't charge for alias queries made to AWS resources, while the equivalent CNAME queries are billed, making alias the cheaper choice at scale.

      Scenario 13

      An engineer is pointing one alias record at an API Gateway custom domain (which hands back an A record) and a second alias record at a resource that itself provides a CNAME-style mapping to another name. How should the record type of each alias be chosen?

      • A. Match each alias's type to whatever the target itself provides — A for one, CNAME for the other
      • B. Create both as CNAME record aliases, since alias is fundamentally built on the CNAME mechanism
      • C. Create both as A record aliases, since alias records default to A regardless of the target
      • D. Use a dedicated "AWS alias" record type reserved specifically for AWS resource targets

      Topic: CNAME vs. Route 53 Alias

      Correct answer: A

      • A. Correct — "alias" isn't its own record type, it's a flag on an existing type; match it to whatever the target resource provides, an A record alias for an A-providing target and a CNAME record alias for a CNAME-providing one.
      • B. Wrong — alias isn't always CNAME-based; a target that hands back an A record needs an A record alias, not a CNAME record alias.
      • C. Wrong — alias records don't default to A regardless of the target; the type must match what the target itself provides.
      • D. Wrong — there's no distinct "AWS alias" record type; alias is a modifier applied on top of standard types like A or CNAME.

      Scenario 15

      A multinational is migrating DNS hosting away from Route 53 to a different provider next year, but wants today's records to remain valid afterward with minimal rework. For a subdomain pointing at an AWS resource, does relying on an alias record support that portability goal?

      • A. Yes — alias records are part of the general DNS standard and resolve from any provider
      • B. Yes — alias records automatically convert into equivalent CNAME records once the zone leaves Route 53

      • D. No — neither survives migration; every record would need to become a static-IP A record

      Correct answer: C

      • A. Wrong — alias is a Route 53-specific extension to the DNS standard, not part of the standard itself; it only functions while Route 53 hosts the domain.

      • C. Correct — alias only works while Route 53 hosts the zone; a CNAME, being a DNS-standard mechanism (though billed for AWS-resource queries), would remain valid after migrating providers.

      Scenario 16

      A record www.animalsforlife.org uses simple routing with 3 values pointing at 3 independent app servers. One of the three servers crashes hard and stops responding entirely. A client queries the record moments later. What does Route 53 return?

      • A. Only the 2 healthy values, since Route 53 silently drops values it detects as unreachable
      • B. The query fails outright, since one of the three servers behind the record is unreachable
      • C. All 3 values, but reordered so the crashed server's value always appears last
      • D. All 3 values in random order, exactly as if every server were healthy

      Topic: Simple Routing

      Correct answer: D

      • A. Wrong — this implies health awareness that simple routing doesn't have; it can't detect the crash or drop the value.
      • B. Wrong — simple routing doesn't fail the whole query because one server is down; it simply has no awareness of server health to act on.
      • C. Wrong — simple routing doesn't reorder or rank values by health; order is random, not health-based, and it has no way to detect the crash anyway.
      • D. Correct — simple routing is the one Route 53 policy with no health check support; all 3 values are still returned in random order, including the crashed server's.

      Scenario 17

      Which of these four requirements is the best fit for simple routing, with no need to ever swap to a different Route 53 routing policy?

      • A. A record pointing at one standalone web server, needing no health logic or traffic split
      • B. Automatically redirecting traffic to a backup S3 bucket the instant a health check fails
      • C. Sending exactly 5% of production traffic to a canary release for testing purposes
      • D. Directing each user to whichever AWS Region gives them the lowest network latency

      Topic: Simple Routing

      Correct answer: A

      • A. Correct — a single server needing no health-check-based logic or traffic splitting is exactly simple routing's use case; it's the default, no-frills policy.
      • B. Wrong — automatic failover on health-check failure is failover routing's job; simple routing has no health check capability to trigger it.
      • C. Wrong — sending a specific traffic percentage to a canary release is a weighted routing use case, which simple routing can't express.
      • D. Wrong — directing users by lowest latency is latency-based routing's job; simple routing has no concept of Region or latency.

      Scenario 21

      A health check's globally distributed checkers report the endpoint healthy from exactly 18% of them on the latest evaluation, with the rest reporting unhealthy. Records tied to this check are configured to stop being returned whenever it goes unhealthy. Does querying the record still return this endpoint's value right now?

      • A. No — Route 53 requires more than 18% reporting healthy, so exactly 18% is unhealthy
      • B. Yes — 18% exactly clears the healthy threshold, so the check is healthy
      • C. It depends entirely on the configured failure threshold, which overrides the 18% figure
      • D. Yes — Route 53 rounds 18% up to the nearest boundary that clears the threshold

      Topic: Route 53 Health Checks

      Correct answer: A

      • A. Correct — Route 53 requires more than 18% of checkers to report healthy for the overall status to be healthy; exactly 18% falls short, so the check is unhealthy and the value is withheld.
      • B. Wrong — the threshold is strictly "more than 18%," not "18% or more"; exactly 18% does not clear the bar.
      • C. Wrong — the 18% figure is a fixed aggregation rule; the failure threshold (consecutive pass/fail count) is a separate, unrelated setting.
      • D. Wrong — there's no rounding behavior applied to the 18% aggregation figure; it's a clean more-than-18%-vs-18%-or-fewer split.

      Scenario 22

      A team configures a health check that only opens a TCP connection to port 443 and considers the endpoint healthy the moment that connection completes, without inspecting any HTTP response. Later they discover the web server process was hung and returning no valid pages, yet the check reported healthy the whole time. What's the most direct fix?

      • A. Reduce the check interval from 30 seconds to 10 seconds so failures are caught sooner
      • B. Switch to an HTTP/HTTPS check, which also requires a 2xx or 3xx status within the time limit
      • C. Switch to a CloudWatch alarm check tied to the instance's network-in metric instead
      • D. Lower the failure threshold to 1 so a single bad TCP result flips the status immediately

      Topic: Route 53 Health Checks

      Correct answer: B

      • A. Wrong — a faster interval catches the same blind spot sooner, but doesn't fix the root cause: TCP checks can't see that the app itself is hung.
      • B. Correct — an HTTP/HTTPS check requires a 2xx or 3xx status to be returned within the time limit, not just a completed TCP connection, catching a hung app that TCP alone would miss.
      • C. Wrong — network-in traffic volume doesn't reflect whether the application itself is serving valid pages; it's the wrong signal for this failure mode.
      • D. Wrong — lowering the failure threshold changes how many bad results are needed before flipping status, but a TCP check still can't detect a hung application in the first place.

      Scenario 23

      An application is made up of three independently health-checked components — web, API, and database connectivity — each already with its own Route 53 health check. The team wants one overall health signal representing the whole application. What should they build?

      • A. A single endpoint check pointed at the load balancer URL, replacing the three component checks
      • B. A CloudWatch alarm check watching only the database's CPU utilization metric
      • C. A calculated health check referencing the three existing component checks together
      • D. Three separate simple-routing records, relying on clients to detect failures themselves

      Topic: Route 53 Health Checks

      Correct answer: C

      • A. Wrong — this discards the granular per-component checks the requirement wants combined, replacing them instead of rolling them up.
      • B. Wrong — this only reflects one narrow metric on one component, not a combined signal across web, API, and database checks.
      • C. Correct — a calculated check is a check of other checks, letting the three component-level health checks roll up into one overall application health signal.
      • D. Wrong — this conflates routing policy with health check design; simple routing doesn't provide any health-check rollup mechanism at all.

      Scenario 24

      Scenario 25

      • D. Wrong — geolocation matches a user's own tagged location to an explicitly tagged record; it never calculates distance or selects the nearest resource the way geoproximity does.

      Correct answer: C

      • B. Wrong — growing Singapore's area would pull in even more traffic toward the already over-capacity resource, the opposite of the intended outcome.
      • C. Correct — a positive bias on Ireland expands its effective service area far enough to pull in Indian traffic, while the decision stays purely distance-based under the hood.

      Scenario 53

      A company runs one resource on EC2 in ap-southeast-1 and another in an on-premises data center with no AWS presence. They want to include both in a single geoproximity configuration. How should each resource be defined?

      • B. Both resources need an AWS Region tag, since geoproximity can only route to Regions, not external endpoints

      • D. The EC2 resource is tagged with its AWS Region, while the on-premises resource gets explicit latitude/longitude

      Scenario 54

      A user in Saudi Arabia queries three separately-configured hosted zones for three different companies: one uses latency-based routing, one uses geolocation, and one uses geoproximity, each with resources in the UK and Australia and no bias applied anywhere. Which pairing correctly matches each policy to what determines its answer?

      • A. Latency: estimated Region performance; geolocation: explicit tag match, possibly no answer; geoproximity: pure distance
      • B. Latency: pure physical distance; geolocation: estimated Region performance; geoproximity: explicit tag match
      • C. Latency: explicit tag match, possibly no answer; geolocation: pure distance; geoproximity: estimated performance
      • D. All three ultimately resolve to the same nearest-resource answer whenever no bias or tag conflicts exist

      Topic: Geoproximity Routing

      Correct answer: A

      • A. Correct — latency uses estimated Region performance; geolocation matches an explicit location tag and can return no answer; geoproximity uses pure physical distance, adjustable with bias.
      • B. Wrong — this reshuffles the three mechanisms into the wrong pairings; latency is not distance-based and geolocation is not performance-based.
      • C. Wrong — this also reshuffles the pairings incorrectly; explicit-tag "possibly no answer" behavior belongs to geolocation, not latency, and distance belongs to geoproximity, not geolocation.
      • D. Wrong — the three policies use genuinely different underlying logic and can easily disagree even with no bias or conflicts; they don't converge on one guaranteed shared answer.

      • A. Wrong — transferring the registration would change the very registrar relationship the company explicitly wants to keep, violating the stated constraint.
      • B. Wrong — a private hosted zone is only reachable from associated VPCs, not the public internet, so it wouldn't serve public DNS traffic for the domain.
      • C. Correct — this is the "hosting only" architecture: keep the existing registrar untouched, create a public hosted zone in Route 53, and update NS records at the registrar to point at it.

      Scenario 57

      • B. In the .org registry's own management console directly, since it stores the domain's records

      • D. With the third-party DNS provider, since it hosts the zone file even though Route 53 is only registrar

      Correct answer: D

      • B. Wrong — a TLD registry only stores the domain's delegation (NS) information for the registrar relationship; it doesn't host the actual zone file with its resource records.
      • C. Wrong — there's no dual-storage or mirroring arrangement between a registrar and a hosting provider; exactly one place holds the authoritative zone file at a time.
      • D. Correct — when Route 53 is registrar-only, a separate third-party provider hosts the actual zone file and name servers, so edits must be made there.

      Scenario 63

      A hosted zone has DNSSEC enabled: the DNSKEY record and its RRSIG are published correctly inside the zone itself. Resolvers still cannot validate the chain of trust for this domain. What is most likely missing?

      • A. A ZSK-backed KMS key, since without it the DNSKEY record can't be considered complete
      • B. A DS record in the parent zone, linking a hash of the KSK's public part into the chain
      • C. A second DNSKEY record inside the zone representing the parent zone's own signing key
      • D. A CloudWatch alarm for DNSSEC internal failure, required before validation can succeed

      Topic: DNSSEC with Route 53

      Correct answer: B

      • A. Wrong — the ZSK is never backed by a KMS key, and its absence wouldn't relate to a missing chain-of-trust link at the parent zone; this describes a nonexistent requirement.
      • B. Correct — even with a valid DNSKEY and RRSIG inside the zone, the chain of trust is incomplete until a DS record — a hash of the KSK's public part — is added to the parent zone.
      • C. Wrong — the parent zone doesn't need a copy of a DNSKEY record from the child zone; it needs a DS record, a hash reference, not a duplicated signing key.
      • D. Wrong — a CloudWatch alarm is an operational monitoring tool for detecting failures after the fact; it isn't itself required for the chain of trust to validate successfully.

      A VPC has DNSSEC validation for VPCs enabled. A record in a DNSSEC-enabled hosted zone fails signature validation due to a misconfigured key. What happens when a resolver inside that VPC queries the record?

      • B. The query is answered from a cached unsigned copy of the record, bypassing validation entirely
