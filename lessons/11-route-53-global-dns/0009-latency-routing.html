Route 53 & Global DNS

Latency-Based Routing

Lesson 09 of 13 · ~5 min

Source: Adrian Cantrill SAA-C03 · Choosing a Routing Policy

The next three lessons — latency, geolocation, and geoproximity — are the ones most likely to blur together in your head, because all three route based on where things are in the world. Keep this straight as you go: latency routing optimizes for performance, using measured network latency, not physical distance.

How It Works

Records with the same name (e.g. www) are each tagged with an AWS Region — one record per Region for that name. AWS separately maintains a background database of typical latency between Regions and the rest of the world. When a user resolves the record, Route 53 identifies their approximate location (via an IP lookup), consults that latency database, and returns the record for the Region with the lowest expected latency to that user.

Latency isn't measured live
The latency database AWS uses is not real-time — it's a maintained background dataset, so it won't reflect a sudden local network problem on either end. It's a solid general-purpose optimization, not a live network probe.

Latency routing combines with health checks: if the lowest-latency record is unhealthy, Route 53 moves on to the record with the next-lowest latency instead.

Exam tip: latency vs. geoproximity
Latency routing picks the Region that will likely feel fastest — which is not always the Region that's physically closest. Geoproximity routing (two lessons ahead) is explicitly distance-based instead. Use latency routing when the goal is user-perceived performance for a global application.
