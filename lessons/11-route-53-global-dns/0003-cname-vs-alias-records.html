CNAME vs. Route 53 Alias Records

Lesson 03 of 13 · ~6 min

Source: Adrian Cantrill SAA-C03 · Choosing Between Alias and Non-Alias Records

This distinction shows up repeatedly in exam questions, and it trips up people new to DNS. Get the two failure modes straight and the rest falls into place.

The Problem with CNAME Alone

An A record maps a name to an IP address (catagram.io → 1.3.3.7). A CNAME maps a name to another name (www.catagram.io → catagram.io) — a standard, well-understood DNS mechanism.

The DNS-standard limitation
You cannot create a CNAME for the zone apex — the "naked" domain itself (catagram.io, with no subdomain). This isn't an AWS restriction; it's baked into the DNS standard. www.catagram.io can be a CNAME. catagram.io cannot.

That's a real problem, because many AWS services — Elastic Load Balancers, CloudFront, API Gateway — hand you a DNS name rather than a static IP. If you only had CNAME available, you could point www.catagram.io at a load balancer's DNS name, but never the naked catagram.io.

Alias Records: AWS's Fix

A Route 53 alias record maps a name onto an AWS resource, and — unlike CNAME — it can be used at the zone apex. It's a Route 53–specific extension to the DNS standard, so it only works if Route 53 is hosting your domain.

Exam tip: default to alias for AWS resources
AWS makes alias queries to AWS resources free, specifically to encourage this default. For anything in a Route 53 zone pointing at an AWS resource — ELB, CloudFront, API Gateway, Elastic Beanstalk, Global Accelerator, or an S3 website bucket — default to an alias record, apex or not.

Alias Is a Wrapper, Not a New Record Type

"Alias" isn't its own DNS record type — it's a flag applied to an existing type. You get an A record alias or a CNAME record alias depending on what the target resource itself provides. An ELB hands you an A record, so pointing at an ELB means creating an A record alias — match the alias's record type to the target's record type.
