Choosing Between Instance Store and EBS

Lesson 11 of 21 · ~9 min

Source: Adrian Cantrill SAA-C03 · Amazon EC2 Instance Store

You now understand both storage options individually. This lesson is deliberately fact-dense — it collects the scenario rules, minimums, and performance ceilings that let you pick between EBS and instance store quickly, both in the exam and in real designs.

The clear-cut cases

Start with a default rule: if you need persistent, resilient storage, default to EBS — or equivalently, default away from instance store. Instance store volumes are not persistent. Hardware failure, host maintenance, and anything that moves an instance to a different physical host can destroy the data on them. EBS, by contrast, is hardware-resilient within an Availability Zone and can be backed up to S3 via snapshots, making it region-resilient too.

A second clear case: if storage needs to be isolated from the instance's lifecycle — attached, detached, and reattached to a different instance over time — only EBS supports that. Instance store is physically tied to one host for the life of the instance.

The "it depends" cases

Some scenarios are genuinely ambiguous, and the exam likes to test exactly these:

  • Resilience with app-level replication — if the application already replicates data across many instances (think a distributed database or a cache cluster), you can use instance store on every node and accept that any single node's data is disposable, gaining raw performance without the resilience risk.
  • High performance — both EBS and instance store can deliver strong performance up to a point. Beyond that point, only instance store can keep scaling (see the numbers below).
  • Cost sensitivity — instance store capacity is bundled into the price of many instance types, so if cost is the primary driver and persistence isn't required, instance store is effectively "free" extra storage.
Exam tip
Purely cost-focused EBS questions should default you to ST1 or SC1 (magnetic, cheaper than SSD). Throughput/streaming-focused questions also point to ST1. But watch for the word "boot volume" — neither ST1 nor SC1 can be used as a boot volume, so a boot requirement rules both out regardless of cost or throughput framing.

Performance ceilings you need to memorize

These figures come up repeatedly in performance-scenario questions. See the EC2 Instance Store guide for the underlying detail.

LayerCeiling
gp2 / gp3Up to 16,000 IOPS per volume
io1 / io2Up to 64,000 IOPS per volume
io2 Block ExpressUp to 256,000 IOPS per volume (needs a suitably large instance to realize it)
RAID 0 across EBS volumesCombined performance of all volumes, capped by the instance's own maximum
EC2 instance-level ceilingCurrently up to 260,000 IOPS, regardless of how many volumes you stripe together
Instance storeCan exceed EBS's instance-level ceiling by a wide margin on the right instance type, at the cost of persistence

The practical takeaway: no matter how many EBS volumes you RAID 0 together, an instance has a hard IOPS ceiling that EBS alone cannot exceed. If a requirement genuinely needs more than that ceiling and the workload can tolerate non-persistent storage, instance store is the only path to that level of performance.

Exam tip
These are the rare AWS facts worth rote-memorizing: 16,000 IOPS (gp2/gp3), 64,000 IOPS (io1/io2), 256,000 IOPS (io2 Block Express, large instances only), and 260,000 IOPS as the current per-instance ceiling. If a question pushes past that last number and tolerates data loss, the answer is instance store.
