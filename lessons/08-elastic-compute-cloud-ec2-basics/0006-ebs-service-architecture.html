EC2 Basics

EBS Service Architecture

Lesson 06 of 21 · ~9 min

Source: Adrian Cantrill SAA-C03 · Amazon EBS User Guide

Elastic Block Store (EBS) is AWS's block storage service. It takes physical disks, carves them into allocations called volumes, and lets you address that storage by block number — exactly like a raw disk. When you attach a volume to an EC2 instance, the instance sees a plain block device and can format it with a file system (EXT3/EXT4/XFS on Linux, NTFS on Windows) just as it would a physical drive.

You'll use EBS constantly, directly or indirectly, so its architecture and limitations are worth knowing cold before you look at individual volume types in the next few lessons.

EBS is an Availability Zone service

This is the single most important fact about EBS. A volume is provisioned inside one specific Availability Zone and lives only there. EBS in AZ-A is a completely separate deployment from EBS in AZ-B — there is no cross-AZ attachment. An EC2 instance in AZ-B can never attach to a volume created in AZ-A, full stop.

Within its AZ, EBS replicates a volume's data across multiple physical devices for durability against individual disk failure. But that replication doesn't cross AZ boundaries — a full AZ failure can take down every volume provisioned in it, along with the instances that depend on them.

Exam tip
"Can this EC2 instance attach to that EBS volume?" is almost always answered by checking whether they're in the same Availability Zone. Different AZ, same region — no. Region mismatch — definitely no.

Volumes are decoupled from instance lifecycle

An EBS volume is not tied to any one instance's lifecycle. It is created, has data written to it, and persists until you explicitly delete it. Practically, this means:

  • Persistence across stop/start/restart — the volume's data survives even if the instance stops and starts again.
  • Persistence across host migration — if AWS moves your instance to different underlying hardware, the EBS volume follows it (this works precisely because EBS is a networked, not local, storage service).
  • Detach and reattach — you can detach a volume from one instance and attach it to another instance in the same AZ.

By default, a volume attaches to exactly one instance at a time over a storage network. Some volume types support a feature called multi-attach, allowing simultaneous attachment to multiple instances for clustered applications — but in that case, the cluster software itself is responsible for coordinating writes so concurrent access doesn't corrupt data. EBS does not arbitrate that for you.

Snapshots: escaping the AZ boundary

Because EBS is AZ-locked, AWS gives you a mechanism to move data between AZs and regions: the snapshot. A snapshot copies a volume's data into S3, which — unlike EBS — is a regionally resilient service, replicated across the AZs of that region automatically.

Once a volume is snapshotted into S3, that snapshot can be used to create a brand-new volume in any AZ within the region, or even copied to a different AWS region entirely and used to create a volume there. This is the standard technique for migrating data across AZs or regions, and it's covered in full (including fast snapshot restore) in a dedicated later lesson. See the Amazon EBS User Guide for the underlying service model.

Volume types differ mainly in the underlying physical media (SSD vs. HDD), size limits, and performance profile — the AZ-locked, persistent architecture described here is common to all of them. That's what the next three lessons build on.
