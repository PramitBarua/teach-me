EC2 Basics

Virtualization 101

Lesson 01 of 21 · ~9 min

Source: Adrian Cantrill SAA-C03 · AWS Nitro System

EC2 is virtualization delivered as a service — an Infrastructure as a Service (IaaS) product. Before you can reason about why EC2 features work the way they do (enhanced networking, instance types, the Nitro hypervisor), you need the fundamentals of virtualization itself. This lesson builds that foundation.

Life without virtualization

A physical server has resources — CPU, memory, network cards, storage. On top of that runs an operating system, and a small part of it, the kernel, runs in privileged mode. The kernel is the only software allowed to talk to hardware directly. Everything else — applications — runs in user mode and must go through the OS via a system call to touch hardware. If any non-privileged software attempts a privileged operation directly, the hardware detects it and the system (or at least the application) crashes.

That model assumes one operating system owns the hardware. A CPU, at least historically, can only have one thing running in privileged mode at a time. Virtualization exists to break that assumption safely.

Three eras of virtualization

Running several unmodified guest operating systems on one physical server creates a conflict: every guest still believes it alone owns the hardware and will attempt privileged instructions. Three approaches solved this, each less wasteful than the last.

1. Emulated (software) virtualization

A host OS runs a hypervisor in privileged mode. Guest operating systems run inside virtual machines with virtualized CPU, memory, and devices — all fake, but convincing enough that the guest OS installs normal drivers and believes it's talking to real hardware. When a guest attempts a privileged instruction, the hypervisor intercepts it and performs binary translation — rewriting the instruction on the fly in software. Guests need zero modification, but binary translation is slow: it can halve guest performance or worse.

2. Para-virtualization

Instead of translating privileged calls after the fact, the guest OS source code is modified in advance. Areas that would make privileged hardware calls are rewritten to issue hypercalls — direct calls to the hypervisor — using para-virtual drivers for devices like network cards and storage. This makes the guest OS "virtualization aware" and meaningfully faster than emulation, but it only works for operating systems that can be modified, and those modifications are tied to a specific hypervisor vendor.

3. Hardware-assisted virtualization

The real breakthrough: the CPU itself becomes virtualization-aware. It contains instructions the hypervisor can configure so that when a guest attempts a privileged instruction, the CPU traps it and redirects it to the hypervisor — without crashing the system and without needing the guest OS to be modified. This gets CPU performance very close to bare metal.

Exam tip
You won't be quizzed on binary translation internals, but you should recognize the progression — emulated → para-virtualized → hardware-assisted — and know that modern EC2 relies on hardware-assisted virtualization plus SR-IOV, not the older, slower techniques.

The remaining bottleneck: I/O

Hardware-assisted virtualization fixes CPU-bound privileged instructions, but what usually matters most for a VM's real-world performance is I/O — network throughput and disk operations. A guest's "network card" is really a logical device backed by a driver that shares one physical card on the host. Unless there's a dedicated physical card per VM, software has to sit in the path, and that consumes host CPU cycles and adds latency under heavy I/O.

SR-IOV and EC2 enhanced networking

The final piece is making the device itself virtualization-aware. SR-IOV (Single Root I/O Virtualization) lets a physical network card present itself as multiple independent virtual cards in hardware. Each guest OS gets what looks like a dedicated card with direct, unmediated access — no hypervisor translation required on the data path.

In EC2, this is exposed as enhanced networking: higher throughput, lower and more consistent latency (even under load), and reduced CPU overhead on the host. Many advanced EC2 capabilities you'll meet later in this course trace back to AWS applying industry virtualization techniques like this at scale, underpinned by AWS's own hypervisor platform, the Nitro System.
