EC2 Basics

EBS Encryption

Lesson 13 of 21 · ~8 min

Source: Adrian Cantrill SAA-C03 · Amazon EBS Encryption

By default, an EBS volume stores whatever the operating system writes to it, unencrypted — plain text on physical disk. EBS encryption provides at-rest encryption for both volumes and their snapshots, built on KMS, at no additional cost.

How the architecture works

When you create an encrypted volume, EBS uses a KMS key — either the AWS-managed default key (aws/ebs) or a customer-managed key you control — to generate a unique Data Encryption Key (DEK) for that one volume, via the GenerateDataKeyWithoutPlaintext API call. Only the encrypted form of the DEK is stored alongside the volume; a brand-new volume starts empty, so there's nothing to encrypt yet.

When the volume is actually mounted — either attached manually or as part of an instance launch — EBS asks KMS to decrypt that DEK, and the plaintext key is loaded only into the memory of the EC2 host currently using the volume. That host then uses the key to encrypt data flowing to the raw storage and decrypt data flowing back. The result:

  • Data on the underlying physical storage is always ciphertext.
  • Data exists in plaintext only inside the EC2 host's memory, for as long as it's using that volume.
  • If the instance moves to a different host, the decrypted key in memory is discarded — the new host must ask KMS to decrypt the key again before it can use the volume.
Transparent to the OS
The operating system has no awareness of any of this. It writes and reads plain data as normal; encryption happens in the layer between the EC2 host and the EBS storage system, using AES-256. There is no meaningful performance penalty for using it.

Snapshots and encryption inherit the same key

A snapshot taken of an encrypted volume is itself encrypted, using the same DEK as the source volume. Any new volume created from that snapshot is also encrypted, and also uses that same DEK. This chain — one volume, its snapshots, and any volumes made from those snapshots — all share a single DEK. A different volume created from scratch always gets its own, different DEK.

Exam tip
Memorize the rule precisely: every brand-new volume gets a unique DEK. Every snapshot of an encrypted volume, and every volume restored from that snapshot, reuses the same DEK as the original. The exam likes to test whether you know which operations create a new key and which reuse one.

You cannot decrypt in place

Once a volume or snapshot is encrypted, there is no AWS console, CLI, or API operation to strip the encryption back off. The only workaround is entirely at the OS level: since the operating system only ever sees plaintext, you can copy data from inside the instance to a separate, unencrypted volume manually. AWS itself offers no direct "decrypt" action.

The reverse — going from unencrypted to encrypted — is straightforward: copying an unencrypted snapshot while choosing an encrypted destination is a supported operation, and it's how most existing unencrypted volumes get migrated to encrypted ones.

Account defaults and OS-level encryption

An AWS account can be configured to encrypt all new EBS volumes by default, using either the default AWS-managed key or a customer-managed key of your choosing. Separately, an operating system can run its own software disk encryption, where the OS itself manages the keys instead of relying on EBS/KMS. The two can technically run at once, though for most use cases it's redundant — EBS encryption alone already satisfies most at-rest requirements without the OS needing to hold any keys.
