EC2 Basics

Horizontal & Vertical Scaling

Lesson 20 of 21 · ~10 min

Source: Adrian Cantrill SAA-C03 · Amazon EC2 Auto Scaling

Scaling is what happens when a system needs to grow or shrink to match changing customer load. There are two fundamentally different ways to add capacity to a system built on EC2: make each instance bigger (vertical), or add more instances (horizontal). Both solve the same problem, but they carry very different trade-offs — and this distinction underpins almost everything you'll learn about high availability and Auto Scaling later in the course.

Vertical scaling: a bigger server

Vertical scaling resizes an existing instance to a larger (or smaller) type — a t3.large becomes a t3.xlarge, then a t3.2xlarge, each step roughly doubling vCPU and memory. It's conceptually simple and needs no application changes: if an application runs on an instance, it runs on a bigger one too, which makes vertical scaling viable even for monolithic applications that can't easily be split across machines.

But it comes with real constraints:

  • Downtime — resizing an instance typically requires a stop/start, so scaling usually has to happen inside a pre-agreed outage window rather than instantly in response to load.
  • A hard ceiling — there is always a largest available instance size. Once you're at the top, vertical scaling has nowhere left to go.
  • Non-linear cost — larger instance sizes often carry a price premium, so cost doesn't scale proportionally as you go bigger.

Horizontal scaling: more servers

Horizontal scaling leaves individual instances alone and instead changes how many of them are running — one instance becomes two, then eight, as load demands. Because there's no per-instance size cap, horizontal scaling has effectively no upper limit, and because you're typically using smaller, commodity-priced instances, it's often the cheaper path to a given amount of total capacity. It also allows much finer-grained scaling steps — adding one instance to a fleet of five is roughly a 20% capacity increase, versus the near-doubling that a single vertical resize typically produces.

The catch is that horizontal scaling needs the application to support it. With multiple instances splitting incoming traffic — normally via a load balancer — a given customer's requests can land on any instance in the fleet, not always the same one.

Exam tip
Horizontal scaling requires off-host (external) session storage. If session state is kept only on the instance that first handled a customer, that customer effectively gets logged out — or loses their cart, or their place in a video — every time a later request lands on a different instance. Externalizing sessions to a shared store makes instances stateless, so it genuinely doesn't matter which instance answers which request.

Horizontal scaling is the pattern behind Amazon EC2 Auto Scaling, which automatically launches and terminates instances in response to demand, generally paired with a load balancer distributing traffic across them. That combination — covered in depth later in the high availability and scaling section of the course — is what gives horizontally-scaled architectures both elasticity and resilience. See the Amazon EC2 Auto Scaling guide for how the service fits together.

A memorable way to keep the two straight: vertical scaling turns a small server into a medium, then a large one — but there's always a biggest size available. Horizontal scaling just keeps adding more servers side by side, with no real limit on how many you can have.
