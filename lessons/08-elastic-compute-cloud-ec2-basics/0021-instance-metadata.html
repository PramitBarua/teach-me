EC2 Basics

Instance Metadata (IMDS)

Lesson 21 of 21 · ~10 min

Source: Adrian Cantrill SAA-C03 · EC2 Instance Metadata Service

The Instance Metadata Service (IMDS) is a small HTTP service that EC2 exposes to every instance, giving anything running on it a way to ask "what am I, and what's around me?" It underpins a huge number of EC2 features you'll meet later in the course, it's one of the most exam-tested single facts in the whole certification, and it's also a genuine, real-world security surface — so this lesson is worth locking in properly.

What metadata is — and what it isn't

Metadata is data about the running instance — its hostname, its network configuration, its security groups, IAM role credentials, and more — queryable from inside the instance over HTTP. It is not the same thing as user data, which is the one-time configuration script or data you supply at launch (covered elsewhere in this module); metadata is queried continuously by anything running on the instance, at any point in its life.

Exam tip
Memorize the address: 169.254.169.254, path /latest/meta-data/. Exam questions have been known to ask you to pick the exact URL out of several similar-looking options. Say it as a rhythm — "one-six-nine, two-five-four, repeated" — it sticks.

What you can retrieve

Metadata is organized into categories. The ones you'll use most as a solutions architect:

  • Networking — private IPv4, IPv6, and (notably) the public IPv4 address, which is never configured inside the instance's own operating system. Public IPv4 is applied by the Internet Gateway via NAT, not the guest OS, so the only way software on the instance can learn its own public address is by asking the metadata service.
  • IAM role credentials — when an instance is launched with an IAM role, applications on the instance retrieve temporary credentials for that role through the metadata service rather than ever having long-lived keys hardcoded anywhere.
  • Instance identity — AMI ID, instance ID, instance type, Availability Zone, and security groups.
  • User data — the launch script/configuration you supplied is itself retrievable through the metadata service's user-data path.

You can query it directly with a tool like curl from inside the instance — for example, requesting http://169.254.169.254/latest/meta-data/public-ipv4 returns the instance's public IPv4 address as plain text — or use the bundled ec2-metadata helper tool for a friendlier interface to the same data. See the EC2 Instance Metadata Service guide for the full category reference.

IMDSv1 vs. IMDSv2

The metadata endpoint has no authentication of its own — historically (IMDSv1), any process capable of making an HTTP request from inside the instance could simply query it directly, no credentials required. That's a real risk: a web application vulnerability that lets an attacker trick your server into making an outbound request on its behalf — a Server-Side Request Forgery (SSRF) — could be used to fetch the metadata endpoint and steal that instance's IAM role credentials, entirely from outside the instance.

AWS's mitigation is IMDSv2, a session-oriented mode that requires a token before any metadata request succeeds:

VersionRequest patternSSRF resistance
IMDSv1Simple GET request straight to the metadata pathLow — a single unauthenticated GET is enough
IMDSv2First PUT a request for a session token (with a hop-limit-respecting header), then include that token on subsequent GET requestsMuch higher — most simple SSRF techniques only forge a GET, not the initial token-issuing PUT
Exam tip
IMDSv2 is one of the highest-yield EC2 security topics on SAA-C03. Know that: it's token-based and session-oriented; the token request is a PUT, which most naive SSRF exploits can't forge; and instances can be configured to require IMDSv2, rejecting any IMDSv1-style request outright. If a scenario mentions hardening an instance against credential theft via a web app vulnerability, IMDSv2 enforcement is very likely the answer.
Even with IMDSv2 enforced, treat the metadata endpoint as reachable by anyone with shell access to the instance — it still carries no per-user authentication. Restricting who can log into an instance matters just as much as which IMDS version it runs.
  • Address: 169.254.169.254, path /latest/meta-data/.
  • Metadata ≠ user data — metadata describes the running instance; user data is the launch-time configuration payload.
  • Public IPv4 is visible only via metadata — never inside the guest OS's own network configuration.
  • IMDSv2 adds a token-based session requirement specifically to reduce exposure to SSRF-driven credential theft.
