EC2 Basics

Amazon Machine Images (AMI)

Lesson 15 of 21 · ~10 min

Source: Adrian Cantrill SAA-C03 · Amazon Machine Images (AMI)

Every EC2 instance you've launched so far has been built from an AMI — a template that defines the configuration used to create an instance. You've been consuming AMIs; this lesson covers building your own, and the architecture behind how that works.

Where AMIs come from

  • AWS-provided — official images such as Amazon Linux 2, maintained by AWS.
  • Community-provided — vendors and distributions like Red Hat, CentOS, or Ubuntu publish their own AMIs.
  • Marketplace — commercial AMIs bundling licensed software; launching one typically costs the normal instance rate plus an extra licensing fee.
  • Custom / self-created — an AMI you build yourself from a configured instance, the focus of this lesson.
Exam tip
AMIs are Region-specific. The same operating system has a different, unique AMI ID in every Region — an AMI created in one Region cannot be used directly in another. To use it elsewhere, you must explicitly copy it to the target Region first.

AMI permissions

Every AMI has a permission model with three options: private (default — only your account can use it), public (any AWS account can use it), or shared with specific AWS accounts you explicitly add.

The AMI lifecycle: launch, configure, create image, launch again

Most people only ever experience the first phase — launching an instance from an existing AMI. But you can run the cycle further:

  1. Launch — start an instance from an existing AMI.
  2. Configure — customize that instance: install software, apply settings, attach and size volumes exactly as your organization needs.
  3. Create image — capture that customized instance and its attached volumes as a brand-new AMI.
  4. Launch again — use the new AMI to stamp out many identical, pre-configured instances.

This capture-and-replicate process is commonly called AMI baking: install and configure everything once, bake it into an AMI, then deploy it at scale instead of repeating manual setup on every instance.

What an AMI actually contains

Think of an AMI as a lightweight container, not a copy of the data itself. When you create an AMI from an instance, it holds three things:

  • Permissions — who can use the AMI (private, public, or shared accounts).
  • EBS snapshots — one snapshot is taken of each EBS volume attached to the source instance. As with any snapshot, the first is a full copy of used data.
  • Block device mapping — a table linking each new snapshot ID back to the original device ID it came from, e.g. the boot volume's snapshot maps to /dev/xvda, and a data volume's snapshot maps to /dev/xvdf.

When you later launch an instance from that AMI, EC2 uses the block device mapping to create new EBS volumes — from those referenced snapshots — in the target Availability Zone, and attaches them to the new instance using the same device IDs the original volumes had. The result is a new instance with an identical volume layout and identical starting data. See the AMI documentation for the full reference.

Exam tip
An AMI is Region-scoped but not AZ-scoped: an AMI built from an instance in AZ-A can be used to launch instances into any AZ within that same Region, because the underlying snapshots live in S3, which is already regional.

EBS-backed vs. instance-store-backed AMIs

Most AMIs in modern use are EBS-backed — the root volume is an EBS volume built from a snapshot, as described above, and the instance supports stop/start as well as reboot/terminate. A legacy alternative is the instance-store-backed AMI, where the root device is instance store and the image itself is stored in S3 as a set of files rather than an EBS snapshot. Instance-store-backed instances can only be rebooted or terminated — they cannot be stopped and started, since instance store isn't persistent. For the exam, default to assuming EBS-backed unless a question explicitly says otherwise.

Editing, copying, and billing

QuestionAnswer
Can you edit an existing AMI?No — launch an instance from it, make changes, and create a new AMI instead.
Can an AMI be copied to another Region?Yes, explicitly, as a separate action.
What does an AMI cost?The storage cost of the underlying EBS snapshots it references — billed on data actually used, same as any snapshot.
