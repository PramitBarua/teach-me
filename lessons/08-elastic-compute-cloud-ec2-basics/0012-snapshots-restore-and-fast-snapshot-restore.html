Snapshots, Restore & Fast Snapshot Restore (FSR)

Lesson 12 of 21 · ~10 min

Source: Adrian Cantrill SAA-C03 · Amazon EBS Snapshots

Snapshots are backups of EBS volumes stored on S3. Because EBS volumes are only Availability-Zone resilient, an AZ-wide failure can take a volume with it — snapshots protect against exactly that, and because S3 is a regional service, snapshots make your data region-resilient instead of just AZ-resilient. They also double as a migration tool, letting you move volume data between AZs or between Regions entirely via S3.

Snapshots are incremental

The first snapshot of a volume is always a full copy — but only of the data actually used, not the volume's full allocated size. A 40 GB volume with 10 GB used produces a 10 GB first snapshot. This full copy takes time proportional to the data size, but it happens in the background without impacting the volume's live performance.

Every snapshot after the first is fully incremental: it stores only the blocks that changed since the previous snapshot, referencing the earlier snapshot for everything unchanged. This makes later snapshots both smaller and faster than the first.

Exam tip
Unlike traditional incremental backup chains, deleting a snapshot in the middle of an EBS chain does not break the ones after it — AWS automatically migrates any data those later snapshots still depend on. Every snapshot behaves as if it's self-sufficient, so there's no "must keep every incremental" risk to worry about.

Creating volumes from snapshots

A new EBS volume can be created blank, or built from an existing snapshot — effectively cloning the source volume's data. Because the snapshot lives in S3, the resulting volume can be created:

  • In the same AZ as the original volume.
  • In a different AZ, within the same Region — useful for moving data between AZs.
  • In a different Region, by first copying the snapshot there — useful for DR and cross-region migration.

Restore performance: lazy loading vs. Fast Snapshot Restore

A brand-new blank EBS volume delivers full performance immediately. A volume restored from a snapshot does not — it restores lazily. In the background, EBS gradually pulls the snapshot's data from S3 onto the new volume. If your instance reads a block that hasn't been pulled yet, EBS fetches it from S3 on demand, which is noticeably slower than a native EBS read.

You have two ways to eliminate this "first touch" penalty:

  • Force a full read — use a tool like dd on Linux to read every block of the volume once, pulling all snapshot data from S3 immediately. Typically done once, right after restore, before the volume goes into production.
  • Fast Snapshot Restore (FSR) — an AWS feature you enable on a snapshot that pre-warms it, so any volume created from it delivers full performance from the very first I/O, with no lazy-loading period at all.

See the Fast Snapshot Restore documentation for configuration details.

Exam tip
If a question describes needing guaranteed full performance the instant a restored volume is used — no warm-up period, no manual dd step — the answer is Fast Snapshot Restore. If the scenario is cost-sensitive and a manual step is acceptable, forcing a full read with a tool like dd achieves the same end state for free.

How snapshot billing works

Snapshots bill on a gigabyte-month basis, and only for data actually used, not the volume's allocated size — the same "used, not allocated" principle as the first full snapshot. Because each incremental snapshot only stores changed blocks, taking snapshots frequently (e.g. every five minutes instead of every hour) does not necessarily cost proportionally more — you're still only billed for whatever data actually changed.
