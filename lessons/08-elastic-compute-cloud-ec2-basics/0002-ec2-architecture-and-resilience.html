EC2 Basics

EC2 Architecture and Resilience

Lesson 02 of 21 · ~9 min

Source: Adrian Cantrill SAA-C03 · AWS EC2 User Guide

Now that virtualization fundamentals are in place, this lesson covers how EC2 itself is architected — and the single idea that governs almost every design decision you'll make with it: EC2 is bound to an Availability Zone (AZ).

Instances, hosts, and ownership models

An EC2 instance is a virtual machine: an operating system plus an allocation of vCPU, memory, possibly local storage, network access, and other hardware. Instances run on EC2 hosts — physical servers AWS manages, which are either:

  • Shared hosts — the default. Multiple AWS customers' instances run on the same physical host, fully isolated from one another with no visibility of the sharing. You pay per instance, based on runtime and resources allocated.
  • Dedicated hosts — you pay for the entire physical host, not per instance. It is not shared with any other AWS customer.

Everything lives in one Availability Zone

EC2 is an AZ-resilient service, which is a precise way of saying: an EC2 host runs inside exactly one AZ. If that AZ fails, every host in it — and every instance on those hosts — can fail or be heavily impacted. As a solutions architect, always assume this.

This AZ-locking runs through the entire stack:

  • Compute — the host itself is physically in one AZ.
  • Networking — when an instance is provisioned into a subnet, a primary elastic network interface (ENI) is created in that subnet, mapped to the host's physical hardware. Subnets themselves exist in exactly one AZ. An instance can have multiple ENIs, but all of them must be in the same AZ as the instance.
  • Persistent storage — Elastic Block Store (EBS) also runs per-AZ. A volume created in AZ-A is a wholly separate thing from the EBS service in AZ-B, and volumes can only attach to instances in the same AZ.
  • Local storage — hosts also offer local, host-attached instance store capacity. It's temporary: if the instance moves to a different host, that data is gone.
Exam tip
If an exam question mentions EC2, look for the Availability Zone detail — it's frequently the deciding factor. You can never attach an ENI or an EBS volume located in one AZ to an instance in another AZ. EC2 and EBS are both AZ-scoped services, full stop.

When does an instance move hosts?

An instance stays on the same physical host across a normal restart. It only moves to a different host (always within the same AZ) when:

  1. The host fails, or AWS takes it down for maintenance, or
  2. The instance is stopped and then started — not just rebooted.

Instances can never natively move between AZs. The only way to relocate an instance's effective location is to take a copy — a snapshot or AMI — and launch a brand-new instance in the target AZ, a topic covered later in this module.

Hosts generally run instances from a single type and generation, since a host is built around a specific CPU class, memory type, and storage configuration for a given generation of instance. Different instance types typically land on different physical hosts, even though a single host commonly runs many differently-sized instances from that same family, often belonging to different customers.

When should you reach for EC2?

EC2 is the default AWS compute service. Reach for it as your starting point and only move to something more specialized (Lambda, ECS, etc.) when you have a specific reason to. EC2 fits well when you need:

  • A traditional OS plus application, especially with vendor or internal support requirements tied to a specific runtime.
  • Long-running compute — unlike some AWS compute services with runtime limits, EC2 is built for persistent, 24/7 workloads.
  • Server-style applications that sit and wait for incoming connections.
  • Workloads with either bursty or steady-state load — EC2 offers instance types suited to both.
  • Monolithic application stacks with multiple traditional components (database, middleware, etc.).
  • Lift-and-shift migrations of existing VM-based workloads, or disaster recovery targets for on-premises virtual servers.

Why AZ-locking is a strength, not a limitation

Because the blast radius of any EC2 or EBS problem is always contained to a single AZ, you can design around it deliberately — deploying across multiple AZs and load balancing traffic between them to build highly available architectures.
