EC2 Basics

Instance Status Checks & Auto Recovery

Lesson 19 of 21 · ~7 min

Source: Adrian Cantrill SAA-C03 · EC2 Status Checks · EC2 Auto Recovery

Every EC2 instance is continuously evaluated by two independent status checks. Together they tell you whether a problem, if one exists, lives in AWS's infrastructure or inside your instance's own configuration — and that distinction determines how you fix it.

Two checks, two failure domains

When an instance first launches you'll typically see it move from initializing to 2/2 checks passed. Anything less than 2/2 on a running instance signals a problem, and which check failed tells you where to look.

CheckWhat it testsExample failure causes
System status checkThe underlying EC2 host / AWS infrastructureLoss of system power, loss of network connectivity, hardware or software issues on the physical host
Instance status checkThe instance's own operating system and configurationCorrupted file system, misconfigured networking (e.g. a public IPv4 address statically set inside the OS), kernel issues preventing boot
Exam tip
System check failure = AWS's problem (the host). Instance check failure = your problem (the guest OS/config). This distinction is exactly what exam questions probe — match the failure type to the failure domain before picking a remediation.

Resolving each type of failure

A system status check failure is typically resolved by stopping and starting the instance — since EC2 is EBS-backed and networked storage, a stop/start relocates the instance to different underlying hardware, sidestepping whatever hardware or power issue affected the original host. A simple reboot won't help here, since reboot keeps the instance on the same broken host.

An instance status check failure usually needs a fix at the OS or configuration level — a reboot, a manual repair, or in more serious cases a rebuild from a known-good AMI — because the underlying host is fine; it's the guest that's broken.

Automating the response: CloudWatch + Auto Recovery

Rather than watching the console and reacting manually, you can create a CloudWatch alarm on an instance's status checks. The alarm can notify you via SNS, and — critically — it can also trigger an automated action when either check fails for at least one evaluation period: reboot the instance, stop it, terminate it, or invoke EC2 Auto Recovery.

Auto Recovery moves the instance to a new, healthy host within the same Availability Zone and relaunches it with identical configuration — same private/public IP addressing, same instance ID — so any software configured to auto-start can bring the instance back to a working state with no human intervention. See EC2 Auto Recovery for the full mechanics and requirements.

Exam tip
Auto Recovery has real limits: it stays within the same AZ, so it does nothing for a full AZ outage; it needs spare host capacity to succeed; it only supports specific, modern instance families; and it does not work for instances using instance store volumes — only instances backed entirely by EBS.
  • System check fails → stop/start (moves to new hardware) or Auto Recovery.
  • Instance check fails → reboot or manual OS-level fix; the host itself is healthy.
  • Auto Recovery handles narrow, isolated host or instance failures — it is not a substitute for multi-AZ high availability.
