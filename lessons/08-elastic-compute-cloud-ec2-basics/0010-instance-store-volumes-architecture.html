EC2 Basics

Instance Store Volumes Architecture

Lesson 10 of 21 · ~10 min

Source: Adrian Cantrill SAA-C03 · Amazon EC2 Instance Store (AWS docs)

Instance store volumes are block storage devices too — an instance sees a raw block device, formats a file system on it, and applications use it exactly like EBS. The difference is where the physical disk lives: instance store volumes are physically attached to one specific EC2 host, not accessed over a network like EBS. That local attachment is the source of both their biggest advantage and their biggest risk.

Local, fast, and tied to the host

Because the storage is directly wired to the host's hardware rather than reached over a storage network, instance store delivers the highest raw storage performance available in AWS — well above what EBS, including provisioned IOPS SSD, can provide.

Instance store volumes are also included in the price of any instance type that offers them — it's use-it-or-lose-it capacity you're already paying for.

Exam tip
Instance store volumes can only be attached at launch time. Unlike EBS, you cannot add instance store volumes to a running instance after the fact — this exact restriction is a recurring exam question. If you skip attaching them at launch, that capacity is simply unavailable for the life of that instance.

Ephemeral by design

Each EC2 host has its own pool of physical devices, presented as instance store volumes to whichever instances happen to be running on that host. Multiple instances on the same host can each be allocated their own share of these local disks.

The critical property to internalize: instance store data is ephemeral. It does not survive:

  • Host migration — if the instance moves to different underlying hardware (which happens on stop/start, host maintenance, or an instance type change), it lands on a fresh host with blank, wiped instance store volumes. The old data is gone.
  • Instance stop/start — this is itself a form of host migration, so data is lost.
  • Instance type change — also causes a host migration, with the same data-loss consequence.
  • Hardware failure — if the underlying physical disk fails, any instance using it loses that data, with no automatic redundancy.
Exam tip
Treat instance store data as gone the moment an instance stops, changes type, or its host has any kind of failure. Never use it for anything requiring persistence — it's a performance trade, not a durability option. See the Amazon EC2 Instance Store guide for the authoritative list of which instance families include it and how it behaves across restarts.

How fast is "fast"?

The instructor cites illustrative, instance-family-specific figures from the time of the course — treat exact numbers as indicative rather than something to memorize precisely, and check current EC2 instance type specs for up-to-date figures:

Both figures comfortably exceed anything achievable with EBS, including the highest-end provisioned IOPS SSD volumes — that gap is the entire reason instance store exists as an option.

Instance store is a straightforward trade: you accept ephemeral, host-local, launch-time-only storage in exchange for the highest performance ceiling AWS offers. It's the right call when your application layer already handles durability itself (e.g. replicating across nodes, or the data is disposable scratch/cache space) — never when the volume itself is the only copy of important data.
