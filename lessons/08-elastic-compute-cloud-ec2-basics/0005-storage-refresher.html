Storage Refresher

Lesson 05 of 21 · ~10 min

Source: Adrian Cantrill SAA-C03 · Amazon EBS User Guide · Amazon EC2 Instance Store

Before diving into AWS-specific storage services, this lesson resets the core vocabulary you'll need. The exam consistently tests whether you can match a scenario to the right storage type — this lesson is the foundation for that judgment.

Attachment: direct vs. network

TermMeaningAWS equivalent
Direct/local attached storagePhysical disks connected directly to a deviceThe EC2 instance store — attached directly to the host
Network attached storageVolumes attached over the network (on-prem: iSCSI/Fibre Channel)Elastic Block Store (EBS)

Direct-attached storage is fast because it's physically local, but fragile: a disk failure, host failure, or the instance moving to a different host can all destroy the data. Network-attached storage is decoupled from the compute hardware, so it survives problems that affect the host.

Ephemeral vs. persistent

  • Ephemeral storage — temporary; not guaranteed to survive. The instance store is the canonical example.
  • Persistent storage — outlives the lifetime of the device it's attached to. EBS is the canonical AWS example.
Exam tip
"Which storage is ephemeral and which is persistent" is directly testable. Lock in: instance store = ephemeral, EBS = persistent.

Three categories of storage

CategoryStructureBootable?AWS example
Block storageA raw collection of addressable blocks; no inherent structure — the OS lays a file system on topYesEBS volumes, instance store
File storageA ready-made file system with folders, mounted over the networkNoManaged file system services
Object storageFlat collection of key/value objects with metadata; no folder hierarchyNoS3

Block storage is the only one of the three you can boot from — most EC2 instances boot from an EBS volume that stores the OS. File storage can typically be mounted into an OS's file system but never used to boot. Object storage is neither mountable in the traditional sense nor bootable, but it scales enormously — suited to workloads needing massive concurrent read/write access to discrete objects.

Rule of thumb: need to boot, or need low-level OS disk access? Use block storage. Need a shared folder structure across many clients? Use file storage. Need web-scale storage for arbitrary objects? Use object storage.

Measuring storage performance

Three interrelated terms describe storage performance:

  • I/O (block) size — the size of each unit of data written/read, in KB or MB.
  • IOPS — I/O operations per second the storage system can sustain (reads or writes).
  • Throughput — the rate of data transfer, typically in MB/s.

These aren't independent: throughput ≈ block size × IOPS. A storage system delivering 100 IOPS at a 16KB block size yields roughly 1.6 MB/s of throughput; the same 100 IOPS at 4KB chunks yields only 400 KB/s. Simply increasing block size doesn't guarantee proportionally higher throughput either — a system can have its own throughput ceiling, and IOPS achievable can actually drop as block size grows.

Performance is also only as good as the weakest link in the full chain: application → OS → storage subsystem → transport (network or local bus) → storage interface → physical drive technology. Any one of these can be the bottleneck.

Exam tip
Expect exam scenarios that specify a required IOPS or throughput level and ask you to pick the storage type that can deliver it. Pay close attention to the specific maximum IOPS and throughput ceilings called out for each AWS storage type in upcoming lessons — those numbers are exam-relevant.
