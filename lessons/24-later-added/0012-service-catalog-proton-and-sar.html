Service Catalog, Proton and the Serverless Application Repository

Lesson 12 of 23 · ~6 min

Source: What is Service Catalog? · What is AWS Proton? · What is the Serverless Application Repository?

The CloudFormation module showed how to describe infrastructure as templates. These three services answer the next question: how do you hand approved templates to other people, so they can deploy them safely without becoming CloudFormation experts or getting broad IAM permissions?

AWS Service Catalog: Approved Self-Service

Product
An IT service you want to offer, defined as a CloudFormation (or Terraform) template. For example, "a compliant S3 bucket" or "a standard three-tier web stack".
Portfolio
A collection of products, shared with IAM users, groups or roles, and with other accounts or the Organization.
Constraints
Rules on how a product can be launched. A launch constraint names an IAM role that Service Catalog uses to deploy the product. End users can launch the stack without having permissions to create the underlying resources themselves. Template constraints can limit choices such as instance types.

The result: administrators curate what's allowed, and end users get a self-service portal to launch it. That gives governance and consistency without anyone having to open a ticket.

AWS Proton: Retired

End of support: 7 October 2026
Proton let platform teams publish environment and service templates, so developers could deploy containerized and serverless apps with standard CI/CD. AWS ended support on 7 October 2026. The console and Proton resources are no longer accessible, but infrastructure it already deployed keeps running. It's still listed in the exam guide, so recognize it as "platform team templates for developers". Expect Service Catalog to be the safer answer.

Serverless Application Repository (SAR)

SAR is a managed repository for serverless applications packaged as AWS SAM templates. Publishers share applications privately (with specific accounts or an Organization) or publicly. Consumers find and deploy them from the Lambda console in a few clicks, configuring parameters and getting the Lambda functions, API Gateway APIs and other resources the template defines.

The launch constraint is the key
The most-tested idea here: "Users must deploy approved infrastructure but must not have permissions to create those resources directly." That's Service Catalog with a launch constraint role. Granting users broad CloudFormation and EC2 permissions breaks the requirement.
