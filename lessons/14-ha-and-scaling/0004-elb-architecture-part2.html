Elastic Load Balancer Architecture, Part 2

Lesson 04 of 12 · ~8 min

Source: Adrian Cantrill SAA-C03 · How Elastic Load Balancing Works

Continuing directly from Part 1: a full multi-tier worked example, then the single most commonly tested ELB architecture detail — cross-zone load balancing.

Decoupling Tiers with Load Balancers

Picture a three-tier app: web tier (Auto Scaling group behind an internet-facing ALB), application tier (Auto Scaling group behind an internal ALB), and a database tier. Without load balancers between tiers, everything is tightly coupled — a customer connects to one specific web instance, which talks to one specific application instance; if either fails or the tier scales, something breaks or has to be reconfigured.

Putting a load balancer between each tier loosens that coupling: the web tier only ever talks to the internal load balancer's DNS name, with zero awareness of how many application instances exist or which one it's actually reaching. This is what lets each tier scale independently — the application tier can grow from 2 to 4 instances under load with no reconfiguration required anywhere else in the stack.

Cross-Zone Load Balancing

Each AZ a load balancer uses gets its own node(s), and the DNS name spreads incoming requests evenly across nodes — with 2 nodes, each gets 50% of incoming connections, regardless of how many instances sit behind each node.

The historic problem
Originally, a load balancer node could only forward connections to instances in its own AZ. Picture 4 instances in AZ-A and 1 instance in AZ-B: the AZ-A node splits its 50% of traffic four ways (12.5% per instance), while the AZ-B node sends its entire 50% to the single instance there. That one instance ends up absorbing 4× the load of any instance in AZ-A — a badly uneven distribution, caused purely by uneven instance counts across AZs.

Cross-zone load balancing fixes this: every node can distribute connections to registered instances in any AZ, not just its own. With it enabled, that same 4-instances-in-A / 1-instance-in-B layout gets evenly split across all 5 instances, regardless of which node a connection initially landed on.

Exam tip
Cross-zone load balancing is enabled by default for Application Load Balancers today, but it was not enabled by default historically, and it's a very common way for exam questions to describe "uneven load distribution across instances" — the fix is enabling cross-zone load balancing, not adding more load balancers.

Architecture Recap

  • One load balancer object = multiple nodes, one (or more) per configured AZ subnet.
  • One DNS A record resolves to every active node, spreading load evenly across nodes.
  • Internet-facing vs. internal only changes node IP addressing (public+private vs. private-only) — nothing else.
  • An internet-facing load balancer can forward to public or private back-end instances — no public IP requirement on targets.
  • Minimum 8 free IPs per subnet (/28 technically works; AWS recommends /27 for scaling headroom).
  • Cross-zone load balancing (default-on for ALBs) spreads load evenly across instances, regardless of which AZ a node lives in.
