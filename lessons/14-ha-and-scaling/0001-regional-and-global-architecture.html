Regional and Global AWS Architecture

Lesson 01 of 12 · ~7 min

Source: Adrian Cantrill SAA-C03 · AWS Global Infrastructure Overview

A truly global application — think Netflix — isn't one giant system. It's a global layer that gets customers to the right place, wrapped around many independent regional applications, each a complete, self-contained deployment. This lesson introduces the mental model this whole module builds on: separate the global concerns from the regional ones, because almost every AWS service you'll study lives on one side of that line or the other.

Three Scales of Architecture

  • Single-Region — everything lives in one Region, no DR story.
  • Single-Region with DR — normal operation in one Region, with failover to a secondary Region if it fails.
  • Multi-Region, active everywhere — the application runs in multiple Regions simultaneously and needs to keep working through the failure of any one of them.

The Global Layer

Three jobs happen above any single Region:

  • Global service location and discovery — how a customer's device finds which Region to talk to. In AWS, this is Route 53: DNS with health checks, capable of directing customers to a primary Region, failing over to a secondary, or routing to whichever Region is closest/fastest.
  • Content delivery — getting content physically close to customers everywhere, rather than serving everything from one origin. In AWS, this is CloudFront, which can pull content from an origin like S3 and cache it at edge locations worldwide.
  • Global health checks and failover — detecting when infrastructure in one location is unhealthy and moving customers elsewhere — the mechanism that makes Route 53's failover/latency/geoproximity routing policies actually work at a global scale.
Exam tip
Very few AWS services are actually global — Route 53 and CloudFront are the standout examples in this architecture. Almost everything else you study from this point forward is regional, and the rest of this module (load balancers, Auto Scaling) operates entirely at that regional layer.

The Regional Layer: Tiers

Once traffic lands in a Region, think of the architecture as a stack of tiers — logical groupings of functionality:

TierTypical AWS services
Web tierApplication Load Balancer, API Gateway — the regional entry point, abstracting customers from the infrastructure behind it
Compute tierEC2, Lambda, ECS — does the actual work behind the web tier
Storage tierEBS, EFS, S3 — used by the compute tier; S3 also frequently serves as a CloudFront origin
Database tierRDS, Aurora, DynamoDB, Redshift
Caching layerElastiCache, DynamoDB Accelerator (DAX) — sits in front of the database tier so reads hit cheap, fast in-memory storage before ever reaching the (comparatively expensive) database
Application servicesKinesis, Step Functions, SQS, SNS — decoupling, messaging, and workflow features layered on top of the other tiers

Every tier can consume services from any other tier — that's the whole point of separating them. The web tier abstracts customers from the compute tier, so the compute tier can scale or fail without customers noticing; the caching layer sits between compute and the database tier so the (expensive, byte-for-byte) database is only consulted on a cache miss.
