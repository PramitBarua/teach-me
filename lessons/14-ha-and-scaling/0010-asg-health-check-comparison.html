ASG Health Checks: EC2 vs. ELB vs. Custom

Lesson 10 of 12 · ~5 min

Source: Adrian Cantrill SAA-C03 · Health Checks for Instances in an Auto Scaling Group

An ASG replaces any instance its health checks mark unhealthy. Which check it uses changes what "unhealthy" actually means.

TypeWhat counts as unhealthy
EC2 (default)Anything other than running — stopping, stopped, terminated, shutting down, or impaired (failing status checks)
ELBInstance must be both running and passing the load balancer's own health check
CustomAn external system explicitly marks instances healthy or unhealthy
Exam tip: why ELB checks matter
Application Load Balancer health checks are application-aware — they can request a specific page and pattern-match the response, not just confirm the instance is powered on. Switching an ASG from EC2 checks to ELB checks is how you catch an instance that's technically running but whose application has actually crashed.

The Health Check Grace Period

A configurable window — 300 seconds (5 minutes) by default — that must elapse after an instance launches before health checks start affecting it. This gives an instance time to boot, run its bootstrapping (user data, cfn-init, etc.), and start the application before it's judged.

A very real exam scenario: the replacement loop
If the grace period is too short for how long your instances actually take to bootstrap, health checks start failing before the application is even ready — the ASG terminates the "unhealthy" instance and launches a replacement, which fails the same check for the same reason, on repeat, indefinitely. Set the grace period to match (or exceed) your instance's real launch-to-ready time.
