Application Load Balancer vs. Network Load Balancer

Lesson 05 of 12 · ~10 min

Source: Adrian Cantrill SAA-C03 · Application Load Balancers · What Is a Network Load Balancer?

This is the decision the exam tests most directly in this module: given a scenario, pick ALB or NLB. The reliable approach — memorize the handful of situations that demand an NLB, and default to ALB for everything else.

Application Load Balancer: True Layer 7

ALBs listen only on HTTP or HTTPS — never raw TCP, UDP, or TLS directly — and because they're genuinely Layer 7, they can see and act on everything inside those protocols: content type, cookies, custom headers, and more.

HTTPS on an ALB always terminates there
Every HTTPS connection to an ALB is decrypted (terminated) on the load balancer — there's no way to pass an unbroken encrypted connection straight through to the instances. The ALB needs its own SSL certificate, and a fresh connection is made from the ALB to the instance. If a security team requires unbroken end-to-end encryption from client to instance, an ALB cannot deliver that — only an NLB with a TCP or TLS-passthrough listener can.

Because ALBs process more of the networking stack, they're slower than NLBs — but in exchange they can evaluate application-layer health checks (an actual HTTP request to a specific path), not just a network-level check.

Rules: Conditions and Actions

ALB listeners hold rules, evaluated in priority order, ending in a catch-all default rule. Each rule pairs a condition with an action:

  • Conditions — host header, HTTP header, HTTP method, path pattern, query string, source IP.
  • Actions — forward to a target group, redirect elsewhere, return a fixed HTTP response, or authenticate via OpenID/Cognito.

This is what lets one ALB serve multiple domains (host-based routing), give one specific corporate client's IP a different back end than everyone else, or redirect one domain to another — all from a single load balancer.

Network Load Balancer: Layer 4, Built for Speed

NLBs operate at Layer 4 — TCP, TLS, and UDP — with zero visibility into HTTP: no headers, no cookies, no HTTP-level session stickiness. In exchange, they're extremely fast: millions of requests per second, at roughly 25% of the latency of an ALB, because there's no upper-stack processing to do.

NLB-only capabilityWhy it matters
Static IP addressesCorporate clients can whitelist a fixed IP through their firewall
Unbroken TCP/TLS pass-throughThe only way to deliver true end-to-end encryption from client to instance
PrivateLinkNLBs are the mechanism used to expose a service to other VPCs via PrivateLink
Non-HTTP protocolsSMTP, SSH, custom game protocols, financial protocols — anything that isn't HTTP/HTTPS
The trade-off: dumb health checks
Because NLBs have no Layer 7 visibility, their health checks are limited to ICMP and basic TCP handshaking — they cannot verify that an application is actually functioning correctly, only that something is listening on the port.
Exam tip: memorize the NLB triggers, default to ALB
Pick NLB only if the scenario needs: unbroken end-to-end encryption, static IPs for whitelisting, absolute maximum performance (millions of req/s, lowest latency), a non-HTTP/HTTPS protocol, or PrivateLink. For everything else — anything HTTP/HTTPS where you want rich, application-aware routing — default to ALB.
