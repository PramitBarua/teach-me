HA & Scaling

Auto Scaling Groups

Lesson 07 of 12 · ~10 min

Source: Adrian Cantrill SAA-C03 · Auto Scaling Groups

An Auto Scaling group (ASG) has exactly one job: keep the number of running instances equal to the desired capacity, provisioning or terminating instances as needed. Along the way it can also deliver self-healing and, combined with a load balancer, true elastic architecture.

Min, Desired, Max

Every ASG has three core values, often written as a triple like 1, 2, 4 (min, desired, max):

  • Minimum size — the floor; the ASG never lets running instance count drop below this.
  • Desired capacity — the target the ASG actively maintains, always between min and max.
  • Maximum size — the ceiling; the ASG never exceeds this.

If desired capacity is 2 but only 1 instance is running, the ASG provisions one more. If desired capacity is 2 but 3 are running, it terminates one. This reconciliation is the ASG's entire reason for existing.

Where Instances Land

An ASG is linked to a VPC and a set of subnets within it — instances are provisioned into whichever subnets are configured, and AWS tries to keep the instance count even across Availability Zones where possible.

Scaling Methods

MethodHow it works
ManualYou directly adjust min/desired/max; no automation at all — useful for testing, urgent situations, or holding a fixed instance count as a cost-control measure
Scheduled scalingAdjusts desired capacity on a schedule — ideal for known traffic patterns (sale events, off-hours scale-in)
Dynamic scalingReacts to a live metric (CPU, memory, an SQS queue length, a custom app metric) — covered in depth next lesson

Self-Healing

ASGs monitor instance health (EC2 status checks by default) and automatically terminate and replace any unhealthy instance — the same happens if you terminate an instance manually. This works even in isolation from scaling.

Exam tip: the cheapest possible HA pattern
An ASG with min = desired = max = 1, spanning multiple subnets across multiple AZs, gives you simple, cheap, effective self-healing: if the single instance fails, it's automatically relaunched — potentially in a different AZ if the original one is unavailable. No load balancer, no complexity, just automatic recovery.

Integration with Load Balancers

Rather than statically registering instances with a target group, an ASG can be configured to automatically register newly launched instances with a load balancer's target group, and deregister them on termination. This is what actually delivers elasticity: a metric drives the ASG's desired capacity, the ASG adds or removes instances, and the load balancer transparently absorbs the change — customers, connecting only via the load balancer, never notice.

Health check source matters
An ASG can use EC2 status checks (the default) or switch to load balancer health checks, which are far richer for HTTP/HTTPS applications since they can check a specific page's response. But be deliberate about what the health check actually tests: a check against a static page won't catch a broken application, while a check that depends on a database will fail (and trigger mass instance replacement) if the database — not the instances — is the actual problem.

Scaling Processes: Suspend and Resume

Individual ASG behaviors can be independently suspended: Launch, Terminate, Add to Load Balancer, Alarm Notification, AZ Rebalance, Health Check, Replace Unhealthy, and Scheduled Actions. A single instance can also be set to Standby, exempting it from all ASG activity — useful for performing maintenance on one instance without the ASG interfering.

Exam tip: cost control
Auto Scaling groups themselves are free — you only pay for the resources they provision. A cooldown period (seconds after a scaling action before another can occur) prevents chaotic thrashing. Preferring more, smaller instances over fewer, larger ones gives finer-grained, more cost-effective scaling steps.
