SSL Offload and Session Stickiness

Lesson 11 of 12 · ~9 min

Source: Adrian Cantrill SAA-C03 · Sticky Sessions for Your Application Load Balancer

Two independent features, both frequently tested: how a load balancer handles encrypted connections, and how it can keep one user pinned to one back-end instance.

Three Ways to Handle SSL/TLS

ModeCertificate locationLoad balancer sees plaintext HTTP?Instance CPU overhead?
Bridging (ALB default)Load balancer and instancesYes — decrypted, then re-encrypted to the instanceYes — instances do crypto too
Pass-through (NLB, TCP listener)Instances onlyNo — encryption is never touchedYes — instances do all crypto
SSL offload (ALB/NLB, HTTP to instances)Load balancer onlyYes — instances only ever see HTTPNo — instances do no crypto

Bridging is the ALB's default mode: the client's HTTPS connection terminates on the load balancer (requiring a certificate there matching the app's domain), and the load balancer opens a new, separately-encrypted connection to the instance (which needs its own matching certificate too). The payoff is that the load balancer can see and act on plaintext HTTP — headers, cookies, paths — which is the entire reason ALBs default to this mode.

Bridging's real cost
Every back-end instance in bridging mode has to store a certificate and perform cryptographic operations — real CPU overhead at scale, plus the operational burden of keeping certificates in sync across every instance.

SSL pass-through is NLB-only: the load balancer (using a TCP listener) never decrypts anything — it just routes based on source/destination IP and port, leaving one unbroken encrypted tunnel from client all the way to the instance. AWS never sees the certificate at all here — you retain full control (even a CloudHSM appliance is an option). The cost: the load balancer can't make any decision based on HTTP content, since it never sees it.

SSL offload gets you the best of both administrative worlds for many use cases: HTTPS terminates on the load balancer (so it needs a certificate), but the connection to the instance is plain HTTP — no certificate, no crypto overhead, on any instance. The trade-off is that traffic between the load balancer and instances travels unencrypted across AWS's internal network.

Exam tip: match the mode to the requirement
Need the load balancer to inspect/act on HTTP content? → Bridging. Need truly unbroken end-to-end encryption with zero AWS visibility into the certificate? → Pass-through (NLB only). Want to remove crypto overhead from instances and don't mind plaintext inside AWS's network? → SSL offload.

Session Stickiness

Without stickiness, connections are load balanced fairly across all instances — fine for stateless apps (session state held externally, e.g. in DynamoDB), but a problem if session state lives on a specific instance: every time a user lands on a different instance, they'd appear logged out, cart emptied, etc.

Session stickiness, enabled per target group on an ALB, fixes this: on a user's first request, the load balancer issues a cookie (AWSALB) with a duration you set, anywhere from 1 second to 7 days. While that cookie is valid, every request from that user goes to the same back-end instance.

Two ways stickiness ends
A sticky session moves a user to a different instance only when the cookie expires, or the pinned instance fails — either way, they get a fresh cookie and a new instance assignment.
Exam tip: stickiness has a cost
Stickiness can cause uneven load — one heavy user is permanently pinned to one instance, regardless of that instance's actual load. The architecturally preferable fix is to make instances stateless (session data stored externally), which removes the need for stickiness entirely and lets the load balancer distribute fairly.
