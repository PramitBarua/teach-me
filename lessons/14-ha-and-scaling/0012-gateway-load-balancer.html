Gateway Load Balancer

Lesson 12 of 12 · ~9 min

Source: Adrian Cantrill SAA-C03 · What Is a Gateway Load Balancer?

The last member of the ELB family, and the most narrowly scoped: Gateway Load Balancer (GWLB) exists to run and scale third-party security appliances — firewalls, IDS/IPS, deep packet inspection — in front of your traffic, transparently.

The Problem It Solves

A single security appliance sitting inline with traffic works fine — until your application scales. Growing or shrinking application capacity means you need a matching number of security appliances, and manually keeping application and security capacity in lockstep is complex, fragile, and gets worse in multi-tenant setups. GWLB decouples the two: your application scales independently, and the security appliance fleet scales independently, with GWLB gluing them together.

The Two Components

  • GWLB endpoints — live in the VPC where traffic originates/is destined (e.g. your application VPC). Architecturally similar to a VPC interface endpoint, but with one critical extra capability: it can be the target of a route table entry, letting it sit directly in a traffic flow.
  • The Gateway Load Balancer itself — a Layer 3/4 device (like an NLB) that distributes packets across a fleet of EC2 instances running the actual security software.

Geneve: Keeping Packets Intact

The security appliances need to inspect packets exactly as sent — same source/destination IP and port — but the appliance fleet might live in an entirely different VPC with a conflicting IP range. GWLB solves this with Geneve, a tunneling protocol: original packets are encapsulated unaltered and sent through a tunnel to the appliance, inspected, and returned the same way. From the appliance's perspective it sees the true original packet; from the network's perspective, nothing about addressing had to change.

Exam tip: the one-word answer
If an exam question describes running third-party firewalls/IDS/IPS at scale, decoupled from application scaling, transparently in-line — that's a Gateway Load Balancer question. "Geneve" is the tunneling protocol keyword to associate with GWLB specifically.

What This Buys You

  • Horizontal scaling of the security appliance fleet, independent of the application.
  • Flow stickiness — one flow of traffic always uses the same appliance instance, which matters for appliances that track connection state.
  • Resilience — if one appliance instance fails, traffic simply moves to another.
Traffic flow, end to end
Client → Internet Gateway → (route table sends traffic matching the app's subnet to) → GWLB endpoint → GWLB (in the security VPC) → traffic Geneve-encapsulated, unaltered → security appliance inspects it → returned encapsulated → de-encapsulated at the GWLB → back through the endpoint → onward to the actual destination (e.g. an ALB, then the application). The return path retraces the same route in reverse. Despite all these hops, source/destination IP and port are preserved throughout — that's the entire point of Geneve encapsulation.

Architecturally, GWLB shares elements with NLB and ALB — including target groups — but its purpose is singular: scalable, resilient, transparent network security appliance placement.
