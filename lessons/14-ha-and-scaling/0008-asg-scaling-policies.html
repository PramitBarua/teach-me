Auto Scaling Group Scaling Policies

Lesson 08 of 12 · ~9 min

Source: Adrian Cantrill SAA-C03 · Dynamic Scaling for Amazon EC2 Auto Scaling

An ASG doesn't need any scaling policy to function — without one, min/desired/max are just static values you adjust manually. Scaling policies are what let an ASG react to real conditions automatically. There are three dynamic scaling types, each adjusting desired capacity in a different way.

Simple Scaling

A pair of static rules tied to an alarm — e.g. "if CPU > 50%, add 2 instances" and "if CPU < 50%, remove 2 instances." Whatever the size of the breach — 1% over, or 50% over — the same fixed amount is added or removed every time.

Step Scaling

Like simple scaling, but with tiered step adjustments based on how far the metric is from the target. Example: CPU 50–59% → no change; 60–69% → add 1; 70–79% → add 2; 80–100% → add 3 (and mirrored in reverse for scale-in). The more extreme the breach, the bigger the reaction — step scaling responds proportionally where simple scaling always reacts the same amount regardless of severity.

Exam tip: AWS recommends step over simple
Step scaling is almost always preferable to simple scaling because it can react proportionally to how severe a load spike is — a 1% breach and a 50% breach get treated very differently. Pick simple scaling only when the priority is pure simplicity over responsiveness.

Target Tracking

The most hands-off option: define a target value for a supported metric (e.g. "keep average CPU at 40%"), and the ASG calculates and applies whatever scaling is needed to hold that target — continuously, automatically. Supported metrics include average CPU utilization, average network in/out, and (specifically relevant when paired with an ALB) ALB request count per target.

Scaling Based on a Queue

A common worker-pool pattern: scale based on the approximate number of visible messages in an SQS queue — more messages, more workers; queue drains, capacity scales back down.

Cooldown

A configurable period (in seconds) after a scaling action completes, during which further scaling actions are held off. This prevents chaotic, rapid-fire scaling in response to a noisy metric, and avoids extra cost from instances that get billed for at least their minimum billable period regardless of actual usage duration.

Worked example: step scaling in practice
ASG with min=1, max=4, currently at 1 instance, 5% CPU. Load spikes to 100% CPU → step rule adds 3 instances → now at 4 (the max). CPU settles to 55% with 4 instances running → 55% falls in the "no change" band (50–59%) → nothing happens. Load drops to 5% CPU → step rule would remove 3, but the ASG can never go below min=1, so it drops to exactly 1. This is the mechanism: step rules propose an adjustment, but min/max always win.
