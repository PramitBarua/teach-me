Elastic Kubernetes Service (EKS) 101

Lesson 04 of 04 · ~8 min

Source: Adrian Cantrill SAA-C03 · Amazon EKS User Guide · Manage compute resources by using nodes

EKS (Elastic Kubernetes Service) is AWS's managed implementation of Kubernetes — the same open-source, cloud-agnostic Kubernetes you'd run anywhere, just extended to integrate with AWS. That's the whole pitch: if a team needs to avoid vendor lock-in, or already runs Kubernetes elsewhere, EKS lets them keep using it while AWS manages the hardest operational piece — the control plane.

This lesson assumes you already know Kubernetes fundamentals — pods, nodes, the control plane, etcd. It stays focused on what EKS specifically adds on top of that as an AWS product, deployed the normal way: within AWS itself. (Kubernetes can also run via EKS on Outposts, EKS Anywhere for on-premises clusters, or the fully open-source EKS Distro — worth knowing these exist, but out of scope here.)

What AWS Manages

The control plane — including etcd, Kubernetes' key-value store — is managed by AWS, scales with load, and is distributed across multiple Availability Zones. The product integrates with the rest of AWS the way you'd expect: ECR for image storage, Elastic Load Balancers wherever Kubernetes needs load-balancer functionality, IAM for security, and VPCs for networking.

Node Types

The control plane is always AWS-managed. What varies is how the nodes — where your pods actually run — are provisioned:

Node typeWho manages it
Self-managed nodesPlain EC2 instances in an Auto Scaling group; you provision, patch, and scale them, billed at normal EC2 rates
Managed node groupsStill EC2 under the hood, but AWS handles provisioning and lifecycle (creation, updates, termination)
FargateNo nodes at all — you define Fargate profiles and pods launch directly onto serverless capacity, same idea as ECS Fargate
Check compatibility before choosing
Requirements like Windows pods, GPU capability, Inferentia, Bottlerocket, Outposts, or Local Zones aren't supported uniformly across all three node types. Pick the node type based on what the workload actually needs, and verify support first — picking the wrong one has derailed real projects. See Manage compute resources by using nodes for the current capability matrix.

Storage

As in any Kubernetes cluster, storage is ephemeral by default. For persistent storage, EKS supports EBS, EFS, and FSx as storage providers.

Architecture: Two VPCs

A typical EKS deployment involves two separate VPCs:

  • An AWS-managed VPC, where the control plane runs, spread across multiple Availability Zones.
  • Your own customer-managed VPC, where EC2-based worker nodes are deployed (self-managed or managed node groups).

The kubelet running on each worker node talks to the control plane via elastic network interfaces injected into your VPC — the same cross-VPC-boundary pattern you saw with ECS Fargate tasks. A public control plane endpoint is also available for administration. Anything consuming the services running in the cluster does so via ingress configuration, originating from your own VPC.

Exam tip
If a scenario stresses avoiding vendor lock-in or an existing investment in Kubernetes, that phrasing points at EKS over plain ECS — even though ECS is the AWS-native option, EKS is the portable one.
