      Scenario 1

      A developer is reviewing an ECS task definition and wants to know specifically where the container image location and exposed ports are declared, as distinct from where CPU, memory, and IAM permissions live. Which object holds the image and ports?

      • A. The service definition
      • B. The container definition
      • C. The task role
      • D. The cluster

      Topic: ECS Concepts

      Correct answer: B

      • A. Wrong — a service definition wraps tasks for scaling and resilience; it doesn't declare an image or ports.
      • B. Correct — the container definition is the pointer to where the image lives and which ports it exposes; everything else (resources, IAM, networking) lives at the task definition level.
      • C. Wrong — the task role is an IAM role for AWS API calls, unrelated to image location or ports.
      • D. Wrong — a cluster is where tasks and services are deployed; it has no per-container configuration of its own.

      Scenario 2

      A container in a newly launched ECS task fails immediately, before the application even starts, with an error indicating the image could not be pulled from a private ECR repository. Which IAM role is most likely misconfigured?

      • A. The task execution role
      • B. The task role
      • C. A service-linked role for the Auto Scaling group
      • D. An IAM user attached to the container definition

      Topic: ECS Concepts

      Correct answer: A

      • A. Correct — the task execution role is assumed by the ECS agent itself, before your code runs, to pull the image from ECR and write logs; this failure mode points straight at it.
      • B. Wrong — the task role is what your application code uses after startup to call AWS services; it has no role in pulling the container image.
      • C. Wrong — Auto Scaling group service-linked roles govern EC2 host scaling, not ECS image pulls.
      • D. Wrong — container definitions don't carry IAM identities of their own; permissions are granted via the task's IAM roles.

      Scenario 3

      A running container's application code makes a call to read an object from S3, and the call fails with an access-denied error, even though the image pulled and started successfully and logs are shipping to CloudWatch normally. Which IAM role should be checked first?

      • A. The task execution role
      • B. A bucket policy on the ECS cluster itself
      • C. The task role
      • D. The container registry's IAM policy

      Topic: ECS Concepts

      Correct answer: C

      • A. Wrong — the task execution role only covers image pulls and log delivery, both of which are already working here; it isn't used for application-level AWS API calls.
      • B. Wrong — an ECS cluster isn't a principal that a bucket policy would reference for this kind of access; the identity making the call is the task itself.
      • C. Correct — the task role is assumed by application code inside the container for its own AWS API calls, such as reading from S3; that's the one to check when the app itself is denied access.
      • D. Wrong — a registry-level policy affects pulling images, not runtime S3 access from inside a running container.

      Scenario 4

      A team launches a single ECS task directly (not wrapped in a service) to run a business-critical, long-running process. The task later crashes under load, and nothing replaces it. What's the underlying reason?

      • A. A bare task has no built-in scaling or resilience; only a service definition provides restarts and multiple copies
      • B. The task execution role wasn't attached, so ECS couldn't relaunch the container
      • C. The cluster was running in Fargate mode, which doesn't support automatic restarts
      • D. The container definition was missing a health check configuration

      Topic: ECS Concepts

      Correct answer: A

      • A. Correct — a single task does not scale itself and is not highly available; if it dies, nothing replaces it. A service definition is what wraps tasks with restart handling, scaling, and load distribution.
      • B. Wrong — the task execution role governs image pulls and logging, not whether a dead task gets relaunched; that's a service-level responsibility regardless of role configuration.
      • C. Wrong — Fargate mode doesn't remove restart capability; the missing piece here is a service definition, independent of cluster mode.
      • D. Wrong — a missing health check would affect load balancer routing decisions, not the fundamental fact that a bare task has no replacement mechanism at all.

      Scenario 5

      An architect needs to specify how much CPU and memory a task consumes, which launch types (EC2 or Fargate) it's compatible with, and its networking mode. Where is this configured?

      • A. In the container definition
      • B. In the ECS cluster's settings
      • C. In the service definition
      • D. In the task definition

      Topic: ECS Concepts

      Correct answer: D

      • A. Wrong — the container definition scopes down to just the image and its ports; resource and launch-type settings live one level up.
      • B. Wrong — cluster settings apply broadly across the cluster; per-task CPU/memory/networking/launch-type compatibility is set per task definition, not per cluster.
      • C. Wrong — a service definition controls scaling and restart behavior for tasks, not the resource or compatibility settings of the task itself.
      • D. Correct — the task definition stores CPU and memory consumption, networking mode, compatible launch types, and the task role, alongside the container definitions it bundles.

      Scenario 6

      A task definition bundles a web server container and a companion database container that must always be scheduled and scaled together as one application unit. What is the correct way to model this?

      • A. One task definition holding both container definitions, since a task represents one application as a whole
      • B. Two separate task definitions, one per container, linked by a shared service definition
      • C. One container definition covering both containers, since they must always run together
      • D. Two clusters, one for the web container and one for the database container

      Topic: ECS Concepts

      Correct answer: A

      • A. Correct — a task definition represents one application as a whole and can bundle multiple container definitions, exactly the pairing described here.
      • B. Wrong — splitting them into separate task definitions breaks the "always scheduled together" requirement; a service can't force two independent tasks to co-locate.
      • C. Wrong — a container definition scopes to one container's image and ports; it can't hold two separate containers.
      • D. Wrong — splitting across two clusters doesn't achieve co-scheduling at all and adds unnecessary complexity for what a single task definition already handles.

      Scenario 7

      An ECS cluster's Auto Scaling group maintains 6 EC2 container instances at all times, but on a typical day only 2 of them have any tasks scheduled on them. What is the company being billed for?

      • A. Only the resource usage of the tasks actually running, since ECS is serverless by default
      • B. All 6 EC2 instances, whether or not tasks are scheduled on them
      • C. Only the 2 instances with tasks scheduled, since idle instances are automatically stopped
      • D. Nothing, since EC2-mode clusters are covered under the ECS service fee

      Topic: ECS Cluster Modes

      Correct answer: B

      • A. Wrong — this describes Fargate's billing model, not EC2 mode; EC2 mode is explicitly not a serverless mode.
      • B. Correct — in EC2 mode you pay for the EC2 instances backing the cluster whether or not anything is running on them; the Auto Scaling group's 6 instances are billed regardless of task placement.
      • C. Wrong — ECS doesn't automatically stop idle container instances in EC2 mode; sizing and scaling the hosts is the customer's responsibility.
      • D. Wrong — there's no such blanket ECS service fee that covers underlying EC2 instance costs; the EC2 instances are billed as ordinary EC2 usage.

      Scenario 8

      A task running on a Fargate-mode cluster needs to be reachable by other resources inside the same VPC, using standard VPC networking constructs like security groups. How does this actually work under the hood?

      • A. The task is confined to AWS's shared Fargate platform and is not reachable from the VPC at all
      • B. The task attaches as a secondary ENI on one of the cluster's EC2 container instances
      • C. The task is injected into the VPC with its own ENI and an IP address from the VPC's range
      • D. The task requires a NAT gateway to bridge it into the VPC's address space

      Topic: ECS Cluster Modes

      Correct answer: C

      • A. Wrong — Fargate tasks aren't isolated from the VPC; each one is injected directly into it with its own network presence.
      • B. Wrong — Fargate mode has no EC2 container instances at all, so there's no host to attach a secondary ENI to.
      • C. Correct — each Fargate task gets its own elastic network interface and IP address from the VPC, so it behaves like any other VPC resource for connectivity, including security groups.
      • D. Wrong — a NAT gateway handles outbound internet access for private resources; it has no role in giving a Fargate task a VPC network presence.

      Scenario 9

      A company runs a large, steady-state containerized workload, already holds EC2 Reserved Instances they want to keep using, and is comfortable managing host scaling and patching themselves in exchange for lower cost. Which ECS cluster mode fits best?

      • A. Fargate mode, since Reserved Instance pricing applies automatically to Fargate tasks
      • B. A "hybrid mode" that applies Reserved Instance discounts to Fargate billing
      • C. Plain EC2 with no ECS at all, since Reserved Instances make containers unnecessary
      • D. EC2 mode, so the existing Reserved Instances can back the cluster's container hosts

      Topic: ECS Cluster Modes

      Correct answer: D

      • A. Wrong — Fargate has no concept of host-level Reserved Instances; you can't apply existing RI capacity to it.
      • B. Wrong — no such hybrid billing mode exists; the real options are EC2 mode, Fargate mode, or mixing capacity providers, not RI discounts applied to Fargate.
      • C. Wrong — abandoning ECS gives up orchestration benefits the workload doesn't need to sacrifice; nothing about holding RIs requires dropping containers.
      • D. Correct — a large, consistent, price-conscious workload that already holds RIs and is willing to manage capacity is the classic case for EC2 mode, since it's plain EC2 underneath and can use existing Reserved Instance pricing.

      Scenario 10

      A team runs short, bursty batch jobs a few times a day and wants to avoid paying for any idle host capacity between runs. Which cluster mode minimizes cost for this pattern?

      • A. Fargate mode, since it bills purely for the container resources consumed, with no host cost ever
      • B. EC2 mode with an Auto Scaling group sized to zero between runs
      • C. EC2 mode using Reserved Instances to lower the idle-time cost
      • D. EC2 mode, since bursty workloads always run cheaper on owned hosts

      Topic: ECS Cluster Modes

      Correct answer: A

      • A. Correct — Fargate bills purely for container resources consumed with no host cost at all, making it the natural fit for small or bursty workloads that shouldn't pay for idle capacity.
      • B. Wrong — while scaling to zero reduces idle cost, it reintroduces cold-start delay and management overhead that Fargate avoids entirely by design.
      • C. Wrong — Reserved Instances still bill for the reserved capacity regardless of utilization, which doesn't solve idle-cost avoidance for bursty, infrequent jobs.
      • D. Wrong — EC2 mode's economics favor large, consistent workloads; bursty jobs are exactly the case Fargate's per-task billing is designed to fit better.

      Scenario 11

      A team wants one ECS cluster that can place some tasks on cost-optimized EC2 Spot capacity they already manage and other tasks on Fargate, without committing the whole cluster to a single mode. What does modern AWS documentation call the mechanism enabling this mix?

      • A. Capacity providers, which let a cluster mix EC2 and Fargate capacity rather than being locked to one mode
      • B. Cluster modes, since EC2 and Fargate modes can be toggled per task at runtime
      • C. Task execution roles, since they determine which capacity type a task lands on
      • D. Cross-account replication, extending capacity from a second account's cluster

      Topic: ECS Cluster Modes

      Correct answer: A

      • A. Correct — current AWS documentation describes launch types and capacity providers, letting a single cluster mix EC2 and Fargate capacity rather than being locked to one mode.
      • B. Wrong — "cluster modes" is the older framing where a cluster was locked to one mode; it doesn't describe today's per-task mixing capability.
      • C. Wrong — task execution roles govern IAM permissions for the agent, not which compute capacity a task is placed on.
      • D. Wrong — cross-account replication is an ECR concept for distributing container images, unrelated to mixing compute capacity within one cluster.

      Scenario 12

      A Fargate task is placed in a public subnet and assigned a public IP. A separate task, otherwise identical, is placed in a private subnet with no NAT gateway. What's true of their internet reachability?

      • A. Neither task can be reached from or reach the internet, since Fargate tasks are always isolated from the internet by default
      • B. Both tasks behave identically, since Fargate tasks ignore subnet routing entirely
      • C. The public-subnet task behaves like any internet-facing VPC resource; the private-subnet task has no path out without NAT
      • D. Only EC2-mode tasks are affected by subnet placement; Fargate tasks bypass subnet routing

      Topic: ECS Cluster Modes

      Correct answer: C

      • A. Wrong — a Fargate task in a public subnet with a public IP is reachable from the internet, just like any other public VPC resource; isolation isn't automatic.
      • B. Wrong — Fargate tasks are injected as real VPC resources and follow normal subnet routing rules, not some bypass mechanism.
      • C. Correct — once injected into the VPC, a task behaves like any other VPC resource: reachable from the internet if public-subnet-plus-public-IP, and without any outbound internet path if private-subnet with no NAT gateway.
      • D. Wrong — subnet placement and routing rules apply to Fargate tasks exactly as they would to any ENI in the VPC, EC2-mode or not.

      Scenario 13

      A repository in a private ECR registry already contains an image tagged "v1.2". A developer tries to push a new image using the exact same tag "v1.2" in the same repository. What happens?

      • A. The push succeeds and both images share the tag, distinguished only by push timestamp
      • B. The push is blocked, since tags must be unique within a repository — a tag identifies one specific image at a time
      • C. The push succeeds and creates a new, separate repository automatically
      • D. The push succeeds since tags are only required to be unique across the entire registry, not per repository

      Topic: Elastic Container Registry (ECR)

      Correct answer: B

      • A. Wrong — ECR doesn't support two images silently sharing one tag distinguished by timestamp; a tag must uniquely identify one image within its repository (typically the new push replaces what the tag points to).
      • B. Correct — tags must be unique within a repository; this is how a specific image version is identified and referenced within that repository.
      • C. Wrong — ECR doesn't auto-create a new repository to resolve a tag conflict; the push targets the repository specified.
      • D. Wrong — tag uniqueness is scoped to the repository, not the whole registry; this inverts the actual scoping rule.

      Scenario 14

      A company wants external partners to pull a container image without needing any AWS credentials, while still requiring IAM permission for anyone pushing new versions of that image. What registry configuration satisfies this?

      • A. A private registry, since it can be configured to allow anonymous reads on request
      • B. Enhanced scanning enabled on a private repository
      • C. Cross-account replication configured to each partner's AWS account
      • D. A public registry, which allows credential-free pulls but still gates pushes behind IAM permissions

      Topic: Elastic Container Registry (ECR)

      Correct answer: D

      • A. Wrong — a private registry requires IAM permissions for reads too; it has no "allow anonymous" toggle that turns it into a public registry.
      • B. Wrong — enhanced scanning affects vulnerability detection, not who can read from or write to the registry.
      • C. Wrong — cross-account replication copies images into accounts you control; it doesn't grant open, credential-free public access to outside partners.
      • D. Correct — a public ECR registry allows anyone to pull without credentials, while push access still always requires IAM permissions, exactly matching this asymmetric requirement.

      Scenario 15

      A security team requires continuous rescanning of container images for newly published CVEs, covering both the OS layer and programming-language-level packages inside the image, not just a one-time scan at push time. What should they enable?

      • A. Basic scanning, since it covers every vulnerability class by default
      • B. Enhanced scanning, which uses Amazon Inspector for continuous, layer-by-layer scans
      • C. Cross-Region replication, to duplicate the scan results in each destination Region
      • D. EventBridge rules configured to trigger a manual scan on every push

      Topic: Elastic Container Registry (ECR)

      Correct answer: B

      • A. Wrong — basic scanning checks against a CVE database on push or on demand, but doesn't continuously rescan or cover language-level packages.
      • B. Correct — enhanced scanning uses Amazon Inspector for continuous, layer-by-layer scanning of both the OS and language-level software packages, rescanning as new CVEs are published.
      • C. Wrong — cross-Region replication copies image data between Regions; it has no vulnerability-scanning capability of its own.
      • D. Wrong — EventBridge delivers events about registry activity for building workflows; it doesn't itself perform continuous vulnerability scanning.

      Scenario 16

      A team wants an automated workflow that kicks off an image-processing pipeline the moment a new image is pushed to an ECR repository, without polling the registry. What ECR-integrated capability enables this?

      • A. EventBridge events emitted on push/pull activity, which can trigger downstream workflows
      • B. Basic scanning results, polled on a fixed schedule
      • C. The public registry's anonymous read access
      • D. Cross-account replication settings on the repository

      Topic: Elastic Container Registry (ECR)

      Correct answer: A

      • A. Correct — ECR emits EventBridge events for pushes and pulls, letting an event-driven workflow react immediately without any polling.
      • B. Wrong — basic scanning results relate to vulnerability findings, not a general-purpose event trigger for downstream workflows, and polling defeats the "without polling" requirement anyway.
      • C. Wrong — public registry read access controls who can pull images; it has no relationship to triggering workflows on push.
      • D. Wrong — cross-account replication copies images to another account's registry; it isn't a general event/trigger mechanism for pipelines.

      Scenario 17

      A global company wants container images built in one Region and account to be automatically available closer to consumers in other Regions and in a separate subsidiary AWS account, without a manual push to each destination. What ECR feature addresses this?

      • A. Enhanced scanning, extended across every destination Region
      • B. A public registry shared across all accounts and Regions
      • C. Increasing the image tag limit on the source repository
      • D. Cross-Region and cross-account replication

      Topic: Elastic Container Registry (ECR)

      Correct answer: D

      • A. Wrong — enhanced scanning is a vulnerability-detection feature; it has nothing to do with distributing images across Regions or accounts.
      • B. Wrong — making the registry public would grant open access to anyone, going far beyond the subsidiary-account distribution need, and isn't the mechanism for automatic multi-Region distribution.
      • C. Wrong — tag limits govern how many tags an image can carry; they have no bearing on distributing images to other Regions or accounts.
      • D. Correct — ECR supports both cross-Region and cross-account replication, automatically distributing images closer to where they're consumed without manual re-pushing.

      Scenario 18

      A compliance team needs a complete audit trail of every API action taken against an ECR registry — who created a repository, who changed a repository policy, and when. Which AWS service provides this?

      • A. Basic scanning's vulnerability report
      • B. The registry's near real-time CloudWatch metrics
      • C. CloudTrail, which logs every API action against the registry
      • D. EventBridge, since it only stores the most recent event per repository

      Topic: Elastic Container Registry (ECR)

      Correct answer: C

      • A. Wrong — basic scanning reports on CVEs found in images, not on who took which API action against the registry.
      • B. Wrong — CloudWatch metrics track operational counts like pushes and pulls, not a detailed, attributable audit log of every API call.
      • C. Correct — CloudTrail logs every API action against the registry, giving the complete audit trail this compliance requirement calls for.
      • D. Wrong — EventBridge is for driving event-driven workflows in near real time, not for retaining a durable, queryable audit history, and it doesn't store "only the most recent event" as a limitation either.

      Scenario 19

      A team is choosing an EKS node type and wants to confirm one fact that holds true no matter which type they pick: self-managed nodes, managed node groups, or Fargate. Which statement is always true?

      • A. The customer-managed VPC hosting worker nodes is always created and configured by AWS
      • B. AWS always manages the control plane, including etcd, across multiple Availability Zones
      • C. EC2 instances always exist as worker nodes, regardless of node type
      • D. Fargate profiles are always required, even for self-managed nodes

      Topic: Elastic Kubernetes Service (EKS) 101

      Correct answer: B

      • A. Wrong — the customer-managed VPC, where worker nodes live, is created and configured by the customer, not AWS.
      • B. Correct — the control plane, including etcd, is always AWS-managed and distributed across multiple AZs, regardless of which node type backs the workers.
      • C. Wrong — Fargate node type removes EC2 instances entirely; pods launch directly onto serverless capacity with no nodes at all.
      • D. Wrong — Fargate profiles are only relevant when using the Fargate node type; self-managed nodes and managed node groups don't use them.

      Scenario 20

      A team wants to run Kubernetes pods on EKS without provisioning, patching, or scaling any EC2 instances themselves, while AWS still manages the control plane as it always does. Which node type fits?

      • A. Self-managed nodes, since they offer the most granular control
      • B. Managed node groups, since AWS fully replaces the underlying EC2 instances
      • C. EKS Anywhere, since it removes all infrastructure management
      • D. Fargate, since pods launch onto serverless capacity with no nodes to manage at all

      Topic: Elastic Kubernetes Service (EKS) 101

      Correct answer: D

      • A. Wrong — self-managed nodes require the team to provision, patch, and scale the EC2 instances themselves, the opposite of what's asked.
      • B. Wrong — managed node groups still run on real EC2 instances; AWS handles their lifecycle, but instances still exist and must be sized.
      • C. Wrong — EKS Anywhere is for running EKS on-premises or outside AWS; it doesn't describe a node type for an in-AWS EKS deployment.
      • D. Correct — Fargate removes nodes from the picture entirely; pods launch onto serverless capacity via Fargate profiles, with no instances to provision, patch, or scale.

      Scenario 21

      A stateful application on EKS writes files to local pod storage and expects that data to survive a pod restart. What should the architect know about default EKS storage behavior, and what's the fix?

      • A. Storage is persistent by default in EKS, so no changes are needed
      • B. Storage is ephemeral by default; persistent storage requires an external provider like EBS, EFS, or FSx
      • C. Storage persistence depends solely on which VPC the cluster uses
      • D. Persistent storage is only available when using self-managed nodes, not Fargate or managed node groups

      Topic: Elastic Kubernetes Service (EKS) 101

      Correct answer: B

      • A. Wrong — as in any Kubernetes cluster, storage is ephemeral by default; assuming otherwise would lose data on pod restart.
      • B. Correct — EKS storage is ephemeral by default, and persistent storage needs an external provider — EFS, EBS, or FSx are the supported options.
      • C. Wrong — persistence isn't a function of VPC choice; it depends on whether a persistent storage provider is configured for the pod.
      • D. Wrong — persistent storage providers aren't restricted to self-managed nodes; they're a Kubernetes-level storage concern independent of node type.

      Scenario 22

      In a typical EKS deployment, worker nodes running in a customer-managed VPC need to communicate with the AWS-managed control plane VPC. How does this cross-VPC communication actually happen?

      • A. Via VPC peering configured manually by the customer between the two VPCs
      • B. Via a Transit Gateway attachment created automatically at cluster launch
      • C. Via elastic network interfaces injected into the customer's VPC, which the kubelet uses to reach the control plane
      • D. Via a NAT gateway that translates all control-plane traffic through the public internet

      Topic: Elastic Kubernetes Service (EKS) 101

      Correct answer: C

      • A. Wrong — this cross-VPC connection is handled by AWS-managed ENIs, not a customer-configured VPC peering connection.
      • B. Wrong — EKS doesn't rely on a Transit Gateway attachment for control-plane-to-node communication; the actual mechanism is ENI injection.
      • C. Correct — the kubelet on each worker node talks to the control plane via elastic network interfaces injected into the customer's VPC, the same cross-VPC-boundary pattern used by ECS Fargate tasks.
      • D. Wrong — control-plane communication doesn't route through a NAT gateway over the public internet; it uses the injected ENIs, and a public endpoint is a separate, optional path for administration.

      Scenario 23

      A company already has significant investment in Kubernetes tooling and explicitly wants to avoid AWS vendor lock-in, while still deploying within AWS. Which container orchestration service best fits this stated priority, even though it isn't the more "AWS-native" option?

      • A. ECS in Fargate mode, since it requires the least operational overhead
      • B. ECS in EC2 mode, since it offers the most billing flexibility
      • C. EKS, since it runs standard, cloud-agnostic Kubernetes extended to integrate with AWS
      • D. AWS Batch, since it abstracts away the orchestration layer entirely

      Topic: Elastic Kubernetes Service (EKS) 101

      Correct answer: C

      • A. Wrong — ECS, in either mode, is an AWS-native orchestrator; it doesn't offer the portability an existing Kubernetes investment or lock-in concern calls for.
      • B. Wrong — like Fargate mode, EC2-mode ECS is still an AWS-proprietary orchestration model, not portable Kubernetes.
      • C. Correct — EKS runs the same open-source, cloud-agnostic Kubernetes usable anywhere, just extended to integrate with AWS; this is exactly the phrasing ("vendor lock-in," "existing Kubernetes investment") that points at EKS over ECS.
      • D. Wrong — AWS Batch is a job-scheduling service for batch computing workloads, not a Kubernetes-compatible orchestration platform.

      Scenario 24

      A workload requires Windows-based pods and GPU acceleration. Before selecting an EKS node type, what should the architect do?

      • A. Assume any node type supports both requirements, since EKS abstracts away hardware differences
      • B. Switch the control plane configuration to a Windows/GPU-optimized variant
      • C. Change the persistent storage provider to FSx, which unlocks Windows and GPU support
      • D. Check the current capability matrix, since support for Windows pods and GPUs isn't uniform across node types

      Topic: Elastic Kubernetes Service (EKS) 101

      Correct answer: D

      • A. Wrong — requirements like Windows pods, GPU capability, Inferentia, Bottlerocket, Outposts, or Local Zones aren't supported uniformly across all node types; assuming so has derailed real projects.
      • B. Wrong — the control plane runs the same way regardless of node type or workload requirements; that's not where Windows/GPU compatibility is decided.
      • C. Wrong — FSx is a storage provider addressing persistent file storage, unrelated to compute-level Windows pod or GPU support on a node type.
      • D. Correct — node type capability for things like Windows pods and GPUs varies and should be verified against the current capability matrix before choosing, since picking the wrong node type has derailed real projects.
