ECS Cluster Modes: EC2 vs Fargate

Lesson 02 of 04 · ~9 min

Source: Adrian Cantrill SAA-C03 · Amazon ECS Clusters · AWS Fargate

Both cluster modes share the same high-level ECS components — scheduling, orchestration, cluster management, and the placement engine that decides where a container runs. What differs is who manages the container hosts, and that difference drives cost, capacity planning, and when you'd pick one over the other.

EC2 Mode

An EC2-mode cluster lives inside a VPC in your account, spanning whichever Availability Zones that VPC uses. The container hosts are ordinary EC2 instances running the ECS agent — you'll see them in your account, you're billed for them, and you can even connect to them directly. Their count is controlled by an Auto Scaling group, sized to whatever initial capacity you specify.

The catch
You pay for these EC2 instances whether or not anything is running on them. ECS provisions the hosts, but capacity and availability planning is on you — this is explicitly not a serverless mode.

Because it's plain EC2 underneath, EC2 mode can use whatever pricing your business already has: Reserved Instances, Savings Plans, Spot pricing. That's the trade you're making — more admin overhead (sizing, patching, scaling the hosts) in exchange for more control over cost.

Fargate Mode

Fargate removes the host layer entirely. There are no EC2 instances to size, patch, or scale — AWS maintains a shared Fargate infrastructure platform behind the scenes, the same way EC2 itself isolates tenants on shared hardware. You still define tasks and services the same way — image, ports, CPU/memory — but those resources are allocated from the shared platform rather than onto hosts you manage.

A Fargate cluster still uses a VPC across multiple AZs, and here's the detail worth remembering: each running task is injected into your VPC with its own elastic network interface and an IP address from that VPC's range. From that point on, a task behaves like any other VPC resource — reachable from within the VPC, and from the public internet if it sits in a public subnet with a public IP.

Exam tip
With Fargate you pay purely for the container resources you consume — no host cost, ever, because there's no host to see. This is the single fastest way to distinguish an EC2-mode scenario from a Fargate-mode scenario in an exam question: does the question mention paying for idle capacity, or managing/patching instances? That's EC2 mode. Does it emphasize "no servers to manage" or per-task billing? That's Fargate.

Choosing Between Them

As a solutions architect you're really choosing between three options: run the app natively on EC2, run it containerized on ECS in EC2 mode, or run it containerized on ECS in Fargate mode. If a workload already uses containers, ECS beats plain EC2 — the question is just which cluster mode.

Favors EC2 modeFavors Fargate mode
Large, consistent workload, price-consciousSmall or bursty workloads — pay only for what runs
Business already holds RIs / Spot capacity to reuseBatch or periodic jobs — no idle host cost
Comfortable managing scaling, sizing, and faultsOverhead-averse, even at large scale
Modern terminology note
Current AWS documentation talks less about "cluster modes" and more about launch types and capacity providers — a cluster can mix EC2 and Fargate capacity providers rather than being locked to one mode. The underlying trade-off taught here is unchanged; see Amazon ECS clusters for the current model.
