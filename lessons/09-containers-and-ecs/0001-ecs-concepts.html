Containers & ECS

ECS Concepts

Lesson 01 of 04 · ~8 min

Source: Adrian Cantrill SAA-C03 · Amazon ECS Task Definitions

You've already built a container image and run it with Docker directly on an EC2 instance. That works, but it means you're managing the host, the engine, and the container yourself. ECS (Elastic Container Service) takes over the orchestration: you hand it a container image and instructions, and it decides where and how that container runs. ECS is to containers roughly what EC2 is to virtual machines.

ECS runs in one of two cluster modes — EC2 mode and Fargate mode — covered in the next lesson. This lesson stays one level up: the building blocks that apply to both modes.

From Image to Running Container

Working bottom-up, four concepts stack on top of each other:

Container definition
Points ECS at a container image stored on a registry — ECR (Amazon's own) or something external like Docker Hub — and declares which ports the container exposes. That's the associate-level scope: image + ports.
Task definition
Represents one application as a whole. A task definition bundles one or more container definitions — a simple app might be a single container, a more complex one might pair a web container with a database container. Alongside the container definitions, the task definition stores the CPU and memory the task consumes, its networking mode, which launch types (EC2 / Fargate) it's compatible with, and the task role (below).
Task
A running instance of a task definition. A single task does not scale itself and is not highly available — if it dies, nothing replaces it automatically.
Service (service definition)
Wraps one or more tasks to provide scaling and resilience: how many copies to run, restarting failed tasks, and distributing incoming load across copies via a load balancer. Anything long-running and business-critical is deployed as a service, not a bare task.

Creating a task definition in the console also creates a container definition alongside it, and a lot of real task definitions only ever hold one container — which is exactly why the two get confused. Keep them conceptually separate: the container definition is a pointer to an image and its ports; everything else — resources, networking, IAM, and the containers themselves — lives in the task definition.

The Task Role

The task definition specifies a task role — an IAM role the task assumes, giving every container inside that task temporary credentials to call AWS APIs. This is the best-practice way to give containerized code permissions, instead of baking credentials into the image or the host. This one comes up on the exam.

Exam tip: two roles, not one
ECS actually uses two separate IAM roles, and mixing them up is a classic exam trap:
  • Task role — assumed by your application code inside the container, for calls it makes to AWS services (e.g. reading from S3).
  • Task execution role — assumed by the ECS agent itself, before your code even runs, to pull the image from ECR and write logs to CloudWatch Logs.
See Task IAM role and Task execution IAM role. If a question describes a container that fails to pull its image or can't ship logs, that's an execution-role problem, not a task-role problem.

Putting It Together

You deploy tasks or services into an ECS cluster — the same top-level building blocks apply whether the cluster is EC2-based or Fargate-based. The next lesson covers the technical differences between those two modes.
