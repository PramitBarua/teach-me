Enhanced Networking and EBS-Optimized Instances

Lesson 08 of 08 · ~7 min

Source: Adrian Cantrill SAA-C03 · Enhanced Networking on Amazon EC2 · Amazon EBS-Optimized Instances

Two related performance features underpin everything in the previous lesson on placement groups — and matter broadly for EC2 performance in general.

Enhanced Networking (SR-IOV)

Without enhanced networking, a physical network interface card on an EC2 host has no awareness of virtualization. Every instance's virtual NIC talks back to the host, and the host itself has to mediate access to the single physical card in software — work that consumes host CPU and gets worse the busier the host is, leading to inconsistent latency and bandwidth.

Enhanced networking uses SR-IOV (Single Root I/O Virtualization) to fix this at the hardware level: the physical NIC itself becomes virtualization-aware, presenting multiple logical cards instead of one physical card the host must broker. Each instance gets exclusive access to its own logical card, communicating with it almost as if it had dedicated physical hardware — no host CPU mediation required.

BenefitWhy
Higher I/O, lower host CPUThe host is no longer in the data path brokering access
More bandwidthRemoving the host bottleneck lets networking scale further
Higher packets-per-second (PPS)Direct virtual-to-logical interface path, no host mediation per packet
Consistent low latencyHost CPU contention no longer introduces variable delay
Exam tip
Enhanced networking is free and enabled by default on most modern instance types — you don't need to know the implementation details for the exam, just that it exists and what it enables. It's also a prerequisite for the maximum performance numbers quoted for cluster placement groups.

EBS-Optimized Instances

EBS is block storage delivered over the network. Historically, that traffic shared the same network stack as an instance's regular data networking — meaning heavy storage I/O and heavy data traffic could contend with and slow down each other.

An EBS-optimized instance gets dedicated network capacity just for EBS traffic, separate from general data networking, so neither side starves the other. This matters most for volume types promising high, consistent performance — gp2/gp3 and io1/io2 — where the network path itself would otherwise become the bottleneck.

Mostly a non-issue today
On modern instance types, EBS optimization is enabled by default at no extra charge, and disabling it has no effect since the dedicated capacity is built into the hardware. Only on some older instance types is it optional and separately charged. Either way, for the exam: know it exists and what it does, not implementation specifics.
