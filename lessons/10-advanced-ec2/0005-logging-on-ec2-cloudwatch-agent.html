System and Application Logging on EC2

Lesson 05 of 08 · ~7 min

Source: Adrian Cantrill SAA-C03 · Installing the CloudWatch Agent

CloudWatch monitors EC2's external face — CPU utilization, network throughput, status checks. It has no native visibility into what's happening inside the operating system: memory usage per process, application logs, security logs. That inside view requires the CloudWatch agent, software that runs inside the instance itself.

What the Agent Needs

Three things have to be in place before the agent can do anything useful:

  • The agent installed on the instance's operating system.
  • Configuration telling the agent exactly which metrics and log files to capture and ship.
  • Permissions to actually call CloudWatch and CloudWatch Logs — delivered the best-practice way, via an IAM role attached to the instance (see the instance roles lesson), never long-term credentials baked in.

Log Groups and Log Streams

Once running, the agent ships data into CloudWatch Logs using a consistent mapping: one log group per log file you want captured, and inside each log group, one log stream per instance writing to that log. So three log files monitored across a fleet of instances means three log groups, each containing one stream per instance in that fleet.

Worked example
Monitoring Apache's access_log, error_log, and the OS-level /var/log/secure across a WordPress fleet produces three log groups (one per log file) — each holding one log stream per EC2 instance sending that particular log.

Configuring at Scale

For a single instance, you can install and configure the agent by hand. At fleet scale, that's not practical — the agent needs to be installed and configured identically across every instance, which is where automation (CloudFormation, or the bootstrapping techniques from earlier lessons) comes in. The agent also supports pulling its configuration from external sources, and one convenient option is storing that configuration as a parameter in SSM Parameter Store — tying directly back into the previous lesson, and giving you one consistent, centrally-managed configuration that every instance in the fleet can reference.
