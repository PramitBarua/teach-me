EC2 Bootstrapping with User Data

Lesson 01 of 08 · ~8 min

Source: Adrian Cantrill SAA-C03 · Amazon EC2 User Data

You've launched instances from an AMI and manually configured them afterward — installing WordPress by hand, command by command. Bootstrapping automates that step: instructions that run when an instance first launches, bringing it into a pre-configured state instead of a bare default one.

How User Data Works

EC2's implementation of bootstrapping is user data — injected into the instance the same way instance metadata is, and retrieved from the same special IP address, 169.254.169.254, just under the path latest/user-data instead of latest/meta-data. Whatever you pass in is executed by the instance's operating system as the root user.

Exam tip: once, at launch, only
User data runs exactly once — at the instance's first launch. Stop the instance, change the user data, and start it again, and the new data is not re-executed. User data is for launch-time configuration only, not ongoing configuration management.

EC2 Doesn't Understand What It's Running

This is the detail that matters most: EC2 treats user data as opaque. It doesn't validate it, interpret it, or care what it contains — it just hands the data to the operating system and lets a startup process execute it. If your script is well-formed, the instance ends up running and ready for service. If the script has an error, the instance is still running and still passes its status checks — but it's a bad configuration, silently broken from the outside.

Not secure, not unlimited
User data is readable by anyone with access to the instance's operating system — never use it to pass long-term credentials. It's also capped at 16 KB (raw, before base64 encoding); anything larger needs a script that downloads the rest.

Boot Time to Service Time

A recurring exam theme is how quickly an instance is ready to serve traffic after launch — the time AWS takes to provision it, plus any time needed for software installs or configuration afterward (post-launch time). For a stock AWS AMI, that's minutes. For an instance that needs an application installed and configured by hand, post-launch time can stretch to hours.

Three ways to shrink it, in increasing order of sophistication:

ApproachTrade-off
Bootstrapping (user data)Automates the post-launch steps, cutting the time they take, but they still run after launch
AMI bakingDo the work in advance, baked into the AMI — removes post-launch time entirely, but sacrifices runtime flexibility
Bake + bootstrap (optimal)Bake the time-intensive, static parts (e.g. the 90% of an install that never changes) into the AMI; bootstrap only the final, variable configuration

That combined approach — front-load what's slow and static, bootstrap what's fast and variable — comes up again later in the course when scaling and high availability are covered, since it directly affects how quickly a fleet can scale out under load.
