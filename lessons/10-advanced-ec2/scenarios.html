      Scenario 1

      A team stops a running EC2 instance, edits its user data to add a step that installs a monitoring agent, then starts the instance again. They expect the monitoring agent to be installed on this boot. What should they actually expect?

      • A. The new user data will not execute, since user data runs only once at the instance's initial launch
      • B. cfn-init will detect the metadata change and install the agent automatically on boot
      • C. The instance will merge the old and new user data scripts and run both in sequence
      • D. EC2 will reject the start request because user data content cannot be changed after launch

      Topic: EC2 Bootstrapping with User Data

      Correct answer: A

      • A. Correct — user data executes exactly once, at initial launch. A stop/start does not re-trigger it, so the edited script won't run.
      • B. Wrong — cfn-init's metadata-watching behavior is a CloudFormation-specific feature; this scenario describes plain user data with no cfn-init involved at all.
      • C. Wrong — EC2 treats user data as opaque and has no concept of merging or re-running scripts; it never re-executes after first launch.
      • D. Wrong — EC2 never validates or blocks changes to user data content; it simply won't be re-executed on this instance.

      Scenario 2

      A user data script has a subtle typo in a package name partway through installing a web application. After launch, the instance shows 2/2 status checks passed in the console. What does this tell an engineer about the application's install state?

      • A. The application definitely installed correctly, since status checks passed
      • B. The instance was automatically stopped once the script error was detected
      • C. Nothing about the application — status checks don't verify user data script success, only system reachability
      • D. CloudWatch automatically flagged the instance as misconfigured based on the script exit code

      Topic: EC2 Bootstrapping with User Data

      Correct answer: C

      • A. Wrong — EC2 treats user data as opaque and never validates its content; passing status checks says nothing about whether the script logically succeeded.
      • B. Wrong — EC2 has no mechanism to detect script errors inside user data and stop the instance because of them.
      • C. Correct — status checks verify system and instance reachability, not the outcome of a user data script; a broken install can still show a running, healthy-looking instance.
      • D. Wrong — CloudWatch has no built-in awareness of user data script exit codes without custom instrumentation, and none is described here.

      Scenario 3

      An architect needs to pass a database connection string into a new instance's user data script. Instance access is limited to a small ops team, but the architect is warned this method may not be appropriate for sensitive values. Why?

      • A. User data is readable by anyone with access to the instance's operating system, so it's unsuitable for long-term secrets
      • B. User data is limited to 1 KB, too small to hold a typical connection string
      • C. User data is automatically deleted before the instance finishes booting, breaking the script
      • D. User data can only contain binary data, not readable configuration strings

      Topic: EC2 Bootstrapping with User Data

      Correct answer: A

      • A. Correct — user data is not secure; anyone with OS-level access to the instance can read it, so it should never carry long-term credentials.
      • B. Wrong — the raw limit is 16 KB, not 1 KB, and size isn't the concern being raised here anyway.
      • C. Wrong — user data persists and is retrievable from the metadata service; it isn't deleted before boot completes.
      • D. Wrong — user data commonly holds plain-text scripts and strings; there's no binary-only restriction.

      Scenario 4

      A script inside user data needs to install a package that requires root privileges, and the operator is unsure whether to prefix commands with sudo. Under what privilege level does EC2 actually execute user data on Linux instances?

      • A. As the ec2-user account, requiring explicit sudo for privileged commands
      • B. As whatever IAM role is attached to the instance, translated into an OS user
      • C. As an unprivileged sandbox user with no filesystem write access
      • D. As the root user, so privileged commands run without needing sudo

      Topic: EC2 Bootstrapping with User Data

      Correct answer: D

      • A. Wrong — this describes typical interactive SSH access, not how user data itself executes at launch.
      • B. Wrong — IAM roles govern AWS API permissions delivered via metadata; they have no bearing on the OS user that executes user data.
      • C. Wrong — user data is not sandboxed or restricted; it has full access to the instance's operating system.
      • D. Correct — user data is executed by the operating system as the root user, so privileged commands run without needing sudo.

      Scenario 5

      A developer wants an application on an instance to programmatically read the user data that was supplied at launch, using the same retrieval mechanism the instance itself used during boot. Which endpoint and path should the application query?

      • A. A public S3 bucket URL where AWS temporarily stores each instance's user data
      • B. 169.254.169.254, under the latest/user-data path
      • C. 169.254.169.254, under the latest/meta-data path
      • D. A CloudFormation stack output exposed through the AWS Systems Manager console

      Topic: EC2 Bootstrapping with User Data

      Correct answer: B

      • A. Wrong — user data isn't delivered via an S3 bucket; it comes from the instance metadata service, the same as instance metadata itself.
      • B. Correct — user data is retrieved from the same special IP, 169.254.169.254, under the latest/user-data path rather than latest/meta-data.
      • C. Wrong — that path retrieves instance metadata (instance ID, IAM role credentials, etc.), not the user data that was supplied at launch.
      • D. Wrong — Systems Manager doesn't expose the raw user data payload through stack outputs; it isn't the retrieval mechanism used.

      Scenario 6

      A fleet installs a 2 GB application package that rarely changes, plus a handful of environment-specific settings that differ per launch. The current design bakes nothing and does everything through a single user data script every time an instance launches, resulting in very long post-launch times. What change would best reduce this?

      • A. Bake both the package and the environment-specific settings into one fixed AMI for every environment
      • B. Split the existing script into two separate user data scripts run on alternating launches
      • C. Bake the 2 GB package into a custom AMI and bootstrap only the small environment-specific settings
      • D. Increase the user data size limit so the script can run more efficiently

      Topic: EC2 Bootstrapping with User Data

      Correct answer: C

      • A. Wrong — baking everything, including the environment-specific settings, removes the flexibility needed since those settings vary per launch.
      • B. Wrong — user data has no built-in mechanism to run only on alternating launches, and this wouldn't reduce the per-launch install time anyway.
      • C. Correct — baking the large, static part into the AMI removes most post-launch time, while bootstrapping only the small variable configuration preserves flexibility. This is the optimal combined approach.
      • D. Wrong — the user data size limit (16 KB raw) is a fixed platform constraint that cannot be raised, and it isn't the bottleneck described here.

      Scenario 7

      An engineer wants an EC2 instance's Apache installation to always match a specific declared version — installing it if missing, upgrading it if outdated, and doing nothing if it's already correct — driven from within a CloudFormation template rather than a step-by-step script. Which tool is designed for this desired-state approach?

      • A. A CreationPolicy with a ResourceSignal timeout
      • B. A plain user data script run once at launch
      • C. An AWS Config managed rule for Apache compliance
      • D. cfn-init, using an AWS::CloudFormation::Init metadata block

      Topic: cfn-init and CreationPolicy

      Correct answer: D

      • A. Wrong — a CreationPolicy only governs whether CloudFormation waits for a success/failure signal during resource creation; it doesn't install or manage software state.
      • B. Wrong — plain user data is procedural, running a script once; it has no built-in desired-state logic to check and reconcile installed versions.
      • C. Wrong — AWS Config evaluates resource compliance against rules; it doesn't install, update, or manage software on an instance.
      • D. Correct — cfn-init reads a desired-state declaration from the AWS::CloudFormation::Init metadata block and reconciles the instance to match it, doing nothing if already compliant.

      Scenario 8

      A template defines an AWS::CloudFormation::Init block with the desired configuration for an instance. For cfn-init to actually run this configuration when the instance launches, what must the instance's user data contain?

      • A. A call invoking cfn-init with the stack, resource, and region, pointing it at the metadata to apply
      • B. The full desired-state configuration copied directly into the user data script
      • C. Nothing — cfn-init runs automatically without being referenced from user data
      • D. A CreationPolicy declaration embedded inline within the user data text

      Topic: cfn-init and CreationPolicy

      Correct answer: A

      • A. Correct — cfn-init is still invoked from user data, the same way user data always triggers bootstrapping; the line just tells cfn-init which stack, resource, and region to pull its real instructions from.
      • B. Wrong — the whole point of cfn-init is that the desired-state configuration lives in the template's metadata block, not duplicated into the user data script.
      • C. Wrong — cfn-init doesn't run on its own; it must be explicitly invoked, and user data is how that invocation happens.
      • D. Wrong — a CreationPolicy is a resource attribute in the template YAML/JSON, not something declared inside user data text.

      Scenario 9

      A running instance was originally configured by cfn-init. Later, the CloudFormation template is updated to require a newer application version, and the stack update completes successfully. The instance keeps running the old version with no further action. What configuration would have caused it to update automatically?

      • A. A larger CreationPolicy timeout so CloudFormation waits longer for the change
      • B. Increasing the user data size limit to accommodate the new version string
      • C. cfn-init configured to watch its resource's metadata for changes and reapply the desired state
      • D. Attaching a new IAM instance role granting the instance permission to self-update

      Topic: cfn-init and CreationPolicy

      Correct answer: C

      • A. Wrong — a CreationPolicy timeout only affects how long CloudFormation waits for a creation signal; it has no effect on whether running instances pick up later stack updates.
      • B. Wrong — the user data size limit is unrelated to whether configuration changes get reapplied after a stack update.
      • C. Correct — cfn-init can be configured to watch for metadata changes on its resource and reapply configuration whenever the stack updates, which plain user data cannot do at all.
      • D. Wrong — an IAM role grants API permissions; it doesn't cause cfn-init to re-check or reapply desired-state configuration on its own.

      Scenario 10

      A CloudFormation template launches an EC2 instance whose user data runs a bootstrapping script that silently fails partway through. No CreationPolicy is defined on the resource. What will the stack's final status be?

      • A. CREATE_FAILED, since CloudFormation inspects the user data script's outcome
      • B. The stack pauses indefinitely, waiting for a cfn-signal that will never arrive
      • C. CREATE_COMPLETE, because CloudFormation only tracks whether EC2 reported the instance provisioned
      • D. ROLLBACK_COMPLETE, as CloudFormation automatically reverts failed bootstrapping

      Topic: cfn-init and CreationPolicy

      Correct answer: C

      • A. Wrong — CloudFormation doesn't understand user data any better than EC2 does; it has no way to inspect whether the internal script succeeded.
      • B. Wrong — waiting for a signal only happens if a CreationPolicy with ResourceSignal is explicitly configured, which this resource lacks.
      • C. Correct — without a CreationPolicy, CloudFormation's naive process marks the resource complete as soon as EC2 reports the instance provisioned, regardless of bootstrapping success.
      • D. Wrong — CloudFormation has no mechanism to detect or roll back based on a bootstrapping script's internal failure when no signal-based policy exists.

      Scenario 11

      A resource defines CreationPolicy: ResourceSignal: Timeout: PT15M. cfn-init finishes and cfn-signal reports a failure exit code just 4 minutes into the launch. What does CloudFormation do?

      • A. Marks the resource failed immediately based on the reported signal, without waiting out the rest of the timeout
      • B. Waits the full 15 minutes before evaluating any signal that was received
      • C. Automatically retries cfn-init as many times as fit within the remaining timeout
      • D. Marks the resource CREATE_COMPLETE, since a signal of any kind was received

      Topic: cfn-init and CreationPolicy

      Correct answer: A

      • A. Correct — a received failure signal fails the resource right away; CloudFormation doesn't need to wait out the remaining timeout once it has an explicit result.
      • B. Wrong — the timeout is a maximum wait for a signal to arrive, not a mandatory delay once a signal has already been received.
      • C. Wrong — CloudFormation has no automatic retry behavior for cfn-init; the timeout only bounds how long it waits for a signal.
      • D. Wrong — the exit code carried by cfn-signal matters; a failure code moves the resource to a failed state, not CREATE_COMPLETE, even though a signal arrived.

      Scenario 12

      Beyond installing packages, a template's AWS::CloudFormation::Init block also needs to create an OS user, write a configuration file with specific ownership and permissions, and ensure a service is enabled at boot. Which tool covers all of this in one declarative configuration?

      • A. A CreationPolicy, which handles OS-level configuration during creation
      • B. Plain user data, run as several sequential shell commands
      • C. cfn-init, since it manages users, files, and services as part of its desired-state model
      • D. AWS Systems Manager Automation documents triggered post-launch

      Topic: cfn-init and CreationPolicy

      Correct answer: C

      • A. Wrong — a CreationPolicy only controls whether CloudFormation waits for a signal; it has no role in configuring the instance's operating system.
      • B. Wrong — user data can run shell commands procedurally, but it has none of cfn-init's declarative desired-state reconciliation for users, files, and services.
      • C. Correct — cfn-init can manage OS users and groups, write files with specific contents/permissions/ownership, and ensure services are started or enabled at boot, all from the same metadata block.
      • D. Wrong — this scenario's configuration is declared in the template's cfn-init metadata block, not driven through separate Systems Manager Automation documents.

      Scenario 13

      Using the AWS CLI, an engineer creates an IAM role for EC2 with an S3 read-only policy attached, then tries to launch an instance and attach that role directly by name. The launch fails, with nothing matching found to attach. What's missing?

      • A. A trust policy allowing the S3 service to assume the role
      • B. An instance profile wrapping the role, which the CLI does not auto-create
      • C. A set of long-term access keys generated for the role
      • D. A security group permitting the instance to reach IAM's API endpoint

      Topic: EC2 Instance Roles and Profiles

      Correct answer: B

      • A. Wrong — the role needs a trust policy allowing EC2 (not S3) to assume it, but that's a separate concern from why nothing exists to attach to the instance.
      • B. Correct — unlike the console, the CLI doesn't automatically create a matching instance profile; a role can't attach to an instance directly, so the profile must be created and the role added to it separately.
      • C. Wrong — instance roles use temporary STS credentials by design; generating long-term access keys is the exact bad practice this feature exists to avoid.
      • D. Wrong — security groups control network traffic, not whether an IAM role can be attached to an instance.

      Scenario 14

      A new hire created an IAM role for EC2 entirely through the console, attached it to an instance, and now insists they attached "a role" directly, with no separate object involved. What's actually true about what happened behind the scenes?

      • A. The console attached the role's underlying access keys directly to the instance's metadata
      • B. Roles genuinely attach directly to instances when created via the console, unlike the CLI
      • C. Nothing was attached until the instance made its first successful API call using the role
      • D. The console silently created a matching instance profile, and that profile is what's actually attached

      Topic: EC2 Instance Roles and Profiles

      Correct answer: D

      • A. Wrong — instance roles never involve long-term access keys attached to metadata; credentials are delivered as temporary STS tokens instead.
      • B. Wrong — the underlying mechanism is identical everywhere; a role can never attach to an instance directly, console included.
      • C. Wrong — the instance profile attachment happens at launch/attach time, not lazily on first API call.
      • D. Correct — creating a role through the console automatically creates an instance profile with the same name, hiding the distinction; the profile, not the role itself, is what attaches.

      Scenario 15

      An application on an EC2 instance has been calling the S3 API continuously for six hours using credentials obtained via its instance profile. The role has stayed attached the entire time and the app periodically re-reads its credentials. What is the state of its credentials right now?

      • A. They expired after the first hour and every subsequent call has failed
      • B. They downgraded to read-only automatically after a few hours of use
      • C. The application must call IAM directly each hour to request fresh credentials
      • D. They remain valid, since EC2 and STS coordinate to keep them renewed before expiry

      Topic: EC2 Instance Roles and Profiles

      Correct answer: D

      • A. Wrong — instance role credentials are temporary but continuously renewed automatically, so they don't simply expire and fail without intervention.
      • B. Wrong — the permissions a role's credentials carry stay scoped to its attached policy for as long as it's attached; they don't silently downgrade over time.
      • C. Wrong — renewal happens automatically in the background via metadata; the application isn't required to make explicit IAM renewal calls.
      • D. Correct — EC2 and STS continuously coordinate to renew instance role credentials before they expire, so as long as the role stays attached, valid credentials are always available via metadata.

      Scenario 16

      An instance is currently running with an instance profile granting read access to one S3 bucket. Operations now needs it to also write to a DynamoDB table, and wants to avoid relaunching the instance. What's the correct way to grant this?

      • A. Attach a second instance profile alongside the first one, one per required service
      • B. Update the permissions policy on the role behind the existing instance profile, or swap the attached instance profile for one wrapping a role with broader permissions
      • C. Embed a DynamoDB access key into the instance's user data for the new capability
      • D. Terminate and relaunch the instance, since attached instance profiles cannot change after launch

      Topic: EC2 Instance Roles and Profiles

      Correct answer: B

      • A. Wrong — an instance can only have one instance profile attached at a time; a second one can't be attached alongside the first.
      • B. Correct — you can either broaden the existing role's policy or replace the attached instance profile with a different one, all without relaunching the instance.
      • C. Wrong — embedding an access key reintroduces the exact long-term credential risk that instance roles are meant to eliminate.
      • D. Wrong — the attached instance profile on a running instance can be changed or swapped without needing to terminate and relaunch it.

      Scenario 17

      A security review finds an application on an EC2 instance calling AWS APIs using access keys hardcoded into its configuration file, even though the instance already has an instance profile attached with equivalent permissions. What should the reviewer recommend?

      • A. Rotate the hardcoded keys more frequently instead of removing them
      • B. Remove the hardcoded keys and let the application rely on the instance profile's temporary credentials
      • C. Move the hardcoded keys into the user data script instead of the config file
      • D. Keep both mechanisms active as a redundancy in case the instance profile is removed

      Topic: EC2 Instance Roles and Profiles

      Correct answer: B

      • A. Wrong — rotation reduces but doesn't eliminate the risk; hardcoded long-term keys remain bad practice regardless of rotation frequency.
      • B. Correct — storing access keys is explicitly bad practice; since an equivalent instance profile already exists, the application should use its self-renewing temporary credentials instead.
      • C. Wrong — user data is even less secure than a config file, being readable by anyone with OS access; this makes the exposure worse, not better.
      • D. Wrong — keeping both doesn't remove the risk the hardcoded keys pose; the recommendation is to eliminate long-term keys, not keep them as a backup.

      Scenario 18

      A CloudFormation template needs to create both an IAM role for an EC2 instance and whatever wrapper object is required to attach that role to the instance resource. Which two resource types must the template declare?

      • A. AWS::IAM::Role and a matching CreationPolicy on the instance resource
      • B. AWS::IAM::Role only — CloudFormation always auto-generates the profile like the console does
      • C. AWS::IAM::Role and AWS::IAM::InstanceProfile, referencing the role
      • D. AWS::IAM::Role and an AWS::IAM::Policy resource attached directly to the EC2 instance

      Topic: EC2 Instance Roles and Profiles

      Correct answer: C

      • A. Wrong — a CreationPolicy governs waiting for a creation signal; it has nothing to do with wrapping a role for attachment to an instance.
      • B. Wrong — the console's auto-creation behavior is a console convenience only; CloudFormation, like the CLI, requires the instance profile to be declared explicitly.
      • C. Correct — CloudFormation, like the CLI, needs both the role and a separate AWS::IAM::InstanceProfile resource that references it, since a role cannot attach to an instance directly.
      • D. Wrong — an IAM policy can be attached to a role, but there's no mechanism to attach a policy resource directly onto an EC2 instance in place of an instance profile.

      Scenario 19

      An application needs to store a database master password in Parameter Store such that only principals with both Parameter Store read access and the relevant KMS key permission can see the plaintext value. Which parameter type should it use?

      • A. String, with a resource-based policy restricting who can read it
      • B. StringList, so the password can be split across multiple encrypted segments
      • C. A hierarchical path parameter, since path scoping restricts visibility on its own
      • D. SecureString, encrypted using KMS

      Topic: SSM Parameter Store

      Correct answer: D

      • A. Wrong — a String parameter is stored in plain text; restricting read access alone doesn't add the KMS-based encryption this requirement calls for.
      • B. Wrong — StringList only stores a comma-separated plain-text list; it provides no encryption regardless of how the value is split.
      • C. Wrong — hierarchy is a naming convention for organizing and scoping IAM permissions, not a mechanism for encrypting a parameter's value.
      • D. Correct — SecureString parameters are encrypted via KMS, so reading the plaintext value requires both Parameter Store permission and the relevant CMK permission.

      Scenario 20

      A company stores parameters under paths like /dev-team-passwords/db and /prod-team-passwords/db. They want the dev team to read and write only under their own branch, with zero visibility into the prod branch. How should this be scoped?

      • A. Grant the dev team's IAM policy access scoped to the /dev-team-passwords/ path only
      • B. Make every parameter under both paths a SecureString to separate the teams
      • C. Move the prod parameters into a separate flat namespace with no path structure
      • D. Enable versioning on the dev team's parameters so older values aren't visible to prod

      Topic: SSM Parameter Store

      Correct answer: A

      • A. Correct — IAM permissions can be scoped to an individual parameter or to a whole branch of the path hierarchy, letting the dev team be restricted to just their own tree.
      • B. Wrong — SecureString controls whether a value is encrypted, not which team can see or access which parameter paths.
      • C. Wrong — removing path structure from prod doesn't scope dev's access; IAM policy scoping on the existing paths is what controls visibility.
      • D. Wrong — versioning tracks a parameter's value history over time; it has no effect on cross-team access boundaries.

      Scenario 21

      A CloudFormation template launches EC2 instances without a hardcoded AMI ID, yet it always resolves to the current recommended Amazon Linux AMI for whatever Region the stack is deployed in. What underlying mechanism makes this possible?

      • A. An instance role that queries the EC2 API for the newest AMI at boot time
      • B. A reference to an AWS-published public parameter in Parameter Store that resolves to the latest AMI ID
      • C. User data that selects an AMI after the instance has already launched
      • D. CloudFormation's built-in default AMI table, hardcoded into the service itself

      Topic: SSM Parameter Store

      Correct answer: B

      • A. Wrong — the AMI must already be selected before the instance can launch; an instance role only grants API permissions to an instance that already exists.
      • B. Correct — AWS publishes public parameters into Parameter Store, and templates can reference these to resolve the latest AMI ID for a given OS and Region at deploy time.
      • C. Wrong — the AMI choice determines what the instance boots from; it's fixed before launch and can't be selected retroactively via user data.
      • D. Wrong — CloudFormation has no privileged built-in AMI table; it resolves this dynamically through an explicit parameter lookup at deploy time.

      Scenario 22

      Several Lambda functions and EC2 instances across an account need to read configuration values from Parameter Store. The security team wants this done without distributing any long-term credentials. What's the recommended access pattern?

      • A. Distribute a shared IAM access key pair to all the Lambda functions and instances
      • B. Grant access to Parameter Store to those services and instances via IAM roles
      • C. Make every parameter public so no credentials are needed to read them
      • D. Embed each parameter's value directly into the Lambda deployment package instead

      Topic: SSM Parameter Store

      Correct answer: B

      • A. Wrong — distributing a shared long-term access key is exactly the practice IAM roles are meant to replace, and it's not how Parameter Store access is typically granted.
      • B. Correct — Parameter Store is fully IAM-integrated, and EC2 instances, Lambda functions, and other applications are typically granted access via an IAM role rather than long-term credentials.
      • C. Wrong — making parameters public removes access control entirely and isn't how Parameter Store's IAM integration is meant to be used.
      • D. Wrong — embedding values directly defeats the purpose of centralizing configuration in Parameter Store and loses versioning and access control.

      Scenario 23

      An application needs to store a list of allowed IP ranges as plain, unencrypted configuration in Parameter Store, with all values retrievable together as a single comma-separated entry. Which parameter type fits this need?

      • A. StringList, storing the plain-text comma-separated values
      • B. SecureString, since any list of values should default to encryption
      • C. A hierarchical parameter tree, with one path segment per IP range
      • D. String, split manually into several separately named parameters

      Topic: SSM Parameter Store

      Correct answer: A

      • A. Correct — StringList is designed exactly for this: a plain-text, comma-separated list of values retrieved together as one parameter.
      • B. Wrong — SecureString adds KMS encryption, which isn't needed here and isn't the defining feature that fits this "plain, single comma-separated entry" requirement.
      • C. Wrong — a path hierarchy organizes and scopes access to separate parameters; it doesn't produce one combined comma-separated value.
      • D. Wrong — this works but requires managing many separate parameters instead of the single StringList entry the requirement calls for.

      Scenario 24

      A parameter's value is updated in Parameter Store, and a team wants to both see the parameter's prior values over time and trigger a downstream Lambda function automatically whenever it changes. Which capabilities of Parameter Store make this possible?

      • A. SecureString encryption combined with a KMS key rotation schedule
      • B. A hierarchical path structure combined with scoped IAM permissions
      • C. The StringList type, which stores every historical value in one comma-separated entry
      • D. Built-in parameter versioning, plus change events that can drive other AWS services

      Topic: SSM Parameter Store

      Correct answer: D

      • A. Wrong — SecureString and KMS key rotation govern encryption of the value, not version history or the ability to trigger downstream events.
      • B. Wrong — path hierarchy and IAM scoping control organization and access, not historical values or event-driven integration.
      • C. Wrong — StringList stores a single comma-separated set of current values, not a history of past versions.
      • D. Correct — Parameter Store keeps versions of parameters as they change, just like S3, and parameter changes can generate events that drive other AWS services such as Lambda.

      Scenario 25

      Your team wants to alert when a specific process's memory usage on an EC2 instance crosses a threshold, using CloudWatch metrics without installing anything extra beyond what EC2 exposes by default. The ops lead insists no extra agent should be needed since "CloudWatch already monitors EC2 metrics." Is this achievable, and why or why not?

      • A. No — default EC2 metrics are external-facing (CPU, network, status checks); per-process memory requires the CloudWatch agent installed inside the OS.
      • B. Yes — enabling detailed 1-minute monitoring exposes all OS-level, per-process metrics automatically.
      • C. No — this needs AWS Systems Manager Inventory instead, since CloudWatch cannot process OS-level data under any configuration.
      • D. Yes — attaching an IAM role with CloudWatch full access permissions grants the console visibility into per-process memory.

      Topic: CloudWatch Agent for EC2 Logging

      Correct answer: A

      • A. Correct — CloudWatch's default EC2 metrics are external only; OS-level detail like per-process memory requires the CloudWatch agent running inside the instance.
      • B. Detailed monitoring changes the frequency of existing external metrics, not their scope — it never adds OS-level, per-process visibility.
      • C. SSM Inventory catalogs software/config data, not live per-process memory metrics — and the real fix is the CloudWatch agent, not switching services entirely.
      • D. Permissions alone don't create data — the agent still has to be installed and configured to collect and ship the metric in the first place.

      Scenario 26

      A fleet of 15 EC2 instances runs the CloudWatch agent, and each instance ships 4 distinct application log files to CloudWatch Logs. No custom stream naming or grouping deviates from the agent's default mapping. How many log groups and log streams should this fleet produce in total?

      • A. 15 log groups, each containing 4 log streams — one group per instance.
      • B. 4 log groups, each containing 15 log streams — one group per log file, one stream per instance.
      • C. 1 combined log group containing 60 merged log streams for simplicity.
      • D. 60 log groups, one for every unique combination of instance and log file.

      Topic: CloudWatch Agent for EC2 Logging

      Correct answer: B

      • A. This reverses the mapping — log groups map to log files, not to individual instances.
      • B. Correct — each distinct log file gets its own log group, and each instance sending that log gets its own stream within it: 4 groups × 15 streams.
      • C. A single shared group would lose the per-log-file separation the agent's mapping is designed to preserve.
      • D. The agent doesn't create a new group per instance-file pair — groups are per log file only, with streams handling the per-instance split.

      Scenario 27
