SSM Parameter Store

Lesson 04 of 08 · ~7 min

Source: Adrian Cantrill SAA-C03 · AWS Systems Manager Parameter Store

Passing secrets into an instance via user data is bad practice — anyone with instance access can read them. Parameter Store, part of Systems Manager, is the fix: a resilient, scalable place to store configuration strings, documents, and secrets, referenced by name instead of embedded in a script.

Parameter Types

TypeUse
StringPlain-text single value — connection strings, hostnames, ports, license codes
StringListPlain-text, comma-separated list of values
SecureStringCiphertext, encrypted via KMS — for passwords or anything sensitive

Encrypting a parameter as a SecureString means KMS permissions come into play too — whoever reads the parameter needs both Parameter Store and the relevant CMK permission.

Hierarchical Structure

Parameters can be flat (myDBpassword) or organized into a tree using path-style names, e.g. /wordpress/DBUser and /wordpress/DBPassword. Permissions can be granted on an individual parameter or on a whole branch of the tree — so a team could be scoped to just /dev-team-passwords/ without seeing anything else in the store. Just like S3, Parameter Store keeps versions of parameters as they change, and parameter changes can generate events that drive other AWS services.

Exam tip: public parameters
AWS itself publishes public parameters into Parameter Store — the reason a CloudFormation template can create an EC2 instance without you hardcoding an AMI ID: it looks up the latest AMI ID for a given OS/Region from a public parameter instead.

Access and Integration

Parameter Store is a public AWS service — anything using it needs to either be an AWS service or reach the public AWS endpoints, and it's fully IAM-integrated. EC2 instances, Lambda functions, and other applications can all be granted access, typically via an IAM role rather than long-term credentials — the same best practice covered in the previous lesson on instance roles.
