Enhanced Bootstrapping with cfn-init and Creation Policies

Lesson 02 of 08 · ~8 min

Source: Adrian Cantrill SAA-C03 · cfn-init · CreationPolicy Attribute

Plain user data is procedural — a script, run line by line, once. CloudFormation offers something more powerful for bootstrapping instances it creates: cfn-init, an AWS-provided helper script pre-installed on operating systems like Amazon Linux 2 that behaves less like a script and more like a lightweight configuration management system.

Desired State, Not Just Procedure

cfn-init can run commands procedurally like user data, but its real strength is desired state: you declare what you want to be true — "Apache version X installed" — and cfn-init figures out what to do. If Apache is already at that version, it does nothing. If it's missing or outdated, cfn-init installs or updates it. It can also manage OS users and groups, download and extract authenticated sources, write files with specific contents/permissions/ownership, run commands with post-condition checks, and ensure services are started or enabled at boot.

The desired state itself lives in the CloudFormation template, inside a special metadata block on the EC2 instance's logical resource: AWS::CloudFormation::Init. The cfn-init command is invoked from user data — so it's still triggered the same way user data always is — but instead of containing the configuration itself, that user data line just tells cfn-init which stack, resource, and region to pull its real instructions from:

/opt/aws/bin/cfn-init -v --stack ${AWS::StackId} --resource EC2Instance \
  --configsets wordpress_install --region ${AWS::Region}

CloudFormation substitutes the real stack ID and Region into that command before it ever reaches the instance, which is what lets cfn-init phone home to the right CloudFormation stack and retrieve its configuration.

Exam tip: cfn-init survives stack updates
User data only ever runs once, at launch — full stop. cfn-init can be configured to watch for metadata changes on its resource, and re-apply configuration whenever the stack is updated, moving the instance toward whatever the new desired state is. This is the single biggest practical advantage cfn-init has over plain user data.

Creation Policies and cfn-signal

Without anything extra, CloudFormation's resource-creation process is naive: it creates the EC2 instance, hands it user data (which might invoke cfn-init), and as soon as EC2 itself reports the instance provisioned, CloudFormation marks the resource complete — regardless of whether the bootstrapping inside that instance actually succeeded. CloudFormation doesn't understand user data any better than EC2 does.

A CreationPolicy fixes this by making CloudFormation wait for an explicit signal from inside the resource itself, instead of trusting EC2's "instance provisioned" status:

CreationPolicy:
  ResourceSignal:
    Timeout: PT15M

With this in place, CloudFormation holds the resource in a pending state until it receives a signal via cfn-signal — typically the last line of the user data, run right after cfn-init:

/opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackId} --resource EC2Instance --region ${AWS::Region}

-e $? captures the exit code of the previous command (cfn-init) and reports it as the signal. A success code moves the resource to CREATE_COMPLETE; a failure code — or no signal at all within the timeout — moves it to a failed/error state instead.

Scope
The transcript this lesson is based on notes that CreationPolicy/cfn-signal detail is slightly beyond core associate-level requirements, but understanding the architecture helps with any automation-flavored exam question. You won't be tested on writing the exact syntax.
