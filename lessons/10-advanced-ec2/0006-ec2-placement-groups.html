EC2 Placement Groups

Lesson 06 of 08 · ~10 min

Source: Adrian Cantrill SAA-C03 · Placement Groups for Your EC2 Instances

By default, AWS decides where an instance physically lands within an Availability Zone. A placement group lets you influence that decision — forcing instances either close together or deliberately apart, depending on whether you're chasing performance or resilience. There are three types, each solving a different problem.

Cluster Placement Groups: Maximum Performance

Cluster placement groups pack instances tightly — typically the same rack, often the same physical host — inside a single Availability Zone. You don't choose the AZ up front; it's locked in by wherever the first instance you launch into the group actually lands.

The payoff: instances in the same cluster placement group get direct, fast connections to each other, achieving 10 Gbps single-stream transfer (versus the usual 5 Gbps), plus the lowest latency and highest packets-per-second possible in AWS. Getting these numbers requires instance types with high-performance networking and enhanced networking enabled — covered in the next lesson.

The cost of that performance
All that physical closeness means almost no resilience — a single hardware failure can take out every instance in the group. Best practice is to launch all instances in the group at the same time and of the same instance type, so AWS reserves capacity for everything you need up front.

Spread Placement Groups: Maximum Isolation

Spread placement groups do the opposite: each instance lands on separate, isolated hardware — its own rack, own network, own power source — so a single rack failure can't take out more than one instance. Unlike cluster groups, spread groups can span multiple Availability Zones.

Exam tip: the hard limit
Spread placement groups are capped at 7 instances per Availability Zone — because each instance needs its own isolated rack, and that's a finite resource. Use cases: a small number of critical instances that must never share a failure domain, e.g. domain controllers or file server mirrors. Dedicated Hosts/Instances aren't supported in spread placement groups.

Partition Placement Groups: Isolation at Scale

Partition placement groups solve the problem spread groups can't: what if you need more than 7 isolated instances per AZ? A partition group divides its capacity into partitions (max 7 per AZ), each with its own isolated rack — no sharing of hardware between partitions — but you can put as many instances as you like into each partition, and you choose which partition an instance lands in (or let EC2 decide).

SpreadPartition
Instance cap7 per AZ, one per rack, no exceptions7 partitions per AZ, unlimited instances per partition
Isolation controlFully automatic — always isolatedYou (or your app) choose the grouping
Best forA handful of critical, independent instancesLarge distributed systems that are topology-aware

The real value shows up with topology-aware distributed applications — HDFS, HBase, Cassandra — which can query which partition each instance belongs to and use that to make intelligent replication decisions. A 75-instance application replicating data 3 ways can deliberately spread each replica across a different partition, guaranteeing that losing one partition's hardware never takes out more than one copy of any given piece of data. Without partition awareness, all 75 instances could theoretically share hardware, and resilience would be down to luck.

Exam tip: spread vs. partition, in one line
Spread guarantees isolation automatically but caps you at 7 instances per AZ. Partition trades that automatic guarantee for scale — you (or a topology-aware app) manage which partition instances land in, but there's no hard cap on total instance count, only on the number of partitions (7 per AZ).
