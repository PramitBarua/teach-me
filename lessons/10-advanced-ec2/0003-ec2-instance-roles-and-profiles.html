EC2 Instance Roles and Profiles

Lesson 03 of 08 · ~6 min

Source: Adrian Cantrill SAA-C03 · IAM Roles for Amazon EC2

IAM roles are the best-practice way for AWS services to gain permissions on your behalf. An EC2 instance role is that same idea applied to EC2: an IAM role the EC2 service can assume, so that anything running inside the instance inherits whatever permissions the role's policy grants — no long-term credentials required.

Role, Profile, Instance: Three Distinct Things

The architecture has one layer of indirection that's easy to miss. An IAM role has a permissions policy attached to it — assuming it generates temporary credentials with that policy's permissions. But a role can't attach to an EC2 instance directly. The thing that actually attaches is an instance profile — a thin wrapper around the role that's the real mechanism for getting the role's credentials into the instance.

Exam tip: the console hides this from you
Create a role through the IAM console and it automatically creates an instance profile with the same name — so it looks like you're attaching a role directly to an instance. You're not; you're attaching the instance profile. Using the CLI or CloudFormation, you must create the role and the instance profile as two separate resources. This distinction is a known exam trap.

How Credentials Reach the Instance

Once an instance profile is attached, temporary security credentials are delivered via instance metadata — specifically under the IAM tree, in a security-credentials path named for the role. Any application on the instance can read that metadata path and use the credentials to call AWS APIs, the same way the AWS CLI does automatically when it finds instance role credentials available.

The standout feature of this delivery mechanism: EC2 and the Security Token Service continuously coordinate to keep these credentials renewed before they expire. As long as the instance role stays attached and your application re-checks the metadata periodically, it never ends up holding expired credentials.

Always prefer roles over long-term credentials
Storing access keys inside an EC2 instance — or anywhere else long-term, like a laptop — is explicitly bad practice. Instance roles remove the need entirely: no keys to leak, rotate, or manage, since the credentials are temporary and self-renewing for as long as the role is attached.
