AWS Lambda, Part 1: Functions, Runtimes, and Resources

Lesson 03 of 22 · ~9 min

Source: Adrian Cantrill SAA-C03 · Configuring AWS Lambda Functions · Configure Lambda Function Memory

AWS Lambda is a Function-as-a-Service (FaaS) product: you provide short-running, focused code, Lambda runs it, and you're billed only for the time it actually executes. That last part is the whole point — no idle capacity, no always-on server.

Functions and Runtimes

A Lambda function is more than code — it's the code (a deployment package) plus its configuration: the runtime it uses (a specific language and version, e.g. Python 3.12), the resources allocated, and any environment variables. When a function is invoked, Lambda downloads and executes the deployment package inside a purpose-built runtime environment.

Supported runtimes span multiple versions of Python, Node.js, Java, Ruby, Go, and C#. Community and custom runtimes — built via Lambda layers — extend this to other languages such as Rust.

"Docker" and Lambda container images are not the same thing
For the exam, if you hear the bare term Docker, read it as traditional containerized compute (e.g. ECS) — not Lambda. Lambda does support deploying functions as container images, reusing your existing image-build tooling, but the resulting image is built specifically to run inside the Lambda execution environment. Treat "Docker" and "Lambda container images" as related but distinct concepts.

Memory, CPU, and Ephemeral Storage

You directly set a function's memory, from 128 MB up to 10,240 MB. CPU is not chosen directly — it scales proportionally with memory, so more memory always means more compute, never the reverse.

ResourceRange / behavior
Memory128 MB – 10,240 MB, adjustable in 1 MB steps
vCPUScales with memory automatically; roughly one full vCPU at 1,769 MB
/tmp storage512 MB by default, configurable up to 10,240 MB — treat as temporary only
TimeoutUp to 900 seconds (15 minutes) maximum per invocation
Exam tip: the 15-minute ceiling is non-negotiable
A single Lambda invocation can run for at most 900 seconds (15 minutes). There is no way to extend this for one invocation — workloads that genuinely need longer must be broken up, commonly orchestrated with Step Functions. Seeing "must run for 20+ minutes in one execution" in a scenario should immediately rule out plain Lambda.

Statelessness

By default, assume every invocation gets a brand-new, clean runtime environment — nothing persists between invocations. This is a design requirement: your code must work correctly even when it has no memory of anything that happened before. (Lambda Part 3 covers the nuance — environments can sometimes be reused — but never design code that depends on that.)

Execution Role

Every function's permissions to interact with other AWS services come from its execution role — an IAM role that Lambda assumes on the function's behalf. No execution role, no access to anything beyond the function's own compute.

Common Lambda Use Cases

  • Serverless web apps — typically S3 + API Gateway + Lambda together.
  • File processing — an S3 event (e.g. an upload) invokes a Lambda function, such as watermarking an image, billed only for the processing time.
  • Database triggers — DynamoDB Streams invoking Lambda on insert/modify/delete.
  • Serverless cron — EventBridge (or CloudWatch Events) invoking Lambda on a schedule, with no server sitting idle between runs.
  • Real-time stream processing — Lambda scaling with data arriving on a Kinesis stream.
