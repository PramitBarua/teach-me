Serverless & Application Services

Architecture Deep Dive, Part 1: Monolith to Tiered

Lesson 01 of 22 · ~8 min

Source: Adrian Cantrill SAA-C03 · Implementing Microservices on AWS

Before touching a single serverless AWS service, you need a mental model for how application architectures evolve — because the exam expects you to recognize why a design moved from one stage to the next, not just name the stages. Picture "CatTube," a video-sharing site: users upload videos, the platform processes them into multiple resolutions, and a store and manage component handles playback, playlists, and the database.

Stage 1: The Monolith

A monolithic architecture puts every component — upload, processing, store and manage — inside one single deployable unit, one codebase, typically one server. It's the simplest thing to build, but it has three defining weaknesses:

  • Fails together. Because everything shares one runtime, a fault in any one component can take down the whole application, even though the components are logically separate.
  • Scales together. Components are tightly coupled to the same hardware, so the usual fix is vertical scaling of the entire monolith — you can't give the processing component more power without upgrading everything.
  • Bills together. All components run continuously whether or not they're doing work. Capacity has to be provisioned for peak load on every component, all the time — the least cost-efficient shape available.

Stage 2: Tiered Architecture

Splitting the monolith into separate tiers — upload, processing, store and manage — each potentially on its own server, is the first evolution. This is the same move you saw earlier in the course when the WordPress database was pulled out onto its own RDS instance while the web tier stayed on EC2.

The immediate win: each tier can now be vertically scaled independently. If processing needs more CPU, only the processing tier grows. But the tiers still talk to each other directly, instance to instance, which is fragile and doesn't scale well.

Adding Load Balancers Between Tiers

Placing an (often internal) load balancer between tiers removes the dependency on any one specific instance. The upload tier now talks to the processing tier as a whole via its load balancer, not to a named instance — enabling:

  • Horizontal scaling — add more processing instances behind the load balancer with zero visibility required from the tiers calling it.
  • High availability — an unhealthy instance is simply removed from rotation; the load balancer redistributes traffic to the rest.
Load balancers fix scaling, not coupling
Even with a load balancer in front of it, the processing tier still has to exist and respond — the upload tier makes a synchronous call and waits for an answer. Two problems remain: if processing is completely down, uploads fail too; and because the call is synchronous, the processing tier can never scale down to zero — something has to always be listening, or the next upload request fails immediately.
Exam tip: know what each evolution actually fixes
Monolith → tiered fixes independent vertical scaling. Tiered → load-balanced fixes horizontal scaling and availability. Neither fixes coupling — that requires decoupling the tiers with something asynchronous, which is exactly where the next lesson picks up.

MonolithVertical, whole systemFully coupledAlways-on for everything

1. A team runs a single-codebase application where a bug in the video-processing component crashes the entire system, including unrelated upload and playback features. Which architecture are they describing?

2. A company splits its monolith into upload, processing, and storage tiers on separate EC2 instances, but each tier still connects directly to a specific instance of the next tier. What is the main limitation that remains?

3. An architecture places an internal load balancer between the upload tier and a horizontally-scaled processing tier. The upload tier still makes a synchronous call and waits for a response. What problem does this design still have?
