Amazon MQ 101

Lesson 21 of 22 · ~9 min

Source: Adrian Cantrill SAA-C03 · What Is Amazon MQ? · Using Amazon MQ for RabbitMQ

Amazon MQ sits in an odd spot: conceptually it's "SNS and SQS merged together," but built on open standards instead of AWS-native APIs. Understanding why it exists is more useful for the exam than any deep operational detail.

Why Not Just Use SNS and SQS?

SNS gives you topics (one-to-many), SQS gives you queues (one-to-one, decoupling application components). Both are public AWS services — reachable from anywhere with network connectivity — highly scalable, and tightly integrated with the rest of AWS. For anything built natively on AWS, they're the right default.

The problem shows up when an organization already runs an on-premises messaging or queuing system built on industry standards — the JMS API, or protocols like AMQP, MQTT, OpenWire, or STOMP. SNS and SQS don't speak those protocols, so migrating without rewriting the application isn't possible.

Amazon MQ: A Standards-Compliant Managed Broker

Amazon MQ is a managed message broker service, built on managed implementations of Apache ActiveMQ and RabbitMQ. Because it speaks JMS, AMQP, MQTT, OpenWire, and STOMP, an existing standards-based system can move onto it with little to no application-code change. Unlike SNS/SQS, a single MQ deployment provides both queues and topics.

Update: RabbitMQ, not just ActiveMQ
The source lecture describes Amazon MQ purely in terms of ActiveMQ. AWS has since added RabbitMQ as a second supported broker engine — so for a system built on RabbitMQ specifically, Amazon MQ is still the answer, not just for ActiveMQ-based systems.

"Managed" here means something different than for SNS/SQS: you're provisioned actual broker instances — either a single instance (cheaper, fine for dev/test) or a highly available active/standby pair (for production), typically backed by shared storage replicated across Availability Zones.

The detail exam questions hinge on
Amazon MQ is not a public service — it runs inside a VPC. Anything that needs to reach it, including an on-premises system, needs private network connectivity: a VPN or Direct Connect. It also has no native integration with other AWS services the way SNS/SQS do — services that expect to talk to SNS/SQS won't talk to MQ instead.

The decision rule: default to SNS/SQS for anything new that benefits from native AWS integration. Reach for Amazon MQ only when migrating (or coexisting with) an existing messaging system that needs its application code left alone — and remember to plan the private networking, because that's the detail exam questions like to catch people on.
