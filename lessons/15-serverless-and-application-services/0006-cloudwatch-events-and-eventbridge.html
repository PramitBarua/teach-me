CloudWatch Events and EventBridge

Lesson 06 of 22 · ~7 min

Source: Adrian Cantrill SAA-C03 · What Is Amazon EventBridge? · EventBridge is the evolution of Amazon CloudWatch Events

You've already met CloudWatch for metrics and CloudWatch Logs for log ingestion. This lesson covers a third, distinct capability: a near real-time stream of system events describing changes inside AWS products and services — an instance stopping, an alarm changing state, a CloudFormation stack completing. The service that delivers this is Amazon EventBridge, and it grew out of an older feature called CloudWatch Events.

The Same Idea, Two Names

Both CloudWatch Events and EventBridge let you implement one pattern: if X happens, or if it's time Y, then do Z.

X — the producer
A supported service that generates an event, such as EC2 changing an instance's state.
Y — the schedule
A specific time or recurring time period, expressed with Unix cron-style syntax.
Z — the target
Where the matched event is delivered — commonly a Lambda function, but many AWS services can be targets.

EventBridge is effectively CloudWatch Events version 2: same underlying APIs, same core architecture, but a strict superset of functionality. It can additionally ingest events from third-party SaaS applications and custom applications you build yourself, not just native AWS services.

What actually changed vs. what stayed the same
Architecturally, nothing about the event-bus/rule/target model changed — EventBridge reuses the CloudWatch Events API, so existing CloudWatch Events rules and code keep working. What changed is scope: EventBridge adds custom and third-party event buses, a schema registry, and richer routing, and AWS now positions EventBridge as the default choice for all new event-driven work, with CloudWatch Events treated as the legacy name for the same original capability. For the exam, know both names but design new answers around EventBridge.

Event Buses

Both services operate on an event bus — a stream of events from supported services within an account.

ServiceEvent bus behavior
CloudWatch EventsExactly one bus, implicit and not exposed in the UI — it's just always there.
EventBridgeOne default account bus, plus the ability to create additional custom buses for your own applications or third-party products.

Rules: Pattern Matching or Schedule

A rule is attached to a specific bus (the account default bus unless you specify otherwise) and comes in one of two forms:

  • Pattern-matching rules — inspect events flowing across the bus and match on their structure or content.
  • Scheduled rules — match a cron expression representing a time or range of times, firing whenever that expression is satisfied.

Either way, a matched rule delivers the event to one or more configured targets. Events themselves are just JSON — for an EC2 state-change event, that JSON carries which instance changed, what state it moved to, and the timestamp, and the target (say, a Lambda function) receives that structure as its input.

Exam tip: EventBridge is the default answer
If a scenario needs to react to an AWS service state change, a schedule, or an event from a third-party SaaS product or custom application, EventBridge is the service to reach for. CloudWatch Events can technically do the AWS-native subset, but any question involving third-party or custom application events is a clear signal that the intended answer is EventBridge, not CloudWatch Events.
