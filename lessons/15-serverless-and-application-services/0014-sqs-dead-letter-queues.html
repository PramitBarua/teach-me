SQS Dead-Letter Queues

Lesson 14 of 22 · ~5 min

Source: Adrian Cantrill SAA-C03 · Using Dead-Letter Queues in Amazon SQS · Setting Up DLQ Retention

Without intervention, a message that keeps failing processing would cycle forever: received, hidden for the visibility timeout, reappear, received again, and so on. A dead-letter queue (DLQ) breaks that loop by giving problem messages somewhere else to go.

The Redrive Policy

Every time a message is received, SQS increments its receive count attribute. A redrive policy on the source queue defines the target DLQ and a maxReceiveCount — once a message's receive count exceeds that threshold without being deleted, SQS moves it to the DLQ instead of returning it to the source queue.

Exam tip
A dead-letter queue is just another SQS queue — there's no special queue type for it. What makes it a DLQ is purely that a source queue's redrive policy points at it. One DLQ can also serve as the target for multiple different source queues.

Isolating failures this way unlocks useful patterns: alarming on any message landing in the DLQ, running isolated diagnostics against just the problem messages, and applying separate processing logic tailored to whatever's going wrong.

The Retention Trap

Every message carries an enqueue timestamp — set when it first entered the source queue — and moving a message to a DLQ does not reset that timestamp. If a message sat in the source queue for a day, and the DLQ's retention period is two days, it only survives one more day in the DLQ before being dropped for good.

Design rule: DLQ retention must exceed source retention
Because the enqueue timestamp carries over unchanged, always configure a DLQ's retention period to be longer than the source queue's retention period — otherwise messages can be silently deleted from the DLQ before anyone has a chance to diagnose them. This is confirmed as an explicit best practice in the AWS documentation.
