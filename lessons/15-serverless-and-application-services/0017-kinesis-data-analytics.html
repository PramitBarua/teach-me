Kinesis Data Analytics

Lesson 17 of 22 · ~8 min

Source: Adrian Cantrill SAA-C03 · What Is Amazon Managed Service for Apache Flink? · Kinesis Data Analytics for SQL Applications Discontinuation

Stale vs. current: this product has been renamed AND the SQL variant is now retired
Two separate things have changed since this course was recorded. First, in August 2023 AWS renamed Kinesis Data Analytics to Amazon Managed Service for Apache Flink — endpoints, APIs, and IAM policies were unaffected, purely a rebrand. Second, and more significantly: the SQL-based variant this lesson describes — with in-application streams and reference tables driven by plain SQL — was formally discontinued. AWS stopped accepting new SQL applications on October 15, 2025, and deleted all remaining SQL applications on January 27, 2026 (before today's date). If you're studying this after that point, the SQL-only workflow described below no longer exists to create in the console — it survives here purely because SAA-C03 exam content may still reference the concept under its old name. The current, supported path for this use case is Managed Service for Apache Flink (using the DataStream/Table APIs or Flink Studio for interactive SQL).

Kinesis Data Streams ingests data. Firehose delivers it near real time. What this product adds is real-time processing using SQL — queries running continuously against data as it flows through, from input streams to output streams.

How the SQL Model Worked

Conceptually, the application sits between an input stream (Kinesis Data Streams or Firehose) and an output stream (Firehose, Lambda, or Kinesis Data Streams directly). Inside the application:

In-application input stream
A virtual table that continuously mirrors the real external source stream
Reference table
Optional static data pulled from S3 to enrich the streaming data — e.g. player metadata alongside a raw stream of game scores
Application code
SQL queries run against the input stream table and the reference table
In-application output stream
A virtual table that mirrors results back out to the real destination stream
Error stream
Captures any records the SQL query fails to process
Exam tip: the destination decides real-time vs. near real-time
Sending output directly to Kinesis Data Streams or Lambda keeps it real-time. Sending it to Firehose (or anything Firehose delivers to) makes it near real-time, because Firehose's own buffering behavior applies downstream. The analytics processing itself is always real-time — what changes is the last hop.

When to Reach for This vs. a Firehose Lambda Transform

Firehose's Lambda transform handles relatively simple per-record manipulation. This product is the answer when a scenario needs complex, SQL-expressed logic against continuously flowing data — time-series analytics, real-time leaderboards, or real-time security/ops dashboards. You pay only for data processed, but it isn't cheap, so it's reserved for scenarios that genuinely need real-time SQL over a stream rather than batch analysis after the fact.

Exam tip: match the vocabulary to the era
If an exam question says "Kinesis Data Analytics," mentally substitute "real-time SQL/stream processing service" and evaluate the scenario the same way regardless of which name is used. The architectural reasoning — input stream, optional reference data, processing logic, output stream — is what's actually being tested, not the current product branding.
