Synchronous

The caller — a human via CLI/API, or a client via API Gateway — waits for the function to finish and return success or failure. Any retry logic on failure is the caller's responsibility, not Lambda's.

Asynchronous

Used when an AWS service invokes Lambda on your behalf, e.g. S3 event notifications. The source service fires the event and moves on immediately — it never waits and never learns the outcome. Lambda handles retries itself (configurable 0–2 times) and can route persistently-failing events to a dead-letter queue or, using the newer destinations feature, to SQS, SNS, another Lambda function, or EventBridge — with separate destinations selectable for success versus failure.

Exam tip: asynchronous invocations demand idempotent code
Because Lambda may silently retry an asynchronous invocation, your function must be idempotent — running it multiple times must produce the same end state as running it once. Prefer operations that set a final state ("set balance to $20") over operations that modify a state ("add $10"), since a retried additive operation can double-apply and corrupt data.

Event Source Mapping

Used for stream- and queue-based sources that don't natively push events — SQS, Kinesis Data Streams, DynamoDB Streams, and Amazon MSK. A hidden polling component (the event source mapping) reads batches of records from the source and invokes the function with an event batch.

The permissions model flips here
With asynchronous invocation, the source pushes the event — the function's execution role generally doesn't need permissions on that source unless it needs to fetch more data. With event source mapping, the mapping itself uses the execution role's permissions to poll the source. Even though the function never directly calls, say, Kinesis, its execution role still needs Kinesis read permissions — because the polling happens on its behalf. This distinction is a frequently tested exam trap.

Batches that consistently fail processing can be sent to an SQS queue or SNS topic for further investigation, and batch size must be tuned carefully against the 15-minute function timeout — a batch too large to finish processing in time will cause the invocation to be cut off mid-batch.

Versions and Aliases

Version
An immutable snapshot of a function's code and configuration (resources, environment variables, etc.) at the moment it's published. Once published, it never changes and has its own ARN.
$LATEST
A mutable pointer that always reflects the most recently saved code/configuration — the opposite of a published version.
Alias
A mutable, named pointer (e.g. dev, stage, prod) to a specific version. Repoint the alias to roll a component of your architecture forward to a new version without changing any caller's configuration.
Exam tip: production traffic should target aliases, not $LATEST
Best practice is to publish immutable versions for meaningful changes and have downstream services invoke a stable alias rather than $LATEST — this lets you control exactly when new code reaches production, and roll back instantly by repointing the alias.

Cold Starts and Warm Starts

Lambda code executes inside a runtime environment (execution context). The first time a function runs (or runs after being idle), Lambda must provision hardware, install the runtime, and download the deployment package — a cold start, adding hundreds of milliseconds or more. If the same function is invoked again soon after, Lambda can reuse that same execution context — a warm start — skipping straight to execution.

Concurrency multiplies cold starts
One execution context handles one invocation at a time. Twenty simultaneous invocations of a function that has no warm context available can mean twenty separate cold starts, not one. This is why bursty, highly concurrent, latency-sensitive workloads are the ones most likely to need mitigation.

Provisioned concurrency is that mitigation — you tell Lambda in advance how many execution contexts to keep pre-initialized, eliminating cold starts for that capacity. It's applied to a specific version or alias, never to $LATEST. Two further code-level techniques reduce cold-start impact:

  • Reuse the /tmp space across invocations sharing a context (e.g. caching downloaded assets) — but never assume it will be there.
  • Declare expensive resources (database connections, SDK clients) outside the function handler — code outside the handler runs once per context and is reused by later invocations in that same context, while code inside the handler runs on every single invocation.
