Kinesis Data Streams

Lesson 15 of 22 · ~9 min

Source: Adrian Cantrill SAA-C03 · What Is Amazon Kinesis Data Streams? · Kinesis Data Streams Terminology and Concepts

Kinesis and SQS get confused constantly, including on the exam — but they solve different problems. Kinesis Data Streams is a scalable streaming service built to ingest large volumes of data from many producers and make it available to many consumers, at whatever granularity each consumer needs.

Shards: the Unit of Scale

A stream starts with one shard and grows by adding more as throughput demands increase. Each shard provides fixed capacity:

DirectionCapacity per shard
Ingestion (write)1 MB per second
Consumption (read)2 MB per second

More shards mean more throughput and more cost — performance scales linearly because Kinesis data records (max 1 MB each) are distributed across shards.

Exam tip: shard math
If a scenario states an ingestion rate, divide by 1 MB/sec to size the shard count. A producer pushing 4.5 MB/sec of data needs at least 5 shards on the write side, regardless of how many consumers read it back.

Persistence: the Rolling Window

Data ingested into a stream stays available for a default 24-hour rolling window — storage for that window is included in the shard cost. This window can be extended up to 365 days for additional cost, and a longer window means more data is retained and billed for at any given moment. Multiple consumers can read from anywhere within that window, each at its own pace — one might process every record in real time, another might sample once an hour for a dashboard.

Kinesis vs. SQS: the Decision Lens

When an exam question is ambiguous, ask: is this about ingesting data at scale, or about decoupling/worker pools/asynchronous messaging?

SQSKinesis Data Streams
Typical producersOne tier (e.g. a web app)Many — sensors, devices, mobile apps
Typical consumersOne worker tierMultiple, each at a different rate
PersistenceNone — deleted once processedRolling window, up to 365 days
Core use caseDecoupling, async messagingHigh-volume ingestion, analytics
Exam tip: default to SQS unless it's clearly ingestion
If a question is about ingestion of high-volume data (sensors, clickstreams, IoT), pick Kinesis. For anything else — decoupling, worker pools, async communication — default to SQS first, and only switch if there's a strong specific reason to.

Kinesis has no native way to persist data beyond the rolling window or deliver it directly to other services — that's the job of its sibling product, Kinesis Data Firehose, covered next.
