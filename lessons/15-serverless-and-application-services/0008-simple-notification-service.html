Simple Notification Service (SNS)

Lesson 08 of 22 · ~7 min

Source: Adrian Cantrill SAA-C03 · What Is Amazon SNS? · Common Amazon SNS Scenarios (Fanout)

SNS is a highly available, durable pub/sub messaging service, and a foundational building block across countless AWS architectures. It's a public service — reachable over the public AWS endpoints — so anything with network connectivity to that public zone, including a VPC configured for it, can use it.

Core Entities

Topic
The base entity of SNS. Permissions and most configuration live here.
Publisher
Anything that sends a message into a topic — an application, CloudWatch, CloudFormation, an Auto Scaling group.
Subscriber
Anything registered to receive messages sent to a topic. By default, a subscriber receives every message — though a filter policy can restrict a subscriber to only the messages relevant to it.

Messages are payloads up to 256 KB — SNS is built for notifications and structured data, not for shipping large binary files.

Subscriber Types

SubscriberBehavior
HTTP / HTTPS endpointMessage posted to a URL
EmailMessage delivered to an inbox
SQS queueMessage added as a queue item
Mobile push / SMSDelivered as a push notification or text message
LambdaFunction invoked with the message as its event

A single entity can be both a publisher and a subscriber on the same topic — an API, for instance, can publish messages in and also receive messages back.

The Fanout Pattern

One SNS topic can have multiple SQS queues as subscribers. A single published message — say, "a new video needs processing" — lands in every subscribed queue simultaneously, letting several independent workers each pick up a copy and process it differently (one queue transcodes to low bitrate, another to high bitrate, a third updates a search index). One publish, many decoupled, parallel consumers.

Exam tip: SNS vs. SQS, and why fanout needs both
SNS pushes messages out to every subscriber; SQS holds messages in a queue for a single consumer (or competing consumers) to pull. They solve different problems, which is exactly why fanout combines them: SNS distributes one event to multiple independent queues, and each SQS queue then provides durable, poll-based processing and retry semantics for its own downstream consumer.

Reliability, Residency, and Security

  • Delivery status is trackable for some subscriber types (HTTP/HTTPS, Lambda, SQS), and SNS performs delivery retries on failure.
  • Regionally resilient — data is replicated across Availability Zones within the region, so an AZ failure doesn't take a topic down.
  • Server-side encryption (SSE) is available for data at rest.
  • Cross-account access is controlled with a topic policy — a resource policy, the same concept as an S3 bucket policy, attached directly to the topic.
