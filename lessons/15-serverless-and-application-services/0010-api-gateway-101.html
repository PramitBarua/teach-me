API Gateway 101

Lesson 10 of 22 · ~10 min

Source: Adrian Cantrill SAA-C03 · Choose Between REST APIs and HTTP APIs · Cache Settings for REST APIs

API Gateway is a managed entry point that sits between applications consuming an API and the integrations that actually provide its functionality — an HTTP endpoint, a Lambda function, or a direct connection to services like DynamoDB, SNS, or Step Functions. It's highly available and scalable by default, and it's commonly the front door of a serverless architecture.

Three Phases of a Request

  1. Request phase — authorizes, validates, and transforms the incoming client request into a form the integration understands.
  2. Integration — the backend (Lambda, HTTP endpoint, or direct AWS service) does the actual work.
  3. Response phase — transforms and returns the integration's output back to the client.

Along the way, API Gateway can handle authorization, throttling, caching, CORS, and request/response transformation, and it integrates with CloudWatch for logs and metrics.

Exam tip: REST API vs. HTTP API vs. WebSocket API
API Gateway offers three product types, and picking between them is a common scenario question:
  • REST API — the full-featured option: usage plans, API keys, per-client throttling, request validation, WAF integration, private endpoints.
  • HTTP API — a lighter, cheaper, lower-latency option for simple Lambda or HTTP proxy integrations, with built-in CORS and automatic deployments, but fewer advanced features.
  • WebSocket API — for persistent, two-way connections (chat apps, live dashboards) where the server needs to push data to connected clients.
Default to REST API when a scenario needs advanced governance (usage plans, WAF, private endpoints); default to HTTP API when it just needs a cheap, fast Lambda front door; pick WebSocket only when the traffic pattern is genuinely bidirectional and persistent.

Endpoint Types

Edge-optimized
Requests route to the nearest CloudFront point of presence — best for geographically distributed clients.
Regional
No CloudFront hop; suited to clients within the same AWS Region as the API.
Private
Reachable only from inside a VPC, via an interface VPC endpoint.

Stages and Canary Deployments

Every deployment goes to a stage (e.g., prod, dev), each with its own endpoint URL, its own settings, and — because stages can point at different backing Lambda versions — effective isolation between environments. Enabling canary on a stage lets a new deployment absorb a configurable percentage of that stage's traffic before being promoted to the full base stage, or rolled back if it misbehaves.

Error Codes Worth Memorizing

CodeMeaning
400Generic client-side error — many possible causes
403Access denied — an authorizer rejected the request, or WAF filtered it
429Throttling — request rate exceeded a configured limit
502Bad gateway — the integration returned an invalid response
503Service unavailable — the backend is offline or overloaded
504Integration failure — the backend didn't respond in time
The 29-second limit isn't as fixed as it used to be
Every REST API integration historically had a hard 29-second timeout, and exceeding it produces a 504. That's still the fixed limit for edge-optimized APIs, but since mid-2024 AWS allows raising this quota beyond 29 seconds for Regional and private REST APIs, via a Service Quotas request — potentially trading off against your account's Region-level throttle quota. Lambda's own 15-minute execution limit was never the constraint here; the API Gateway integration timeout was.

Caching

Caching is configured per stage. When enabled, responses are served from the cache instead of hitting the integration on every request — reducing backend load, cost, and latency. Cache size ranges from 0.5 GB up to 237 GB; default TTL is 300 seconds, adjustable from 0 (disabled) up to a maximum of 3,600 seconds; and cached data can be encrypted.
