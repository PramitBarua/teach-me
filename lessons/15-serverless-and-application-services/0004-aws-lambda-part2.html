Two Networking Modes

Lambda functions run in one of two networking modes, and the exam expects you to know the reach and limits of both.

ModeCan reachCannot reach (without extra config)
Public (default)Public AWS service endpoints (e.g. DynamoDB, SQS) and the public internetAnything inside a VPC that lacks public addressing and permissive security rules
VPC-attachedResources inside the same VPC (subject to security groups / NACLs)Public AWS services or the internet — unless the VPC has a NAT gateway + internet gateway, or relevant VPC endpoints
Exam tip: treat a VPC-attached Lambda like any other VPC resource
Once attached to a VPC, a Lambda function follows the same rules as an EC2 instance in that VPC. Needs DynamoDB access from inside the VPC? Add a gateway VPC endpoint. Needs internet access? Add a NAT gateway in a public subnet plus an internet gateway on the VPC. There's no Lambda-specific shortcut — design the VPC networking exactly as you would for any other private resource.

How VPC Networking Actually Works Today

Historically, each function invocation created its own elastic network interface (ENI) in the customer VPC — slow to set up and a poor fit for concurrency, since more parallel invocations meant more ENIs. AWS's current architecture instead analyzes every function in a region/account and creates one ENI per unique combination of subnets and security groups used across all functions. That ENI is created once, at configuration time (function creation or VPC-config update) — not per invocation.

VPC-attached Lambda is no longer a performance trap
This shared-ENI model means VPC networking no longer adds meaningful per-invocation latency or scaling limits the way it used to. The function's execution role still needs EC2 networking permissions (to create/manage those interfaces), typically via the AWSLambdaVPCAccessExecutionRole managed policy.

Two Layers of Permissions

Lambda security has two distinct, easily confused halves:

Execution role
An IAM role the function assumes at runtime, governing what the function's code is allowed to do — read from DynamoDB, write to S3, and so on. Conceptually identical to an EC2 instance role.
Resource-based (resource) policy
Attached to the function itself, governing who or what is allowed to invoke it — another AWS account, or a service like S3 or SNS. Conceptually similar to an S3 bucket policy.
Stale-transcript flag: resource-policy editing in the console
The source lecture states resource-based policies can only be changed via the CLI or API, not the console. That is no longer accurate — the Lambda console's Configuration → Permissions → Resource-based policy panel now supports adding and viewing these statements directly. The underlying concept (execution role = what the function can do, resource policy = who can invoke it) is still exactly what the exam tests, but don't assume the console is limited to read-only here.

Logging and Monitoring

  • CloudWatch Logs — all function output: your logged messages, errors, and execution duration details.
  • CloudWatch (metrics) — invocation counts, successes, failures, retries, and latency.
  • X-Ray — optional distributed tracing across a serverless application.
Exam tip: "nothing in CloudWatch Logs" almost always means missing permissions
A classic exam scenario: a Lambda function appears to run but produces no CloudWatch Logs output at all. The near-universal cause is that the execution role lacks the logging permissions — normally supplied by attaching the AWSLambdaBasicExecutionRole managed policy. Without it, Lambda has nowhere it's allowed to write logs to.
