Simple Queue Service (SQS)

Lesson 11 of 22 · ~9 min

Source: Adrian Cantrill SAA-C03 · What Is Amazon SQS? · Amazon SQS Visibility Timeout

SQS provides fully managed message queues. It's a public, regional service — highly available and highly performant by design, with no replication or resiliency work for you to do. Producers send messages in; consumers poll for messages out. Neither side needs to know the other exists.

How a Queue Actually Works

A message added to a queue can be up to 256 KB. Anything larger belongs in S3, with the message carrying only a link to the object — architecturally, small messages are easier to move and process at scale.

Consumers retrieve messages by polling. Critically, a poll doesn't delete a message — it hides it for a configurable visibility timeout. If the consumer finishes processing and explicitly deletes the message, it's gone for good. If it doesn't — because the job failed, or the consumer crashed outright — the message silently reappears on the queue once the timeout expires, ready for another consumer to try.

Exam tip
Visibility timeout is the single most-tested SQS detail. It's what makes queues fault-tolerant for free: a failed consumer doesn't need to tell the queue anything went wrong — it just needs to do nothing, and the message comes back automatically.

Problem messages that keep failing and reappearing can be routed to a dead-letter queue for separate handling — covered in full in lesson 14.

Decoupling and Elastic Worker Pools

Queues decouple application components and enable scaling on both sides independently. A classic pattern: a web tier uploads a master video to S3 and drops a message (with a link to the object, not the video itself) onto a queue. The web tier's Auto Scaling Group scales on CPU load and its job ends there.

A separate worker-tier ASG scales on queue length. As messages pile up, workers scale out, poll the queue, fetch the video, transcode it, store the result, and delete the message. If a worker or its processing fails, the message reappears after the visibility timeout and another worker picks it up. As the queue empties, the worker pool scales back in — all the way to zero.

Exam tip: SNS + SQS fan-out
An S3 event can only fire once per upload, but you often need multiple independent jobs from that one event (say, transcoding to 480p, 720p, and 1080p separately). The fix: publish the event to an SNS topic with one SQS queue per subscriber. Each queue gets its own copy of the message and its own independently scaling worker pool. This fan-out pattern is a favorite exam scenario — commit it to memory.

Polling, Cost, and Security

SQS bills per request, not per message — one request can return 0 to 10 messages, up to 64 KB total. That distinction matters because there are two polling styles:

StyleBehaviorCost implication
Short pollingReturns immediately, even with zero messagesAn empty queue still burns a billable request on every poll
Long pollingWaits up to 20 seconds for a message to arrive before returningFar fewer wasted requests — the recommended default

Messages can sit in a queue for up to 14 days, so SQS supports server-side encryption at rest via KMS. Data is encrypted in transit by default — but remember, encryption in transit and encryption at rest are two separate, independently configured things. Access to a queue is controlled by identity policies (same account) or a queue policy, a resource policy like the ones used on S3 buckets or SNS topics — queue policies are required for granting access to a different account.
