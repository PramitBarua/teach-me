Serverless & Application Services

Serverless Architecture

Lesson 07 of 22 · ~9 min

Source: Adrian Cantrill SAA-C03 · What Is Serverless Development? · Amazon Cognito Identity Pools

Despite the name, serverless doesn't mean there are no servers — it means you manage as few of them, if any, as possible. It's a software architecture, not a hardware one, blending ideas from microservices and event-driven design: break an application into tiny, specialized pieces that start up, do one thing well, and stop.

Three Defining Traits

Stateless and ephemeral compute
Functions (typically Lambda) run in a clean environment every time. Any data they need is fetched at the start of execution; any result is persisted or handed off at the end. Because every environment is identical and disposable, it's trivial to scale.
Event-driven, not always-on
Nothing runs until something triggers it. Compute is billed by execution duration, so an idle serverless system costs close to nothing — the opposite of provisioning fixed capacity for peak load.
Consume, don't reinvent
Wherever a managed service exists, use it instead of writing and operating the equivalent yourself: S3 for object storage, DynamoDB for persistent data, third-party identity providers for authentication, Elastic Transcoder for media processing.
Exam tip: why third-party identity providers matter
A serverless app should avoid rolling its own user store. Beyond the admin overhead, an AWS account has a hard quota of 5,000 IAM users — nowhere near enough for a public-facing application's customer base, and IAM users aren't meant for end-user application logins anyway. Federating through a provider like Google, Facebook, or corporate Active Directory sidesteps this entirely.

Walking Through a Serverless App: PetTube

Julie wants to upload a video of her dog Woofie. Trace what happens, and notice that no step provisions or manages a server:

  1. Static front end. Julie's browser loads HTML and JavaScript from an S3 static website bucket. The JavaScript running client-side is the application's front end.
  2. Authentication. The JavaScript sends Julie to a third-party identity provider (Google). On success, Google returns an identity token proving she authenticated.
  3. Credential exchange. AWS can't consume a Google token directly, so the JavaScript hands it to Cognito, which exchanges it for temporary AWS credentials.
  4. Upload. Using those temporary credentials, the browser uploads Woofie's video straight to an S3 "originals" bucket.
  5. Processing trigger. The originals bucket is configured to emit an event on object creation, invoking a Lambda function.
  6. Transcoding. That Lambda function creates jobs in Elastic Transcoder, one per output size. Each job reads the master file and writes a resized output to a transcoded bucket, and each output's location is recorded in DynamoDB.
  7. Retrieval. A second Lambda function, invoked when Julie views her media page, reads DynamoDB, finds her videos, and returns URLs the browser can use.
The diagram is simplified
A real implementation of this flow would put API Gateway in front of both Lambda functions rather than letting the browser invoke them directly — API Gateway is the standard front door for client-to-Lambda communication in serverless architectures, covered later in this module. The simplified version here is for teaching the concept, not the complete production shape.

End to end: no EC2 instances, no self-managed database servers, and cost is incurred only for storage used and compute time actually consumed — S3, Cognito, Lambda invocation time, and Elastic Transcoder job time. Everything else is idle at zero cost.
