Architecture Deep Dive, Part 2: Queues, Microservices, and Event-Driven Design

Lesson 02 of 22 · ~9 min

Source: Adrian Cantrill SAA-C03 · How Amazon SQS Works · What Is Event-Driven Architecture?

Part 1 left the tiered, load-balanced CatTube architecture with one unsolved problem: the upload tier's synchronous call to the processing tier means processing can never scale to zero, and a full processing outage breaks uploads too. A queue fixes this by breaking the direct connection entirely.

Queue-Based Decoupling

Instead of calling the processing tier directly, the upload tier now: stores the master video in S3, then places a message on a queue describing where the video lives and what needs doing. That's the whole transaction — the upload tier doesn't know or care whether anything is listening on the other end.

On the far side, an Auto Scaling group configured with min = 0, desired = 0, max = <large> watches queue length as its scaling metric. Messages appear → desired capacity rises above zero → instances launch, poll the queue, retrieve the referenced object from S3, process it, and delete the message. As the queue drains, the ASG scales desired capacity back down — all the way to zero when there's nothing left to do.

Exam tip: this is the "scale to zero" pattern
A queue converts a synchronous dependency into an asynchronous one. The producer (upload tier) never waits for a response, and the consumer (processing tier) can legitimately run zero instances when idle — something a direct or load-balanced synchronous call can never do. Whenever a scenario mentions unpredictable, bursty background work that should cost nothing while idle, think queue + Auto Scaling on queue length.

Microservices

Keep decomposing a tiered application and you eventually reach a microservice architecture: many small, self-sufficient services, each with its own logic, its own data, and its own inputs/outputs. A real application might have hundreds or thousands of these. Each microservice is either a producer (generates data/events), a consumer (acts on data/events), or both.

A queue per pair of services doesn't scale
Connecting every producer microservice to every consumer microservice with its own dedicated queue works, but it turns into an unmanageable web of point-to-point queues as the number of services grows. This is the exact problem an event router solves.

Event-Driven Architecture

An event is simply a state change or notable occurrence — a button click, an upload finishing (or failing), an error during order processing. In a mature event-driven design:

Producers
Generate events only when something actually happens. They are not constantly running or polling.
Event router / event bus
A central, highly available exchange point. Producers publish onto it; the router delivers events to whichever consumers care about them — removing the need for every service to know about every other service.
Consumers
Sit idle until an event they care about is delivered, take an action, then return to idle. Like producers, they don't consume resources while waiting.
Exam tip: the defining trait of event-driven = resource use only while handling events
Contrast this with an always-on EC2 instance, which is billed continuously regardless of load. A mature event-driven system's producers and consumers consume compute only while actively handling an event — this is precisely the property that makes event-driven design the architectural foundation of serverless, covered later in this module.

Direct / load-balanced tiersSynchronousNo — something must always answer
