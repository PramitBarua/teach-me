Kinesis Data Firehose

Lesson 16 of 22 · ~8 min

Source: Adrian Cantrill SAA-C03 · What Is Amazon Data Firehose? · Send Data to a Firehose Stream

Stale vs. current: the product has been renamed
The course refers to this product throughout as Kinesis Data Firehose. In February 2024, AWS renamed it to Amazon Data Firehose — a pure rebrand reflecting that it now ingests from many more sources than just Kinesis Data Streams (including Amazon MSK and 40+ other connectors). Endpoints, APIs, IAM policies, and CloudWatch metrics are all unchanged. Everything below still applies; just expect to see "Amazon Data Firehose" in current documentation and the console.

Kinesis Data Streams ingests and holds data for a rolling window, but offers no native way to persist it permanently or hand it to other services. Firehose fills that gap: a fully managed, serverless, auto-scaling delivery service that moves streaming data into supported destinations.

Near Real-Time, Not Real-Time

This is the single most exam-relevant fact about Firehose: it is near real-time, not real-time. Firehose buffers incoming data and flushes on whichever threshold hits first — 1 MB of data, or 60 seconds (both configurable, these are the general minimums). Low-volume producers typically wait out the full 60 seconds; high-volume producers flush closer to every megabyte.

Exam tip: real-time vs. near real-time
Kinesis Data Streams delivers to consumers in real time (think ~200 ms). Firehose is near real-time (think ~60 seconds), because of its buffering behavior. Any answer option involving Firehose cannot be the real-time solution — if a scenario demands true real-time delivery, Firehose is disqualified regardless of how convenient it looks otherwise.

Sources and Destinations

Firehose accepts data either directly from producers, or from an upstream Kinesis data stream. On the way out, it supports:

  • Amazon S3 — the most common target, for long-term storage beyond the Kinesis rolling window
  • Amazon Redshift — delivered indirectly: Firehose stages data in an intermediate S3 bucket, then runs a Redshift COPY command to load it
  • OpenSearch Service (the course refers to this by its earlier name, Elasticsearch — see callout below)
  • Splunk
  • HTTP endpoints — for third-party providers
Stale vs. current: Elasticsearch → OpenSearch
Amazon renamed its managed Elasticsearch offering to Amazon OpenSearch Service back in 2021. Where the course says "Elasticsearch" as a Firehose destination, current AWS material — and the exam — will refer to it as OpenSearch Service. The underlying delivery mechanism is unchanged.

Transformation with Lambda

Firehose can invoke a Lambda function to transform records in flight before delivery — anything expressible in that function's code. This adds latency proportional to the transform's complexity, and you can optionally retain the untransformed source records in a separate backup S3 bucket.

Exam tip: Firehose transforms are simpler than Kinesis Data Analytics
Lambda-based transforms in Firehose suit relatively simple record manipulation. If a scenario needs complex, SQL-driven real-time analysis of streaming data, that's a job for Kinesis Data Analytics (next lesson) — not a Firehose Lambda transform.
