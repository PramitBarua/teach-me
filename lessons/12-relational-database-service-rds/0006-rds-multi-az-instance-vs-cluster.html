RDS Multi-AZ: Instance vs Cluster

Lesson 06 of 16 · ~9 min

Source: Adrian Cantrill SAA-C03 · Configuring and managing a Multi-AZ deployment

RDS offers two Multi-AZ high-availability architectures: the original Multi-AZ instance deployment, and the newer Multi-AZ cluster deployment. They solve the same problem — surviving an AZ or instance failure — with meaningfully different trade-offs.

Multi-AZ Instance Deployment

One primary, one standby, in different AZs. Replication is synchronous at the storage level (the exact mechanism depends on the engine — Amazon failover technology for MariaDB/MySQL/Oracle/PostgreSQL, SQL Server mirroring/always-on for SQL Server — but the behaviour is the same either way).

  • All reads and writes go to the primary via the DB C-name (a DNS endpoint). The standby is never used for reads.
  • The standby's only job is to be ready for failover.
  • Failover changes what the C-name points to — a DNS update that typically takes 60–120 seconds.
  • Backups can be taken from the standby, avoiding any I/O performance hit on the primary.
  • Multi-AZ is not included in the free tier — you're paying for a second instance.
  • Failovers happen for AZ outages, primary instance failure, instance type changes, manual testing, or even routine patching (patch the standby, then fail over).

Multi-AZ Cluster Deployment

The newer model: one writer, two readers, each in a different AZ. Unlike instance mode, the readers are usable — for read operations, provided your application is built to route reads there.

EndpointPurpose
Cluster endpointPoints at the writer; use for reads, writes, and admin
Reader endpointPoints at available readers (sometimes including the writer); load-balances read traffic
Instance endpointsOne per instance; generally for testing only — no automatic failover if you connect directly

A write is considered committed once it's been sent to the writer and confirmed by at least one reader — resilience is baked into the commit itself, spanning multiple AZs. Cluster mode also runs on faster hardware: Graviton processors with local NVMe SSD storage, writing locally first and flushing to EBS after.

Exam tip
Multi-AZ cluster mode replicates using transaction logs rather than full storage-level sync, which is why failover drops to as little as ~35 seconds (plus log replay time) — versus 60–120 seconds for instance mode.

Don't confuse with Aurora
Multi-AZ cluster mode sounds a lot like Aurora, but each RDS instance in the cluster still has its own dedicated local storage — there's no shared cluster storage volume the way Aurora has. Keep this distinction sharp before you reach the Aurora lessons.
