Database Migration Service (DMS)

Lesson 16 of 16 · ~9 min

Source: Adrian Cantrill SAA-C03 · AWS DMS User Guide

Manually migrating a database means either standing up complex replication yourself, or taking a point-in-time backup and restoring it — leaving the question of how to capture every change made while that migration was in flight. DMS automates this entire problem, and it's a tool you'll reach for constantly as a solutions architect, not just on the exam.

Core Architecture

ComponentWhat it does
Replication instanceAn EC2 instance running DMS's migration software
Replication taskDefines the migration; a replication instance can run multiple tasks
Source / target endpointsConnection details for the source and destination databases

Supported engines span MySQL, Aurora, SQL Server, MariaDB, MongoDB, PostgreSQL, Oracle, Azure SQL, and more. The one hard rule: at least one endpoint must be inside AWS — DMS can't migrate between two on-premises databases.

Exam tip
If an exam scenario describes a database migration where at least one side is already in AWS, and no exotic unsupported engine is involved, DMS is almost always the correct default answer — especially for "zero downtime" migration requirements.

Three Task Types

Full load
Migrates existing data only. Simplest option — appropriate if you can tolerate an outage long enough to complete the copy.
Full load + CDC (Change Data Capture)
Migrates existing data and captures ongoing changes during the migration. Once changes reach a steady state, cut over: stop the source application, let remaining changes flow through, then point applications at the target.
CDC only
Replicates only ongoing changes. Useful when the bulk data load is done through some other, more efficient tool (e.g. Oracle's native export/import), and DMS only needs to pick up changes from that point forward.

Schema Conversion Tool (SCT)

DMS moves data, not schemas. When source and target use different database engines — say, on-premises Microsoft SQL Server to RDS MySQL, or on-premises Oracle to Aurora — you need the standalone Schema Conversion Tool (SCT) to convert the schema and code objects first.

The rule that matters most
SCT is used only when the database engine changes. Migrating on-premises MySQL to RDS MySQL? No SCT needed — same engine, DMS alone handles it. Migrating on-premises Oracle to Aurora? SCT is needed — different engines.

DMS + Snowball for Large Migrations

For multi-terabyte migrations where transferring data over the network would take too long or consume too much bandwidth, DMS can combine with the Snowball family:

  1. SCT extracts the data locally and converts it to a generic transferable format.
  2. That data is loaded onto a physical Snowball device and shipped to AWS.
  3. AWS loads the Snowball's contents into an S3 bucket.
  4. DMS migrates from S3 into the target database.
  5. If CDC is used, ongoing changes since the bulk transfer are captured, staged through S3, and applied by DMS as well.

This still respects the "only when the engine changes" rule for SCT — you're transforming the source into a generic file format for physical transport, which is itself a kind of engine change.
