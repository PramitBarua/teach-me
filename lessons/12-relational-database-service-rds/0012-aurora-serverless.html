RDS & Aurora

Aurora Serverless

Lesson 12 of 16 · ~8 min

Source: Adrian Cantrill SAA-C03 · Using Aurora Serverless

If Aurora (provisioned) is Aurora's core product, Aurora Serverless is what Fargate is to ECS: the same underlying engine, minus the need to statically size and manage instances. From this point on, the fixed-instance version is called Aurora provisioned to distinguish it from serverless.

Aurora Capacity Units (ACUs)

Instead of picking instance classes, you set a minimum and maximum ACU range for the cluster. Aurora Serverless scales between those bounds automatically based on load — and can scale all the way to zero, pausing the cluster so you're billed only for storage.

  • Billing is per-second, based on the ACUs actually consumed.
  • Resilience matches Aurora provisioned: the same shared cluster storage, replicated across 6 storage nodes in 3 AZs.

How Scaling Actually Works

ACUs are allocated from a warm pool managed by AWS — stateless, shared across customers, with no local storage of their own. This is what makes them fast to allocate. When load increases, new (larger) capacity is brought online, storage access is handed over, and only then is the old capacity released — a seamless transition.

Because compute capacity changes size dynamically, clients don't connect directly to an ACU. Instead, a shared proxy fleet, managed by AWS, brokers the connection between the application and whichever ACU is currently serving the cluster. This is what lets Aurora Serverless scale in and out without disrupting existing connections.

Exam tip
The proxy fleet is what makes Aurora Serverless's scaling "invisible" to the application — this is conceptually similar to what RDS Proxy does for standard RDS/Aurora provisioned, though the two are separate mechanisms.

When Aurora Serverless Fits

Use caseWhy it fits
Infrequent / low-volume appsPay only when connections actually occur — no idle instance cost
New applicationsNo need to guess the right instance size upfront
Variable / spiky workloadsScales to peak automatically instead of provisioning for it permanently
Unpredictable workloadsSet a wide min/max range and let observed usage guide future sizing
Dev/test databasesPauses to zero compute during idle periods — only storage cost remains
Multi-tenant appsInfrastructure cost scales in line with the revenue driving the load
