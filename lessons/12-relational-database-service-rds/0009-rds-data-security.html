RDS Data Security

Lesson 09 of 16 · ~9 min

Source: Adrian Cantrill SAA-C03 · Security in Amazon RDS · AWS KMS Documentation

RDS data security breaks into four areas: authentication (logging in), authorization (what you can do once in), encryption in transit, and encryption at rest.

Encryption in Transit

Every RDS engine supports encrypting client-to-instance traffic via SSL/TLS. This can be made mandatory per database user, not just optional.

Encryption at Rest — Two Approaches

MethodWhere encryption happensEngines
KMS + EBS encryption The host, not the database engine — the engine writes data as if unencrypted, and the host encrypts before it hits storage All RDS engines (default mechanism)
TDE (Transparent Data Encryption) Inside the database engine itself, before data ever leaves the engine Microsoft SQL Server, Oracle
TDE + CloudHSM Engine-level, with keys in a customer-managed CloudHSM — no key exposure to AWS at all Oracle only

With KMS-based encryption, you select a CMK (customer-managed or AWS-managed), which is used to generate DEKs (data encryption keys) — the actual keys performing encrypt/decrypt operations, loaded onto the RDS host as needed. Storage, logs, snapshots, and replicas all inherit the same CMK.

Encryption is one-way
Once enabled on an RDS instance, encryption at rest cannot be removed. To "unencrypt," you'd need to create a new, unencrypted instance and migrate the data across.

TDE is the more trustworthy option where it's available: because the database engine itself handles encryption before writing, data is protected from the moment it leaves the engine — you don't need to trust the host layer at all. Add CloudHSM on Oracle, and even AWS has zero visibility into your keys, which matters for the most demanding regulatory environments.

IAM Authentication for RDS

By default, RDS logins use local database users — created and managed inside the database engine, entirely separate from IAM. RDS can optionally be configured to allow IAM-based authentication instead of passwords:

  1. Create a local database user configured to accept AWS auth tokens.
  2. Attach an IAM policy to a user or role that maps that identity to the local database user.
  3. The IAM identity calls generate DB auth token, receiving a token valid for 15 minutes.
  4. That token is used to log in — no password required.
Exam tip
IAM authentication for RDS is authentication only, not authorization. Once logged in, permissions inside the database are still governed entirely by the local database user's own grants — IAM plays no role in what that user can actually do.
