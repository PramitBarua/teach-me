Databases on EC2

Lesson 04 of 16 · ~7 min

Source: Adrian Cantrill SAA-C03 · RDS vs EC2 vs on-premises comparison

Every managed database product in this module exists to answer one question: why not just run a database on EC2? This lesson sets the baseline. Running a database on EC2 is always a workable option, and almost always a worse one — the question is whether a specific justification outweighs the downsides.

Why You Might Choose EC2 Anyway

JustificationWorth questioning?
Need OS-level / root access to the database hostUsually — few real requirements demand this; RDS exposes many tunable parameters without root access
Need a DB engine or version AWS doesn't offerLegitimate, especially for niche or emerging databases
Need a specific OS + DB version combinationLegitimate for tightly-coupled legacy applications
Need a replication architecture RDS doesn't supportLegitimate in some advanced scenarios
"Decision makers just want it on EC2"Worth challenging, but sometimes non-negotiable
Exam tip
Don't assume EC2-hosted databases are always the wrong exam answer. Cantrill notes tricky questions exist where a database on EC2 is the correct choice — usually when the scenario demands OS-level access or an unsupported engine.

Why You Usually Shouldn't

Even when a justification exists, weigh it against these costs:

  • Admin overhead — you patch the OS and the database engine, and you own backup and disaster-recovery planning end-to-end.
  • Single-AZ exposure — an EC2 instance and its EBS volume both live in one Availability Zone. If that AZ fails, the database fails, unless you build your own multi-AZ replication.
  • Missing features — AWS invests heavily in performance and availability features that ship only with managed products, not a self-installed engine.
  • No serverless option — EC2 is on or off. It can't scale to zero or burst automatically the way some managed database products can.
  • Replication is on you — designing, monitoring, and validating replication is work that managed products largely automate away.
  • Reduced performance ceiling — off-the-shelf engine software on generic EC2 doesn't benefit from the optimisation work AWS puts into its own database products.

The Architecture Question

Running a database on EC2 usually means one of two shapes:

  • Single instance — app, web server, and database all on one EC2 instance, in one AZ. Simple, but a single point of failure and hard to scale independently.
  • Split architecture — database on its own instance, separate from the application tier. This introduces a network dependency between the two, and if they're split across AZs, cross-AZ data transfer has a (small) cost, unlike same-AZ private IP traffic, which is free.

Splitting the database out of a monolithic stack is a necessary first step even if you plan to stay on EC2 — and it's also the natural on-ramp to migrating that database into RDS later, without re-architecting the application tier at the same time.
