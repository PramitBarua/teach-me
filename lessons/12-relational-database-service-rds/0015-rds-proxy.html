RDS & Aurora

RDS Proxy

Lesson 15 of 16 · ~8 min

Source: Adrian Cantrill SAA-C03 · Amazon RDS Proxy

Opening and closing a database connection has real overhead — trivial for a long-lived app server, but a serious problem for Lambda, where every invocation might open a fresh connection. Add in the complexity of handling connection failures and failovers correctly in application code, and you have a strong case for a dedicated database proxy. That's what RDS Proxy is.

The Core Idea

Instead of applications connecting to the database directly, they connect to RDS Proxy, which maintains a long-lived pool of connections to the actual database instance. Proxy connections are cheap to establish and place no load on the database. The proxy then multiplexes — routing many client connections over a smaller number of actual database connections — which matters most for small instance classes like T2/T3, where connection overhead eats into limited resources.

Architecture

  • RDS Proxy runs only within a VPC, across multiple AZs — it's not reachable from the public internet.
  • Clients (EC2, Lambda) connect to the proxy's endpoint, which looks and behaves just like a normal database endpoint.
  • The proxy maintains the long-running connection pool to the database, reused across many client connections and repeated Lambda invocations.
  • The proxy can enforce SSL/TLS and can use existing IAM authentication, including credentials Lambda already has via its execution role.

How It Helps With Failover

This is the standout benefit. Without RDS Proxy, an application connects directly to the database endpoint, and during failover it must wait for the DNS change and reconnect itself. With RDS Proxy:

  1. Clients stay connected to the same proxy endpoint, the whole time.
  2. If the backend database fails over, the proxy detects it and establishes new connections to the new primary in the background.
  3. Client requests simply wait briefly — no reconnect logic needed in the application.
Exam tip
RDS Proxy can reduce Aurora failover time by roughly 60–67% compared to connecting directly. Combined with connection pooling, this is the headline reason RDS Proxy shows up on the exam.

When to Reach for RDS Proxy

ScenarioWhy RDS Proxy helps
"Too many connections" errorsReduces actual DB connection count via pooling and multiplexing
Lambda functions accessing RDS/AuroraAvoids per-invocation connection setup/teardown; reuses a long-running pool
Small/burstable instance classes (T2/T3)Connection overhead is proportionally more expensive on small instances
Long-running SaaS apps needing low latencyNo repeated connection-establishment cost per user interaction
High resilience to DB failureFailover becomes transparent to the application
