NoSQL Database Models

Lesson 02 of 16 · ~8 min

Source: Adrian Cantrill SAA-C03 · Choosing an AWS database service

NoSQL isn't one thing. It's a catch-all for everything that isn't relational — a family of models that trade the rigid schema of SQL for flexibility, scale, or speed. The exam expects you to recognise each model from a scenario description and eliminate the wrong database type. Let's go through them.

ModelStructureBest forAWS example
Key-value Just keys and opaque values — no schema, no relationships Simple lookups, in-memory caching ElastiCache
Wide column Partition key (+ optional sort key); items in a table can have any mix of attributes Massive scale, fast reads/writes, no SQL joins needed DynamoDB
Document Self-contained JSON/XML documents, each with a unique ID; nested attributes are queryable Catalogues, profiles, content management DocumentDB
Column (OLAP) Data physically grouped by column, not row Reporting and analytics over one column at a time Redshift
Graph Nodes (nouns) + edges (named, directional relationships) stored alongside the data Highly interconnected data — social networks, HR systems Neptune

Key-Value: the Simplest Model

A key-value store is nothing more than a list of unique keys, each pointing at a value. The database has no awareness of what's inside the value — text, JSON, a cat picture, it's all opaque. As long as keys are unique, there's no structure to enforce, which makes key-value stores extremely fast and easy to shard across servers.

Exam tip
If a scenario mentions simple key/value pairs, no structure, or in-memory caching, think key-value store.

Wide Column: Key-Value's Scalable Cousin

A wide column store still centres on keys — a mandatory partition key, plus an optional secondary key (DynamoDB calls it the sort key). The only rigid rule: every item in a table must share the same key structure, and that key must be unique.

Unlike a relational table, items don't all need the same attributes. One item can have every attribute, another a mix, another none at all. This is what makes wide column stores like DynamoDB so fast and scalable — there's no schema to enforce across rows.

Document Databases

Think of a document database as key-value with the value made visible to the database. Each document (JSON or XML) has a unique ID, but the database can see and query inside the document — including deeply nested attributes. This suits data that's naturally document-shaped and versioned over time: user profiles, orders, CMS content.

Row vs Column Storage: OLTP vs OLAP

This distinction explains why some databases are built for transactions and others for reporting.

  • Row-based (OLTP) — data for a full row is stored together on disk. Reading or writing one order is efficient; scanning one attribute across every order is not. Most SQL/relational engines are OLTP.
  • Column-based (OLAP) — data is grouped by column instead. Querying "every price ever charged" is efficient because that column sits together on disk, but updating a single row is inefficient. Redshift is AWS's column-store/data-warehousing product.

The common real-world pattern: run transactions on an OLTP (row) database, then periodically shift the data into an OLAP (column) database for reporting and analytics.

Graph Databases

Relational databases compute relationships at query time by joining keys across tables. Graph databases store the relationship itself, as first-class data. Nodes are objects (with key-value properties); edges are named, directional relationships between nodes, and edges can carry their own data too (e.g. an employment start date).

Because the relationship is already stored rather than recalculated, queries over highly interconnected data — "find everyone who works for XYZ Corp" — run far faster than the equivalent relational join.

Exam tip
Scenario mentions social media or complex, fluid relationships? Think graph database first.
