Aurora Multi-Master Writes

Lesson 14 of 16 · ~7 min

Source: Adrian Cantrill SAA-C03 · Amazon Aurora User Guide

The Aurora clusters you've seen so far run in single-master mode: one read-write instance, plus zero or more read-only replicas. Multi-master mode changes this fundamentally — every instance in the cluster can read and write.

Exam tip
Cantrill flags this as a low-priority topic — "not something I expect to immediately feature in detail on the exam." Understand the concept, don't over-invest in memorizing it.

Single-Master: Why Failover Takes Time

In single-master mode, all read/write traffic goes through the cluster endpoint, which points at the primary. If the primary fails, a replica must be promoted from read-only to read-write before traffic can resume — this promotion step is what makes failover non-instant.

Multi-Master: No Promotion Needed

In a multi-master cluster, the same shared storage architecture exists, but there is no cluster endpoint — the application connects directly to individual instances and decides how to distribute operations across them. There's no built-in load balancing.

How a Write Is Committed

  1. An instance receiving a write proposes the change to every storage node in the cluster.
  2. Each node confirms or rejects — rejecting if the change conflicts with another in-flight write.
  3. If a quorum of nodes agrees, the write commits to shared storage. If not, the write is cancelled and an error is returned to the application.
  4. The change is then replicated to other writer instances so their in-memory caches stay current — keeping reads from any instance consistent with what's on disk.

Why This Matters: Fault Tolerance

In single-master mode, if the primary fails, the application loses access to the database until the cluster promotes a new primary and updates the cluster endpoint — a real (if brief) disruption. In multi-master mode, an application that maintains connections to multiple writers simultaneously can simply route all future writes to a surviving writer immediately — with little to no disruption.

Not automatic fault tolerance
Multi-master gives you the foundation for a fault-tolerant application — it doesn't hand you fault tolerance for free. Your application still has to be designed to hold connections to multiple writers and manually load-balance across them; the cluster does none of this on your behalf.
