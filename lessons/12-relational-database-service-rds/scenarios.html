      Scenario 1

      A payroll system stores one row per employee in a table keyed on employee ID. An engineer proposes inserting a second row that reuses an existing employee ID after the employee changes department, since the department value differs from the first row. Is this a valid design under standard relational rules?

      • A. No — every row must still have a unique primary key value, so reusing the ID would create a duplicate key
      • B. Yes — differing attribute values are enough to make two rows distinct, even with a repeated primary key
      • C. Yes — this becomes valid the moment the table's key is changed to a composite of employee ID and department
      • D. No — but only because relational tables forbid any attribute value from ever repeating across two rows

      Topic: Relational Database Fundamentals

      Correct answer: A

      • A. Correct — every row must have a unique primary key value; inserting a second row with the same employee ID duplicates the key, which a relational table doesn't allow.
      • B. Wrong — this confuses attribute distinctness with primary key uniqueness. Differing department values don't excuse a repeated primary key.
      • C. Wrong — that would only be valid if the table's schema were actually redefined with a composite key first, which isn't what's described; as stated, the table still has a single-column key.
      • D. Wrong — the actual rule is that primary keys must be unique, not that every attribute value must be unique across the whole table; that overgeneralizes the rule.

      Scenario 2

      A startup's product catalog needs new kinds of relationships between products, categories, and suppliers added every few weeks as the business model shifts, and the team wants minimal friction each time a new relationship type appears. Why might a strict relational database create ongoing friction here?

      • A. Because primary keys must be regenerated for every row whenever a new relationship type is introduced
      • B. Because attribute values can only be added after a table's existing relationships are fully removed
      • C. Because the schema, including table relationships, is fixed in advance and rigid to change once data exists
      • D. Because join tables are limited to exactly one composite key per pair of related tables, forever

      Topic: Relational Database Fundamentals

      Correct answer: C

      • A. Wrong — primary keys aren't tied to relationship types and never need regeneration when a new relationship appears.
      • B. Wrong — attributes and relationships aren't linked this way; removing relationships isn't a prerequisite for adding attributes.
      • C. Correct — a relational schema, including the relationships between tables, is declared before data goes in and is rigid to change, which is exactly what makes fast-changing relationship shapes costly to accommodate.
      • D. Wrong — this describes a fabricated constraint; join tables aren't inherently capped at one composite key per table pair.

      Scenario 3

      An engineering team needs a database for a session-cache layer that just stores an opaque blob of session data behind a unique key, with no need for the database to inspect or query anything inside that blob. Which NoSQL model best fits, and why?

      • A. Document database, because it can query deeply nested attributes inside the value that gets stored
      • B. Key-value store, because the database treats the value as opaque and only needs a unique key for lookup
      • C. Wide column store, because it requires a shared key structure across every item in the table
      • D. Graph database, because nodes and edges can represent the relationship between a session and a user

      Topic: NoSQL Database Models

      Correct answer: B

      • A. Wrong — document databases make the value queryable, which is more capability than this scenario needs; the requirement is explicitly that the value stays opaque.
      • B. Correct — a key-value store has no awareness of what's inside the value, making it the simplest and fastest fit when only unique-key lookups of an opaque blob are needed.
      • C. Wrong — wide column stores add structural rules around shared key composition that this simple opaque-blob use case doesn't require.
      • D. Wrong — graph databases exist to make relationships between entities fast to query, but this scenario has no relationships to model at all.

      Scenario 4

      An exam question describes DynamoDB being used with strict all-or-nothing, multi-item update guarantees, explicitly labelled as an "ACID" capability layered onto an otherwise NoSQL database. What feature is most likely being described?

      • A. RDS Multi-AZ synchronous replication, since only relational engines can ever offer ACID guarantees
      • B. DynamoDB's default eventually-consistent read behavior, which already satisfies ACID requirements
      • C. The CAP theorem's partition tolerance guarantee being permanently enabled for the table
      • D. DynamoDB transactions, a feature that layers ACID guarantees onto an otherwise BASE-style database

      Topic: ACID vs. BASE

      Correct answer: D

      • A. Wrong — this isn't a DynamoDB feature at all, and it wrongly claims relational engines are the only source of ACID guarantees.
      • B. Wrong — DynamoDB's default reads are eventually consistent, which is BASE-style behavior, the opposite of ACID's strict consistency.
      • C. Wrong — partition tolerance is a CAP theorem property, not an ACID feature, and isn't something you "enable" for a table.
      • D. Correct — DynamoDB transactions specifically layer ACID-style all-or-nothing guarantees onto DynamoDB, which is otherwise a BASE-style, eventually-consistent database by default.

      Scenario 5

      A team needs to run a niche, recently-released database engine that RDS does not support anywhere in its list of managed engines, and switching engines isn't an option given existing application code. What does this suggest about running that database on EC2 in this specific case?

      • A. It's never justified — RDS should always be re-evaluated regardless of the specific engine requirement
      • B. It's a legitimate justification for choosing EC2, since RDS doesn't offer every database engine or version
      • C. It's unnecessary, because every current and future engine version is eventually added to RDS automatically
      • D. It's only legitimate if the decision comes purely from leadership preference rather than a technical need

      Topic: Databases on EC2

      Correct answer: B

      • A. Wrong — needing an engine or version AWS doesn't offer is called out as a legitimate justification for EC2, not something to dismiss outright.
      • B. Correct — needing a database engine or version RDS doesn't offer is a legitimate reason to run on EC2, even though EC2 is usually the worse option overall.
      • C. Wrong — RDS's engine list is not guaranteed to expand to cover every engine version automatically; this is a fabricated claim.
      • D. Wrong — this reverses the lesson's framing: a pure leadership preference is the justification worth challenging, while a genuine unsupported-engine need is the stronger, legitimate one.

      Scenario 6

      A workload is completely idle most nights and heavy for a few hours each morning, and the team wants a database that can scale down to no compute cost automatically during idle periods. Is a database hosted directly on EC2 well suited to this pattern?

      • A. Yes — the instance can be stopped manually during idle hours, satisfying the automatic scale-to-zero requirement
      • B. Yes — EC2-hosted databases inherit the same automatic pause-and-resume behavior that Aurora Serverless offers
      • C. No — but only because EC2 instances are contractually required to keep running for 24 hours once started
      • D. No — EC2 is simply on or off, and can't scale to zero or burst automatically the way some managed products can

      Topic: Databases on EC2

      Correct answer: D

      • A. Wrong — manually stopping an instance isn't automatic scaling; the requirement was specifically for automatic behavior, which manual stopping doesn't satisfy.

      • C. Wrong — there's no such minimum-runtime requirement; this is a fabricated reason for the correct "no."
      • D. Correct — EC2 has no serverless option; it's on or off, so it can't automatically scale to zero or burst the way some managed database products can.

      Scenario 7

      A company runs its production database on a single EC2 instance backed by one EBS volume, with no additional replication configured. The Availability Zone hosting that instance experiences a full outage. What happens to the database?

      • A. It becomes unavailable, since both the EC2 instance and its EBS volume live in a single AZ with no built-in resilience
      • B. It automatically fails over to a standby EBS volume that AWS maintains in a different AZ by default
      • C. It remains available, since EBS volumes are automatically replicated to a second Availability Zone by default
      • D. It becomes read-only automatically until the Availability Zone recovers, preserving query access

      Topic: Databases on EC2

      Correct answer: A

      • A. Correct — an EC2 instance and its EBS volume both live in one Availability Zone, so if that AZ fails, the database fails unless you've built your own cross-AZ replication.
      • B. Wrong — AWS doesn't automatically maintain a cross-AZ standby EBS volume for you; that architecture has to be built deliberately.
      • C. Wrong — EBS volumes are bound to a single AZ, not automatically replicated across AZs; this is a common but incorrect assumption.
      • D. Wrong — there's no automatic read-only failback behavior for a single-AZ EC2 database; it simply becomes unavailable during the outage.

      Scenario 8

      A team currently runs its app server and database on the same EC2 instance. They plan to eventually migrate the database to RDS but want an intermediate step now that doesn't require re-architecting the application tier. What should they do first, and what's a side effect of placing the two instances in different AZs?

      • A. Move the database into RDS immediately, since RDS migration requires no application changes at all
      • B. Keep both tiers on one instance, since splitting them offers no benefit until RDS migration is complete
      • C. Split the database onto its own instance now; a different AZ than the app tier incurs a small data transfer cost
      • D. Split the database onto its own instance now; a different AZ than the app tier is always free, like same-AZ traffic

      Topic: Databases on EC2

      Correct answer: C

      • A. Wrong — this skips the described intermediate step entirely and overstates how effortless an RDS migration is.
      • B. Wrong — splitting the database out of the monolithic stack is described as a useful first step in its own right, ahead of any RDS migration.
      • C. Correct — splitting the database onto its own instance decouples it from the app tier and eases a later RDS migration; if split across AZs, cross-AZ data transfer carries a small cost, unlike free same-AZ private IP traffic.
      • D. Wrong — cross-AZ data transfer does carry a small cost; only same-AZ private IP traffic is free, so this reverses the actual pricing behavior.

      Scenario 9

      • A. Nothing changes — AWS continues to patch both the OS and the database engine automatically on EC2
      • B. Patching the OS and the database engine, plus owning backup and disaster-recovery planning end-to-end
      • C. Only patching the database engine, since AWS still manages OS patches on EC2 the same way it does on RDS
      • D. Only enabling encryption at rest, since every other operational task remains automated on EC2 by default

      • A. Wrong — this is precisely backwards; on EC2 you patch the OS and the database engine yourself, unlike on RDS.
      • B. Correct — running a database on EC2 means owning both OS and engine patching, plus backup and disaster-recovery planning end-to-end, none of which RDS requires of you.
      • C. Wrong — AWS does not manage OS patching on a self-managed EC2 database the way it does with RDS; OS patching also becomes the team's job.

      Scenario 10

      • A. No — RDS instances are limited to exactly one database each, matching the phrase database-as-a-service
      • B. No — hosting multiple databases on one instance requires Aurora specifically, not standard RDS engines
      • C. Yes, but only if Multi-AZ is enabled first, since a single-AZ instance is capped at one database
      • D. Yes — an RDS instance is more accurately a database server as a service and can host multiple databases

      Correct answer: D

      • C. Wrong — Multi-AZ controls availability, not how many databases an instance can host; there's no such cap being lifted by it.

      Scenario 11

      An architect is defining where a new RDS instance can be placed and wants the flexibility to fail over across at least two Availability Zones, while keeping the instance unreachable from the public internet. What should they configure?

      • A. A DB subnet group listing private subnets across at least two AZs, avoiding public subnets entirely
      • B. A DB subnet group listing a single public subnet, since public addressing is required for Multi-AZ failover
      • C. A DB subnet group listing private subnets, but confined to a single Availability Zone for simplicity
      • D. No subnet group at all, since RDS instances are reachable over the public internet by default like S3

      Topic: RDS Architecture

      Correct answer: A

      • A. Correct — a DB subnet group listing private subnets across at least two AZs keeps the instance off the public internet while giving it the AZ flexibility needed for failover.
      • B. Wrong — public addressing is not required for Multi-AZ failover, and public subnets are strongly discouraged for RDS on security grounds.
      • C. Wrong — a single-AZ subnet group undermines the stated goal of failing over across at least two AZs; best practice is to span multiple AZs.
      • D. Wrong — unlike S3, RDS is not a public service; it runs inside a VPC and requires a DB subnet group to be placed at all.

      Scenario 13

      A team needs the absolute latest committed data guaranteed on failover, and separately wants a scalable way to serve read-heavy reporting queries without impacting the primary. Which replication types map to each of these two needs, respectively?

      • A. Read replicas for guaranteed-latest failover data, and Multi-AZ standbys for scalable reporting reads
      • B. Multi-AZ standbys, synchronous, for guaranteed failover data, and read replicas, asynchronous, for reporting
      • C. Multi-AZ standbys for both needs, since synchronous replication also scales horizontally for reporting reads
      • D. Read replicas for both needs, since asynchronous replication still guarantees zero data loss on failover

      Topic: RDS Architecture

      Correct answer: B

      • A. Wrong — this swaps the two: read replicas are asynchronous and don't guarantee the latest data, and Multi-AZ standbys aren't usable for reads at all.
      • B. Correct — Multi-AZ primary-to-standby replication is synchronous, so the standby always matches the primary for failover; read replicas use asynchronous replication and exist to scale read traffic.
      • C. Wrong — a Multi-AZ standby isn't used for reads at all; it exists purely for failover readiness, not read scaling.
      • D. Wrong — asynchronous read replica replication doesn't guarantee zero data loss on failover, since the replica can lag behind the primary.

      • A. Both are correct — RDS billing scales with query volume, and Multi-AZ standbys are provided free
      • B. Query volume billing is correct, but Multi-AZ does carry an extra cost for the standby instance
      • C. Neither is correct — RDS billing is entirely flat regardless of instance size or storage provisioned
      • D. Neither is correct — billing is based on resource allocation, and Multi-AZ adds cost for the standby

      Scenario 15

      An application connects directly to the DB C-name endpoint of a Multi-AZ instance deployment and issues both read and write queries. During normal operation, with no failover in progress, where do these queries actually go?

      • A. All of them go to the primary — the standby is never used for reads or writes, only failover readiness
      • B. Reads are automatically load-balanced to the standby, while writes are routed only to the primary
      • C. Both reads and writes are split evenly between the primary and standby via C-name load balancing
      • D. All of them go to whichever instance currently has the lowest CPU utilization, primary or standby

      Topic: RDS Multi-AZ: Instance vs. Cluster

      Correct answer: A

      • A. Correct — in Multi-AZ instance mode, all reads and writes go through the primary via the DB C-name; the standby's only job is to be ready for failover.
      • B. Wrong — the standby in instance mode never serves reads; there's no load balancing of read traffic to it at all.
      • C. Wrong — there's no load-balancing behavior built into the C-name in instance mode; it always resolves to the primary.
      • D. Wrong — routing isn't based on CPU utilization; the C-name simply points at the primary until a failover changes that.

      • A. The reader endpoint for writes and admin, and the cluster endpoint for load-balanced reads
      • B. Individual instance endpoints for both reads and writes, since they auto-fail over when connected directly
      • C. The reader endpoint for load-balanced reads, and the cluster endpoint for writes and admin operations

      Scenario 17

      An architect needs to explain why a Multi-AZ cluster deployment typically recovers from a failure faster, around 35 seconds plus log replay, than a Multi-AZ instance deployment's 60–120 seconds. What's the underlying reason?

      • A. Cluster mode skips DNS updates entirely during failover, while instance mode always waits on DNS
      • B. Cluster mode replicates via transaction logs rather than the full storage-level sync instance mode uses
      • C. Cluster mode's readers sit in the same Availability Zone as the writer, avoiding cross-AZ failover delay
      • D. Cluster mode uses manual, administrator-triggered failover, which completes faster than automatic detection

      Topic: RDS Multi-AZ: Instance vs. Cluster

      Correct answer: B

      • A. Wrong — both modes involve an endpoint change on failover; cluster mode doesn't skip DNS mechanics entirely.
      • B. Correct — cluster mode replicates using transaction logs rather than full storage-level synchronous replication, which is what drops its failover time to roughly 35 seconds plus log replay, versus 60–120 seconds for instance mode.
      • C. Wrong — cluster mode readers are placed in different Availability Zones from the writer, not the same one, which is what provides the resilience.
      • D. Wrong — cluster mode failover isn't dependent on a manual administrator trigger; the speed difference comes from the replication mechanism, not who initiates it.

      Scenario 18

      In RDS Multi-AZ cluster mode, a write is being evaluated for durability guarantees. According to the underlying commit rule and hardware model, when is a write considered committed, and what hardware underpins the cluster?

      • A. A write commits once it reaches the writer alone, and the cluster runs on standard EC2 hardware
      • B. A write commits once every reader confirms it, and the cluster runs on standard hardware with EBS only
      • C. A write commits once the writer flushes straight to EBS, bypassing local storage, on Graviton hardware
      • D. A write commits once sent to the writer and confirmed by at least one reader, on Graviton with local NVMe

      Topic: RDS Multi-AZ: Instance vs. Cluster

      Correct answer: D

      • A. Wrong — a commit requires confirmation from at least one reader too, and cluster mode runs on Graviton with local NVMe, not standard EC2 hardware.

      • C. Wrong — writes go to local NVMe storage first and are flushed to EBS afterward, not the reverse.
      • D. Correct — a write is committed once sent to the writer and confirmed by at least one reader, and cluster mode runs on Graviton processors with local NVMe SSD storage, writing locally first before flushing to EBS.

      Scenario 19

      • B. No — manual snapshots are deleted automatically 30 days after creation regardless of any settings

      Scenario 21

      A database experiences data corruption at 9:13am. The most recent automated backup snapshot completed at 1:00am, and RDS writes transaction logs to S3 every 5 minutes. Using point-in-time restore, roughly how close to 9:13am can the database be restored?

      • A. Only back to 1:00am, since point-in-time restore is limited strictly to the most recent snapshot
      • B. To approximately 9:10am, since the nearest snapshot is replayed forward using transaction logs
      • C. Exactly to 9:13am, with zero data loss, since transaction logs capture every write instantly
      • D. This isn't possible at all, since point-in-time restore only works when Multi-AZ is enabled

      Topic: RDS Backups, Snapshots & Restore

      Correct answer: B

      • A. Wrong — transaction logs are replayed on top of the nearest snapshot, extending recovery well past the snapshot's own timestamp.
      • B. Correct — point-in-time restore combines the nearest backup snapshot with transaction logs (captured every 5 minutes), so the database can be restored to close to the failure time, roughly 9:10am.
      • C. Wrong — the recovery granularity is roughly 5 minutes based on transaction log intervals, not instantaneous, so exact zero-loss restore to the failure second isn't guaranteed.
      • D. Wrong — point-in-time restore doesn't require Multi-AZ; it relies on automated backups plus transaction logs, which are captured regardless of Multi-AZ status.

      Scenario 22

      After a production incident, an engineer restores an RDS instance from an automated backup and then simply waits, assuming the original instance's endpoint will start serving the restored data automatically. What actually happens?

      • A. The original endpoint is repointed to the restored data automatically, requiring no application changes
      • B. The restore fails outright, since RDS can't restore automated backups without a manual snapshot present
      • C. The original instance is restored in place, overwriting its current data with the backup's contents
      • D. The restore creates a brand-new instance with a new endpoint, requiring the app to be reconfigured

      Topic: RDS Backups, Snapshots & Restore

      Correct answer: D

      • A. Wrong — the original endpoint doesn't automatically repoint anywhere; restoring produces a separate, new instance and endpoint.
      • B. Wrong — automated backup restores don't require a manual snapshot to exist; automated backups plus transaction logs are enough on their own.
      • C. Wrong — restore is never in-place on the original instance; it always produces a brand-new instance rather than overwriting the existing one.
      • D. Correct — restoring always creates a brand-new RDS instance with a new endpoint, so the application must be updated to point at it; there's no in-place restore.

      Scenario 23

      • A. Automated backups are disabled entirely, not merely shortened, since 0 is a special off value
      • B. Nothing changes in practice, since RDS silently enforces a minimum retention of 1 day regardless

      • D. Automated backups continue as before, but transaction logs stop being written to S3 entirely

      • B. Wrong — there's no silent 1-day minimum being enforced; a value of 0 genuinely turns automated backups off.
      • C. Wrong — manual snapshots are independent of this setting altogether, and automated backups have no hidden 7-day floor.
      • D. Wrong — automated backups don't continue at retention 0; transaction logs are part of the same automated backup mechanism that gets disabled.

      Scenario 24

      A compliance team assumes that because RDS automated backups are stored redundantly across multiple Availability Zones by default, those same backups are also automatically copied to a second AWS Region for disaster recovery. Is this assumption correct?

      • A. Yes — cross-Region backup replication is enabled by default the moment automated backups are turned on
      • B. Yes — cross-Region replication happens automatically once retention is set above 7 days
      • C. No — cross-Region replication of backups and transaction logs must be explicitly enabled, at its own cost
      • D. No — cross-Region replication is only available for manual snapshots, never automated backups or logs

      Topic: RDS Backups, Snapshots & Restore

      Correct answer: C

      • A. Wrong — cross-Region replication is not the default; multi-AZ redundancy within a Region doesn't imply cross-Region copying.

      • C. Correct — backups and transaction logs can optionally be replicated to another Region, but this isn't the default; it must be explicitly enabled, and cross-Region copy plus storage costs apply.
      • D. Wrong — both snapshots and transaction logs can be replicated cross-Region; it isn't limited to manual snapshots only.

      Scenario 25

      A retail application writes a new order to an RDS PostgreSQL primary and, half a second later, reads it back from a same-Region read replica as part of the same checkout flow — the order isn't there yet. What explains this behavior?

      • A. The primary and replica are Multi-AZ partners, and Multi-AZ failover briefly hid the new row
      • B. Read replica replication is asynchronous, so the replica can lag slightly behind the primary
      • C. The replica had already reached its 5-direct-replica limit, so it silently dropped the write
      • D. The checkout flow accidentally wrote to a promoted, now-standalone former replica instead

      Correct answer: C

      • A. Wrong — 16 is the per-secondary-Region limit, not the primary's; this swaps the two numbers.
      • B. Wrong — the primary Region still behaves like a normal Aurora cluster and can hold local read replicas under Global Database.
      • C. Correct — the primary Region behaves like a standalone Aurora cluster: one writer plus up to 15 read replicas, unaffected by any secondary Regions attached.
      • D. Wrong — Global Database doesn't remove the primary's standard replica cap; that cap still applies.

      The primary Region hosting an Aurora Global Database cluster suffers a complete regional outage. The operations team must restore write capability as fast as possible while minimizing data loss. What should they do?

      Topic: Aurora Global Database

      Correct answer: D

      • A. Wrong — a snapshot restore is far slower than promoting an already-replicating secondary and ignores the point of running Global Database.
      • B. Wrong — promoting a secondary Region is a deliberate action the team takes, not an automatic background process.
      • C. Wrong — rebuilding from scratch is slow and defeats the purpose of having secondaries already replicating in near real time.
      • D. Correct — promoting a secondary Region to read-write is the designed recovery path; sub-second replication lag keeps both RPO and RTO low.

      Scenario 54

      • B. A standard Cross-Region Read Replica, since both features use the same storage-layer path

      • D. A standard Cross-Region Read Replica, provided it sits in the same Availability Zone as the primary

      Correct answer: A

      • A. Correct — Global Database's storage-layer replication is purpose-built for this, typically completing in under a second, unlike older cross-Region replication approaches.

      Scenario 55

      A team compares a single-master Aurora cluster to a multi-master one and wants to know specifically why single-master failover takes noticeably longer when the primary instance fails. What is the reason?

      • B. A replica must be promoted to read-write and the cluster endpoint must repoint before writes resume
      • C. Single-master clusters can only run in a single Availability Zone, delaying any failover
      • D. Single-master clusters must complete a full manual snapshot before any replica can be promoted

      Topic: Aurora Multi-Master Writes

      Correct answer: B

      • A. Wrong — both modes share the same underlying cluster storage architecture; storage speed isn't what differentiates failover time.
      • B. Correct — in single-master mode a replica must be promoted from read-only to read-write and the cluster endpoint must repoint before writes can resume, and that promotion step is what makes failover slower.
      • C. Wrong — single-master Aurora clusters span multiple Availability Zones just like multi-master ones; AZ count isn't the distinguishing factor.
      • D. Wrong — no manual snapshot step is required before promotion; failover doesn't depend on taking a fresh backup first.

      Scenario 56

      In a multi-master Aurora cluster, two instances each receive a write to the same row at nearly the same moment. What determines whether either write actually commits?

      • A. The cluster endpoint arbitrates between the two instances and forwards only one write
      • B. Both writes are applied immediately, and a background job reconciles conflicts afterward
      • C. Each write needs quorum confirmation from storage nodes; one failing to reach quorum is rejected
      • D. All writes cluster-wide pause automatically until an administrator resolves the conflict

      Topic: Aurora Multi-Master Writes

      Correct answer: C

      • A. Wrong — multi-master clusters have no cluster endpoint at all, so nothing exists to arbitrate between instances this way.
      • B. Wrong — conflicting writes aren't both applied and merged later; a quorum-based confirmation process resolves this at commit time.
      • C. Correct — the instance receiving a write proposes it to every storage node; if a quorum confirms, it commits, and a write that fails to reach quorum is cancelled with an error returned to the application.
      • D. Wrong — writes aren't paused cluster-wide for manual review; conflicting writes are rejected individually through the quorum mechanism.

      Scenario 60

      A fleet of Lambda functions each open a new direct connection to an RDS for MySQL database, on a small db.t3.medium instance, on every invocation. During traffic spikes they see "too many connections" errors even though CPU and memory are barely used. What is the best fix?

      • B. Add read replicas so Lambda invocations can spread connections across more instances
      • C. Put RDS Proxy in front of the database to pool and multiplex the short-lived connections
      • D. Resize to a larger instance class purely to raise the raw connection ceiling

      Topic: RDS Proxy

      Correct answer: C

      • A. Wrong — backup retention has no relationship to how many concurrent connections a database can serve.
      • B. Wrong — each replica still needs its own set of connections; spreading direct connections across more instances doesn't solve pooling, it just relocates the problem.
      • C. Correct — RDS Proxy maintains a long-lived connection pool and multiplexes many client connections over fewer actual database connections, which is exactly the fix for connection exhaustion on a small instance class.
      • D. Wrong — this treats the symptom, not the cause, and is the costlier route; the lesson frames this exact overhead-on-small-instances scenario as RDS Proxy's headline use case instead.

      • C. Wrong — Aurora Serverless changes the compute/billing model; it doesn't eliminate failover time or the reconnect problem described here.

      Scenario 66

      A company must migrate a live production database to RDS with essentially zero downtime, meaning changes made to the source during the migration window must not be lost at cutover. Which DMS task type should they choose?

      • B. Full load only, since it captures the complete dataset in a single consistent pass
      • C. CDC only, since it captures every change made to the source database
      • D. Schema Conversion Tool, since it replicates both schema and ongoing data changes

      Topic: Database Migration Service (DMS)

      Correct answer: A

      • A. Correct — full load + CDC migrates existing data and captures ongoing changes during the migration, letting the team cut over once changes reach a steady state with nothing lost.
      • B. Wrong — full load alone only migrates existing data; any changes made to the source during the copy would be missed at cutover, violating the zero-loss requirement.
      • C. Wrong — CDC only assumes the bulk data was already loaded some other way; used alone here it would miss the initial dataset entirely.
      • D. Wrong — SCT converts schema and code objects; it doesn't perform data migration or change capture on its own.
