Lesson 10 of 16 · ~5 min

This is a deliberately short lesson — RDS Custom is a niche product. You need a surface-level understanding for the exam, not deep expertise.

Filling the Gap Between RDS and EC2

Standard RDS gives you a fully managed database server, but no OS or engine-level access. Running a database on EC2 gives you full access, but you own everything — OS patching, engine patching, backups, HA, all of it (see Lesson 04). RDS Custom sits in between: RDS-style automation, plus the ability to customize the OS and engine.

Exam tip
RDS Custom currently supports only Oracle and SQL Server. If a scenario needs low-level engine access on MySQL/MariaDB/PostgreSQL, RDS Custom isn't the answer — EC2 is.

Database Automation Pausing

Because RDS Custom still runs RDS-style automation in the background, any manual customization risks conflicting with it. Before making changes, you must pause database automation, perform the customization, then resume automation — ensuring the instance is production-ready again.

Shared Responsibility Shifts

Moving along the spectrum from on-premises → EC2 → RDS → RDS Custom changes who owns what:

  • On-premises: customer owns everything.
  • EC2: AWS owns hardware only; customer owns OS, engine, patching, backups, HA, scaling.
  • RDS: AWS owns everything except application optimization.
  • RDS Custom: AWS owns hardware; customer owns application optimization; everything else is shared between AWS and customer.

RDS Custom trades some of RDS's full automation for the flexibility of OS/engine access — a middle ground for legacy or highly customized applications that genuinely can't run on standard RDS.
