RDS & Aurora

Amazon Aurora Architecture

Lesson 11 of 16 · ~10 min

Source: Adrian Cantrill SAA-C03 · What is Amazon Aurora?

Aurora is technically part of the RDS family, but its architecture is different enough that it's best treated as its own product. Two changes drive almost everything else in this lesson: Aurora is built around a cluster, and it uses shared storage instead of per-instance storage.

Compute: One Writer, Many Usable Readers

An Aurora cluster has a single primary (writer) instance and zero or more replicas. Unlike an RDS Multi-AZ standby, Aurora replicas are usable for reads during normal operation — meaning a single Aurora cluster gives you both the availability benefit of Multi-AZ and the read-scaling benefit of read replicas, without having to choose.

Aurora supports up to 15 replicas, and any of them can be a failover target — a big jump from RDS's single standby.

Storage: Shared Cluster Volume

Aurora compute instances don't have local storage. Instead, the cluster has one shared cluster volume — SSD-based, spanning 6 storage nodes across 3 Availability Zones. Every instance in the cluster (writer and replicas) has access to all of it.

  • Writes are synchronously replicated across all 6 storage nodes at the storage layer — no extra compute resources are consumed on any instance to do this.
  • By default, only the primary can write; replicas and the primary can all read.
  • Aurora self-heals disk segment failures automatically, using data from the other storage nodes — reducing the need for point-in-time or snapshot restores after a disk failure.
  • Because storage belongs to the cluster, not individual instances, adding or removing replicas doesn't require provisioning or de-provisioning storage — replica changes are fast.
Storage limit — check current figures
Cantrill's course states a 128 TiB cluster storage ceiling. AWS's current documentation lists up to 256 TiB. AWS raises these limits over time — for the exam you're studying, treat 128 TiB as the traditionally-taught figure, but verify against the current Aurora User Guide if precision matters.

Billing: Consumption, Not Provisioning

You don't pre-allocate Aurora storage — you're billed on consumption, based on a high-watermark: if you use 50 GiB, you're billed for 50 GiB, even after freeing 10 GiB back down to 40 GiB actually stored. To meaningfully reduce storage cost, you'd need to create a new cluster and migrate the data across.

Watch for changes
Cantrill notes AWS was, at time of recording, moving away from this high-watermark billing model for newer Aurora versions. Confirm current behaviour before relying on this detail heavily for a real deployment.

Endpoints

EndpointPoints at
Cluster endpointAlways the primary — for reads and writes
Reader endpointLoad-balances across all available replicas (falls back to the primary if there are none)
Custom endpointsUser-defined subsets of instances
Instance endpointsOne per instance — direct access, mainly for testing

As you add replicas, the reader endpoint automatically incorporates them — read scaling requires no manual endpoint management.

Advanced Recovery Features

Backtrack
Roll an Aurora cluster back in place to a previous point in time — no new cluster, no application reconfiguration. Must be enabled per-cluster.
Fast clone
Create a new database from an existing one almost instantly. The clone doesn't copy all the data — it references the original storage and only stores the differences that accumulate afterward.
Exam tip
No free tier for Aurora — it doesn't support the micro instance classes the free tier relies on. Backups (up to 100% of your consumed storage) are typically included in the price you already pay for the cluster.
