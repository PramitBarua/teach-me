Amazon Athena

Lesson 09 of 12 · ~9 min

Source: Adrian Cantrill SAA-C03 · What is Amazon Athena? · Use Amazon Athena federated query · Query Apache Iceberg tables

Athena is a serverless, interactive query service: it lets you run ad hoc SQL queries against data sitting in S3, with no infrastructure to provision, no data loading, and no ETL required first. You pay only for the data your query actually scans, plus the normal S3 storage cost of the underlying data — there's no base monthly fee and no per-hour charge for idle capacity.

Schema-on-Read

The concept that makes Athena work is schema-on-read. Think of the schema as a lens or a window you look through, not something that changes what's behind it: the source data in S3 is never modified. You define tables that describe how to translate the raw S3 data into a queryable, table-like structure, and that translation happens transiently, in flight, only at the moment a query runs. Nothing is loaded or transformed in advance — the "table" in Athena is really just a set of directions for reading the original files, not a copy of the data itself.

Athena supports a wide and steadily growing range of source formats: JSON, CSV/TSV, Avro, Parquet, ORC, and common log formats such as Apache web server logs, CloudTrail, and VPC Flow Logs. It also integrates with the Glue Data Catalog for storing and looking up table/schema metadata.

Where Athena wins: ad hoc, sporadic, log-driven
Athena is the right call whenever a scenario describes infrequent or ad hoc querying of data already sitting in S3 — standing up a database or running an ETL pipeline just to answer an occasional question would be wasted effort. It's also the default exam answer for cost-conscious querying of AWS service logs specifically: VPC Flow Logs, CloudTrail, ALB/ELB access logs, and Cost and Usage Reports are strong keyword matches for Athena.

Federated Query: The One Exception to a Reliable Rule

Normally, if an exam question mentions SQL, NoSQL, or names a specific database product, Athena is probably not the right answer — Athena's whole premise is querying files in S3, not another database engine. Athena Federated Query is the deliberate exception to that rule. It uses Lambda-based data source connectors that let Athena reach into systems that aren't S3 at all, translating between Athena's query engine and the target source. Pre-built connectors exist for sources like CloudWatch Logs, DynamoDB, DocumentDB, and Amazon RDS, as well as other JDBC-compliant relational databases such as MySQL and PostgreSQL.

Exam trap: "database mentioned" doesn't always rule out Athena
If a question names a specific database and frames it as something Athena needs to query alongside S3 data, Federated Query is exactly that scenario — don't reflexively eliminate Athena the instant a database name appears. Check whether federation, not a plain "which database service" choice, is what's being tested.

Update Since the Course Was Recorded: Athena Can Now Write, Not Just Read

The original course material treats S3 data as read-only from Athena's perspective — a defensible simplification at the time. That has genuinely changed: Athena now supports the Apache Iceberg table format, and Iceberg tables in Athena support real INSERT, UPDATE, DELETE, and MERGE INTO operations, along with time-travel queries against earlier snapshots. This is powered by Iceberg's own transaction model — Athena writes row-level changes as delete files rather than rewriting whole data files — and it gives Athena genuine ACID semantics for tables built on Iceberg.

What this changes for the exam
"Athena only reads, never writes" is no longer an absolute rule — it's now true for standard/classic Athena tables, but not true for Iceberg-format tables, which support full read-write DML. If a scenario specifically calls out Iceberg tables or asks about updating/deleting rows queried through Athena, this capability is the relevant answer; for everything else, the classic "Athena is read-only against S3" framing still holds.
