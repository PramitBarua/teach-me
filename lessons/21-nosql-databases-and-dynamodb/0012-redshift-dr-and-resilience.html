Amazon Redshift: DR and Resilience

Lesson 12 of 12 · ~7 min

Source: Adrian Cantrill SAA-C03 · Amazon Redshift snapshots and backups · Multi-AZ deployments for Amazon Redshift

The previous lesson ended on a critical risk: a classic Redshift cluster runs its nodes in a single Availability Zone, so an AZ failure is a real threat to the cluster. This lesson picks up exactly there — how Redshift's backup features let you manage that risk, even though the live cluster itself isn't natively spread across AZs.

Automatic Snapshots

Redshift takes automatic snapshots to S3 roughly every 8 hours, or every 5 GB of data change — whichever comes first. By default these are retained for 1 day, configurable up to 35 days. Backup storage up to the size of your cluster's own capacity is included free with the cluster. Snapshots are incremental, so only the data that actually changed since the last snapshot is stored and charged for.

Manual Snapshots

You can also trigger a manual snapshot explicitly — by a person, a script, or a management tool. Unlike automatic snapshots, manual snapshots have no automatic expiry: they persist indefinitely until someone removes them. That makes them the right tool for deliberate, longer-term retention points you want to keep around on purpose.

The mechanism that actually makes Redshift resilient
Both snapshot types land in S3 — and the moment they do, they inherit S3's own multi-AZ durability, even though the live cluster itself still runs in only one AZ. This is the key idea to hold onto: the cluster is single-AZ, but the backup data is not. Resilience comes from where the backups live, not from the cluster's own architecture.

Restoring: Always a New Cluster

Restoring from any snapshot — automatic or manual — creates a brand-new cluster. Critically, when you restore, you can choose to provision that new cluster into a different, working Availability Zone — directly solving the case where the original AZ has failed. Recovery is never "repair the old cluster in place"; it's always "stand up a new one from the snapshot."

Regional Disaster Recovery

For resilience against a problem affecting an entire AWS Region, snapshots can be configured to automatically copy to another Region. The copied snapshots can have their own independently configurable retention period, which helps control cross-Region storage cost separately from the source Region's retention policy. If the original Region has a major event, a new cluster can be provisioned quickly from those copied snapshots in the destination Region.

Exam heuristic
Redshift resilience questions are really testing one idea: the cluster is single-AZ, but the backup data — via S3-backed automatic and manual snapshots — can be made multi-AZ, and even multi-Region with cross-Region snapshot copy. Recovery always means restoring into a new cluster, whether in a different AZ or a different Region, never patching the original cluster back to life.
Remember: Multi-AZ deployments are now a direct alternative
The previous lesson flagged that Redshift Multi-AZ deployments are now generally available for RA3 clusters — compute spread live across two AZs behind one endpoint. That's a materially different resilience story from what this lesson covers: snapshot-based recovery still means provisioning a new cluster after a failure, whereas a genuine Multi-AZ deployment keeps the original cluster serving queries through an AZ failure in the first place. If a scenario demands continuous availability through an AZ failure with no restore step, Multi-AZ is the more direct answer; if it's about surviving data loss or standing up a replacement cluster (including cross-Region), snapshots are still the mechanism being tested.
