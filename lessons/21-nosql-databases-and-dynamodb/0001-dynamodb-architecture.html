NoSQL Databases and DynamoDB

DynamoDB Architecture

Lesson 01 of 12 · ~8 min

Source: Adrian Cantrill SAA-C03 · DynamoDB table classes · Point-in-time recovery for DynamoDB

DynamoDB is a NoSQL, wide-column, key-value database as a service. That last phrase is precise on purpose: products like RDS or Aurora are database-server-as-a-service — you still get a server, even if AWS manages it. DynamoDB skips the server entirely. There is no instance to size, patch, or fail over. You interact with tables, and AWS handles everything underneath them.

The keyword heuristic
If an exam question mentions NoSQL or key-value data, default to DynamoDB unless something strongly rules it out. If a question mentions relational data or SQL (structured query language), DynamoDB is almost certainly not the answer — it has no query language, no joins, and isn't designed for relational modeling.

Public Service, No Infrastructure

DynamoDB is a public service: it's reachable from anywhere with access to its public endpoints, which means the public internet, or from inside a VPC via an internet gateway or a gateway VPC endpoint. There's no concept of placing DynamoDB "inside" a VPC the way you would an EC2 instance — you're always talking to a shared, AWS-operated endpoint.

Under the hood, data is replicated across multiple storage nodes in multiple Availability Zones by default, so multi-AZ resilience is automatic and not something you configure. Global resilience — spreading a table across Regions — is an optional extra, covered in a later lesson on Global Tables. DynamoDB is backed by SSD storage and delivers single-digit-millisecond latency for typical operations.

Tables, Items, and Primary Keys

The table is the base entity in DynamoDB — arguably, DynamoDB is really a database-table-as-a-service product. A table is a grouping of items that all share the same primary key structure. Think of an item roughly like a row in a relational table. A table can hold an unlimited number of items — there's no cap on item count.

Every table needs a primary key, chosen at creation time, and it comes in one of two shapes:

Simple primary key
Just a partition key (PK). Every item's PK value must be unique in the table.
Composite primary key
A partition key (PK) plus a sort key (SK). Individual items can share a PK, but the combination of PK and SK must be unique.

Beyond the primary key, items are flexible: two items sharing a table can have no other attributes, completely different attributes, or entirely overlapping ones. DynamoDB doesn't enforce a schema on non-key attributes at all. The one hard limit is item size: a single item — primary key, attribute names, and attribute values combined — can be at most 400 KB.

Capacity Is About Speed, Not Space

"Capacity" is a slightly misleading term here — it sounds like storage, but in DynamoDB it means throughput. Adding capacity means adding more read or write speed, not more room. Tables can use provisioned capacity, where you set explicit values, or on-demand capacity, where DynamoDB scales automatically and you pay per operation.

With provisioned capacity, two units matter:

  • Write Capacity Unit (WCU) — one WCU allows one write of up to 1 KB per second.
  • Read Capacity Unit (RCU) — one RCU allows one strongly consistent read of up to 4 KB per second.

Most operations have a minimum consumption — a read of even 100 bytes still consumes at least 1 RCU, rounding up. Capacity mechanics get a full treatment in the next lesson; for now, just anchor the two unit definitions and the "capacity means speed" framing.

Two Kinds of Backup

Backup typeHow it worksRestore behavior
On-demand backupManual, full backup of a table, similar to an RDS manual snapshot. Retained until you remove it yourself.Restorable same-Region or cross-Region; you can adjust encryption settings during restore.
Point-in-time recovery (PITR)Opt-in per table, disabled by default. Once enabled, gives a continuous, rolling 35-day window of changes.Restores to a new table, with 1-second granularity anywhere in that 35-day window.

With on-demand backups, you're responsible for taking them and for cleaning up old ones when they're no longer needed. PITR, once switched on, runs continuously in the background with no manual snapshot step.

A newer table class: Standard-IA
Beyond the original Standard table class, DynamoDB now also offers a Standard-Infrequent Access (Standard-IA) table class. It cuts storage costs by roughly 60% compared to Standard, in exchange for higher per-request read/write pricing — a natural fit for tables dominated by storage cost rather than request volume, such as long-retained logs or historical order records. Performance, durability, and availability are identical to Standard, and you can switch table classes without any application code changes. Table class sits alongside capacity mode as another cost lever on a per-table basis.

Billing

Billing is per table, driven by the RCU/WCU settings (or on-demand request volume), the storage consumed, and any additional features enabled, such as PITR or streams. There's no base infrastructure cost — you only pay for what a table actually uses. For predictable long-term workloads, reserved capacity is available: commit for the longer term and get a discounted rate in return.
