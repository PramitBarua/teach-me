This lesson covers DynamoDB's two capacity modes in more depth, the mechanics of capacity units, and the crucial difference between Query and Scan — two operations the exam loves to test against each other. Part 2 continues directly from where this lesson ends.

On-Demand vs. Provisioned Capacity

Every table picks one of two capacity modes at creation, and — with some restriction — you can switch between them afterward. On-demand suits unknown or unpredictable load, or simply a strong preference for zero admin overhead: DynamoDB scales for you automatically, and you pay a per-operation price. That convenience has a cost — on-demand pricing can run as much as 5x the equivalent provisioned price. Provisioned capacity means you explicitly set Read Capacity Units (RCU) and Write Capacity Units (WCU) on the table, optionally paired with auto scaling.

Capacity Unit Mechanics

Whichever mode you use, the same underlying math applies:

  • 1 WCU = one write of up to 1 KB, per second.
  • 1 RCU = one strongly consistent read of up to 4 KB, per second.

Critically, every operation consumes at least one whole unit — usage always rounds up. Read 100 bytes, and you still pay for a full RCU. An item up to the 400 KB maximum would consume 100 RCU to read in a single operation.

The burst pool is an emergency reserve, not a budget line
Every table carries a burst pool worth 300 seconds of its provisioned RCU/WCU. Lean on it sparingly — background table-maintenance tasks compete for that same pool, so heavy reliance on it is risky. Deplete the pool while demand still exceeds capacity, and you'll get a ProvisionedThroughputExceededException: requests are throttled until you retry or raise the table's capacity.

Query: Efficient, But Needs a Partition Key

Picture a weather-station table: partition key is station ID, sort key is day. Each item stores one day's reading for one station.

The Query operation always requires exactly one partition key value — you can't query across multiple stations in a single call. Query can return zero items, one item, or many items, and you can optionally narrow the result with a specific sort key value or a range of them. Query for station 1 with no sort key filter, and you get every reading ever logged for that station; add a sort key range, and you narrow it to specific days.

One big Query beats many small ones
Because every operation has that one-unit minimum floor, retrieving several items in a single Query is always more capacity-efficient than issuing separate Query calls for each item. Two 1.5 KB items fetched together might cost 1 RCU total; fetched as two separate single-item queries, each pays its own rounded-up minimum — costing more overall for identical data.

One more subtlety: Query lets you request only specific attributes back from an item, but billing is based on the full item size regardless. Whatever you filter out is simply discarded after being read — you still pay for it.

Scan: Flexible, But Expensive

Suppose you need every weather-station reading, across every station, where a "sunny day" attribute is set — that attribute is neither the partition key nor the sort key. Query can't help here, since Query only ever works against one partition key value. This is what Scan is for.

Scan walks the entire table, item by item, and can filter on any attribute at all — not just keys. That flexibility is exactly why it's expensive: DynamoDB charges for the capacity of every item scanned, whether or not that item ends up in the filtered result. Scan four items totaling 14 KB looking for sunny days, and you're billed for all 14 KB rounded up to whole RCU, even if only two items actually matched.

The exam heuristic
Need data for one specific, known partition key value? Reach for Query. Need to search on an attribute that isn't part of the key, across the whole table? That requires Scan — and Scan is the most flexible operation DynamoDB offers, but also the most costly.
