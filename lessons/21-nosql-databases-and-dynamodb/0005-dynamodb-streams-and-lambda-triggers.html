DynamoDB Streams & Lambda Triggers

Lesson 05 of 12 · ~7 min

Source: Adrian Cantrill SAA-C03 · Change data capture for DynamoDB Streams · DynamoDB Streams and AWS Lambda triggers

A DynamoDB Stream is a time-ordered, 24-hour rolling window of item-level changes — inserts, updates, and deletes — captured for a table. Streams are enabled on a per-table basis, and behind the scenes they're backed by Kinesis Streams. On their own, streams are just a record of change. Paired with Lambda, they become the foundation of an entirely serverless, event-driven architecture.

Four Stream View Types

When you enable a stream, you choose what information each captured change actually contains:

KEYS_ONLY
Just the key attributes of the changed item. Consumers must read the table themselves to learn what actually changed.
NEW_IMAGE
The full item state after the change.
OLD_IMAGE
The full item state before the change.
NEW_AND_OLD_IMAGES
Both pre- and post-change state together, letting a consumer diff the change without ever touching the table.

All four view types apply equally to inserts, updates, and deletes — with the obvious caveat that a delete has no meaningful "new" state, and an insert has no meaningful "old" state.

Streams + Lambda = Triggers

The real power shows up when a stream is paired with Lambda to build a trigger: an item change generates a stream event, and that event automatically invokes a Lambda function. There's no polling involved anywhere in this chain — the whole thing is event-driven and serverless from end to end.

The exam heuristic
Whenever a scenario needs an event-driven reaction to DynamoDB data changes — without constant polling and without managing servers — think Streams + Lambda triggers.

Real-World Use Cases

  • Reporting and analytics — generating a report the moment a tracked item changes.
  • Aggregation — tallying votes in a voting app, or rolling up stock-level changes as they happen.
  • Messaging and notifications — pushing a notification the instant a new chat message is written to a table.

All three share the same underlying win: instead of a compute resource constantly polling a table to check for changes — burning cycles even when nothing has happened — the architecture reacts only when a real change occurs, consuming the minimum compute necessary.
