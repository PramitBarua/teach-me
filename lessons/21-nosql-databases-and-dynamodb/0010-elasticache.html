Amazon ElastiCache

Lesson 10 of 12 · ~9 min

Source: Adrian Cantrill SAA-C03 · What is Amazon ElastiCache? · Scaling ElastiCache Serverless clusters

ElastiCache is a managed in-memory data store. Where a database like RDS ultimately persists data to disk — and is therefore always bound by disk-level performance limits, however fast the disk — an in-memory store holds data in memory, delivering throughput and latency an order of magnitude better. The tradeoff is that it isn't persistent by default and is meant for temporary, fast-access data rather than a system of record. ElastiCache offers two engine choices, Redis and Memcached, both delivered as a fully managed service and both supporting a wide range of programming languages.

What ElastiCache Is Actually Used For

Two use cases dominate the exam and real-world deployments:

  • Caching for read-heavy workloads. Databases — relational ones especially — don't scale reads cheaply or easily. Offloading repeated reads to ElastiCache reduces load on the backend database and, at scale, reduces cost.
  • Externalizing session state. Storing user session data in ElastiCache rather than on the application instance itself lets application servers be fully stateless. That matters most behind a load balancer and Auto Scaling group: if one instance fails, another instance can pick up the same session data from the cache and continue seamlessly — the difference between an application that's merely highly available and one that's genuinely fault tolerant.
Exam trap: ElastiCache is not invisible
ElastiCache is not a drop-in optimization you bolt on without touching your code. The application has to actively know about the cache: check it first, fall through to the database on a miss, write the result back, and handle invalidation. If a scenario explicitly states "no application changes," ElastiCache is the wrong answer — full stop.

Redis vs. Memcached

Both engines deliver sub-millisecond access and support the same broad range of client languages, but they diverge sharply beyond that:

RedisMemcached
Rich data structures — lists, sets, sorted sets, hashes, bitmaps (e.g. a sorted set for a game leaderboard)Simple strings only
Multi-AZ replication with read replicas — true high availabilityNo true replication; nodes can be manually sharded but each is expendable
Backup and restore — persistence supportedNo persistence or backup capability at all
Supports transactions — all-or-nothing multi-operation atomicityNo transaction support
Single-threaded per nodeMulti-threaded — better multi-core utilization
Exam heuristic
If a question mentions Multi-AZ, high availability, complex data structures (lists, sets, sorted sets, leaderboards), persistence/backup, or transactions, that's Redis. If it's a simple caching need with heavy multi-core throughput demands and no HA requirement, that points to Memcached.

Update Since the Course Was Recorded: ElastiCache Serverless

The classic architecture the transcript describes — sizing and managing individual cache nodes yourself — is still fully current and still the foundation the exam tests. But AWS has since added ElastiCache Serverless: a deployment option with no cache nodes to size or manage at all. It automatically scales compute, memory, and network bandwidth up and down based on real-time demand, replicates data across multiple Availability Zones for high availability, and bills based on actual data stored and compute consumed rather than provisioned node capacity.

How to think about it for the exam
Treat ElastiCache Serverless as a modern alternative to the provisioned-node model, not a replacement for the underlying Redis-vs-Memcached decision — you still choose an engine, and the same engine tradeoffs (data structures, persistence, transactions) still apply. Serverless just removes the capacity-planning step. If a scenario emphasizes not wanting to size or manage nodes, Serverless is the fit; if it's testing Redis vs. Memcached fundamentals, the classic node-based framing still applies.
