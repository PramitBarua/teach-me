DynamoDB Global Tables

Lesson 06 of 12 · ~8 min

Source: Adrian Cantrill SAA-C03 · Global tables: multi-active, multi-Region replication · DynamoDB global tables versions

Global Tables extend a DynamoDB table across multiple AWS Regions using multi-master replication — no single table is "the" master with others as replicas. Every regional table is a peer, equally able to serve reads and writes. To set one up, you create a table in each participating Region, then link them together from any one of them into a single global table configuration; DynamoDB handles replication between every replica from that point on.

Conflict Resolution: Last-Writer-Wins

Because any Region can write to the same item at nearly the same time, DynamoDB needs a conflict-resolution rule. It uses last-writer-wins: simple and predictable, but it means that if the same item is written concurrently in two Regions, one of those writes is silently overwritten by the other, more recent one. Replication between Regions is typically sub-second.

Consistency Across Regions

Strongly consistent reads are only possible in the same Region as the write that produced the data. Anything cross-Region is necessarily eventually consistent, because inter-Region replication is asynchronous. An application built on Global Tables has to be designed to tolerate that — there's no way to request a strongly consistent read of data written in a different Region.

The consistency rule to memorize
Same Region as the write → strong or eventual consistency, your choice. Different Region than the write → eventual consistency only, no exceptions.

Use Cases

  • Globally available applications that need to keep serving traffic even if one Region has issues.
  • Improved global latency — reading and writing from whichever Region is closest to the user.
  • Disaster recovery and business continuity for a data layer, without building custom cross-Region replication yourself.
Terminology and feature parity have moved on since this was recorded
Current AWS documentation now describes this feature as multi-Region, multi-active replication — functionally the same "every replica is a peer" idea as "multi-master," just AWS's newer preferred phrasing. More substantively, the version of global tables in use today (2019.11.21, labeled "Current" in the console and CLI, versus the older "2017.11.29 Legacy") closes several gaps that older material sometimes describes as limitations: it now synchronizes TTL settings and TTL-driven deletes, auto scaling settings, GSI settings, and encryption-at-rest settings automatically across every replica, and it's available in all AWS Regions rather than a limited set. It's also cheaper — it consumes fewer replicated write capacity units per write than the legacy version. For the exam, the architectural picture taught here (multi-master/multi-active, last-writer-wins, sub-second replication, region-scoped strong consistency) still holds; just be aware "Global Tables" today means this newer, more capable version by default.
