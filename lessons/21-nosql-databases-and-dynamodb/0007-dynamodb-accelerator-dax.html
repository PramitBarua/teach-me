DynamoDB Accelerator (DAX)

Lesson 07 of 12 · ~8 min

Source: Adrian Cantrill SAA-C03 · In-memory acceleration with DynamoDB Accelerator (DAX) · DAX: How it works

DAX is an in-memory cache for DynamoDB. That description alone could apply to almost any cache sitting in front of almost any database — the part that matters for the exam is what makes DAX different from a generic cache you'd bolt on yourself: it's purpose-built and tightly integrated with DynamoDB specifically, which removes most of the admin overhead a generic caching layer normally demands.

A Generic Cache vs. DAX

Picture a traditional in-memory cache sitting beside DynamoDB. The application checks the cache first. On a cache miss, the application itself has to query DynamoDB directly, take the result, write it back into the cache, and only then return it to the caller. Every one of those steps — checking, falling through, writing back, invalidating — is application logic the developer has to build and maintain. The cache and the database are two entirely separate systems that happen to sit next to each other.

DAX collapses that into one API surface. The application installs the DAX SDK and talks to a single DAX endpoint as if it were talking to DynamoDB itself. If DAX already has the data, it's a cache hit and DAX returns it directly. If not, DAX itself goes to DynamoDB on the application's behalf, retrieves the data, populates its own cache, and returns the result — all invisible to the calling application. There's one set of API calls, one SDK, and DAX quietly handles the cache-miss round trip that a generic architecture would have forced the application to manage itself.

Cluster Architecture

DAX runs as a cluster deployed inside a VPC, spread across multiple Availability Zones for high availability. One node is the primary node, which handles both reads and writes; the rest are replica nodes, which serve reads only. If the primary node fails, the cluster holds an election and promotes one of the replicas to become the new primary — the same failover pattern you'd expect from any AZ-aware cluster service. Clients connect through a single cluster endpoint that load-balances requests, much like connecting to an RDS endpoint.

DAX brings its own VPC requirement
DynamoDB itself is a public AWS service — no VPC needed. DAX is the exception: because the DAX cluster is deployed inside a VPC, any application that wants to use DAX must also be deployed inside that same VPC. This is a real architectural constraint, not a detail — it's the kind of fact an exam question can hinge on.

Two Internal Caches

DAX actually maintains two separate caches internally:

  • The item cache holds individual items retrieved via GetItem or BatchGetItem, keyed by the item's partition key (and sort key, if the table has one).
  • The query cache holds the results of Query or Scan operations — but critically, it stores the exact parameters used alongside the result set. That means if the same query or scan is re-run with identical parameters, DAX can serve the whole result set straight from cache rather than touching DynamoDB again.

DAX also supports write-through caching: writes made via the DAX SDK are committed to DynamoDB and written into the cache at the same time, keeping the two in sync without extra application logic. If a cache miss occurs during a read, the retrieved data is written into the primary node and then replicated out to the replica nodes.

Performance

Cache hits from DAX typically return in microseconds — the transcript cites roughly 400 microseconds as a representative figure. Cache misses still fall back to DynamoDB's own native performance, which is single-digit milliseconds. So the worst case with DAX is "as fast as DynamoDB normally is," and the best case is an order of magnitude faster. DAX scales in both directions: scale up with larger node types, or scale out with more nodes in the cluster.

Exam heuristic: caching + DynamoDB defaults to DAX
Whenever a question describes a caching requirement layered on top of DynamoDB, default to DAX and only move away from that assumption if the scenario gives you a specific reason not to. The one reason that reliably rules DAX out: a requirement for strongly consistent reads. DAX cannot serve strongly consistent reads at all — if the scenario insists on them, DAX is the wrong answer regardless of how read-heavy the workload is.

When to Reach for DAX — and When Not To

DAX fits well when a workload is read-heavy or bursty — for example, a sudden spike in reads during a sale, or a table that always gets hammered with reads at certain times. It also fits when the same hot data is read over and over (perhaps a small, popular slice of a much larger table), or when an application is latency-critical and needs microsecond-level response times. Beyond performance, DAX can meaningfully reduce cost: rather than provisioning large RCU values to absorb repeated reads of the same data, offloading those reads to DAX can be markedly cheaper.

DAX is a poor fit when an application needs strongly consistent reads it cannot do without, when the workload isn't latency-sensitive at all, or when the workload is write-heavy with little repeated reading of the same data — in that last case, there's simply not much for a cache to do.
