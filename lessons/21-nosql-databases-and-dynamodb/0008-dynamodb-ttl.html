DynamoDB Time to Live (TTL)

Lesson 08 of 12 · ~6 min

Source: Adrian Cantrill SAA-C03 · Enable time to live (TTL) in DynamoDB · Working with expired items and time to live (TTL)

TTL, Time to Live, is a simple idea with real exam and real-world weight: it lets you mark items in a DynamoDB table so they're automatically deleted once they're no longer needed — no scheduled job, no manual cleanup script, no application code required to enforce it.

Exam tip — flagged in the course diagram
The single highest-yield fact in this lesson: the TTL attribute holds a timestamp — the number of seconds since the Unix epoch (January 1, 1970) — and DynamoDB uses that value to automatically delete the item once the timestamp is in the past. If an exam question describes a numeric attribute driving automatic item deletion, that's TTL, and the value format is epoch seconds.

Setting It Up

You enable TTL on a table and nominate one attribute to act as the TTL attribute. That attribute must hold a number: the epoch-seconds value of when the item should expire. If you want an item to expire in exactly one week, you calculate the epoch-seconds value for "one week from now" and store that number in the TTL attribute for that item. You apply this to every item you want the TTL mechanism to manage — items without a value in that attribute are left alone.

Two Independent Background Processes

Enabling TTL sets up automated processes that run on every partition of the table, and it's worth understanding that there are genuinely two separate steps, not one:

  • Step one — expire. A background process periodically scans items in a partition and compares each item's TTL attribute against the current epoch time. Once that value is in the past, the item is marked expired. Nothing is removed yet — an expired item is still fully visible and queryable in the table.
  • Step two — delete. A second, independent background process periodically looks for items already marked expired and deletes them — removing them from the table's partitions and from any indexes built on the table.

Because these are internal, system-driven background events, the deletes themselves cause no performance impact and carry no charge.

Tracking What TTL Deletes

If the table has a normal DynamoDB Stream enabled, TTL-driven deletes appear in that stream alongside ordinary creates and modifies. On top of that, you can separately enable a dedicated TTL-only stream, which gives you a rolling 24-hour window containing just the deletions TTL itself caused. That's useful for housekeeping tasks like auditing what TTL has removed, or building an undelete-style recovery path from recently expired data.

Common use cases
Automatically purging stale user or sensor data once it's no longer useful (say, after a year of inactivity), and enforcing regulatory or contractual data-retention windows — one, three, or five years, for example — without writing and maintaining a manual cleanup job to do it.
