Amazon Redshift: Architecture

Lesson 11 of 12 · ~9 min

Source: Adrian Cantrill SAA-C03 · Data warehouse system architecture · Controlling network traffic with enhanced VPC routing

Redshift is a petabyte-scale data warehouse — a place where many operational databases across a business feed data for long-term analysis, reporting, and trending. It's an OLAP system: Online Analytical Processing, built for complex aggregate queries over historical data. That's a deliberate contrast with a system like RDS, which is OLTP — Online Transaction Processing, built for real-time inserts, updates, and deletes of individual records (think: adding an order, editing a customer row). OLTP systems are typically where OLAP systems like Redshift get their data from in the first place.

Why Column Storage Fits OLAP

Redshift stores data by column rather than by row. Imagine a table of cats: each row holds one cat's microchip ID, name, age, colour, and favourite food. A row-based OLTP layout is efficient for interacting with one specific record — updating one cat's age touches one row. But an aggregate query like "what's the average age across every cat" has to scan every row just to read one field from each. A column-based layout stores all the ages together, all the names together, and so on — so an aggregate query over one column only has to scan that column, not full rows. That's precisely the query pattern OLAP workloads run constantly, which is why columnar storage is the natural fit.

Provisioned, Not Ad Hoc

Redshift is provisioned — it uses servers you stand up, not a serverless product like Athena. It's quicker to provision than an on-premises warehouse you'd build yourself, and it's realistic to spin a cluster up, load data, run analysis, and tear it down again. But it still isn't the tool for one-off, ad hoc querying of a dataset sitting in S3 — that's squarely Athena's job, covered two lessons ago. If a scenario needs true ad hoc S3 querying with no standing infrastructure, default to Athena; if it needs a persistent, loaded data warehouse for repeated heavy analytics, that's Redshift.

Two features extend what Redshift can reach without a full load: Redshift Spectrum lets a running cluster query data directly in S3 without loading it in first — still requires a live cluster, unlike Athena — and Federated Query lets Redshift directly query data sitting in remote/foreign databases. Redshift also connects via standard JDBC/ODBC, and integrates with QuickSight for visualization.

Cluster Architecture

A Redshift cluster has a leader node and one or more compute nodes. The leader node is the only thing clients and applications actually connect to — it manages all client communication and builds the execution plan for each query. Compute nodes carry out that plan and hold the actual data. Each compute node is itself divided into slices — 2, 4, 16, or 32 depending on the node's size — and those slices process their share of the workload in parallel.

Critical architectural fact: single-AZ by default
A Redshift cluster's nodes and the high-speed networking between them run in one Availability Zone. The classic architecture is not natively highly available across AZs — if that AZ has a problem, the cluster is affected. The next lesson covers how backups mitigate this risk; for now, just hold onto the fact itself, since it's one of the most exam-tested points about Redshift.

Redshift is a full VPC service, so the usual controls apply normally: security groups, NACLs, IAM for permissions, KMS for at-rest encryption, and CloudWatch for monitoring.

Enhanced VPC Routing

By default, traffic between a Redshift cluster and other AWS services — S3, for instance, when loading data via COPY — travels over Amazon's public AWS network paths rather than through your own VPC. Enabling Enhanced VPC Routing forces that traffic through your actual VPC networking configuration instead, which means security groups, NACLs, custom DNS, and the relevant gateways (internet gateway, NAT gateway, VPC endpoints) all now apply to it, just as they would for any other VPC-routed traffic.

Exam heuristic
Any scenario that needs customized or controlled networking for Redshift's traffic to external services — inspecting it, restricting it, routing it through specific gateways — points to enabling Enhanced VPC Routing.

Getting Data In

Common ingestion paths into Redshift include a COPY from S3, the Database Migration Service, Kinesis Data Firehose streaming directly in, and a direct copy from DynamoDB.

Updates Since the Course Was Recorded

Redshift Serverless and Multi-AZ now exist
Two capabilities have arrived since this material was recorded, and both matter architecturally. Redshift Serverless automatically provisions and scales data warehouse capacity, removing the need to size or manage compute directly — a genuine alternative to hand-sizing a cluster. More significantly, Redshift Multi-AZ deployments are now generally available (for RA3 clusters): compute resources are deployed across two Availability Zones, reachable through a single endpoint, letting the warehouse keep operating through an AZ-level failure. This directly updates the "single-AZ only" framing above — it's still the foundational, most-tested default architecture, but Multi-AZ is now a real option when a scenario specifically calls for cross-AZ resilience in the live cluster itself, rather than resilience recovered only through backups (which the next lesson covers).
