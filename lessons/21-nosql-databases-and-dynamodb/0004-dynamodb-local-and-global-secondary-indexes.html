DynamoDB Local & Global Secondary Indexes

Lesson 04 of 12 · ~9 min

Source: Adrian Cantrill SAA-C03 · Local secondary indexes · Global secondary indexes

Query is DynamoDB's most efficient operation, but it has one hard limitation: it only ever works against a single partition key value. Indexes exist to work around that — they're alternative views over a base table's data, letting Query serve access patterns the base table's own primary key can't support directly. There are two types: Local Secondary Indexes (LSI) and Global Secondary Indexes (GSI).

Local Secondary Index (LSI)

An LSI provides an alternative sort key, while keeping the same partition key as the base table. Using the weather-station example again — partition key station ID, base sort key day — an LSI could reindex the same items by a "sunny day" attribute as its sort key, letting you query one station for just its sunny-day entries.

LSIs are locked in at table creation
A local secondary index must be created at the same time as the base table. There is no way to add one afterward — this is a hard, frequently tested exam fact. LSIs also share the base table's provisioned RCU/WCU rather than getting their own separate capacity.

Global Secondary Index (GSI)

A GSI is far more flexible: it defines a completely independent partition key and sort key, unrelated to the base table's own keys. Back to the weather example — a GSI could use the "alarm" attribute as its partition key and station ID as its sort key, letting you efficiently query for every alarm, optionally narrowed to specific stations.

Unlike an LSI, a GSI can be created or removed at any time after the base table already exists, and it comes with its own separate RCU/WCU capacity settings, independent of the base table's. The trade-off: a GSI is always eventually consistent, with no strongly-consistent option at all, because data replicates from the base table into the index asynchronously.

Both Types Are Sparse

Both LSIs and GSIs are sparse indexes: only items that actually have a value for the indexed attribute appear in the index at all. If the "sunny day" attribute is only ever set on days that were, in fact, sunny, the sunny-day index contains nothing but sunny-day items. That sparseness means even a Scan against a well-designed index can be cheap — you're only paying for the relevant subset, not the whole base table.

Choosing What to Project

Both index types let you choose which attributes get copied in — ALL attributes, KEYS_ONLY, or INCLUDE to name specific ones. This choice matters a lot:

  • Projecting too much wastes capacity and storage, since every projected attribute is duplicated and billed for.
  • Projecting too little means that querying the index for a non-projected attribute silently triggers a fetch back to the base table — a hidden extra operation that's noticeably more expensive and slower than reading only from the index.
AWS's own default guidance
When you're unsure which index type to reach for, default to a GSI — it's more flexible, can be added after the fact, and gets independent capacity. Reach for an LSI specifically when you need strong consistency on the alternative access pattern, since that's the one thing a GSI structurally cannot offer.

Verified current per-table limits: 5 LSIs per base table (unchanged from the source course figure), and a default of 20 GSIs per base table, though this default quota can be raised on request. Both figures still match current AWS documentation, with no drift to flag.
