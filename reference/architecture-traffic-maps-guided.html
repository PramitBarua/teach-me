Architecture Traffic Maps (Guided)

16 reusable architecture patterns showing how a request (or a byte of data) travels between AWS services. Each pattern is distilled from clusters of questions in the exam question bank. These are general shapes, not answers to individual questions, and they only use services covered in this workspace's lessons/ modules 05–23.

How to use this page
Most SAA-C03 scenarios are one of these 16 shapes with one requirement changed. For each map: 1. read The idea box: the problem this shape solves; 2. follow the numbered steps (hover a step, or press Step through, to light up that hop on the map); 3. work through the Swap one requirement table. Each row shows the twist in the question, the answer, what changes in the map (from → to), and why. That table is where the exam's distractors live. For retrieval practice, press Hide service names and name each box before clicking to reveal it.

The big picture: how the maps fit together

A typical request passes through an entry (DNS / edge), a front door (load balancer or API), compute, an optional buffer, and finally data. Click any box to jump to its map. Maps 11–16 are the cross-cutting layers wrapped around this path: private networking, hybrid links, migration, DR, identity and security.

01 Highly available 3-tier web app

Question says: highly availablefault tolerantMulti-AZscale with demandprivate subnets need internet access

The ideaSpread every tier across at least two Availability Zones (separate data centers), so losing one AZ doesn't take the app down. Only the load balancer faces the internet. The app servers and the database sit in private subnets where nobody outside can reach them.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Users lose their cart when the ASG scales inStore sessions in ElastiCache or DynamoDBSession in each EC2's memory↓Session in a shared storeWhen an instance is terminated, its memory is gone. With sessions in a shared store, any instance can serve any user, so scaling in is safe. Sticky sessions only hide the problem.
Web servers max out CPU on SSL/TLSHTTPS listener on the ALB with an ACM certificateTLS ends on every EC2 instance↓TLS ends on the ALBEncryption is CPU-heavy. Letting the ALB do it frees instance CPU for the app, and ACM renews the certificate for you.
Load jumps at a known time (month-end, 9 a.m.)Scheduled scalingScaling only after metrics rise↓Capacity added on a schedule, before the spikeDynamic policies react after load has already risen, and new instances take minutes to boot. A schedule has capacity ready when users arrive.
Keep average CPU around 40 %Target tracking scaling policyNo policy or hand-tuned step policy↓Target tracking on average CPUWorks like a thermostat: you set the target and the ASG adds or removes instances to hold it. No alarms or step sizes to tune.
Block a few abusive IP addressesNACL deny rule (or WAF IP set)Security groups only↓Deny rule in the public subnet's NACLSecurity groups can only allow traffic, never deny it. A network ACL can deny an IP range at the subnet edge. WAF can do the same at the ALB.
Least operational effort to run this stackElastic Beanstalk (or ECS Fargate, map 05)Hand-built ALB + ASG + launch template↓A Beanstalk environmentBeanstalk creates and manages the load balancer, scaling group and deployments from your code, so you don't wire them up yourself.
Static files (images, CSS) drive scaling and costCloudFront + S3 for static contentStatic files served by EC2↓Static files served from S3 via CloudFrontEdge locations cache files close to users, so those requests never reach the ASG. You need fewer instances and pages load faster.
Readable standbys and faster failoverRDS Multi-AZ DB clusterOne hidden standby↓Two readable standbysA Multi-AZ DB cluster has two standbys in different AZs that also serve reads, and failover typically takes under 35 seconds.
Traps
  • An internet-facing ALB must sit in public subnets in each AZ, even when its targets are private. If traffic "isn't reaching the instances", check this first.
  • Use one NAT gateway per AZ, each with its own private route table. A single NAT gateway is a single-AZ point of failure. Use NAT gateways, not NAT instances.
  • "Highest availability" means instances spread across at least two AZs. Moving more instances into the same AZ doesn't count.
  • Classic Multi-AZ standby ≠ read replica: it serves no reads.

02 Global content delivery with CloudFront

Question says: users around the worldstatic and dynamic contentreduce load on originaccessible only through CloudFrontHTTPS

The ideaKeep copies of your content at edge locations close to users. CloudFront answers from its cache when it can and goes back to your origin (S3 or an ALB) only when it must. The site gets faster and your servers get less traffic.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Only paying users may download a fileCloudFront signed URLPlain public file URL↓URL with a signature and an expiry timeCloudFront serves the file only if the signature is valid and not expired. Your app creates a signed URL for each customer who paid.
Paid access to many files, or users can't change URLsCloudFront signed cookiesA signed URL per file↓One signed cookie for the sessionOne cookie unlocks every file it covers, and the URLs stay the same. Use it for a members-only area, or when the client can't change URLs.
Content may only be viewed in certain countriesGeo restriction (allow list)Open to every country↓Distribution with a country allow listCloudFront looks up each viewer's country and blocks the rest at the edge, with no code. Without CloudFront, a WAF geo-match rule on the ALB does the same.
Different content per device or languageCache on the header, or Lambda@EdgeOne cached version for everyone↓A cached version per header valueAdding User-Agent or Accept-Language to the cache key stores a separate copy for each value. Lambda@Edge can choose which object to return.
Users far away upload slowlyS3 Transfer AccelerationUpload straight to the bucket's Region↓Upload enters AWS at the nearest edgeCloudFront speeds up downloads. Transfer Acceleration speeds up uploads: data enters AWS nearby and crosses the AWS backbone to the bucket.
Users still see old files after a deployInvalidation, or versioned file namesSame file name each release↓New name (app.v2.js) or an invalidationEdges keep copies until the TTL expires. An invalidation forces a refresh. Versioned names make each release a new object, which is instant and free.
Sensitive form fields must stay encrypted to the backendField-level encryptionHTTPS only↓Chosen fields encrypted at the edgeHTTPS is decrypted at CloudFront and at the ALB. Field-level encryption encrypts those fields with your public key, so only the app holding the private key can read them.
Large DDoS attack, no downtime allowedShield Advanced + CloudFrontShield Standard↓Shield Advanced on the distributionCloudFront spreads the attack across hundreds of edge locations. Shield Advanced adds the AWS response team and credits for scaling costs caused by the attack.
Not HTTP, or clients need fixed IP addressesGlobal Accelerator (map 03)CloudFront↓Global AcceleratorCloudFront handles only HTTP/HTTPS, and its IPs change. Global Accelerator carries any TCP/UDP traffic and gives you two fixed IPs.
Traps
  • The viewer certificate for CloudFront must be in ACM in us-east-1. A certificate for an ALB lives in the ALB's own Region.
  • Lock the bucket with OAC (Origin Access Control), which supersedes OAI. Exam answers may still say "OAI", which is the same idea. S3 static website endpoints can't use OAC/OAI because they are custom origins.
  • CloudFront isn't only for static files. "Serve all static and dynamic content via CloudFront with the ALB as origin" is a common correct answer.
  • WAF attaches to CloudFront, ALB, API Gateway, AppSync and Cognito, but not to an NLB.

03 Static-IP global entry with Global Accelerator

Question says: UDPTCPstatic IP addressesgaming / VoIP / IoTroute to nearest healthy Region

The ideaGive users two fixed IP addresses that work worldwide. Traffic enters AWS at the nearest edge location and crosses the private AWS network to the closest healthy Region. Nothing is cached, so this works for any TCP or UDP traffic, not just web pages.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Cacheable HTTP content (pages, images)CloudFront (map 02)Global Accelerator↓CloudFrontGlobal Accelerator only routes traffic and never stores content. For cacheable HTTP content, CloudFront serves it from the edge and takes load off the origin.
UDP, but in one Region onlyNLB with an Elastic IP per AZGlobal Accelerator + NLB↓NLB aloneAn NLB already handles UDP and can have fixed IPs. Global Accelerator adds value only for global edge entry or multi-Region failover. An ALB can't carry UDP at all.
Regional failover through DNS is good enoughRoute 53 failover or latency recordsGlobal Accelerator↓Route 53 routing policyIt's cheaper, but clients and resolvers cache DNS answers until the TTL expires, so failover is slower and less predictable.
The app must stay in the on-prem data centerNLB with on-prem IP targets, Global Accelerator in frontTargets inside AWS↓Targets are on-prem IP addressesUsers still get the nearby edge entry and the AWS backbone. The NLB forwards over Direct Connect or VPN to the data center.
Protect the accelerator from DDoSShield Advanced on the acceleratorShield Standard↓Shield AdvancedGlobal Accelerator is one of the resource types Shield Advanced can protect, along with CloudFront, ALB, NLB/EIP and Route 53.

04 Serverless web app & API

Question says: minimize operational overheadno servers to patchunpredictable / spiky trafficREST APIpay only when used

The ideaEvery layer is a managed service that scales by itself and costs nothing when idle: S3 + CloudFront for the web page, API Gateway for the API, Lambda for the code, DynamoDB for the data. There are no servers to patch and no capacity to plan.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Response time must be consistently lowProvisioned concurrencyOn-demand Lambda only↓Lambda with pre-warmed environmentsA cold start happens when Lambda creates a new environment, which adds latency. Provisioned concurrency keeps environments ready, so every request is fast.
Only subscribers or partners, each with a quotaUsage plans + API keysOpen API↓API keys tied to a usage planEach client gets a key, and the plan sets its request rate and quota. Requests without a valid key are rejected.
Callable only from company IP rangesAPI Gateway resource policyNo policy on the API↓Resource policy denying other IPsThe policy is attached to the API itself and denies any request whose aws:SourceIp isn't in your ranges.
HTTP flood or bots hit the APIWAF rate-based rule on the stageNo WAF↓WAF web ACL on the API stageA rate-based rule counts requests per IP and blocks any IP over the limit before it reaches Lambda.
Backend is containers in private subnetsAPI Gateway → VPC link → NLB/ALB → ECSLambda integration↓Private integration through a VPC linkA VPC link lets API Gateway reach a private load balancer without exposing the backend to the internet.
One function just needs an HTTPS webhookLambda function URLAPI Gateway in front↓Function URL on the functionA function URL gives one function its own HTTPS endpoint. It's the simplest option when you don't need API Gateway's features.
Lambda opens too many DB connectionsRDS ProxyLambda connects straight to RDS↓Lambda connects through RDS ProxyEach Lambda copy opens its own connection, and databases have a hard limit. The proxy pools and reuses connections, so the database sees only a few.
Microsecond reads on DynamoDB, no code rewriteDAXLambda reads DynamoDB directly↓Lambda reads through DAXDAX is an in-memory cache that speaks the DynamoDB API, so only the endpoint changes. Reads drop from milliseconds to microseconds.
Write bursts exceed what the DB can absorbSQS between the API and the writer (map 06)Synchronous write per request↓Queue, then a steady writerThe queue holds the burst and a consumer writes at a pace the database can handle, so requests aren't throttled or lost.
Traps
  • Lambda gets AWS permissions from its execution role. Who may invoke it (EventBridge, S3, API Gateway) is set in its resource-based policy.
  • Lambda runs at most 15 minutes. Jobs that run longer belong on ECS Fargate or AWS Batch.
  • A Lambda function attached to a VPC needs a NAT gateway or VPC endpoints to reach the internet or AWS APIs.

05 Container platform (ECS / EKS)

Question says: containerized applicationmicroservicescannot manage infrastructureKubernetes

The ideaPackage each service as a container image, store it in ECR, and let ECS (or EKS) run it as tasks. With Fargate, AWS runs the servers underneath. An ALB routes each URL path to the right service.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
No servers to manage or patchFargateECS on EC2 instances↓ECS on FargateOn the EC2 launch type you patch and scale the instances yourself. With Fargate you set CPU and memory per task and AWS supplies the capacity.
Already on Kubernetes, keep the same toolsEKS (managed node groups or Fargate)ECS↓EKSEKS runs standard Kubernetes, so existing manifests, Helm charts and kubectl keep working.
Stateless, interruption-tolerant, cheapestSpot (Fargate Spot / Spot node groups)On-Demand capacity↓Spot capacitySpot uses spare AWS capacity at up to ~90 % off. AWS can reclaim it with 2 minutes' notice, which stateless tasks can survive.
Each service needs different AWS permissionsECS task role / EKS IRSAOne instance role shared by all↓A role per serviceWith a role per task or pod, a compromised service can only touch its own resources (least privilege).
Run a container job every 10 minutesEventBridge scheduled ECS taskAlways-running service↓Task started on a scheduleYou pay only while the task runs, and no server sits idle running cron.
EKS must scale both pods and nodesHPA + Cluster Autoscaler (or Karpenter)Fixed number of nodes↓Pod scaler plus node scalerThe Horizontal Pod Autoscaler adds pods as load rises. When pods no longer fit, the Cluster Autoscaler or Karpenter adds nodes. Each layer needs its own scaler.
Async batch inference with large modelsSQS → ECS service scaling on queue depthRequests through the ALB↓Queue feeding ECS workersRequests wait safely in the queue and the task count follows the backlog, so slow jobs don't time out and capacity matches demand.
Global UDP traffic to containersGlobal Accelerator → NLB → FargateALB↓NLB behind Global AcceleratorAn ALB can't carry UDP. An NLB can, and Global Accelerator adds fixed IPs and nearest-Region routing.
Traps
  • Task role = what your code can call. Task execution role = what the ECS agent needs to pull from ECR and write logs. Exam answers on "app permissions" use taskRoleArn.
  • A private EKS cluster with no internet access needs interface endpoints (ECR, STS, EC2, logs) and an S3 gateway endpoint before nodes can join.

06 Decoupling with queues & fan-out

Question says: orders are lost during peaksdecoupleprocess in the order receivedsend to multiple systemsmust not get lost

The ideaPut a queue between the part that receives work and the part that does it. The receiver answers immediately, and workers pull jobs at their own pace. Spikes wait in the queue instead of crashing the backend, and nothing is lost if a worker fails. SNS adds fan-out: one message delivered to many queues.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Strict order per customer or payment IDSQS FIFO, message group ID = that IDStandard queue↓FIFO queue grouped by IDFIFO keeps order within each message group. Using the customer ID as the group keeps each customer's messages in order, while different customers still run in parallel.
Ordered stream that many readers can replayKinesis Data Streams, partition key = IDSQS queue↓Kinesis data streamA queue message is gone once consumed. A stream keeps records for its retention period, so several consumers can read the same data, in order per key, and replay it.
Resubmitted forms create duplicate ordersSQS FIFO deduplicationStandard queue↓FIFO with a deduplication IDFIFO drops a message whose deduplication ID it has already seen in the last 5 minutes, so each order is processed once.
Ordered fan-out to several servicesSNS FIFO topic → SQS FIFO queuesStandard SNS topic↓SNS FIFO topicA standard topic doesn't guarantee order. SNS FIFO keeps the same order for every subscriber.
A bad message blocks the restDead-letter queueEndless retries↓Moved to a DLQ after N attemptsWithout a DLQ, a message that always fails keeps coming back. The DLQ removes it from the main queue after maxReceiveCount tries.
Async Lambda invocations fail and vanishOn-failure destination (SQS or SNS)Failed events are dropped↓Failed events sent to a queueAfter its retries, Lambda sends the failed event and the error details to the destination, so you can reprocess it.
SNS → HTTPS endpoint loses messagesDead-letter queue on the SNS subscriptionMessage dropped after retries↓Message kept in an SQS DLQIf the endpoint stays down past SNS's retries, the message lands in the DLQ instead of being discarded.
Messages bigger than the SQS size limitSQS Extended Client LibraryPayload inside the message↓Payload in S3, pointer in the messageThe library stores the payload in S3 and sends only a reference through SQS, so payloads up to 2 GB work.
Existing app uses AMQP, MQTT or JMSAmazon MQ (active/standby across AZs)SQS / SNS↓Managed message brokerMoving to SQS means rewriting code. Amazon MQ runs ActiveMQ or RabbitMQ with those protocols, so the app moves unchanged.
Traps
  • Scale workers on queue depth / backlog per instance, not CPU. CPU can be low while the backlog grows.
  • SNS alone doesn't store messages. If a subscriber is down, the message is gone, so pair SNS with SQS when it "must not get lost".
  • Set the visibility timeout ≥ processing time, or messages get processed twice.

Update vs. older questions: SQS raised its maximum message size from 256 KiB to 1 MiB (Aug 2025). Questions written before then say 256 KB. The Extended Client Library is still the answer for anything larger.

07 Event-driven S3 processing & scheduled automation

Question says: when a file is uploadedas soon as possible after arrivalevery night / every houroutside business hoursnotify when an API is called

The ideaNothing runs until something happens. A file landing in S3, a schedule ticking, or an AWS API call creates an event, and the event triggers the code. You pay only when work happens, and no server sits waiting.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Large uploads overwhelm the web serversPresigned URL, upload direct to S3Browser → web server → S3↓Browser → S3The servers only sign the URL. The file goes straight to S3, which scales automatically.
Uploads during bursts go unprocessedS3 → SQS → LambdaS3 invokes Lambda directly↓S3 sends to SQS, Lambda polls itThe queue stores every event and retries failures, and a DLQ catches the rest, so nothing is silently dropped.
Several targets or rich filtering on S3 eventsS3 → EventBridgeS3 notification to one target↓EventBridge rulesAn S3 notification goes to a single destination per event type. EventBridge can match on object details and fan out to many targets.
Convert large CSV files to Parquet, managedGlue ETL jobLambda doing the conversion↓Glue job triggered on uploadGlue is serverless Spark built for data transformation, with no 15-minute limit and no cluster to manage.
React when a DynamoDB item changesDynamoDB Streams → LambdaApp code makes extra calls↓Table emits change eventsStreams record every insert, update and delete, so you can add processing without changing or slowing the existing app.
Multi-step workflow with retries and branchingStep FunctionsLambdas calling each other↓A state machineStep Functions handles order, retries, waits and errors between steps and shows every run visually, so each function stays simple.
Remove PII for some readers onlyS3 Object LambdaSeveral redacted copies of the data↓One copy, transformed on readA Lambda runs on each GET through the Object Lambda access point and can redact data before returning it, so you store only one copy.
Scheduled job runs longer than 15 minutesEventBridge → ECS Fargate task or AWS BatchLambda as the target↓Container task as the targetLambda stops at 15 minutes. A container task can run for hours and still needs no servers.
Traps
  • Writing the output back to the same prefix that triggers the function creates an invocation loop. Use a different bucket or prefix.
  • "Least operational overhead" for a scheduled script almost always means EventBridge + Lambda, not cron on an EC2 instance.

08 Streaming ingestion & analytics

Question says: real timenear-real timeclickstream / sensors / IoTquery with SQLdata lakedashboards

The ideaCollect a continuous flow of small records (clicks, sensor readings, logs) into a stream, process them in near-real time, then land them in an S3 data lake that you can query with SQL and turn into dashboards.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Just land the data in S3/Redshift/OpenSearch, no codeData Firehose directlyData Streams + custom consumer↓Firehose onlyFirehose is a managed delivery service that batches, converts and writes for you. No shards or consumer code to manage.
Several consumers, replay, order per keyKinesis Data StreamsFirehose only↓Data Streams in frontFirehose delivers each record once to a destination. A stream keeps records so many consumers can read them independently and in order.
Consumers miss records when they fall behindLonger stream retention24-hour retention↓Retention up to 365 daysRecords older than the retention period are deleted. A longer period gives slow consumers time to catch up.
In-flight data is lost when EC2 rebootsPut a stream in front of processingData held in EC2 memory↓Data stored durably in KinesisThe stream stores records across AZs, so a crashed processor restarts from where it left off.
Analyze the stream in real timeManaged Service for Apache FlinkBatch queries later↓Continuous queries on the streamFlink computes results (windows, aggregates, alerts) as records arrive. Exam answers may call it Kinesis Data Analytics.
Ad-hoc SQL on S3 with nothing to runAthenaLoad the data into a database first↓Query the files where they areAthena is serverless: point it at the data and query. You pay per data scanned, and Parquet plus partitions cut that cost.
Complex joins for a BI data warehouseRedshiftAthena↓RedshiftFor heavy, repeated analytics over large structured data, a columnar warehouse is faster and more predictable.
Restrict columns or rows in the data lakeLake Formation permissionsBucket-level IAM policies↓Table, column and row grantsIAM only sees S3 objects. Lake Formation grants access to databases, tables, columns and rows, including across accounts.
Pull SaaS data (e.g. Salesforce) into S3AppFlowCustom export scripts↓Managed AppFlow flowAppFlow has built-in SaaS connectors, runs on a schedule or an event, and encrypts data in transit and at rest.
Stream app logs into OpenSearch in near-real timeCloudWatch Logs subscription filterPeriodic log exports↓Live subscription streamA subscription filter streams matching log events as they arrive, with no agents or pipelines to build.

Naming drift: "Kinesis Data Firehose" is now Amazon Data Firehose. "Kinesis Data Analytics" is now Managed Service for Apache Flink, and its SQL-application flavour has been discontinued. Exam answers still use the old names.

09 Database read scaling, caching & connections

Question says: read-heavyreports slow down productionidentical queriestoo many connectionsRPO near zero

The ideaKeep the main database for writes and move everything else off it: a cache answers repeated reads, read replicas take reporting queries, RDS Proxy shares connections, and a Multi-AZ standby protects against failure.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
The same data is requested over and overElastiCache (cache-aside)App queries the DB every time↓App checks the cache firstRepeated reads are answered from memory, cutting database load and latency. The app needs code changes to add the cache logic.
Cache must always match the databaseWrite-through strategyLazy loading only↓Cache updated on every writeWith lazy loading, the cache can hold stale data until the TTL expires. Write-through updates the cache every time the database is written.
Real-time leaderboardElastiCache for Redis (sorted sets)SQL ORDER BY on every page view↓Redis sorted setA sorted set keeps scores ranked in memory, so fetching the top 10 is one fast command.
Analysts' queries slow productionRead replica / Aurora ReplicaReports run on the primary↓Reports run on a replicaReports read a copy of the data, so they no longer compete with production writes for CPU and I/O.
Unpredictable read spikesAurora Auto Scaling replicasFixed number of replicas↓Replicas added and removed automaticallyAurora adds replicas when load rises and removes them when it's quiet. The reader endpoint spreads queries across them.
Lambda overwhelms connections, or failover is slowRDS ProxyDirect database connections↓Connections through the proxyThe proxy pools connections and holds client connections during a failover, which shortens the outage significantly.
Variable workload, no instance sizingAurora Serverless v2Fixed instance class↓Capacity measured in ACUsCapacity scales up and down with load automatically, so you never pick or resize an instance type.
Microsecond DynamoDB reads, no code changeDAXApp reads DynamoDB directly↓App reads through DAXDAX is DynamoDB-compatible, so switching is mostly an endpoint change. ElastiCache would need new code.
Disk is filling up, no downtime allowedRDS storage autoscalingFixed volume size↓Storage grows automaticallyRDS adds storage when free space runs low, without stopping the database.
Database is IOPS-bound at busy timesProvisioned IOPS SSD (io2)General Purpose SSD (gp3)↓Provisioned IOPS SSD (io2)io2 delivers much higher, consistent IOPS for I/O-heavy databases.
Traps
  • Multi-AZ is for availability and read replicas are for read scale. A question that needs both needs both.
  • Creating a read replica requires automated backups to be on (retention > 0).
  • ElastiCache needs app code changes (cache logic). DAX is the option that needs almost none.

11 Private access from a VPC (endpoints vs. NAT)

Question says: must not traverse the internetprivate subnetreduce data transfer costdownload updatesconnect to a partner service privately

The ideaInstances in a private subnet have no public IP, so each destination outside the VPC needs its own path: a gateway endpoint for S3/DynamoDB, an interface endpoint for other AWS services, or a NAT gateway for the internet. The two endpoint types keep traffic on the AWS network.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Reach S3 or DynamoDB privately and cheaplyGateway endpoint + route table entryThrough the NAT gateway↓Through a gateway endpointNo hourly or per-GB charge, and traffic never leaves AWS. This is the usual answer to "cut NAT data charges for S3".
Reach another AWS service privately (SQS, KMS, ECR…)Interface endpoint (PrivateLink)Through the NAT gateway↓Through an interface endpointGateway endpoints exist only for S3 and DynamoDB. Every other service needs an interface endpoint, which gives it a private IP inside your VPC.
Reach S3 from on-prem over DX/VPNInterface endpoint for S3Gateway endpoint↓Interface endpointA gateway endpoint is only a route inside the VPC, so on-prem networks can't use it. An interface endpoint has an IP they can reach.
Use a vendor's service privately, only you start connectionsPrivateLink to the vendor's endpoint serviceInternet or VPC peering↓Interface endpoint to their servicePrivateLink exposes only that one service, connections are one-way from your side, and the networks never merge, so overlapping CIDRs don't matter.
Private instances need internet access for patchesNAT gateway in each AZNo outbound route↓0.0.0.0/0 → NAT gatewayNAT only allows connections that start inside. One per AZ means an AZ failure doesn't cut off the others.
IPv6 instances need outbound-only internetEgress-only internet gatewayNAT gateway↓Egress-only IGWIPv6 addresses are already public, so there's nothing to translate. The egress-only IGW lets traffic out and blocks inbound-initiated connections.
Allow only approved domains outboundNetwork Firewall with domain-list rulesNAT gateway alone↓Firewall in the outbound pathA NAT gateway doesn't filter anything. Network Firewall inspects outbound traffic and allows only the listed domains.
Send traffic through third-party inspection appliancesGateway Load Balancer + GWLB endpointDirect path↓Path through the appliance fleetGWLB inserts the appliances transparently and load-balances across them, without complex routing.
Traps
  • Gateway endpoints exist only for S3 and DynamoDB and are used through route tables. Interface endpoints are used through DNS and have security groups.
  • An answer that moves instances into public subnets fails "must not traverse the internet" even if it's cheaper.

12 Multi-VPC & hybrid connectivity

Question says: hundreds of VPCs / accountson-premises data centerconsistent latencyno single point of failurecommunicate across Regions

The ideaUse one hub to connect many networks. On-prem links (Direct Connect or VPN) and every VPC attach to a Transit Gateway, which routes between all of them. VPC peering is the simpler option when you only need to connect a couple of VPCs.

Swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Just two VPCs, high bandwidth, no single point of failureVPC peeringTransit Gateway↓Direct peering connectionPeering has no gateway in the middle and no bandwidth cap, and it costs less than a TGW for a simple pair.
Many VPCs across many accounts, managed centrallyTransit Gateway shared with AWS RAMA mesh of peerings↓One hub50 VPCs would need 1,225 peerings. With a TGW, each VPC needs one attachment, and one team owns the routing.

Large daily transfers, latency-sensitive, to on-premDirect Connect (+ TGW)VPN over the internet↓Dedicated DX linkDX doesn't share the internet, so bandwidth and latency stay consistent, and data transfer out costs less.
Need a link this week, or a cheap backup for DXSite-to-Site VPNNo connection yet↓IPsec VPNA VPN is up in minutes over the existing internet connection. A new DX link can take weeks.
VPN must survive an on-prem router failureSecond customer gateway + second VPNOne on-prem router↓Two routers, two VPNsEach VPN already has two tunnels on the AWS side, but if the single on-prem router dies, both tunnels go down with it.
DX link is mostly idle, cut the costSmaller hosted connection from a partner1 Gbps dedicated connection↓Sub-1 Gbps hosted connection (e.g. 200 Mbps)Partners sell capacity below 1 Gbps, so you pay only for the bandwidth you actually use.
Remote employees need access to the VPCAWS Client VPNSite-to-Site VPN↓Per-user Client VPNSite-to-Site connects whole networks. Client VPN connects individual laptops, with per-user authentication.
Traps
  • Peering CIDRs can't overlap, and peering is not transitive. A→B and B→C doesn't give A→C.
  • Direct Connect isn't encrypted by default. For encryption, run VPN over a public VIF or use MACsec.

14 Multi-Region disaster recovery

Question says: another AWS RegionRPO / RTORegional failureminimal downtimefewest resources during normal operation

The ideaKeep a copy of the app and its data in a second Region. Route 53 sends users to the primary while it's healthy and to the DR Region when it fails. How much you keep running in the DR Region decides both the cost and how fast you recover. RPO = how much data you can afford to lose. RTO = how long you can afford to be down.

First pick the DR strategy from the RPO/RTO…

Strategy (cheapest → most expensive)RPO / RTOWhat runs in the DR RegionTypical data mechanism
Backup & restoreHours / hoursNothing. Rebuild from AMIs + CloudFormationAWS Backup cross-Region copies, snapshot copies
Pilot lightMinutes / tens of minutesData keeps replicating, compute is off until neededCross-Region read replica, Aurora Global Database
Warm standbySeconds / minutesA small but complete copy of the stack, scaled up on failoverAurora Global Database, DynamoDB global tables
Multi-site active/activeNear zero / near zeroThe full stack, serving live trafficDynamoDB global tables, Route 53 latency routing

…then swap one requirement → swap one component

If the question adds…AnswerWhat changes in the mapWhy
Relational, RPO in seconds, RTO in minutesAurora Global DatabaseAurora in one Region↓Global cluster with a DR secondaryStorage-level replication keeps lag under about a second, and the secondary can be promoted in about a minute.
NoSQL, active in every RegionDynamoDB global tablesTable in one Region↓Replica table in each RegionEvery Region accepts writes locally, so users get low latency everywhere and a Region failure loses almost nothing.
Non-Aurora RDS (or RDS Custom) in another RegionCross-Region read replica, promoted on disasterRDS in one Region↓Replica in the DR RegionThe replica stays nearly current. Promoting it turns it into a standalone, writable database.

  • "Fewest resources during normal operations" points to backup & restore or pilot light, not warm standby.

Retrieval drill: which shape fits?

New scenarios in the style of the question bank. Name the architecture from memory before checking.

1. A news site's images and API feel slow for overseas readers. Everything runs in one Region: media in S3, API on EC2 behind an ALB. The fix must add as little infrastructure as possible.

2. A multiplayer game uses UDP. Players worldwide must reach it through two fixed IP addresses, and traffic must shift to a second Region within seconds if the first fails.

3. An order API must never lose orders during flash sales. The downstream payment service can handle only 50 requests per second.

4. EC2 instances in private subnets pull terabytes from S3 every day through a NAT gateway. Finance wants the data charges cut, and the traffic must not use the internet.

5. Month-end reports drive ReadIOPS on an Aurora MySQL writer to 100 % and checkout slows down. The team wants the most cost-effective fix.

6. A 30 TB NAS must be in S3 within two weeks. The 50 Mbps internet link is already busy. Afterwards the data will live only in AWS.

7. A relational application in one Region needs an RPO of seconds and an RTO of minutes if the entire Region becomes unavailable.

8. A mobile app must let each signed-in user upload photos straight into their own S3 prefix, with no backend proxy in the upload path.

9. Linux and Windows applications must read and write the same files, over NFS and SMB respectively, on fully managed storage.

10. A handful of abusive IP addresses are flooding the web tier's public subnets behind an ALB. They must be blocked at the subnet boundary right away.
