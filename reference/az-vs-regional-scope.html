AZ-Bound vs. Regional Service Scope

One quick-glance answer to "does this live in one Availability Zone, or does AWS spread it across the Region for me?" — compiled only from services actually covered in this workspace's lessons (modules 05–23).

Facts pulled from this workspace's own lessons and aws-saa-c03-cheatsheet.html; click any service to jump to the lesson it's taught in.

The pattern behind almost every row below

A Region contains many Availability Zones. A VPC is Region-wide; a Subnet is exactly one AZ, never more. That single relationship predicts most of this page:

  • Anything that has to live inside a subnet — an EC2 instance, an EBS volume, an ENI, a NAT Gateway, a Dedicated Host — is pinned to that subnet's one AZ. AWS never silently moves it to another AZ for you.
  • Anything that sits above the VPC/subnet layer entirely — S3, DynamoDB, Lambda's control plane, an ECS/EKS control plane — is Regional, and AWS spreads its own internals across AZs without you doing anything.
  • A lot of the "high-yield" exam content in this course is really about the middle case: a Regional, logical resource (ALB, Auto Scaling Group, RDS Multi-AZ, an Interface VPC Endpoint) whose underlying pieces still have to be placed into specific AZ subnets — by you. Get the AZ placement wrong and the HA story falls apart even though the "resource" itself is Regional.
  • Only a handful of services skip the Region concept altogether: Route 53, CloudFront, IAM/STS, Organizations, and Global Accelerator.
Global no Region at all AZ-bound lives in exactly one AZ — you build the multi-AZ pattern Regional · auto spans AZs by default, nothing to configure Regional · you choose Regional resource, but you pick which AZs it lands in

AZ-bound Lives in exactly one Availability Zone

If the AZ hosting one of these fails, the resource fails with it. High availability means you deploy more than one, in different AZs — AWS never relocates these across an AZ boundary on its own.

Service / resourceWhat's pinned to one AZLesson
VPC SubnetThe foundational case — one subnet = exactly one AZ, never spans AZs. Every other row on this list ultimately traces back to this rule.Mod 07
EC2 instance"AZ-locked, full stop" — host, ENI, subnet and attached EBS all live in exactly one AZ; an instance only ever moves host within the same AZ, never across AZs (only a relaunch from an AMI/snapshot can move it).Mod 08
EBS volumeSame AZ-lock as EC2 — no cross-AZ attach. A snapshot to S3 is the only way to move the data to another AZ or Region.Mod 08
EC2 Instance StorePhysically attached to the host itself — even more tightly bound than EBS; wiped entirely on stop/start or host migration, let alone an AZ change.Mod 08
Elastic Network Interface (secondary ENI)Detachable, but only ever re-attachable within the same AZ as where it was created.Mod 08
NAT Gateway"AZ-resilient only — need one per AZ for full HA." A single NAT Gateway shared across all AZs is the classic exam failure scenario: that AZ's outage kills outbound internet for every private subnet routed to it.Mod 07
EC2 Dedicated HostA specific physical server, which by definition sits in one specific AZ.Mod 10
Cluster Placement Group"Single AZ, same rack" — the whole point is minimum-latency proximity, which caps it to one AZ with almost zero built-in resilience.Mod 10
RDS DB instance (Single-AZ)The default deployment: one instance in one AZ. The surrounding DB subnet group must span ≥2 AZs only so you have the option to enable Multi-AZ later — on its own, a Single-AZ instance has no standby.Mod 12
Amazon S3 One Zone-IAThe deliberate exception inside S3 — every other S3 storage class replicates across 3 AZs automatically, but One Zone-IA is explicitly stored in a single AZ (cheaper, but lost entirely if that AZ is destroyed).Mod 06
Amazon Redshift (classic cluster)"Classic clusters run in one AZ — not natively HA across AZs," with resilience instead coming from snapshots landing in S3. (Redshift Serverless and genuine Multi-AZ for RA3 clusters now exist alongside this, but the classic architecture the exam tests is single-AZ.)Mod 21
ElastiCache for Memcached (node)"No true replication" — a given node has no cross-AZ copy of itself, unlike Redis.Mod 21
FSx for Lustre — ScratchNo replication at all — a hardware failure in that one AZ loses the data outright. Chosen for speed over durability.Mod 18
FSx for Lustre — Persistent (Gen 1)"Replicated within one AZ (not multi-AZ)," self-healing against disk failure but not an AZ outage. (Persistent 2 with Intelligent-Tiering is the newer exception — see the Regional/you-choose table.)Mod 18
AWS Local Zone"Behaves like a single AZ with no built-in redundancy of its own" — it's an extension of a parent Region, not a resilient location in itself. EBS snapshots still land in S3 back in the parent Region.Mod 23
AWS Direct Connect connectionNot technically an "AZ," but the same single-point-of-failure pattern: one physical cable into one DX location. "No built-in resilience" — a full HA design needs multiple locations and premises, a choice you make (see Regional/you-choose).Mod 18

Regional · automatic Spans AZs by default — nothing to configure

You interact with these as one Regional endpoint. AWS distributes the underlying storage/compute across multiple AZs on its own, with no AZ picker in the console.

ServiceHow the AZ spread happens automaticallyLesson
VPC"Regional, spans every AZ in the Region automatically" — you never provision a VPC per AZ, only subnets.Mod 07
S3 (Standard, Standard-IA, Glacier tiers)Every class except One Zone-IA stores across 3 AZs automatically — this is literally a column in the lesson's storage-class comparison table.Mod 06
DynamoDB"Every item replicates to 3 storage nodes across 3 AZs" with one elected leader — built into the base service, not an optional setting.Mod 21
Aurora (cluster storage)"Shared cluster storage volume: 6 storage nodes across 3 AZs, self-healing" — the key architectural difference from RDS's per-instance EBS volume.Mod 12
AWS Lambda (default networking mode)AWS places execution environments across AZs on your behalf; you only step into AZ-placement decisions once you attach the function to a VPC (see Regional/you-choose).Mod 15
EKS control plane"AWS-managed control plane (including etcd) across multiple AZs, always AWS-managed regardless of node type" — the worker nodes are a separate, you-choose decision (see below).Mod 09
ECS cluster (the logical construct)A cluster itself is just a Regional namespace with no AZ concept; the tasks/services placed into it are where AZ choice actually happens (see below).Mod 09
S3 Gateway VPC Endpoint"Automatic, all AZs" — the one thing that structurally distinguishes it from an Interface Endpoint.Mod 17
EFS (filesystem data)The filesystem's data durability spans multiple AZs in the Region automatically; only the mount targets (the access points) are a per-AZ resource you create yourself (see below).Mod 13
SQS, SNS, EventBridge, Step FunctionsFully-managed Regional services with AWS-managed redundancy behind the scenes — no AZ configuration is ever exposed to you.Mod 15
Kinesis (Data Streams / Firehose / Managed Flink / Video Streams)Regional ingestion/processing services; shard/stream placement across AZs is entirely AWS-managed.Mod 15
API GatewayRegional (or edge-optimized, which layers CloudFront in front) — no AZ concept exposed to the user.Mod 15
Amazon Cognito, AWS Glue, AWS AppFlowFully-managed Regional application services with no AZ picker.Mod 15
Amazon AthenaServerless SQL over S3 — you never provision compute, so there's nothing to place into an AZ.Mod 21
AWS Transit GatewayA Regional hub that works cross-Region and cross-account riding AWS's own network — AWS manages its internal AZ redundancy.Mod 18
Secrets Manager, AWS Config, Macie, Inspector, GuardDutyRegional control/security services (one per Region, some support cross-Region aggregation) — they don't deploy anything into a subnet, so there's no AZ to place.Mod 19
CloudFormation (stacks / StackSets)Purely a control-plane service — a stack lives in one Region (StackSets span many), but CloudFormation itself never occupies a subnet or an AZ.Mod 20
Comprehend, Kendra, Lex, Polly, Rekognition, Textract, Transcribe, Translate, Forecast, Fraud Detector, SageMakerAll ten pre-built AI APIs plus SageMaker are Regional, fully-managed services with no AZ concept exposed to the caller.Mod 22

Regional · you choose A Regional resource whose pieces you place into specific AZs

This is where most of the course's "high-yield" HA-design content actually lives: the resource is Regional and logical, but its real availability depends entirely on which AZs you spread it across.

ServiceWhat you place, and whereLesson
ALB / NLB / Gateway Load Balancer"One LB 'object' = multiple nodes (1+ per AZ subnet you pick)" — you choose which AZ subnets get a node; a single DNS record then resolves to every node across them.Mod 14
Auto Scaling GroupSpans exactly the AZ subnets you attach to it; self-healing works across those subnets even with zero scaling policy — the cheapest HA pattern is min=desired=max=1 spread across multiple AZ subnets.Mod 14
RDS Multi-AZ (instance or cluster)The DB subnet group spans ≥2 AZs; enabling Multi-AZ adds a synchronous standby (instance) or up to 2 additional readers (cluster) in a second AZ you don't individually pick — it comes from the subnet group.Mod 12
RDS Read ReplicaCan be created same-AZ, cross-AZ, or cross-Region — a per-replica choice you make at creation time.Mod 12
RDS Proxy"VPC-only, multi-AZ" — it deploys across the AZs of the DB subnet group you give it.Mod 12
DMS replication instanceA managed instance you can optionally deploy in Multi-AZ, exactly like an RDS instance's own Multi-AZ option.Mod 12
Interface VPC Endpoint (PrivateLink)"Manual — one per AZ needed," unlike the Gateway Endpoint's automatic coverage — you create one ENI per AZ subnet you want it reachable from.Mod 17
EFS Mount Targets"One mount target per AZ for HA" — the same one-per-AZ pattern as NAT Gateway and Interface Endpoints, except here the underlying data is already Regional; only the access point is per-AZ.Mod 13
ECS/EKS tasks, services & worker nodesFargate tasks and EC2 worker nodes are placed into whichever subnets (AZs) you configure for the service or node group — the control plane is auto-multi-AZ, but your compute isn't unless you spread it yourself.Mod 09
ElastiCache for Redis (replication group)"True Multi-AZ HA" — but the primary and its replicas are placed into the specific AZs your subnet group covers.Mod 21
FSx for Lustre — Persistent 2 (Intelligent-Tiering)The newer exception to the single-AZ Persistent default — it can replicate across multiple AZs, a deployment choice at creation.Mod 18
FSx for Windows File ServerDeploys with either a Single-AZ or Multi-AZ file server, a choice you make at creation (the lesson focuses on AD integration and throughput rather than this deployment option, so treat it as a lighter-confidence entry).Mod 18
AWS CloudHSM clusterRuns inside an AWS-managed CloudHSM VPC; best-practice HA is achieved by adding HSMs into more than one AZ within that cluster — a design decision you make.Mod 19
AWS WAF (ALB / API Gateway / AppSync scope)Regional here (unlike the CloudFront case above) — "the Web ACL must be created in the same Region as the resource" it protects.Mod 19
Site-to-Site VPN / Virtual Private GatewayThe VGW attaches per-VPC (Regional); true HA comes from a second Customer Gateway at a separate premises/ISP — a design choice, not something AWS does for you.Mod 18
Direct Connect (resilience progression)You choose how many locations, ports and premises to use — the progression from "7 single points of failure" to maximum resilience (2 locations × 2 ports × 2 premises) is entirely your architecture decision.Mod 18
Storage Gateway (any mode)A gateway appliance you deploy on-prem or on EC2 — its resilience is entirely your own design, not an AWS-managed AZ concept.Mod 18
AWS Transfer Family (VPC endpoint)The VPC-hosted endpoint types are placed into whichever subnets you configure.Mod 18
Placement Groups — Spread & PartitionSpread "can span AZs"; Partition is "per AZ" with up to 7 partitions per AZ — both let you decide the AZ spread, unlike Cluster (always single-AZ).Mod 10
AWS Directory Service (Managed Microsoft AD)Deploys domain controllers across the AZs of the VPC/subnets you specify for redundancy (a standard multi-AZ pattern; not spelled out in the lesson's own text, so treat as a lighter-confidence entry).Mod 18
Amazon MQRuns inside a VPC as either a single-instance or active/standby broker — active/standby places the two brokers in AZs you choose.Mod 15

A few entries above are flagged as "lighter-confidence" where this workspace's lessons don't spell out the exact AZ mechanics and the note relies on standard, current AWS architecture instead — everything else traces directly to a specific lesson fact.
