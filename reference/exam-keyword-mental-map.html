Exam Keyword Mental Map

A branching mental map for the seven keywords in the cheat sheet's "Read the last sentence first" section — spot the keyword in the question stem, follow the branch that matches the scenario detail, land on the service.

Source: this workspace's own aws-saa-c03-cheatsheet.html, expanded with the surrounding per-module facts that explain why each branch resolves the way it does.

How to use this page
Each card starts from one exam keyword, gives the single "first reach for" default, then branches into the specific scenario details that actually decide between the candidates. The keyword alone rarely picks the answer — it just narrows the field to one branch's few services. A "Don't confuse with" box flags the keyword's usual trap pairing.

MOST cost-effective

Signal words: "most cost-effective," "cheapest," "minimize cost," "reduce spend."

First reach forThe cheapest option that still satisfies every other stated requirement — this is a filter applied after the requirements, never a reason to violate one of them.
Compute pricing model
Spot interruptible / batch / fault-tolerant / stateless work · Reserved Instances or Savings Plans known steady-state, 1–3yr commitment · rule out On-Demand as the cost-effective answer whenever a commitment or interruption tolerance is mentioned
Storage with unpredictable or aging access pattern
S3 Lifecycle known, stable transition schedule · S3 Intelligent-Tiering unknown/variable access pattern · EBS gp3 over provisioned-IOPS unless a specific IOPS number is actually required
Spiky, idle, or unpredictable workload
Lambda · Fargate · Aurora Serverless · DynamoDB on-demand — anything that scales to zero beats an always-on EC2/RDS instance sized for peak
Rolling out new static content via CloudFront
Versioned filenames (e.g. whiskers_v2.jpg) over CloudFront invalidation, which isn't free at volume
Don't confuse with
LEAST operational overhead — the cheapest-per-hour option and the least-management option are often different services (e.g. self-managed EC2 can be cheaper than Fargate but is more overhead). Check which word the question actually uses.
LEAST operational overhead

Signal words: "least admin effort," "minimal management," "no servers to manage," "hands-off."

First reach forWhichever candidate is the most fully AWS-managed — the one that removes the most patching/scaling/failover work from you, even if it costs more per hour.
Relational database, HA required
Aurora Serverless over self-managed Multi-AZ HA on EC2, and over RDS Custom (which trades managed-ness for OS access on purpose)
Container compute
Fargate over ECS/EKS EC2 mode — "idle capacity billing" or "managing instances" in the stem means EC2 mode is the wrong answer here
General compute
Lambda over EC2 whenever the workload fits within Lambda's execution model (≤15 min, stateless)
"When stuck between two otherwise-equal answers"
Pick whichever is more AWS-managed — the cheat sheet's own tie-breaker rule for this exact situation
Don't confuse with
MOST cost-effective (see above) and LEAST application code changes — overhead is about who manages the infrastructure, not what the app's own code has to do or how much it costs.
LEAST application code changes

Signal words: "without modifying the application," "transparent to the application," "no code changes."

First reach forThe option the application doesn't have to know about — if a solution requires the app to explicitly check-cache-then-fallback, it's disqualified by this exact keyword.
Caching in front of DynamoDB
DAX — API-compatible, close to drop-in
Caching in front of RDS/Aurora
ElastiCache is the trap here — it needs the app to actively check the cache, handle misses, and write back. If the stem says "no application changes," ElastiCache is being deliberately ruled out even though it's the "obvious" caching answer.
Swapping credentials/identity without a rewrite
Prefer IAM roles / instance profiles over hard-coded credentials — the app calls the SDK the same way either way
Don't confuse with
Lowest latency — both keywords can point at a caching layer, but "lowest latency" doesn't rule out ElastiCache the way "least code changes" does. Read which constraint is actually stated.
Highest / high availability

Signal words: "highly available," "survive an AZ failure," "no single point of failure," "resilient."

First reach forMulti-AZ, within one Region — duplicate the resource across at least two Availability Zones. This is a same-Region concern; see the DR card below for the cross-Region version.
Outbound internet from private subnets
NAT Gateway × 1 per AZ — a single shared NAT Gateway is the classic exam failure scenario: that AZ's outage kills outbound internet for every private subnet routed to it
Load-balanced web tier with uneven per-instance load
Cross-zone load balancing — check this setting before assuming you need more load balancers
Compute fleet
Auto Scaling Group across ≥2 AZ subnets — self-healing works even with zero scaling policy; min=desired=max=1 spread across AZs is the cheapest HA pattern
Relational database
RDS/Aurora Multi-AZ — synchronous replication to a standby/reader in a second AZ, automatic failover
Don't confuse with
Disaster recovery / DR — the single most-tested distinction in this whole list. HA = survives an AZ failure, inside one Region. DR = survives a whole-Region failure. A Multi-AZ RDS instance gives you HA; it gives you zero DR, because Multi-AZ never leaves the Region.
Lowest latency

Signal words: "lowest latency," "fastest response time," "improve performance for end users."

First reach forPut something faster and closer in front of the slow thing — a cache, an edge location, or a physically nearer path — rather than making the slow thing itself faster.
Static/cacheable content, global users, HTTP(S)
CloudFront edge locations
Database reads
DAX in front of DynamoDB · ElastiCache in front of RDS/Aurora
Non-HTTP protocol, or raw network performance with no caching mentioned
Global Accelerator — two static Anycast IPs, rides AWS's private backbone instead of the public internet
Tightly-coupled compute needing single-digit-microsecond network hops
Cluster placement group — single AZ, same rack, max throughput/lowest latency, at the cost of almost zero resilience
Lambda cold starts
Provisioned concurrency — pre-inits execution contexts on a version/alias (never $LATEST)
Don't confuse with
CloudFront vs. Global Accelerator specifically: caching / signed URLs / HTTP-specific behavior → CloudFront. TCP/UDP or "no HTTP concept at all" → Global Accelerator, which never caches anything.
Disaster recovery / DR

Signal words: "disaster recovery," "if the Region becomes unavailable," "RTO/RPO," "business continuity."

First reach forCross-Region replication of data, plus one of the four standard DR patterns (in increasing cost/speed): backup & restore → pilot light → warm standby → multi-site active-active.
Relational database, need fast cross-Region failover
Aurora Global Database — storage-layer replication <1 second, one primary Region + read-only secondary Regions
Object storage
S3 Cross-Region Replication (CRR)
EC2/EBS-based workloads
EBS snapshot copy to another Region · AMI copy to another Region — the only way to move either resource out of its home AZ/Region at all
"Minimal cost, can tolerate hours of downtime" vs. "must fail over in minutes"
Cheaper/slower → pilot light (core services idle, scaled up on failover) · more expensive/faster → warm standby (scaled-down copy always running)
Don't confuse with
Highest / high availability — see that card's note. If the failure scenario named in the question is "an Availability Zone," you want HA (Multi-AZ). If it's "the Region," you want DR (cross-Region). Multi-AZ alone never answers a DR question.
Secure without internet exposure

Signal words: "without traversing the public internet," "no internet gateway," "fully private," "without exposing to the internet."

First reach forA VPC endpoint — keep the traffic on AWS's private network end to end, with no IGW and no NAT Gateway involved at all.
Private subnet needs S3 or DynamoDB only
Gateway Endpoint — free, automatic HA across all AZs, route-table + prefix-list based
Private subnet needs any other AWS service (or wants S3 via ENI too)
Interface Endpoint (PrivateLink) — ENI-based, one per AZ needed manually, security-group-capable
VPC-to-VPC private connectivity
VPC Peering (2 VPCs, no transitive routing) or Transit Gateway (many VPCs, transitive) — never routed over the public internet either way
On-premises to a private VPC
Site-to-Site VPN or Direct Connect (private VIF) — note a VPN riding over Direct Connect still needs a public VIF, since the VPN endpoint itself has a public IP
Don't confuse with
"Block one specific bad IP address" is a Network ACL question, not a VPC-endpoint question — Security Groups can't explicitly deny, and endpoints control which service is reachable, not which caller IP is blocked.

Confusable pairs, side by side

The three mix-ups that account for a disproportionate share of wrong answers on this whole keyword list.

Cost-effective

Cheapest option that still meets every requirement. Can conflict with "least overhead" — self-managed is sometimes cheaper but always more work.

Least overhead

Most AWS-managed option, regardless of raw price. The tie-breaker when two answers both "work."

vs.

High availability

Survives an Availability Zone failure. Stays inside one Region. Multi-AZ is the keyword.

Disaster recovery

Survives a Region failure. Always involves a second Region. Multi-AZ alone never satisfies this.

vs.

Lowest latency

A performance goal — caching, edge locations, proximity. Often uses the same services (Multi-AZ setups) as HA, but for a different reason.

High availability

A resilience goal — survive a failure. Don't pick a latency-motivated answer (e.g. Global Accelerator) when the question is actually about failover.
